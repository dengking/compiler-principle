# Sparse VS sparse
"Sparse" 这个词是相对**传统 dense 数据流分析**说的。要理解它,得先看 dense 表示浪费在哪。

## Dense 的做法

经典数据流分析(比如常量传播)把信息存在**每个程序点 × 每个变量**上。想知道 `x` 在某条指令处是不是常量,就得维护一张表:

```
程序点 p1: {x↦0, y↦0, z↦⊤, w↦⊤, ...}
程序点 p2: {x↦0, y↦0, z↦⊤, w↦⊤, ...}
程序点 p3: {x↦1, y↦0, z↦⊤, w↦⊤, ...}
...
```

存储量是 O(程序点数 × 变量数),而且迭代求不动点时要沿 CFG 边一遍遍传播整张表。问题在于:绝大多数表项在相邻程序点之间**完全没变**。一个只在函数开头和结尾用到的变量,中间几百条指令都得为它保留一份不变的信息,并且在每个汇合点为它做一次 meet 运算。这些都是冗余工作。

## SSA 为什么稀疏

SSA 的关键性质是**每个变量只有一个定义点**。由此:

**信息可以挂在变量上,而不是程序点上。** 因为 `x₂` 在整个作用范围内不可能被重新赋值,关于它的事实(是不是常量、常量是多少、类型是什么)是全局唯一的。一个变量存一份,存储量从 O(点 × 变量) 降到 O(变量)。

**def-use 关系是显式且现成的。** 单一定义意味着每个使用点的定义立刻可知,不需要跑 reaching-definitions 分析去建 def-use chain。把这些边连起来就得到 **SSA graph**,它是一张稀疏图:信息从定义**直接跳到**使用点,中间那些与该变量无关的指令被完全跳过。

**汇合处的 meet 只发生在 φ 上。** dense 分析在每个 join block 对所有变量做 meet;SSA 里只有真正在该汇合点取值不确定的变量才有 φ,也只有这些 φ 需要做 meet。φ 函数的位置(支配边界)精确标出了"控制流合并对哪些变量有影响",其余变量一个字都不用算。

## 一个对比

```
x₁ ← 0
L1: x₂ ← φ(x₁, x₃)
    ... 50 条与 x 无关的指令 ...
    x₃ ← x₂ + 1
```

dense 常量传播要在这 50 条指令的每个点上都记录 `x` 的格值,并逐点传播。SSA 的稀疏传播只有 3 个节点、几条 def-use 边:`x₁ → x₂`、`x₃ → x₂`、`x₂ → x₃`,中间 50 条指令根本不参与。这就是 Wegman & Zadeck 的 **SCCP(sparse conditional constant propagation)** 相对朴素常量传播的加速来源。

## 代价与边界

插 φ 会增加节点,但用支配边界算法插入的 φ 数量在实际程序里基本是线性的,换来的稀疏性收益远超这点开销。

更重要的是要知道 SSA 的稀疏性**不是万能的**。它只对"与位置无关、可归属于某个值的标量性质"有效:常量、类型、取值区间、是否为 null 等。对于本质上就依赖程序点的性质,SSA 并不能让它变稀疏:

- **活跃性(liveness)**:同一个 `x₂` 在不同程序点可能活跃也可能不活跃,信息必须按点存。
- **可用表达式、指令调度相关的信息**:同样是 per-point 的。
- **内存与别名**:普通 SSA 只管标量,堆内存的 load/store 不在其中。要获得类似的稀疏性,需要扩展形式,比如 Memory SSA、HSSA,把内存状态也版本化。

所以更准确的说法是:SSA 为**标量值的流信息**提供了一个稀疏的传播骨架,把"信息只在变化的地方流动"这件事直接编码进了程序表示本身。

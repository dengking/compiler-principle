# 编译原理中 NFA → DFA 的应用全景

> **核心命题**
> NFA → DFA（子集构造 / powerset construction）在编译器里之所以反复出现，不是巧合。凡是出现"**当前有多个候选，还不知道该选哪个**"的地方，就有**不确定性**；而消除这种**不确定性**的通用手法只有一个：
> **并行推进所有候选，把"候选集合"本身当作一个新状态。**
> 这就是**子集构造**。
> 
> 编译器前端的三大决策问题——该识别成哪个 token、该用哪条产生式规约、该选哪条备选分支——本质上是同一个问题的三个化身。

## 0. 算法本体：子集构造回顾

### 0.1 算法

给定 NFA `N = (Q, Σ, δ, q₀, F)`，构造等价 DFA `D`：

```
DFA 状态 = NFA 状态的子集
起始状态 s₀ = ε-closure({q₀})
δ_D(S, a)  = ε-closure( ⋃_{q∈S} δ_N(q, a) )     // move 后取 ε-闭包
接受状态   = { S | S ∩ F ≠ ∅ }
```

工作表（worklist）实现：

```python
def subset_construction(nfa):
    s0 = eps_closure({nfa.start})
    dfa_states = {frozenset(s0)}
    worklist   = [frozenset(s0)]
    delta      = {}
    while worklist:
        S = worklist.pop()
        for a in alphabet:
            T = eps_closure(move(S, a))
            if not T: continue
            T = frozenset(T)
            delta[(S, a)] = T
            if T not in dfa_states:      # 新状态，加入待处理
                dfa_states.add(T)
                worklist.append(T)
    return dfa_states, delta
```

### 0.2 三个必须记住的性质

| 性质           | 说明                                                                    |
| ------------ | --------------------------------------------------------------------- |
| **正确性**      | `L(D) = L(N)`，即确定化不改变所识别的语言                                           |
| **状态上界**     | NFA 有 `n` 个状态 ⇒ DFA 最多 `2ⁿ` 个状态（**状态爆炸**）。且这个界是紧的（存在达到 2ⁿ 的例子）        |
| **本质是不动点计算** | worklist 循环在求"可达子集集合"的最小不动点。这与数据流分析的迭代求解在结构上**完全同构**——都是"格上的单调函数求不动点" |

**值得记住的类比**：
子集构造 : 自动机 = 数据流分析的 worklist 算法 : 控制流图。

- 两者都是 `while worklist: 取一个节点，算 transfer，若结果变化则把后继入队`。理解了一个就理解了另一个。
- 自动机 VS 控制流图
- 子集构造 VS 数据流分析的 worklist 算法

### 0.3 状态爆炸在实践中很少发生

一个经验事实：**真实编译器中的 NFA 几乎从不触发指数爆炸**。原因是真实的正则表达式/文法具有高度的"**局部性**"——不同分支很快就被首字符区分开了。**指数爆炸**需要形如 `(a|b)*a(a|b)^n` 这类刻意构造的"需要记住 n 步历史"的模式。这也是子集构造在工程上如此成功的原因。

## 1. 词法分析：最经典的应用

这是每本教材都会讲的路径，也是 `lex`/`flex`/`re2c`/JFlex 的实现主线。

### 1.1 完整流水线

```
词法规则（正则表达式集合）
        │
        │  ① Thompson 构造
        ▼
   ε-NFA（每个规则一个，再用 ε 边接到统一起始状态）
        │
        │  ② 子集构造（NFA → DFA）★
        ▼
      DFA
        │
        │  ③ Hopcroft / Moore 最小化
        ▼
   最小 DFA
        │
        │  ④ 表压缩（等价字符类、行压缩、default 链）
        ▼
  表驱动扫描器代码
```

### 1.2 ① Thompson 构造：正则 → ε-NFA

对每个正则算子给出一个"积木"，递归组合：

| 正则式      | NFA 片段                           |
| -------- | -------------------------------- |
| `ε`      | `①──ε──>②`                       |
| `a`      | `①──a──>②`                       |
| `r₁r₂`   | 串联，`r₁` 的接受态 ─ε→ `r₂` 的起始态       |
| `r₁\|r₂` | 新起始态 ─ε→ 两个分支的起始态；两个接受态 ─ε→ 新接受态 |
| `r*`     | 新起始/接受态 + 回边 ─ε→ 起始，以及跨越边 ─ε→ 接受 |

**关键性质**：Thompson 构造产生的 NFA 状态数是 `O(|r|)`（线性于正则式长度），每个状态出边数 ≤ 2。这是"先转 NFA 再确定化"这条路线的效率基础。

### 1.3 ② 多规则合并：这一步才是 lexer 的真正难点

词法器不是识别**一个**正则式，而是要在**几十上百条规则**中同时竞争。做法是：

```
                 ┌─ε─> NFA(IF 规则)        接受 → token=IF,      优先级 1
                 ├─ε─> NFA(WHILE 规则)     接受 → token=WHILE,   优先级 2
  新起始态 s₀ ───┼─ε─> NFA(ID 规则)        接受 → token=ID,      优先级 3
                 ├─ε─> NFA(NUM 规则)       接受 → token=NUM,     优先级 4
                 └─ε─> NFA(WS 规则)        接受 → token=WS,      优先级 5
```

对这个"大 NFA"做子集构造。**关键在于 DFA 接受状态要携带额外信息**：

一个 DFA 状态 `S` 可能同时包含**多个规则的接受态**（例如读完 `if` 后，`S` 里既有 IF 的接受态，也有 ID 的接受态）。于是：

| 词法歧义规则                    | 在 DFA 中的实现                                                                            |
| ------------------------- | ------------------------------------------------------------------------------------- |
| **最长匹配优先**（maximal munch） | DFA 不在第一次进入接受状态时停止，而是**继续读**，同时记录 `(最后一次接受的位置, 当时的 token 类型)`；直到无路可走时回退（`yyless`）到该位置 |
| **规则优先**（同长度时取书写靠前者）      | 子集构造时，若 `S` 含多个接受态，取其中**规则序号最小**的那个作为 `S` 的 token 标签                                  |

```c
// 词法器主循环的骨架（flex 生成代码的本质）
state = s0;
last_accept_pos  = -1;
last_accept_kind = NONE;
while ((c = next_char()) != EOF) {
    next = delta[state][ec[c]];        // ec[] 是字符等价类映射
    if (next == DEAD) break;           // 无路可走
    state = next;
    pos++;
    if (accept[state] != NONE) {       // 记住这次接受，但继续往下读
        last_accept_pos  = pos;
        last_accept_kind = accept[state];
    }
}
rollback_to(last_accept_pos);          // 回退到最后一次接受点
emit(last_accept_kind);
```

> **教学要点**：很多人只记住"最长匹配"，但没意识到它**恰恰是子集构造必须携带优先级标签的原因**。这是"NFA→DFA 在真实系统中要做的适配"的最好例子。

### 1.4 ③ DFA 最小化

子集构造产生的 DFA 通常有冗余状态（不同子集可能语言等价）。

| 算法               | 复杂度                | 思路                                                            |
| ---------------- | ------------------ | ------------------------------------------------------------- |
| **Moore / 划分精化** | `O(n²·\|Σ\|)`      | 从 `{接受态}, {非接受态}` 开始，反复按转移目标所在块细分                             |
| **Hopcroft**     | `O(n·\|Σ\|·log n)` | 划分精化 + "总是处理较小的那半"（smaller half）技巧                            |
| **Brzozowski**   | 可能指数               | `min-DFA = reverse→determinize→reverse→determinize`，极简优雅但可能爆炸 |

注意：**词法器的最小化要按 token 标签分块初始化**，不能只分"接受/非接受"——否则会把接受 IF 和接受 ID 的状态错误合并。

### 1.5 直接从正则式构造 DFA（跳过 NFA）

龙书 3.9.5 节的方法：在正则式的语法树上计算四个属性

- `nullable(n)`：子树能否匹配 ε
- `firstpos(n)`：能作为第一个符号的位置集合
- `lastpos(n)`：能作为最后一个符号的位置集合
- `followpos(p)`：位置 `p` 之后可紧跟的位置集合

然后 **DFA 状态 = 位置集合**，`δ(S, a) = ⋃{followpos(p) | p∈S, symbol(p)=a}`。

> **这仍然是子集构造**——只不过 `followpos` 把 ε-闭包**预先算好并内联**了，所以看起来像"直接构造"。理解这一点很重要：它不是另一个算法，而是同一算法的**融合优化（fusion）版本**。

### 1.6 ④ 表压缩：flex 的工程细节

原始转移表是 `状态数 × 256`，对上千状态的词法器就是 MB 级。flex 的多级压缩：

| 技术                                 | flex 选项       | 说明                                                      |
| ---------------------------------- | ------------- | ------------------------------------------------------- |
| **字符等价类**（equivalence classes）     | `-Ce`         | 把行为完全相同的字符归为一类。C 语言词法器通常把 256 个字符压到 ~30 个类。这是**列方向**的压缩 |
| **元等价类**（meta-equivalence classes） | `-Cm`         | 把行为相同的**状态**归类，**行**方向压缩                                |
| **default 链 + next/check 数组**      | `-Cf` 关闭时默认   | 稀疏表压缩：`yy_nxt`/`yy_chk`/`yy_def`，用"失败转移链"共享行            |
| **全表**（不压缩）                        | `-Cf` / `-CF` | 最快但最大，适合性能敏感场景                                          |

## 2. LR 分析表构造：最深刻的"隐藏"应用

这是最容易被忽略、但理论上最漂亮的一处：**LR(0) 项目集规范族的构造，就是一次子集构造。**

### 2.1 关键理论事实

> **定理**：对任意上下文无关文法 `G`，其**活前缀（viable prefix）**的集合是一个**正则语言**。

- 活前缀 = 某个右句型（right-sentential form）的前缀，且不越过句柄右端；
- 直观说：栈上可能出现的所有内容构成一个正则语言。

**这就是整个 LR 理论成立的根基**：CFG 本身不是正则的，但"栈的合法内容"是正则的。于是可以用一个**有限自动机**来识别栈内容，并据此决定移进/规约。这个自动机就是 LR(0) 自动机（也叫**识别活前缀的 DFA**）。

### 2.2 项目 NFA（Item NFA）

把每个 **LR(0) 项目**当作一个 NFA 状态：

| 转移类型     | 规则                                              |
| -------- | ----------------------------------------------- |
| **符号转移** | `A → α·Xβ` ──`X`──> `A → αX·β`（`X` 可以是终结符或非终结符） |
| **ε 转移** | `A → α·Bβ` ──`ε`──> `B → ·γ`（对每条 `B` 的产生式）      |
| 起始状态     | `S' → ·S`                                       |

**例**：文法 `S' → S`, `S → aSb | ε`

```
        S'→·S ──S──> S'→S·
          │
          ε
          ↓
        S→·aSb ──a──> S→a·Sb ──S──> S→aS·b ──b──> S→aSb·
        S→·                    │
                               ε
                               ↓
                            S→·aSb , S→·
```

### 2.3 CLOSURE 就是 ε-闭包，GOTO 就是子集构造的一步

对照关系一目了然：

| 子集构造                            | LR(0) 自动机构造                                          |
| ------------------------------- | ---------------------------------------------------- |
| NFA 状态                          | LR(0) 项目                                             |
| ε 转移                            | `A → α·Bβ` 到 `B → ·γ`                                |
| `ε-closure(S)`                  | **`CLOSURE(I)`**                                     |
| `move(S, a)`                    | 把 `A → α·Xβ` 推进为 `A → αX·β`                          |
| `δ(S,a) = ε-closure(move(S,a))` | **`GOTO(I, X) = CLOSURE(move(I, X))`**               |
| DFA 状态 = NFA 状态子集               | **LR(0) 项目集（item set）= 项目的子集**                       |
| DFA 状态集                         | **项目集规范族（canonical collection）** `C = {I₀, I₁, ...}` |
| worklist 迭代直到无新状态               | "重复：对每个 `I∈C` 和每个 `X`，若 `GOTO(I,X)∉C` 则加入"           |

```
CLOSURE(I):
    repeat
        for each item [A → α·Bβ] in I:
            for each production B → γ:
                add [B → ·γ] to I           // 这就是 ε-闭包
    until I 不再变化
    return I

items(G'):                                   // 这就是子集构造
    C = { CLOSURE({[S' → ·S]}) }             //   s₀ = ε-closure({q₀})
    repeat
        for each I in C, for each grammar symbol X:
            J = GOTO(I, X)
            if J ≠ ∅ and J ∉ C:  add J to C
    until C 不再变化
```

> **结论**：教科书把 `CLOSURE`/`GOTO` 当作"新概念"来教，但它们只是 ε-闭包和子集构造在项目 NFA 上的实例。一旦看穿这层，LR 表构造就从"要背的算法"变成了"已知算法的应用"。

### 2.4 由此推出的 LR 家族关系

在 LR(0) 自动机之上加不同强度的"前看信息"，就得到不同的 LR 变体：

| 变体          | 自动机                    | 前看来源                      | 状态数（Java/C 量级文法）               |
| ----------- | ---------------------- | ------------------------- | ------------------------------ |
| **LR(0)**   | 项目 NFA 的子集构造结果         | 无                         | 基准                             |
| **SLR(1)**  | **同一个** LR(0) 自动机      | 全局 `FOLLOW(A)`（**最粗的近似**） | 与 LR(0) 相同                     |
| **LALR(1)** | LR(0) 自动机 + 每个项目的前看集   | 上下文相关但**合并同心状态**          | 与 LR(0) 相同（~几百）                |
| **LR(1)**   | `[A→α·β, a]` 作为项目的子集构造 | 精确                        | **爆炸**（可达数万，是 LALR 的 10–100 倍） |

三个重要认识：

1. **LR(1) 的状态爆炸，就是子集构造的状态爆炸**——因为项目里多带了前看符号，NFA 状态数乘以 `|T|`，子集数量随之暴涨。
2. **LALR(1) = 合并 LR(1) 中"同心"（same core，即去掉前看后相同）的状态**。这是一种**状态合并**（state merging）而非最小化：它可能引入 reduce/reduce 冲突（但绝不会引入 shift/reduce 冲突）。这与"DFA 最小化"是不同性质的操作——最小化保语言，合并同心状态不保。
3. **SLR 用 `FOLLOW(A)` 近似前看**，这与 [ANTLR 的线性近似前看](#33-ll-一：线性近似前看有界子集构造)、[ANTLR 4 的 SLL 模式](#35-all-运行期惰性带栈子集构造) 在思想上是同一类操作：**用一个更粗但更便宜的近似替代精确分析**。这是编译器设计中反复出现的母题。

### 2.5 实际工具

| 工具             | 算法                             | 备注                             |
| -------------- | ------------------------------ | ------------------------------ |
| Yacc / Bison   | LALR(1)（Bison 也支持 IELR(1)、GLR） | DeRemer–Pennello 的高效 LALR 前看计算 |
| CUP / SableCC  | LALR(1)                        |                                |
| Menhir (OCaml) | LR(1)（Pager 算法做状态合并）           | 兼顾 LR(1) 能力和可接受的状态数            |
| LALRPOP (Rust) | LR(1) / LALR(1)                |                                |

## 3. LL 分析中的前看计算

自顶向下分析的核心决策是"在规则 `A → α₁ | α₂ | ... | αₙ` 处该选哪条**备选分支**"。这同样是一个**不确定性消除**问题，因此也用**子集构造**。

### 3.1 深度 1：LL(1) 预测集 —— 退化的子集构造

```
PREDICT(A → α) = FIRST(α) ∪ (if α ⇒* ε then FOLLOW(A) else ∅)
```

`FIRST` 集合的计算就是"在项目 NFA 上做深度为 1 的 ε-闭包 + 一步 move"。文法是 LL(1) 的条件 = 各分支的预测集两两不交 = 子集构造的第一步就已确定。

### 3.2 递归下降中的 EBNF 右部：正则右部驱动的循环判定

写 `A : x (b | c)* d ;` 这类 EBNF 时，生成的递归下降代码需要在循环处判断"继续循环还是退出"。这个判定本质是**为规则右部的正则结构构造一个小 DFA**，用它驱动 `while` 循环的条件。ANTLR、Coco/R、JavaCC 都这样做。

### 3.3 LL(k)：线性近似前看（有界子集构造）

Terence Parr 在 PCCTS/ANTLR 1–2 中的做法（他博士论文的核心）：

**观察**：计算 LL(k) 前看集，本质上是一次**深度有界的 NFA → DFA 子集构造**（在项目 NFA 上向前推进最多 `k` 步）。

**问题**：精确 LL(k) 前看是 `k` 元组的集合，空间 `O(|T|^k)`。

**近似**：不记录精确元组，而是把**每个深度 n（1≤n≤k）上出现的符号合并成一个集合**：

```
精确 LL(k):   LOOK(A) ⊆ T^k                    // k 元组的集合，指数
近似 LL(k):   LOOK(A) = [S₁, S₂, ..., S_k]     // k 个集合的数组，线性
              冲突判定：逐位求交，全部非空才算冲突
```

**效果**：`O(|T|^k)` → **`O(|T|×k)`**，指数变成乘数。代价是丢失了元组间的关联（可能虚报冲突），但实测精确前看只多带来约 5% 的识别能力。ANTLR 采用两级策略：先用近似前看过滤，只在报冲突时才对该决策做精确的全前看。

> **注意这里与 SLR 的对偶性**：SLR 用全局 `FOLLOW` 近似 LR(1) 的上下文相关前看；近似 LL(k) 用"集合数组"近似元组集合。两者都是**把精确的笛卡尔积压扁成投影**，都是牺牲少量精度换取从指数到线性。

### 3.4 LL(\*)：编译期构造前看 DFA（ANTLR 3, PLDI 2011）

固定 `k` 的天花板：公共前缀可能**无界**。

```antlr
A : a b* c
  | a b* d
  ;
```

`a b*` 长度无界，任何固定 `k` 都不够。

**LL(\*) 的做法**：把前看语言从"`k` 个集合的乘积"提升为**任意正则语言**，即为每个决策点在**编译期**构造一个**前看 DFA**：

```
             ┌──── b ────┐            // b 上的自环：跨越无限重复
             ↓           │
  s₀ ──a──> s₁ ─────────┘
             ├── c ──> [预测分支 1]
             └── d ──> [预测分支 2]
```

这个 DFA 就是对项目 NFA（用 FOLLOW 近似掉调用栈后）做**完整的、不限深度的子集构造**得到的。它能向前看任意远，并越过循环去看后续的区分符号。

**LL(\*) 的死穴**：这个 DFA 用**正则语言**近似前看语言，但真实的前看语言可能是**非正则的上下文无关语言**（需要"记住调用栈"才能区分）。此时子集构造根本无法收敛到一个有用的 DFA，ANTLR 3 只能报警告并退化为回溯。

### 3.5 ALL(\*)：运行期惰性、带栈的子集构造（ANTLR 4, OOPSLA 2014）

这是把 NFA→DFA 玩到极致的一处，有**两个关键变化**：

#### 变化一：从编译期改到运行期（惰性 + 增量）

不在编译期构造完整 DFA，而是在**解析时**、面对**真实输入**，按需做子集模拟；模拟经过的每个配置子集被**缓存为一个 DFA 状态**：

```
第 1 次遇到决策 d 且输入前缀为 "int ID = ..."：
    → 在 ATN 上做子集模拟（慢）
    → 沿途的配置子集 → 增量加入 d 的 DFA 缓存

第 2..n 次遇到决策 d 且输入前缀相同：
    → 直接沿缓存 DFA 走（快，本质是查表）
```

**"分析成本随解析进行被摊销掉"——这就是 Adaptive 的含义。** 解析器越"热"，行为越接近纯 DFA 驱动。

> 这个"**lazy DFA construction**"技巧在 [第 7 节](#71-正则表达式引擎的-lazy-dfare2rust-regexgo-regexp) 还会以另一种形式出现（RE2）。它是应对状态爆炸最有效的通用武器：**只为实际见过的输入付费**。

#### 变化二：配置携带调用栈 —— 超出了纯 NFA→DFA

ANTLR 4 把文法编译成 **ATN（Augmented Transition Network，增强转移网络）**——一个带**规则调用/返回边**的转移网络（概念源自 Woods 1970 的 NLP 工作）。它实际上是一个**递归转移网络 / 下推自动机**，而不是纯 NFA。

模拟时的配置是三元组：

```
configuration = (ATN 状态 p, 备选分支号 i, 调用栈 γ)
                                            ^^^^^^^^^
                                    ← 这一项让它超出正则
```

因为配置里带了**真实的解析器调用栈**，ALL(\*) 的前看语言不再局限于正则语言——这正是它突破 LL(\*) 天花板、能处理**任意非左递归 CFG** 的原因。

> **重要区分**：
> 
> - 普通子集构造：状态子集，前看语言 = **正则语言**
> - ALL(\*) 的子集模拟：**(状态, 栈) 配置的子集**，前看语言可以是**上下文无关的**
> 
> 但这也是它理论最坏复杂度为 `O(n⁴)` 的原因——栈上下文使得"状态"的数量不再有限，缓存可能持续增长。

#### 附带：SLL / LL 两阶段策略（又一次"近似优先"）

| 模式                       | 栈处理                    | 特点                           |
| ------------------------ | ---------------------- | ---------------------------- |
| `PredictionMode.SLL`（默认） | **忽略精确栈**，用"所有可能调用者"近似 | DFA 可在不同调用上下文间**共享**，命中率极高，快 |
| `PredictionMode.LL`      | 携带**精确栈**              | 精确，慢，DFA 复用性差                |

推荐的 two-stage parsing：

```java
// 第一遍：SLL + 立即失败，覆盖 99% 的正确输入，极快
parser.getInterpreter().setPredictionMode(PredictionMode.SLL);
parser.setErrorHandler(new BailErrorStrategy());
try {
    tree = parser.compilationUnit();
} catch (ParseCancellationException e) {
    // 第二遍：仅在失败时用完整 LL 重解析，保证正确性和优质错误消息
    tokens.seek(0);
    parser.reset();
    parser.getInterpreter().setPredictionMode(PredictionMode.LL);
    parser.setErrorHandler(new DefaultErrorStrategy());
    tree = parser.compilationUnit();
}
```

这与 `SLR → LALR → LR(1)` 的阶梯、`近似前看 → 全前看` 的阶梯完全同构：**先用便宜的近似，只在必要时付昂贵的精确代价。**

## 4. 关键字与多模式匹配：Aho–Corasick

在符号表初始化、预处理器指令识别、`switch` 化的关键字判定、以及编译器自带的字符串搜索工具中都会用到。

**Aho–Corasick 自动机**的构造过程本身就是一次隐式的 NFA→DFA：

```
① 把所有模式串建成 Trie（goto 函数）           ← 这是"部分定义"的转移函数
② 用 BFS 计算 failure 链 fail(s)               ← 相当于 ε 转移
③ 补全 δ(s,a) = goto(s,a) 若存在
              = δ(fail(s), a) 否则             ← 这一步就是确定化
```

- **步骤 ①+②** 得到的是一个 **NFA**：在状态 `s` 上遇到 `a` 无 goto 时，需要"不确定地"沿 fail 链回退（可能多步）。
- **步骤 ③** 把 fail 链**预先展开并内联**，得到完全定义的 `δ`，就是一个 **DFA**——每步 `O(1)`，扫描总时间 `O(n)`。

两种实现的权衡：

| 实现                   | 转移表大小              | 每步代价                 | 对应关系         |
| -------------------- | ------------------ | -------------------- | ------------ |
| goto + fail 链（NFA 式） | `O(总模式长度)`         | 均摊 `O(1)`，最坏 `O(深度)` | 类似"直接模拟 NFA" |
| 完全展开 δ（DFA 式）        | `O(总模式长度 × \|Σ\|)` | 严格 `O(1)`            | 类似"子集构造后查表"  |

这个权衡与 flex 的 `-Cf`（全表）vs 默认（压缩表）**完全是同一个权衡**。

> **另一个视角**：KMP 的 `next` 数组是单模式版的 failure 链；Aho–Corasick 是它的多模式推广；而"把 failure 链展开成完整转移表"就是确定化。

## 5. 指令选择：树 NFA → 树 DFA

这是后端的一处应用，思想与词法分析完全平行，只是把**串**换成了**树**。

### 5.1 问题

指令选择需要用**树模式**（对应目标机指令）去覆盖 IR 表达式树。多条模式同时是候选：

```
;; 目标机指令模式（树文法）
reg  → PLUS(reg, reg)              ; ADD    cost 1
reg  → PLUS(reg, CONST)            ; ADDI   cost 1
reg  → LOAD(PLUS(reg, CONST))      ; LDR    cost 1   ← 与下面两条竞争
reg  → LOAD(reg)                   ; LDR    cost 1
reg  → CONST                       ; MOV    cost 1
```

给定一棵 IR 树，要在**每个节点上**知道"哪些模式的哪些位置可以匹配到这里"——这是不确定性。

### 5.2 Hoffmann–O'Donnell：树 NFA → 树 DFA

- **树 NFA**：状态 = "模式集合中的某个子模式位置"（类比 LR 项目 / 正则式位置）
- **确定化**：状态 = **子模式位置的集合**（match set），自底向上传播
- 预处理阶段把这些 match set 编号，生成表；匹配阶段每个节点只需一次查表 `O(1)`

```
δ_op(状态₁, 状态₂, ..., 状态_k) = 状态   // 对 k 元运算符 op 的转移表
```

**这就是树上的子集构造。** 但树自动机的确定化状态爆炸比串更严重（表是多维的：`|状态|^arity`），所以工程上常见的替代方案：

| 工具                     | 方案                                     | 是否真的确定化                                |
| ---------------------- | -------------------------------------- | -------------------------------------- |
| **twig**               | 树模式匹配 + 动态规划                           | 类似 Aho–Corasick 的树版本                   |
| **BURG**               | 预计算的 BURS 状态表 + 离线状态编号                 | **是**，真做树自动机确定化                        |
| **iburg / lburg**      | **不预计算**，运行时自底向上做 DP（labeler）          | **否**，用"运行时 DP"替代确定化，牺牲常数换取零预处理和易维护    |
| LLVM ISel / GlobalISel | 基于 `MatcherTable` 的字节码解释 + TableGen 生成 | 部分：TableGen 做前缀共享（类似 Trie 压缩），但不做完全确定化 |

> **这是"不确定化"的经典理由**：当状态空间维度太高时，**直接模拟 NFA（用 DP）可能比确定化更划算**。iburg 论文明确论证了这一点：iburg 比 burg 慢一个常数因子，但代码量小一个数量级、易于调试。这与 GLR/GLL 选择"直接模拟"而非确定化的理由如出一辙。

## 6. 静态分析与程序验证

### 6.1 Typestate / 有限状态属性验证

要检查"文件必须先 open 再 read，最后 close，且不能重复 close"这类性质，标准做法：

```
① 用 NFA/正则式描述合法（或非法）的操作序列
   例如：非法模式 = Σ* · close · Σ* · close · Σ*
② 确定化为 DFA                                    ★
③ 把 DFA 状态作为数据流分析的抽象值（格元素）
④ 在 CFG 上做正向数据流分析，transfer 函数 = DFA 转移
⑤ 到达"错误状态"⇒ 报告缺陷
```

**为什么第 ② 步必须做？** 因为数据流分析要求 transfer 函数是**格上的确定函数**。如果留在 NFA 形态，抽象值就得是"NFA 状态集合"——而那恰好就是 DFA 状态。所以要么先离线确定化，要么把"集合"当作抽象域**在线做确定化**（这正是 ANTLR 4 的 lazy DFA 思路）。

代表工具：Fugue、SLAM（SLIC 规约）、ESP、Java Typestate Checker、Facebook Infer 的 topl checker。

### 6.2 字符串分析的抽象域

用**自动机作为抽象值**来分析程序中的字符串（检测 SQL 注入、XSS、验证正则安全性）：

- `concat(A, B)` → 自动机串联（引入 ε 边 ⇒ 需要重新确定化）
- `A ∪ B` → 并（引入不确定分支 ⇒ 需要重新确定化）
- `A ∩ B` → 积构造
- 循环处求 widening → 需要最小化以保持自动机不无限增长

代表：Java String Analyzer (JSA)、Stranger、JSAI。这里 **NFA→DFA + 最小化几乎在每一步抽象操作后都要执行**，否则自动机规模会失控。

### 6.3 模型检验：一个反例

`LTL → 自动机 → 检验`的路线中：

```
LTL 公式 φ  --(Vardi–Wolper)-->  非确定 Büchi 自动机 (NBA)
```

**但 Büchi 自动机不能用子集构造确定化！** 这是一个重要的理论边界：

| 自动机类型      | 确定化                             |
| ---------- | ------------------------------- |
| 有限字（NFA）   | ✔ 子集构造，`2ⁿ`                     |
| 无限字（Büchi） | ✘ 子集构造**不保语言**（经典反例 `(a+b)*aω`） |

必须用更复杂的构造：

- **Safra 构造**（1988）：状态是"Safra 树"，复杂度 `2^O(n log n)`，得到 Rabin 自动机
- **Piterman / Schewe 改进**：得到 parity 自动机，是目前最优
- 或**完全绕过确定化**：用 nested DFS / 补集运算（Kupferman–Vardi），这也是 SPIN 等工具的做法

> **这个反例很有教学价值**：它说明"子集构造"的正确性依赖于"接受条件是有限字上的可达性"。一旦接受条件变成 ω-条件（无限次访问），子集就丢失了"是哪条路径无限次访问接受态"这一关键信息。

### 6.4 IFDS / IDE 框架

Reps–Horwitz–Sagiv 的 IFDS 框架把过程间数据流分析归约为**图可达性**问题。虽然不叫"NFA→DFA"，但其核心的 **summary edge 计算**在结构上是"带栈的可达性闭包"——与 ALL(\*) 的带栈子集模拟是同一类计算（都是求解下推系统的可达性）。

## 7. 其他散落的应用

### 7.1 正则表达式引擎的 lazy DFA（RE2/Rust regex/Go regexp）

如果编译器内建正则支持（或用于 lint 规则、语法高亮），会遇到这个设计：

| 引擎类型                        | 策略                              | 最坏复杂度              |
| --------------------------- | ------------------------------- | ------------------ |
| 回溯式（PCRE, Perl, Java, .NET） | 直接**回溯模拟 NFA**                  | **指数**（ReDoS 漏洞根源） |
| Thompson NFA 模拟             | 逐步推进状态集合，**不缓存**                | `O(n·m)`           |
| **Lazy DFA**（RE2/Go/Rust）   | 推进状态集合，**并缓存为 DFA 状态**，缓存满则清空重建 | `O(n)` 摊销，有界内存     |
| 完全 DFA                      | 预先子集构造                          | `O(n)`，但 `2^m` 空间  |

**Lazy DFA 是同一个"惰性子集构造"技巧在正则引擎中的化身**，与 ANTLR 4 的 ALL(\*) 缓存机制在实现层面几乎一模一样（都是：模拟 → 缓存 → 内存压力时 `clearDFA()`）。

### 7.2 语法高亮与增量词法分析

- TextMate/VSCode 语法（Oniguruma 正则）、Tree-sitter 的词法层，都需要在编辑器中反复重扫；
- **DFA 的关键优势**：状态可以被**保存在每行末尾**（一个整数），从而只需重扫被修改的行 —— 这依赖"DFA 状态完整概括了历史"这一性质，NFA 状态集合虽然也能存但代价高得多。

### 7.3 XML/JSON Schema 与正则树文法

XML Schema 的内容模型验证要求"确定性内容模型"（UPA, Unique Particle Attribution）——本质上要求正则表达式对应的自动机满足某种确定性条件，验证时也做 NFA→DFA。RELAX NG 用 derivative（Brzozowski 导数）方法，是确定化的另一种表述。

### 7.4 编译器构建的其他角落

| 场景                             | NFA→DFA 的角色                           |
| ------------------------------ | ------------------------------------- |
| **预处理器 / 宏展开**                 | token 序列模式匹配                          |
| **peephole 优化**                | 指令序列模式匹配（串上的 Aho–Corasick 或树上的树自动机）   |
| **代码克隆检测**                     | 后缀自动机（DAWG）——本质是最小 DFA                |
| **正则类型 / 会话类型（session types）** | 类型的子类型判定归约为自动机包含检查，需确定化               |
| **CFG 可达性 / 数据流的正则化**          | Kleene 算法把 CFG 转成正则表达式（反方向：DFA → 正则式） |

## 9. 贯穿全局的工程主题：状态爆炸及其六种应对

上表中每一处应用都要面对 `2ⁿ` 的威胁。编译器领域发展出的应对手段可以归纳为六类，**认识这六类比记住任何单个算法都更有价值**：

### ① 惰性 / 按需构造（Lazy / On-demand）

> 只为实际出现过的输入付费。

- ANTLR 4 的 ALL(\*) DFA 缓存
- RE2 / Go / Rust regex 的 lazy DFA
- Bison 的按需 LALR 前看计算（DeRemer–Pennello）

**代价**：需要缓存管理（内存增长、失效策略）；首次命中慢。

### ② 近似 / 投影（Approximation）

> 用更粗但更便宜的抽象替代精确计算，并**量化损失的代价**。

| 精确版                | 近似版                    | 损失         |
| ------------------ | ---------------------- | ---------- |
| LR(1) 上下文相关前看      | **SLR**：全局 `FOLLOW(A)` | 引入部分冲突     |
| 精确 LL(k) 的 `k` 元组集 | **线性近似前看**：`k` 个集合的数组  | 实测仅 ~5% 能力 |
| ALL(\*) 精确栈（LL 模式） | **SLL 模式**：忽略栈         | 少数句子需回退重解析 |
| 精确指向分析             | 上下文不敏感 / k-CFA         | 精度下降       |

**关键工程原则**：近似必须**可检测**——即知道"近似失败了"，从而能回退到精确版。这就是"两级策略"（filter + fallback）的普适模式。

### ③ 最小化（Minimization）

> 构造后压缩，保语言等价。

- 词法 DFA：Hopcroft `O(n log n)`
- 字符串抽象域：每步操作后最小化，防止规模累积
- **注意**：最小化保语言，是"无损压缩"

### ④ 状态合并（Merging，非保语言）

> 主动接受精度损失换取状态数下降。

- **LALR(1) = LR(1) 合并同心状态**（可能引入 reduce/reduce 冲突，但绝不引入 shift/reduce 冲突）
- **Pager 算法**（Menhir 用）：只合并不产生冲突的状态，介于 LALR 和 LR(1) 之间
- **IELR(1)**（Bison 支持）：产生与 LR(1) 等价的冲突行为，但状态数接近 LALR

### ⑤ 表压缩（Table Compression）

> DFA 结构不变，只压缩存储。

- flex：等价字符类（列压缩）、元等价类（行压缩）、`next/check/default` 稀疏表
- Yacc/Bison：`yytable`/`yycheck`/`yydefact` 行共享
- LLVM TableGen 的 `MatcherTable` 字节码

### ⑥ 干脆不确定化（Don't Determinize）

> 当状态空间维度过高时，直接模拟 NFA 可能更划算。

| 场景        | 不确定化的方案                     | 理由                                     |
| --------- | --------------------------- | -------------------------------------- |
| 通用 CFG 解析 | **GLR / GLL / Earley**      | 直接并行模拟，用 GSS/SPPF 共享；确定化不可能（PDA 不可确定化） |
| 指令选择      | **iburg 的运行时 DP**           | 树自动机表是多维的，预计算成本/复杂度太高                  |
| 正则匹配      | **Thompson NFA 模拟** `O(nm)` | 一次性匹配，建 DFA 不摊销得回来                     |
| Büchi 自动机 | **nested DFS**，避免 Safra 构造  | 确定化本身是 `2^O(n log n)` 且实现极复杂           |

---

## 10. 理论边界：什么时候不能确定化

这是一个容易被忽略但很重要的知识点。

| 自动机类型              | 可确定化？     | 说明                                                                                |
| ------------------ | --------- | --------------------------------------------------------------------------------- |
| **NFA（有限字）**       | ✔         | 子集构造，`2ⁿ` 状态上界紧                                                                   |
| **ε-NFA**          | ✔         | 先 ε-闭包，同上                                                                         |
| **NFA + 计数器（有界）**  | ✔         | 展开计数器即可                                                                           |
| **树自动机（自底向上）**     | ✔         | 子集构造推广，但表是多维                                                                      |
| **下推自动机（PDA）**     | ✘         | DPDA ⊊ PDA。存在 CFL 不能被任何 DPDA 识别（如 `{aⁿbⁿ} ∪ {aⁿb²ⁿ}`）。**这是 LR 只能覆盖 CFG 真子集的根本原因** |
| **Büchi 自动机（无限字）** | ✘（子集构造无效） | 需 Safra / Piterman 构造，`2^O(n log n)`                                              |
| **加权/概率自动机**       | ✘（一般）     | 确定化可能不终止                                                                          |

### 由此得到两个重要推论

**推论 1：为什么 LR 能用 DFA，而"解析 CFG"整体不能？**

LR 的成功恰恰因为它**没有试图确定化 PDA**，而是把问题拆成两半：

```
栈内容的识别（活前缀集合）→ 正则语言 → 可以用 DFA  ✔
整个语言的识别            → CFL     → 需要栈       ✔（栈由 parser 显式维护）
```

即：**DFA 管"看栈顶决定动作"，显式的栈管"上下文无关性"**。这个分工是 LR 理论最精妙的地方。

**推论 2：为什么 ALL(\*) 能突破 LL(\*)？**

```
LL(*)  的前看：正则语言（栈被 FOLLOW 近似掉）→ 可确定化为 DFA → 但表达力不足
ALL(*) 的前看：配置带栈 → 超出正则 → 不能预先确定化 → 所以必须移到运行期！
```

**"把分析移到运行期"不是一个随意的工程选择，而是理论必然**：因为前看语言不是正则的，静态子集构造根本无法收敛。运行期之所以可行，是因为此时**栈是一个具体的值而非一个集合**，不确定性大幅降低。

## 11. 小结与学习路径建议

### 11.1 一句话总结

> **NFA → DFA 是编译器前端的"万能锤"。** 它出现在词法分析（识别哪个 token）、LR 表构造（用哪条产生式规约）、LL 前看计算（选哪条备选分支）、多模式匹配、指令选择、静态分析抽象域等所有需要"消除多候选不确定性"的地方。
> 变化的只有三件事：**NFA 状态是什么、ε 转移是什么、以及在什么时候做确定化（编译期 / 运行期 / 惰性）**。

### 11.2 掌握程度自检

如果你能回答下面这些问题，说明真正理解了：

1. `CLOSURE(I)` 和 `ε-closure(S)` 是什么关系？`GOTO(I,X)` 对应子集构造的哪一步？
2. 为什么词法器的 DFA 状态必须携带"规则优先级"？这与"最长匹配"有什么关系？
3. LR(1) 状态爆炸和子集构造的 `2ⁿ` 上界是同一件事吗？LALR 的"合并同心状态"是 DFA 最小化吗？
4. SLR 用 `FOLLOW` 近似、ANTLR 的线性近似前看、ANTLR 4 的 SLL 模式——这三者的共同点是什么？
5. 为什么 ANTLR 4 必须把分析移到运行期？这是工程选择还是理论必然？
6. 为什么 Büchi 自动机不能用子集构造确定化？给出直觉。
7. 什么时候"不确定化"（直接模拟 NFA）反而是更好的选择？举三个例子。

### 11.3 建议的学习顺序

```
① 词法分析全链路（RE → Thompson NFA → 子集构造 → Hopcroft 最小化）
   └─ 亲手实现一遍，包括多规则合并和最长匹配回退
        ↓
② 项目 NFA → LR(0) 自动机
   └─ 关键：亲手画一个小文法的项目 NFA，再确定化，
      验证它和教科书的项目集规范族完全一致
        ↓
③ LR 家族的近似阶梯（LR(0) → SLR → LALR → LR(1)）
   └─ 关键：理解"近似"和"合并"是两种不同的操作
        ↓
④ LL 侧的对偶阶梯（LL(1) → 近似 LL(k) → LL(*) → ALL(*)）
   └─ 关键：理解"投影近似"和"惰性构造"两个母题
        ↓
⑤ 理论边界（DPDA ⊊ PDA；Büchi 不可用子集构造确定化）
   └─ 关键：理解 LR 为什么"能"，以及它的天花板在哪
        ↓
⑥ 后端与分析侧（树自动机 / typestate / 字符串抽象域）
   └─ 关键：看到同一个锤子在不同钉子上的形态变化
```

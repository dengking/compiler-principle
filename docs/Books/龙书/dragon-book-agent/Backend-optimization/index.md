# 编译器后端优化的"万能锤"

后端**没有**一把像 NFA → DFA 那样单一、机械、无争议的万能锤。但有**一把接近的主锤**加**六把大锤**：

|        | 锤子                                                         | 统一的是什么                     |
| ------ | ---------------------------------------------------------- | -------------------------- |
| **主锤** | **格上的单调不动点迭代（抽象解释）**                                       | 一切"程序性质推导"——安全性/合法性判定      |
| 大锤 ①   | **SSA + 支配关系**                                             | 后端的通用坐标系；把**稠密分析**变**稀疏**  |
| 大锤 ②   | **等价类的合并与精化（Union-Find / Partition Refinement / E-graph）** | 一切"这两段代码等价吗"               |
| 大锤 ③   | **最优子结构上的动态规划**                                            | 树/序列上的最优拼接（指令选择、调度、tiling） |
| 大锤 ④   | **归约到图问题 + 启发式**                                           | 资源分配（寄存器、功能单元）             |
| 大锤 ⑤   | **多面体模型（仿射代数）**                                            | 一切循环嵌套变换                   |
| 大锤 ⑥   | **代价模型 + 搜索**                                              | 当上面全都不够用时的最后手段             |

而最深刻的一点是：**前端的锤和后端的主锤其实是同一把。** 子集构造就是**幂集格** `(2^Q, ⊆)` 上的最小不动点计算——`worklist` 循环、`ε-closure` 的传递闭包、"直到不再变化"，全都是 **Kleene 迭代**。前端把它用来**消除不确定性**（判定问题），后端把它用来**在不确定中求最强的可靠断言**（近似问题）。

## 0. 为什么后端不可能只有一把锤子

这不是工程上的偶然，而是**问题性质的根本差异**。

### 0.1 前端解决判定问题，后端解决优化问题

|      | 前端（词法/语法分析）            | 后端（优化/代码生成）                    |
| ---- | ---------------------- | ------------------------------ |
| 问题类型 | **判定**：这串输入合法吗？该走哪条分支？ | **优化**：哪个等价程序最快/最小？            |
| 正确答案 | **唯一**（由文法定义）          | **不唯一**（等价程序有无穷多个）             |
| 评价标准 | 对/错                    | 需要**代价模型**（且模型本身是近似的）          |
| 复杂度  | 多项式（甚至线性）              | 核心子问题多为 **NP-hard 或不可判定**      |
| 可组合性 | 阶段之间干净分层               | **phase ordering 问题**：变换顺序影响结果 |

后端的每一个核心任务都能归约到一个 NP-hard 问题：

| 任务               | 归约到           | 复杂度                       |
| ---------------- | ------------- | ------------------------- |
| 寄存器分配            | 图着色           | NP-complete（Chaitin 1981） |
| 指令调度（基本块内、有资源约束） | 资源约束调度        | NP-complete               |
| DAG 上的指令选择       | 最小代价 DAG 覆盖   | NP-complete               |
| 代码放置 / 基本块排序     | 线性排列 / TSP 变体 | NP-hard                   |
| "这两段代码等价吗"       | 程序等价性         | **不可判定**                  |
| "这个优化有收益吗"       | 依赖精确性能预测      | 不可计算（真实硬件）                |

**所以后端必然是"一族锤子"**：安全性用不动点分析保证，收益性用代价模型和搜索处理，这是两件本质不同的事。

### 0.2 后端优化的统一框架

尽管如此，可以给出一个统一的描述：

```
后端优化 = 在"语义等价的程序空间"中搜索代价最小的点

     ┌────────────────────────────────────────────┐
     │  合法性（Safety）    ← 主锤：不动点分析      │
     │    "这个变换保持语义吗？"                   │
     │    活跃?  别名?  依赖?  溢出?  异常?         │
     ├────────────────────────────────────────────┤
     │  等价性（Equivalence）← 大锤②：等价类       │
     │    "这两个表达式是同一个值吗？"              │
     ├────────────────────────────────────────────┤
     │  收益性（Profitability）← 大锤③④⑤⑥         │
     │    "变换后更快吗？" → DP/图算法/搜索         │
     └────────────────────────────────────────────┘
```

**记住这个三层结构**，后面每把锤子都能定位到其中一层。

## 1. 主锤：格上的单调不动点迭代

这是后端最接近"万能锤"的东西。所有**程序性质推导**——无论叫数据流分析、抽象解释、类型推导、指向分析、别名分析、逃逸分析、区间分析——都是同一个数学结构的实例。

### 1.1 数学骨架

```
给定：
  • 完全格 (L, ⊑, ⊔, ⊓, ⊥, ⊤)      —— 抽象性质的空间
  • 单调函数 F : L → L               —— 由程序结构诱导

求：  lfp(F)  (最小不动点)  或  gfp(F)  (最大不动点)

Tarski 不动点定理：完全格上的单调函数必有最小/最大不动点。
Kleene 迭代：⊥ ⊑ F(⊥) ⊑ F²(⊥) ⊑ ... ⊑ lfp(F)
             若格高度有限，则有限步收敛。
```

**这与子集构造完全同构。** 对照一下：

| 子集构造                          | 数据流分析                               |
| ----------------------------- | ----------------------------------- |
| 格 = `(2^Q, ⊆)`（NFA 状态的幂集）     | 格 = 抽象性质的格                          |
| `F(S) = ε-closure(move(S,a))` | `F(x) = ⊔_{p∈pred} transfer_p(x_p)` |
| "重复直到集合不再增长"                  | "重复直到不动点"                           |
| worklist：新状态入队                | worklist：值变化的节点入队                   |
| 收敛保证：`2^\|Q\|` 有限             | 收敛保证：格高度有限                          |

### 1.2 数据流分析四要素

任何数据流分析都由四个参数确定：

```
(1) 方向        forward / backward
(2) 格          抽象值的集合 + 偏序
(3) transfer    每条指令/基本块对抽象值的作用
(4) meet/join   汇合点如何合并多条路径的信息
```

统一的 worklist 骨架——**注意它和第 0 节子集构造代码的骨架完全一致**：

```python
def dataflow(cfg, direction, bottom, transfer, join):
    IN  = {b: bottom for b in cfg.blocks}
    OUT = {b: bottom for b in cfg.blocks}
    worklist = list(cfg.blocks)

    while worklist:
        b = worklist.pop()
        # ① 汇合：合并所有前驱（或后继）的信息
        preds = cfg.preds(b) if direction == FORWARD else cfg.succs(b)
        IN[b] = join(*[OUT[p] for p in preds]) if preds else boundary

        # ② 传递：应用 transfer 函数
        new_out = transfer(b, IN[b])

        # ③ 若变化则把邻居重新入队（这就是 Kleene 迭代）
        if new_out != OUT[b]:
            OUT[b] = new_out
            worklist.extend(cfg.succs(b) if direction == FORWARD
                            else cfg.preds(b))
    return IN, OUT
```

### 1.3 实例总览：一把锤子打的所有钉子

| 分析                                      | 方向  | 格                        | meet   | 用途                     |
| --------------------------------------- | --- | ------------------------ | ------ | ---------------------- |
| **活跃变量** (liveness)                     | 后向  | `2^Var`, `⊆`             | `∪`    | 寄存器分配、死代码消除            |
| **到达定义** (reaching defs)                | 前向  | `2^Def`, `⊆`             | `∪`    | 构造 use-def 链           |
| **可用表达式** (available exprs)             | 前向  | `2^Expr`, `⊇`            | `∩`    | CSE                    |
| **忙表达式** (very busy)                    | 后向  | `2^Expr`, `⊇`            | `∩`    | 代码提升                   |
| **常量传播**                                | 前向  | `⊤ ⊒ 常量 ⊒ ⊥`（每变量一份）      | 逐点 `⊓` | 常量折叠                   |
| **区间/值域分析**                             | 前向  | `[a,b]` 区间格（**无限高度！**）   | 区间并    | 边界检查消除、溢出检测            |
| **符号/奇偶/同余**                            | 前向  | 有限抽象域                    | 域上 `⊔` | 强度削减、对齐推断              |
| **别名/指向分析**                             | 前向  | `2^(Var×Loc)`            | `∪`    | 内存优化的前提                |
| **逃逸分析**                                | 前向  | 逃逸格                      | `⊔`    | 栈分配、锁消除、标量替换           |
| **支配关系**                                | 前向  | `2^Block`, `⊇`           | `∩`    | SSA 构造（见 §2）           |
| **循环不变量**                               | ——  | 由到达定义导出                  |        | LICM                   |
| **anticipability / partial redundancy** | 双向  | `2^Expr`                 | 混合     | PRE / lazy code motion |
| **依赖分析**（后端）                            | ——  | 距离/方向向量格                 |        | 向量化、调度（见 §6）           |
| **稀疏条件常量传播 SCCP**                       | 前向  | 值格 × CFG 边可达性格           |        | 同时做常量折叠 + 不可达消除        |
| **Typestate / 资源检查**                    | 前向  | **DFA 状态的幂集**（← 就是子集构造！） | `∪`    | 缺陷检测                   |

> **注意最后一行**：Typestate 分析的抽象值恰好是"DFA 状态的集合"。如果不预先做 NFA→DFA，就必须在分析过程中**在线做子集构造**。这是前端锤和后端锤在同一个问题上重合的地方。

### 1.4 关键理论细节

#### MOP vs MFP

有两种"正确答案"：

```
MOP (Meet Over all Paths)：  ⊔_{所有可执行路径 p} f_p(boundary)
                              ← 理想答案，一般不可计算（路径无穷多）
MFP (Maximal Fixed Point)：   worklist 算法算出的不动点
                              ← 实际答案
```

**定理**：

- 若 transfer 函数是**单调的**：`MFP` 不比 `MOP` 精确（保守，安全）
- 若 transfer 函数是**分配的**（`f(x ⊔ y) = f(x) ⊔ f(y)`）：`MFP = MOP`

| 分析                          | 分配性         | 后果              |
| --------------------------- | ----------- | --------------- |
| 活跃变量、可用表达式、到达定义（gen/kill 型） | **分配**      | 迭代解就是最优解        |
| **常量传播**                    | **仅单调，非分配** | 迭代解**严格弱于** MOP |

常量传播的经典反例：

```c
if (c) { x = 1; y = 2; } else { x = 2; y = 1; }
z = x + y;     // MOP 知道 z == 3；MFP 只知道 x=⊤, y=⊤ ⇒ z=⊤
```

> **这与 SLR 用 `FOLLOW` 近似 LR(1) 前看是同一类损失**：合并了本该分开的信息。

#### 无限高度格与 Widening/Narrowing

区间分析的格 `[a,b]` 高度无限，Kleene 迭代可能不终止：

```c
for (i = 0; i < n; i++) { ... }
// 迭代：i ∈ [0,0] → [0,1] → [0,2] → [0,3] → ...  永不收敛
```

**Widening（外扩）** `∇`：主动跳到上界，牺牲精度换终止

```
[0,0] ∇ [0,1] = [0, +∞]      // 上界在增长 ⇒ 直接推到 +∞
```

**Narrowing（收缩）** `Δ`：从粗糙的不动点向下收回一些精度

```
[0,+∞] 与循环条件 i<n 交 ⇒ [0, n-1]   // 部分恢复精度
```

> **这是"近似阶梯"母题在后端的化身**：和 `SLR → LALR → LR(1)`、`近似前看 → 全前看`、`SLL → LL` 一样，都是"先用便宜的粗近似，必要时再付精确的代价"。

#### 抽象解释：不动点分析的统一理论

Cousot & Cousot (1977) 给出了完整框架：

```
具体语义      抽象语义
(2^State, ⊆)  ←γ─  (L, ⊑)          α: 抽象化   γ: 具体化
              ─α→
要求 (Galois 连接):  α(c) ⊑ a  ⟺  c ⊆ γ(a)

可靠性定理: 若 α ∘ F_concrete ⊑ F_abstract ∘ α ，
           则 lfp(F_abstract) 是 lfp(F_concrete) 的可靠近似。
```

意义：**只要证明每条指令的抽象 transfer 是可靠的，整个分析的可靠性自动成立**。这把"证明一个优化正确"从全局论证降为局部论证——这是后端可以规模化的根本原因。

工业实例：Astrée（航天软件零误报验证）、Facebook Infer、IKOS、Sparrow、Polyspace。

#### IFDS/IDE：过程间分析的归约

Reps–Horwitz–Sagiv 把一大类过程间数据流分析归约为**超图可达性**：

```
IFDS: 分布式（distributive）+ 有限子集问题 → 图可达性，O(E·D³)
IDE:  推广到"环境变换"（如常量传播的映射）
核心机制: summary edge —— 把过程的输入输出关系缓存下来
```

> **这与 ANTLR 4 的 ALL(\*) 是同一类计算**：都是求解**下推系统的可达性**（状态 + 调用栈），都用"缓存已算过的上下文"来摊销成本（summary edge ≈ ALL(\*) 的 DFA 缓存）。

## 2. 大锤①：SSA + 支配关系 —— 后端的坐标系

如果主锤是"算法"，SSA 就是"**表示**"。它不解决某个具体问题，而是**改变问题的坐标系**，让主锤变得高效。

### 2.1 SSA 解决了什么

```c
// 非 SSA：变量 x 是一个"存储位置"，多个定义混在一起
x = 1;
x = x + 2;      // 哪个 x？必须靠数据流分析回答
if (c) x = 5;
y = x;          // x 可能来自两处，需要到达定义分析

// SSA：每个变量恰好被定义一次，名字 = 定义点
x1 = 1;
x2 = x1 + 2;
if (c) x3 = 5;
x4 = φ(x2, x3);  // φ 显式表达"控制流汇合"
y1 = x4;         // use-def 关系直接可读，无需分析
```

**核心收益**：把**到达定义分析的结果直接编码进程序表示**。原本需要迭代求解的信息变成了 IR 中的一条边。

### 2.2 稠密（dense）→ 稀疏（sparse）

这是 SSA 最重要的价值：

|             | 稠密分析                  | 稀疏分析（SSA 上）              |
| ----------- | --------------------- | ------------------------ |
| 状态存储        | 每个**程序点** × 每个变量      | 每个 **SSA 名字** 一个值        |
| 空间          | `O(程序点 × 变量)`         | `O(SSA 名字数)`             |
| 信息传播        | 沿 **CFG 边**（包括不相关的指令） | 沿 **use-def 边**（只走真正相关的） |
| worklist 内容 | 基本块                   | SSA 值                    |

```python
# SSA 上的稀疏常量传播（对比 §1.2 的稠密版）
def sparse_ccp(ssa_func):
    val = {v: TOP for v in ssa_func.values}
    worklist = list(ssa_func.values)
    while worklist:
        v = worklist.pop()
        new = evaluate(v, val)             # 只看 v 的操作数
        if new != val[v]:
            val[v] = new
            worklist.extend(v.users)       # ← 只唤醒真正的使用者！
    return val
```

对一个有 10⁴ 个基本块、10⁵ 个变量的函数，稠密版要维护 10⁹ 个格元素，稀疏版只要 10⁵ 个。**这是 LLVM/GCC 能在大函数上跑几十个 pass 的前提。**

### 2.3 支配关系：SSA 的几何基础

```
定义：d dom n  ⟺  从入口到 n 的每条路径都经过 d
     idom(n)  = n 的直接支配者（支配树的父节点）
     DF(n)    = 支配边界 = { y | n 支配 y 的某个前驱，但 n 不严格支配 y }
```

**SSA 的核心不变式**：`每个 use 都被其对应的 def 支配`。

这个不变式带来一连串好处：

| 好处      | 说明                                    |
| ------- | ------------------------------------- |
| φ 函数放哪里 | **放在支配边界上**（Cytron et al. 1991）       |
| 变量在哪活跃  | 活跃范围是支配树上的一个子树片段 ⇒ **干扰图是弦图**（见 §5.3） |
| 代码提升到哪  | 提升到"支配所有 use 的最深位置"                   |
| 支配者树遍历  | 许多优化（GVN、值域传播）沿支配树 DFS 一遍就够，无需迭代      |

**支配关系本身就是不动点计算**（回到主锤）：

```
DOM(entry) = {entry}
DOM(n)     = {n} ∪ ( ⋂_{p ∈ pred(n)} DOM(p) )     ← 格 = (2^Block, ⊇), meet = ∩
```

| 算法                        | 复杂度                        | 实践                 |
| ------------------------- | -------------------------- | ------------------ |
| 朴素迭代                      | `O(n²)` 位向量                | 简单                 |
| **Cooper–Harvey–Kennedy** | 迭代 + RPO 序                 | **实践中最快**，LLVM 早期用 |
| **Lengauer–Tarjan**       | `O(E α(E))` / `O(E log E)` | 理论最优               |
| **Semi-NCA**              | 接近 LT 但更简单                 | LLVM 现用            |

### 2.4 SSA 家族的扩展

SSA 的思想是"把某类信息显式化"，可以继续推广：

| 变体                                 | 显式化了什么                                           | 用途                      |
| ---------------------------------- | ------------------------------------------------ | ----------------------- |
| **MemorySSA**                      | 内存的 def-use（`MemoryDef`/`MemoryUse`/`MemoryPhi`） | 让 load/store 优化也能稀疏化    |
| **Extended SSA (e-SSA)**           | 分支条件带来的值域约束（在分支后重命名）                             | 值域传播、边界检查消除             |
| **Predicated SSA / ψ-SSA**         | 谓词执行                                             | if-conversion 后的优化      |
| **Gated SSA (GSA)**                | φ 的**控制条件**（γ/μ/η 函数）                            | 把控制依赖变成数据依赖             |
| **Program Dependence Graph (PDG)** | 数据依赖 + 控制依赖                                      | 切片、并行化                  |
| **Sea of Nodes**（HotSpot C2）       | 控制流也是节点，只保留必要顺序                                  | 激进的全局代码移动               |
| **CPS / ANF**                      | 续延显式化                                            | 函数式语言后端（SSA 与 CPS 本质等价） |

> **共同模式**：**用"改变表示"来消灭"需要分析"**。这与 ANTLR 4 "把分析移到运行期"是同一层次的突破——**不是把算法做快，而是改变问题的提法**。

### 2.5 SSA 的代价：出 SSA（out-of-SSA）

φ 函数不是真实指令，最终必须消除。天真做法是"在每个前驱块末尾插入拷贝"，但会遇到：

| 问题               | 说明                        | 解法                              |
| ---------------- | ------------------------- | ------------------------------- |
| **lost copy**    | 关键边上插拷贝会改变语义              | 分裂关键边（critical edge splitting）  |
| **swap problem** | `a=φ(b), b=φ(a)` 需要并行拷贝语义 | 并行拷贝顺序化（可能需要临时寄存器 / xor 交换）     |
| 拷贝过多             | 影响性能                      | **coalescing**（与寄存器分配合并考虑，见 §5） |

Sreedhar et al. (1999) 和 Boissinot et al. (2009) 给出了正确且高效的出 SSA 算法。

## 3. 大锤②：等价类的合并与精化

第二类反复出现的机制：**判断"这两个东西是同一个"**，然后合并。这在后端出现的次数几乎和不动点一样多。

### 3.1 两个方向：悲观合并 vs 乐观精化

这是一个非常漂亮的对偶结构：

```
悲观 (pessimistic)                     乐观 (optimistic)
从"全部不等价"开始 ────合并───>  ...  <───分裂──── 从"全部等价"开始
数据结构: Union-Find                   数据结构: Partition Refinement
从格的 ⊥ 向上爬                        从格的 ⊤ 向下降
不动点是"最小的"                       不动点是"最大的"
不能发现循环中的等价                    能发现循环中的等价 ✔
```

**具体对照表**：

|      | 悲观（合并 / Union-Find）                   | 乐观（精化 / Partition Refinement）         |
| ---- | ------------------------------------- | ------------------------------------- |
| 编译器  | **Hash-based GVN**、Congruence Closure | **AWZ 算法**（Alpern–Wegman–Zadeck 1988） |
| 自动机  | ——                                    | **Hopcroft DFA 最小化**                  |
| 常量传播 | 从 `⊥` 起（保守）                           | **SCCP 从 `⊤` 起**（能折叠循环变量）             |
| 类型推导 | Union-Find 合一（unification）            | ——                                    |
| 复杂度  | `O(E α(E))`                           | `O(E log n)`                          |

> **关键洞察：Hopcroft 的 DFA 最小化和乐观 GVN 是同一个算法。**
> AWZ 论文明确说明其算法改编自 Hopcroft 的划分精化。两者都是：
> 
> ```
> 初始：把所有节点放进一个（或按标签分的少数几个）块
> 重复：若同一块内的两个节点，其"后继/操作数"落在不同的块 ⇒ 分裂
> 直到：不再能分裂（不动点）
> ```
> 
> 只是自动机上比较"转移目标"，GVN 上比较"操作数所属类 + 操作码"。

### 3.2 为什么"乐观"更强：循环中的等价

```c
// 循环变量的等价
i1 = 0;  j1 = 0;
loop:
  i2 = φ(i1, i3);  j2 = φ(j1, j3);
  i3 = i2 + 1;     j3 = j2 + 1;
  goto loop;
```

`i` 和 `j` 在所有迭代中始终相等。但：

- **悲观 GVN**：处理 `i2 = φ(i1,i3)` 时，`i3` 还未算出，只能保守地认为 `i2 ≢ j2` ⇒ **发现不了**
- **乐观 GVN**：先假设 `{i1,j1,i2,j2,i3,j3}` 全在一个类里，然后尝试分裂——发现分裂不成立（自洽），最终保留等价 ⇒ **成功发现 `i ≡ j`**

这正是"乐观分析"的本质：**先假设最强的结论，只在被证据推翻时才削弱**。它求的是**最大不动点**（gfp），而悲观分析求的是**最小不动点**（lfp）。

> **前端对应物**：这与 **DFA 最小化必须从"接受态/非接受态"这个粗划分开始向下精化**，而不能从"每个状态自成一类"向上合并，是完全同一件事。若从最细划分开始合并，就无法处理自动机中的环——正如悲观 GVN 无法处理循环中的 φ。

### 3.3 同余闭包（Congruence Closure）：等价合并的完整形态

判断"两个表达式树是否等价"需要考虑**函数应用的同余性**：

```
自反、对称、传递（等价关系的基本要求）
+ 同余规则：  a₁ ≡ b₁, ..., aₙ ≡ bₙ  ⟹  f(a₁..aₙ) ≡ f(b₁..bₙ)
```

标准算法（Downey–Sethi–Tarjan 1980）：**Union-Find + 签名哈希表 + 父节点重哈希**

```python
def congruence_closure(dag, equalities):
    uf = UnionFind()
    sig = {}                                    # 签名 → 代表元
    def canon(n): return uf.find(n)
    def signature(n):
        return (n.op, tuple(canon(c) for c in n.children))

    worklist = list(equalities)
    while worklist:
        a, b = worklist.pop()
        ra, rb = canon(a), canon(b)
        if ra == rb: continue
        # 合并前收集所有受影响的父节点
        parents = uf.parents_of(ra) + uf.parents_of(rb)
        uf.union(ra, rb)
        # ★ 重哈希：合并后签名可能撞上，撞上就是新的等价
        for p in parents:
            s = signature(p)
            if s in sig and canon(sig[s]) != canon(p):
                worklist.append((sig[s], p))    # 发现新等价，继续传播
            else:
                sig[s] = p
    return uf
```

**这个"重哈希后发现新等价 ⇒ 继续传播"的循环，又是一次 worklist 不动点迭代。** 主锤无处不在。

**用途**：GVN/CSE、SMT 求解器的 EUF 理论、e-graph 的底层机制、类型合一。

### 3.4 E-graph 与 Equality Saturation：拒绝提前承诺

传统的重写优化是**破坏性的**：

```
(a * 2) / 2

方案 A：先强度削减 →  (a << 1) / 2  →  卡住，无法约掉
方案 B：先代数化简 →  a             →  最优
```

**一旦重写，原形式就消失了**，后续 pass 再也看不到它。这就是 **phase ordering 问题**在最微观层面的表现。

**E-graph** 的解法：**不删除，只添加等价关系。**

```
e-class：一组语义等价的 e-node（等价类）
e-node ：操作符 + 若干 e-class 作为孩子   ← 关键：指向类而非具体节点

⇒ 一个 e-graph 能紧凑地表示指数多个等价程序
```

**Equality Saturation 流程**：

```
① 把初始程序插入 e-graph
② repeat:
     对每条重写规则 l → r：
       e-matching 找出 l 在 e-graph 中的所有实例
       把 r 加入 e-graph，并 union(class(l), class(r))    ← 只加不删！
   until 饱和（无新等价）或超出迭代/节点预算
③ 提取（extraction）：按代价模型从 e-graph 中选出最优程序
     - 自底向上贪心 DP（代价可加时最优）  ← 大锤③
     - 或 ILP（处理共享带来的非可加代价）
```

**关键性质**：`union` 只加不删 ⇒ **重写顺序不再影响结果**。phase ordering 问题在"重写"这一层被消除了。

> ### E-graph 就是后端的 SPPF
> 
> 这是前后端最精确的一处对应：
> 
> |         | 前端（解析）                         | 后端（优化）                                  |
> | ------- | ------------------------------ | --------------------------------------- |
> | 贪心、提前承诺 | **PEG / packrat** 的有序选择        | **贪心 peephole / 固定 pass 顺序**            |
> | 病理      | `A ← a / ab` 中 `ab` **永远匹配不到** | **phase ordering**、陷入局部最优               |
> | 拒绝承诺的方案 | **GLR / GLL / Earley**         | **Equality Saturation**                 |
> | 共享打包表示  | **SPPF** / **GSS**             | **E-graph**                             |
> | 保留了什么   | 所有合法**解析树**                    | 所有等价**程序**                              |
> | 最后要做什么  | **消歧**：从森林选一棵树                 | **提取**：从 e-graph 选一个程序                  |
> | 选择依据    | 规则顺序 / 优先级 / 结合性               | **代价模型**                                |
> | 风险      | 森林可能指数大                        | e-graph 可能不饱和 / 爆炸                      |
> | 折中方案    | **ALL(\*)**：看足够远再决定 + 缓存       | **aegraph**（Cranelift）：即时合并 + 有界重写 + 无环 |
> 
> **两者是同一思想在两端的镜像：把"何时承诺"从算法内部提升为显式的设计选择。**

**工程现实**：`x+y = y+x` 这类规则会导致组合爆炸，完全饱和常常不可行。所以 **egg** 引入了 e-matching 优化、延迟 rebuilding、以及迭代/节点预算；**Cranelift 的 aegraph** 进一步牺牲完备性换取可预测的编译时间——这与"用 SLL 近似替代完整 LL"是同一类工程判断。

**工业/研究实例**：egg 框架、Cranelift aegraph、TENSAT（张量图优化）、Herbie（浮点表达式重写）、Ruler（自动发现重写规则）。

### 3.5 超优化：让求解器代替人写规则

```
Souper 的工作流：
① 从 LLVM IR 中抽取一小段（切片）
② 枚举候选的更短/更快指令序列
③ 用 SMT 求解器（Z3 / Alive2）证明等价
④ 若等价且更优 ⇒ 自动生成一条新的 peephole 规则
```

- **Alive2**：形式化验证 LLVM 现有优化是否正确，已在真实代码中发现数百个 bug
- **STOKE**：随机搜索 + 验证，能找出人类想不到的位运算技巧

> 这把"人工编写重写规则"替换为"求解器自动发现"。**规则库本身成了被优化的对象。**

## 4. 大锤③：最优子结构上的动态规划

当问题具有**最优子结构**时，DP 给出**多项式时间的最优解**。这是后端唯一能"真正最优"的一类问题，因此格外珍贵。

### 4.1 指令选择：树上的最优覆盖

**问题**：用目标机的指令模式（树模式）覆盖 IR 表达式树，代价最小。

```
;; 指令模式（树文法），带代价
reg  → PLUS(reg, reg)              ; ADD    cost 1
reg  → PLUS(reg, CONST)            ; ADDI   cost 1
reg  → LOAD(reg)                   ; LDR    cost 3
reg  → LOAD(PLUS(reg, CONST))      ; LDR#   cost 3   ← 一条指令干两件事
reg  → CONST                       ; MOV    cost 1
```

**Aho–Johnson DP**（1976）：树上一遍自底向上

```python
def label(node):                                   # 自底向上
    for child in node.children: label(child)
    node.cost = {}                                 # 非终结符 → (代价, 规则)
    for rule in rules_matching(node):
        c = rule.cost + sum(child.cost[nt]
                            for child, nt in zip(node.children, rule.rhs_nts))
        nt = rule.lhs
        if nt not in node.cost or c < node.cost[nt][0]:
            node.cost[nt] = (c, rule)              # 保留最优
```

**定理**：树上的最小代价覆盖，DP 给出**最优解**，时间 `O(树大小 × 规则数)`。

**两种实现路线**——这里又回到了前端的锤子：

| 路线          | 做法                                                                | 是否确定化                                            | 代表工具                                          |
| ----------- | ----------------------------------------------------------------- | ------------------------------------------------ | --------------------------------------------- |
| **预计算树自动机** | 把"哪些子模式能匹配到这里"的**集合**（match set）离线编号，生成多维转移表 `δ_op(s₁,…,s_k) → s` | ✔ **树 NFA → 树 DFA**（Hoffmann–O'Donnell 子集构造的树版本） | **BURG**、Twig（部分）                             |
| **运行时 DP**  | 不预计算，每次匹配时自底向上现算 `cost[nt]`                                       | ✘ 直接"模拟树 NFA"                                    | **iburg / lburg**、LLVM ISel 的 MatcherTable 解释 |

```
树上的模式匹配 = 树自动机识别
    状态       = 子模式位置的集合（match set）
    确定化     = 子集构造（多维！表大小 O(|Q|^arity)）
    ⇒ BURG 付预计算代价换取匹配时 O(1)
    ⇒ iburg 拒绝确定化，用 DP 换取"代码量小一个数量级"
```

> **iburg 论文的论证值得完整记住**，因为它是"**主动不确定化**"最清晰的工程论据：
> 树自动机的转移表是**多维的**（`|Q|^arity`），预计算的空间与实现复杂度都过高；iburg 只比 burg 慢一个常数因子，但代码量小一个数量级、易调试、易维护、支持**动态代价**（代价可依赖上下文，而预计算表要求代价静态已知）。
> 
> 这与 **GLR/GLL 选择"直接模拟 PDA 而不确定化"**、**Thompson NFA 模拟优于建 DFA（一次性匹配场景）** 是同一个判断：**当确定化的预计算成本摊销不回来，或状态空间维度过高时，不确定化是更优工程选择。**

### 4.2 DP 在后端的其他战场

| 问题                        | DP 形态                 | 最优性                         | 备注                     |
| ------------------------- | --------------------- | --------------------------- | ---------------------- |
| **指令选择（树上）**              | 自底向上 `cost[节点][非终结符]` | ✔ **最优**                    | Aho–Johnson；BURG/iburg |
| **Sethi–Ullman 编号**       | 自底向上算"求值该子树所需最少寄存器"   | ✔ **最优**（无 CSE 的表达式树、齐次寄存器） | 决定先算左还是先算右             |
| **Ershov 数**              | 同上的推广                 | ✔                           | 与 Sethi–Ullman 等价      |
| **树上的调度（单位延迟）**           | Hu 算法 / 层次标号          | ✔ **最优**                    | 一般 DAG 上则 NP-hard      |
| **两处理器上的 DAG 调度**         | Coffman–Graham        | ✔ **最优**                    | 三处理器起就 NP-hard         |
| **e-graph 提取**            | 自底向上 `cost[e-class]`  | ✔ 最优**当代价可加**               | 有共享时需 ILP（因为共享使代价非可加）  |
| **循环 tiling 尺寸选择**        | 在有限候选集上 DP / 穷举       | 受限最优                        | 一般情况转入搜索（§7）           |
| **超级块 / trace 形成**        | 路径上的 DP               | 依赖 profile                  | 需要频率信息                 |
| **最优溢出放置（受限）**            | 树/链上 DP 或最小割          | ✔（受限模型）                     | 一般图上 NP-hard           |
| **表达式重结合（reassociation）** | 类似 Huffman / 最优括号化    | 受限最优                        | 缩短关键路径                 |

**共同前提**：**最优子结构 + 无重叠依赖**。一旦子问题之间开始"共享资源"或"互相影响"，DP 就失效。

### 4.3 DP 的边界：从树到 DAG，最优性崩塌

```c
t = a + b;
x = t * 2;
y = t * 3;      // t 被复用 ⇒ 表达式是 DAG，不是树
```

**为什么 DP 在 DAG 上失效**：

```
树：  子树的最优解互不影响 ⇒ 可独立求解后拼接      ✔ 最优子结构
DAG： 一个节点被多处使用 ⇒ 它该"生成到寄存器一次复用"
      还是"在每个使用点重算"？
      这个决定影响所有使用者，且使用者之间互相耦合  ✘ 最优子结构被破坏
```

**定理**：DAG 上的最小代价指令选择是 **NP-complete**（Proebsting 1998；Koes–Goldstein 2008 给出更细的刻画）。

**工程应对**（又是熟悉的六种手段）：

| 手段             | 做法                                                           | 代表                               |
| -------------- | ------------------------------------------------------------ | -------------------------------- |
| **切成树**（近似）    | 在多用途节点处切断 DAG，各棵树独立做 DP                                      | 传统 LLVM SelectionDAG（切成基本块内的树森林） |
| **贪心 + 局部回溯**  | 沿 DAG 拓扑序贪心，允许有限回溯                                           | GCC 的 `recog`                    |
| **归约到已有求解器**   | 建模为 **PBQP**（Partitioned Boolean Quadratic Programming）或 ILP | Eckstein et al.；LLVM 的 PBQP 分配器  |
| **近似最优 + 启发式** | NOLTIS：先树 DP，再迭代改进跨树决策                                       | Koes–Goldstein 2008              |
| **换表示**        | GlobalISel 用 `MachineIR` + 逐步 legalize/combine，放弃"一次性最优覆盖"   | LLVM GlobalISel                  |

> **这是后端的典型剧本，值得反复对照**：
> 
> ```
> 问题在受限结构上（树/链/弦图/仿射空间）多项式最优
>          ↓ 放到真实结构上（DAG/一般图/任意控制流）
> NP-hard
>          ↓
> 三条出路：① 切割成受限结构（损失最优性）
>          ② 归约到通用求解器（ILP/PBQP/SMT，损失编译时间）
>          ③ 启发式 + 代价模型（损失可证明性）
> ```
> 
> 与前端的对照：前端遇到"LL(\*) 的前看语言非正则"时，出路是 ①限制为正则（损失能力）②回溯（损失时间）③**移到运行期**（ALL(\*)，损失静态可预测性）。**三条出路的性质完全对应。**

## 5. 大锤④：归约到图问题 + 启发式

分析完了要**变换**，而变换的核心是**有限资源的分配**：寄存器、功能单元、发射槽、缓存行、指令空间。这类问题的共同签名是：**建模优雅，求解 NP-hard**。

### 5.1 NP-hard 全家桶

| 优化问题                  | 图/组合模型                 | 复杂度                          | 实践算法                                            |
| --------------------- | ---------------------- | ---------------------------- | ----------------------------------------------- |
| **寄存器分配**             | 干扰图 `k`-着色             | NP-complete（Chaitin 1981）    | Chaitin–Briggs；线性扫描；**SSA/弦图**；PBQP；LLVM greedy |
| **指令调度**（有资源约束）       | DAG + 资源约束调度           | NP-complete                  | 表调度（list scheduling）+ 关键路径优先                    |
| **调度 ⊗ 分配（联合）**       | ——                     | NP-hard 且**目标冲突**            | 分阶段 + 寄存器压力感知调度                                 |
| **软件流水**              | 模调度（modulo scheduling） | NP-hard                      | IMS（Rau）、SMS                                    |
| **基本块/函数布局**          | 加权线性排列、类 TSP           | NP-hard                      | Pettis–Hansen 链式；**ext-TSP**（BOLT）              |
| **内联决策**              | 类背包 / 调用图上的选择          | NP-hard                      | 代价模型 + 阈值 + 遍历顺序启发式                             |
| **DAG 指令选择**          | 最小代价 DAG 覆盖            | NP-complete                  | 见 §4.3                                          |
| **溢出代码放置**            | **最小割 / 网络流**          | **多项式**（固定其余变量时）             | 循环深度加权代价模型                                      |
| **PRE / 代码移动**        | 数据流 + **最小割**          | **多项式**                      | LCM；Optimal PRE via min-cut                     |
| **寄存器合并（coalescing）** | 图上的边合并                 | NP-hard（Bouchez et al. 2007） | 保守/迭代/乐观 coalescing                             |

### 5.2 寄存器分配：完整的图着色剧本

```
① 构造干扰图     ← 需要活跃分析（主锤！）
   节点 = 活跃区间 / SSA 值
   边   = 两者同时活跃（不能共享寄存器）

② Simplify：反复移除度数 < k 的节点，压入栈
   （度数 < k ⇒ 无论邻居怎么着色，总有颜色可用）

③ Spill：若所有剩余节点度数 ≥ k
   ⇒ 按"溢出代价 / 度数"最小启发式选一个节点溢出
   （Chaitin：真溢出；Briggs：乐观着色——先压栈，也许还有救）

④ Select：出栈并逐个着色

⑤ Coalesce：消除冗余 move（若 src/dst 不干扰，合并两节点）
   ⚠ 合并会提高度数 ⇒ 可能引入新的溢出
   ⇒ 保守 coalescing（Briggs：只在合并后度数<k 时才合并）
```

**关键张力**：`coalescing`（减少 move）与 `spilling`（减少内存访问）**互相拮抗**。Briggs 的"保守合并"、George–Appel 的"迭代合并"都是在这条张力线上的取舍。

### 5.3 母题：改变表示，落入易解类 —— SSA 与弦图

这是本节最深刻的一处，也是与前端最漂亮的一处呼应。

**经典结论（Chaitin 1981）**：任意图都可以是某个程序的干扰图 ⇒ 寄存器分配 = 一般图着色 = **NP-complete**。

**SSA 时代的翻转（Hack 2005；Pereira–Palsberg 2005；Bouchez et al.）**：

> **严格 SSA 形式程序的干扰图是弦图（chordal graph）。**

**为什么**：SSA 中每个值的活跃范围对应**支配树上的一个连通子树**（因为 def 支配所有 use），而**子树的交图恰是弦图**。

弦图的好处是决定性的：

| 性质             | 内容                                      |
| -------------- | --------------------------------------- |
| **完美消除序**（PEO） | 可由 MCS（最大势搜索）在 `O(V+E)` 求出              |
| **贪心即最优**      | 沿 PEO 逆序贪心着色 ⇒ **最优着色**                 |
| **色数可计算**      | `χ(G) = ω(G) = MAXLIVE`（任一程序点的最大同时活跃值数） |
| **判定容易**       | "`k` 个寄存器够不够" 等价于 "`MAXLIVE ≤ k`"，可局部检查 |

于是整个格局被改写：

```
一般程序 → 干扰图任意     → 着色 NP-complete
   ↓ 转成 SSA
SSA 程序 → 干扰图是弦图   → 着色多项式最优
```

> ### 精确对应：SSA/弦图 ≡ "活前缀是正则语言"
> 
> |            | 前端（LR 理论）             | 后端（SSA 寄存器分配）                    |
> | ---------- | --------------------- | -------------------------------- |
> | 表面难题       | 识别 CFL，似乎需要无限栈        | 图着色，NP-complete                  |
> | **关键结构定理** | **栈的合法内容（活前缀）构成正则语言** | **SSA 干扰图是弦图**                   |
> | 于是可以       | 用**有限自动机**看栈顶做决策      | 用**多项式贪心**最优着色                   |
> | 难度被隔离到     | **显式的栈**（parser 自己维护） | **φ 消除 / coalescing**（仍 NP-hard） |
> | 残留的现实困难    | 冲突消解、错误恢复、歧义          | 寄存器别名、成对约束、调用约定                  |
> 
> **两者是同一个方法论**：**不要试图直接攻克难问题，而是寻找一个使问题落入易解子类的表示，把剩余难度隔离进一个单独的、可控的子问题。**

**残留的难度（必须诚实面对）**：

1. **φ 消除 + coalescing 仍是 NP-hard**（Bouchez et al. 2007）——难度只是被搬家了，没有消失；
2. 若 `MAXLIVE > k`，仍需**溢出**，溢出位置选择 NP-hard；
3. 真实 ISA 有**寄存器别名**（x86 的 `AL/AH/AX/EAX/RAX`）、**成对/对齐约束**（ARM 的 `LDRD`）、**调用约定**、**固定寄存器指令**（x86 除法的 `EDX:EAX`）——这些**破坏纯弦图模型**。

所以 LLVM 的 `greedy` 分配器最终仍是启发式：优先级队列 + **活跃区间分裂**（live range splitting）+ **逐出**（eviction）+ 有界回溯。

> **理论给出方向，工程处理现实。** 这句话适用于整个后端。

### 5.4 指令调度：表调度与相位耦合

```python
def list_schedule(dag, machine):
    ready = [n for n in dag if not n.preds]
    cycle, sched = 0, {}
    while ready or pending:
        # 启发式优先级：关键路径长度 / 后继数 / 寄存器压力 / 是否在关键资源上
        ready.sort(key=lambda n: -priority(n))
        for n in ready[:]:
            if machine.can_issue(n, cycle):        # 资源约束
                sched[n] = cycle
                machine.reserve(n, cycle)
                release_successors(n)              # 延迟满足后进 ready
                ready.remove(n)
        cycle += 1
    return sched
```

**优先级函数就是启发式的全部**。常用：关键路径高度、后继数、`slack`、寄存器压力增量。

**相位耦合的经典冲突**：

| A          | B              | 冲突                                             |
| ---------- | -------------- | ---------------------------------------------- |
| 调度（提高 ILP） | 寄存器分配          | 调度拉开 def-use 距离 ⇒ 活跃区间变长 ⇒ **MAXLIVE 上升 ⇒ 溢出** |
| CSE        | 寄存器压力          | 复用减少计算，但延长活跃区间，**可能净损失**                       |
| 内联         | 代码大小 / I-cache | 消除调用开销，但可能爆炸代码、拖垮 I-cache                      |
| 循环展开       | 向量化            | 展开量取决于向量宽度，而向量化决策又依赖展开后的形态                     |

**部分解法**：

- **寄存器压力感知调度**（在优先级中加入压力项）；
- **联合建模**：用 ILP / PBQP 同时求解调度与分配（编译时间昂贵，用于 DSP/嵌入式）；
- **迭代**：调度 → 分配 → 若溢出严重则重调度。

### 5.5 最小割：后端罕见的"可最优求解"结构

**PRE / Lazy Code Motion** 是"锤子①与锤子④完美配合"的典范。

```c
if (c) { ... }
else   { x = a + b; }     // a+b 只在一条路径上算过
y = a + b;                // 部分冗余
```

**Knoop–Rüthing–Steffen 的 Lazy Code Motion** 用**四轮数据流分析**（全是主锤）求解：

| 轮   | 分析                     | 方向/汇合  | 含义               |
| --- | ---------------------- | ------ | ---------------- |
| 1   | Anticipated（预期）        | 后向 `∩` | 此后所有路径都会求值       |
| 2   | Available（可用）          | 前向 `∩` | 所有前驱路径已算过        |
| 3   | Earliest / Postponable | ——     | 最早可放点，然后尽量往后推    |
| 4   | Latest / Used          | ——     | 最晚放点（**缩短活跃区间**） |

设计目标：**在不增加任何路径上计算次数的前提下最大化冗余消除，并把计算尽量放晚以降低寄存器压力**——"Lazy" 即此意。

**更强的视角（Cai & Xue, CGO 2003）**：把"在哪插入计算"建模为**图的最小割**——割边 = 插入点，容量 = 按执行频率加权的插入代价。**最小割 = 最优插入方案，多项式可解。**

> **这是 NP-hard 汪洋中的一座岛**。后端研究的核心追求之一，就是**找出哪些问题隐藏着网络流/子模/弦结构**，从而逃离 NP-hard。同类岛屿：溢出放置（受限模型）、if-conversion 选择（某些情形）、trace 选择（链上 DP）。

## 6. 大锤⑤：多面体模型 —— 循环变换的统一代数

前面的锤子处理"指令级"和"数据流级"。但**循环嵌套变换**（交换、倾斜、分块、融合、分布、并行化）自成一个世界，且拥有**自己的统一代数**。

### 6.1 表示：三个仿射对象

```c
for (i = 0; i < N; i++)
  for (j = 0; j < N; j++)
    A[i][j] = A[i][j-1] + B[i+j];
```

| 对象                        | 形式                 | 本例                                                            |
| ------------------------- | ------------------ | ------------------------------------------------------------- |
| **迭代域**（iteration domain） | 整数点集 = 仿射不等式定义的多面体 | `D = { (i,j) ∈ ℤ² : 0 ≤ i < N, 0 ≤ j < N }`                   |
| **访存函数**（access function） | 迭代向量 → 数组下标的仿射映射   | `f_A(i,j) = (i, j)`、`f_A'(i,j) = (i, j-1)`、`f_B(i,j) = (i+j)` |
| **调度**（schedule）          | 迭代向量 → 逻辑时间的仿射映射   | 原始 `θ(i,j) = (i,j)`（字典序执行）                                    |

**核心洞见**：**所有经典循环变换 = 给调度左乘一个矩阵。**

| 变换                  | 调度矩阵                              | 效果                             |
| ------------------- | --------------------------------- | ------------------------------ |
| 恒等                  | `[[1,0],[0,1]]`                   | `(i,j)`                        |
| **交换**（interchange） | `[[0,1],[1,0]]`                   | `(j,i)`                        |
| **倾斜**（skewing）     | `[[1,0],[1,1]]`                   | `(i, i+j)` — 常用于使 wavefront 并行 |
| **反转**（reversal）    | `[[-1,0],[0,1]]`                  | `(-i, j)`                      |
| **分块**（tiling）      | 引入额外维度 `(i/T, j/T, i%T, j%T)`     | 提升局部性                          |
| **融合/分布**           | 调整语句间的调度维度（`θ_S1` 与 `θ_S2` 的公共前缀） | 合并/拆分循环                        |

> **这与前端的哪个成就同构？**
> 
> **Terence Parr 的 "Lexing = Parsing = Tree Parsing"**——把三件事统一到同一套 LL(k) 机制下。
> 多面体模型做的是同一件事：把**十几种各自有独立实现、独立合法性条件的 ad-hoc 循环变换，统一为"仿射调度矩阵的选择"这一个问题**。
> 
> 收益完全相同：**一次证明合法性条件，所有变换共享；一次实现代码生成，所有变换共享。**

### 6.2 依赖分析：归约到整数线性规划

两次访存 `f₁(x⃗)`、`f₂(y⃗)` 存在依赖 ⟺ 下列系统有整数解：

```
x⃗ ∈ D₁ ,  y⃗ ∈ D₂                    (都在迭代域内)
f₁(x⃗) = f₂(y⃗)                         (访问同一内存位置)
θ(x⃗) ≺ θ(y⃗)                          (存在执行顺序，字典序在前)
```

这是一个**参数化整数线性规划**（PIP）。

| 方法                       | 精度               | 复杂度       |
| ------------------------ | ---------------- | --------- |
| GCD 测试                   | 弱（只判无解）          | `O(1)`    |
| Banerjee 不等式             | 中                | 多项式       |
| Omega 测试（Pugh）           | 精确（Presburger）   | 指数最坏，实践可用 |
| **Feautrier 的精确依赖**（PIP） | 精确 + 给出**依赖多面体** | 指数最坏      |
| isl（Verdoolaege）         | 精确，工业级           | ——        |

**合法性判据**：调度 `θ` 合法 ⟺ **所有依赖都被保持**，即对每条依赖 `(x⃗ → y⃗)` 有 `θ(x⃗) ≺ θ(y⃗)`。

由 **Farkas 引理**，这个"对所有依赖点成立"的约束可以转化为**调度系数上的线性约束**——于是"寻找合法调度"变成一个 ILP。

### 6.3 自动调度：Feautrier 与 Pluto

| 方法                               | 目标函数                               | 特点                                |
| -------------------------------- | ---------------------------------- | --------------------------------- |
| **Feautrier**（1992）              | 最小化调度延迟（最大并行度）                     | 理论优美；但**不考虑局部性**，常产生 cache 不友好的代码 |
| **Pluto**（Bondhugula 2008）       | **最小化依赖距离**（`θ(y⃗) - θ(x⃗)`）+ 可分块性 | **同时优化局部性与并行性**；工业化的关键突破          |
| **Pluto+ / PolyMage / Tiramisu** | 加入更多目标（向量化、多层 tiling）              | ——                                |

**代码生成**（从多面体回到循环）：**CLooG**（Bastoul）/ isl AST generator——扫描多面体，生成带守卫的循环嵌套。

**工业落地**：LLVM **Polly**、GCC **Graphite**、**PPCG**（CUDA 生成）、**PolyMage**、**Tiramisu**、MLIR 的 `affine` dialect。

### 6.4 局限：为什么多面体模型没有一统天下

| 局限            | 说明                                            |
| ------------- | --------------------------------------------- |
| **仿射性要求**     | 下标 `A[B[i]]`（间接寻址）、`while` 循环、数据相关控制流 ⇒ 模型不适用 |
| **ILP 指数复杂度** | 大规模循环嵌套编译时间爆炸                                 |
| **代价模型仍是启发式** | "最小化依赖距离"只是**代理目标**（proxy），不是真实性能             |
| **tile 尺寸选择** | 仿射框架**不能**决定 tile 大小（那不是仿射问题）⇒ 交给搜索（§7）       |
| **控制流开销**     | 生成的守卫条件可能很复杂，抵消收益                             |

> **这是"改变表示"策略的固有代价**：新表示让一大类问题变得优雅可解，但**表示之外的程序完全无法处理**。
> 
> 前端的对应物：**LL(\*) 的前看 DFA 让"无界公共前缀"变得优雅可解，但前看语言非正则的文法完全无法处理**。两者都需要一个 fallback（多面体 → 传统循环优化；LL(\*) → 回溯 / ALL(\*)）。

## 7. 大锤⑥：代价模型 + 搜索

当前五把锤子都不够用时，只剩最后一招：**放弃解析求解，直接测量或搜索。**

### 7.1 为什么必须有这把锤子

前面所有锤子都依赖一个假设：**我们知道什么更快**。但现代硬件让这个假设崩塌：

| 因素           | 后果                          |
| ------------ | --------------------------- |
| 乱序执行、寄存器重命名  | 静态指令数与实际周期数弱相关              |
| 多级 cache、预取器 | 访存代价相差 100× 且难以静态预测         |
| 分支预测器        | 分支代价取决于历史模式                 |
| SMT / 多核竞争   | 代价依赖其他线程                    |
| 微码、端口冲突、解码限制 | 官方手册都不完整                    |
| **输入数据分布**   | 最优代码依赖运行时数据（分支概率、循环次数、类型分布） |

**结论**：不存在可靠的静态代价模型。所以：

```
① 用近似代价模型 + 启发式        ← 传统编译器（-O2）
② 用搜索 + 真实测量替代代价模型   ← autotuning
③ 用学习到的代价模型            ← ML 引导
④ 把决策推迟到运行期            ← PGO / JIT / 投机   ★最彻底
```

### 7.2 自动调优（Autotuning）

```
搜索空间：tile 尺寸 × 展开因子 × 向量化策略 × 循环顺序 × 数据布局 × ...
          （典型规模 10⁶ – 10¹⁵）
搜索策略：随机 / 遗传 / 模拟退火 / 贝叶斯优化 / 强化学习 / 代价模型引导
评价方式：真机执行时间（ground truth）
```

| 系统                      | 领域         | 方法                          |
| ----------------------- | ---------- | --------------------------- |
| **ATLAS**               | BLAS       | 安装时穷举关键参数                   |
| **FFTW**                | FFT        | "planner" 在运行时搜索并缓存最优计划     |
| **Halide**              | 图像流水线      | **算法与调度分离** + autoscheduler |
| **TVM AutoTVM / Ansor** | 深度学习算子     | 模板/无模板搜索 + 学习代价模型           |
| **OpenTuner**           | 通用         | 多臂老虎机集成多种搜索器                |
| **Milepost GCC**        | 通用 pass 顺序 | ML 预测 + 迭代编译                |

> **Halide 的"算法/调度分离"是一个独立的重大思想**：把"计算什么"（算法，程序员写）与"怎么计算"（调度，可搜索）解耦。这使得**搜索空间成为一等公民**。MLIR、TVM、Tiramisu 都继承了这个设计。

### 7.3 超优化与 ML 引导

| 方法           | 做法                   | 代表                               |
| ------------ | -------------------- | -------------------------------- |
| **穷举超优化**    | 枚举短指令序列 + 形式验证等价     | Massalin (1987)、Souper、peepmatic |
| **随机搜索超优化**  | MCMC 在指令空间随机游走 + 验证  | **STOKE**（找出人类想不到的位技巧）           |
| **学习代价模型**   | 用真机数据训练"基本块 → 周期数"模型 | **Ithemal**、llvm-mca（解析式）        |
| **RL 做编译决策** | 把 pass 决策建模为 MDP     | **MLGO**（LLVM 的内联/寄存器逐出策略）       |
| **验证工具**     | 检查现有优化是否正确           | **Alive2**（已发现 LLVM 数百个真实 bug）   |

### 7.4 最彻底的手段：把决策推迟到运行期

这是本锤的最高形态，也是**与前端最深刻的呼应**。

**动机：抽象解释的根本天花板**

```c
void f(Shape s) { s.area(); }
// 静态分析：s 可能是任何 Shape 子类 ⇒ 无法去虚化、无法内联
// 运行时观测：99.9% 是 Circle ⇒ 内联 Circle::area + 类型守卫
```

**由 Rice 定理，静态分析永远无法精确回答这类问题。唯一出路：去看真实执行。**

> ### 这与 ANTLR 4 的 ALL(\*) 是同一个突破
> 
> 回想 ALL(\*) 的论证：
> 
> > *"The critical innovation is to move grammar analysis to parse-time."*
> > 因为前看语言非正则，静态子集构造根本不收敛；而在运行期，**栈是一个具体值而非一个集合**，不确定性大幅降低。
> 
> **JIT 编译是同一论证在后端的完整展开**：
> 
> | 维度            | ANTLR 4 的 ALL(\*)         | JIT / 投机优化                                |
> | ------------- | ------------------------- | ----------------------------------------- |
> | 静态方案的死穴       | 前看语言非正则，DFA 不收敛           | **Rice 定理**：值/类型/分支不可静态判定                 |
> | 转向运行期获得了什么    | 真实输入 + **真实调用栈**          | 真实值 + **真实类型** + 真实执行频率                   |
> | 决策依据由"所有可能"变为 | "眼前这串 token"              | "实际观测到的类型/值/路径"                           |
> | 缓存机制          | **DFA 状态缓存**（增量）          | **编译代码缓存 + 内联缓存（IC/PIC）**                 |
> | 成本摊销          | 越"热"越接近纯 DFA 查表           | 越"热"越接近静态最优码                              |
> | **猜错时的退路**    | SLL 失败 → **回退到完整 LL 重解析** | 守卫失败 → **去优化（deopt）回解释器**                 |
> | 分层策略          | SLL（快，近似）→ LL（慢，精确）       | Tier-0 解释 → Tier-1 快速 JIT → Tier-N 优化 JIT |
> | 内存管理          | `clearDFA()`              | 代码缓存驱逐 / deopt 后丢弃机器码                     |
> | 代价            | 首次决策慢（预热）                 | **warmup** 期性能差                           |
> | 风险            | 反复 SLL 失败 ⇒ 每句双遍解析        | **去优化风暴**：反复猜错 ⇒ 性能崩塌                     |
> 
> **"两阶段解析（SLL + Bail → LL）"和"分层编译 + 去优化"是同一个模式，三个必要组件：**
> **① 便宜的乐观假设；② 可检测的失败信号；③ 精确但昂贵的退路。**

**运行期化手段全表**：

| 手段                                | 替代了哪个静态近似                  |
| --------------------------------- | -------------------------- |
| **PGO / FDO**（离线 profile）         | 分支概率、调用频率、热冷划分             |
| **内联缓存 / 多态内联缓存**（IC/PIC）         | 虚调用目标（替代类层次分析 CHA）         |
| **去虚化 + 类型守卫**                    | 接收者类型（替代指向分析）              |
| **值投机 / 常量提升**                    | 参数值（替代常量传播的 `⊤`）           |
| **Trace JIT**（LuaJIT、TraceMonkey） | 整条执行路径（替代路径不敏感分析）          |
| **循环 trip count 投机**              | 循环次数（替代 SCEV 的符号上界）        |
| **自适应重编译 + OSR**                  | 全部（观测足够久再决定优化强度）           |
| **Truffle / 部分求值**                | 解释器的 dispatch 开销（用运行期特化消除） |

## 8. 前端锤与后端锤的横向对照

这是全文的核心收获。**编译器从字符流到机器码，反复使用的算法骨架其实只有两个：不动点迭代，和划分精化。**

| #   | 母题                       | 前端形态                                      | 后端形态                                                        |
| --- | ------------------------ | ----------------------------------------- | ----------------------------------------------------------- |
| 1   | **worklist 不动点迭代**       | 子集构造 NFA→DFA；LR(0) 项目集规范族                 | 全部数据流分析；SSA 构造；指向分析；重写到不动点；同余闭包                             |
| 2   | **闭包计算**                 | ε-闭包、`CLOSURE(I)`                         | 支配边界 `DF⁺`、传递闭包、CFL-可达性、congruence closure                  |
| 3   | **划分精化（最大不动点）**          | **Hopcroft DFA 最小化**                      | **AWZ 乐观 GVN**（论文明说改编自 Hopcroft）、SCCP 从 `⊤` 起               |
| 4   | **Union-Find 合并（最小不动点）** | ——                                        | 悲观 GVN、类型合一、e-graph 底层                                      |

## 9. 贯穿全局的三个主题

如果要从这两篇文档里只带走三句话，就是下面三句。

### 主题一：不动点迭代无处不在

```
子集构造 = 幂集格上的最小不动点
LR 项目集规范族 = 同上
数据流分析 = 抽象域上的最小/最大不动点
SSA 构造（φ 插入）= 支配边界的迭代闭包
同余闭包 = 签名重哈希的不动点
重写到不动点 = 程序项格上的不动点
指向分析 = Datalog 的半朴素求值 = worklist 不动点
Typestate = DFA 状态集格上的不动点
```

**统一签名**：

```python
while worklist:
    x = worklist.pop()
    new = transfer(join(inputs(x)))
    if new != current[x]:
        current[x] = new
        worklist.extend(dependents(x))
```

**两个方向**（对偶，都很重要）：

|       | 最小不动点 `lfp`     | 最大不动点 `gfp`          |
| ----- | --------------- | -------------------- |
| 起点    | `⊥`（最保守/最不等价）   | `⊤`（最乐观/最等价）         |
| 动作    | 向上**合并**、加信息    | 向下**分裂**、削弱假设        |
| 数据结构  | Union-Find      | Partition Refinement |
| 前端    | 子集构造（可达子集的最小集合） | **Hopcroft 最小化**     |
| 后端    | 悲观 GVN、活跃分析     | **AWZ 乐观 GVN**、SCCP  |
| 能否处理环 | ✘ 循环中的等价发现不了    | ✔ **能**              |

### 主题二：改变表示胜过改进算法

**最有效的优化往往不是"把算法做快"，而是"改变问题的提法"。**

| 表示              | 消灭了什么                | 换来了什么         | 代价                      |
| --------------- | -------------------- | ------------- | ----------------------- |
| **DFA**（vs NFA） | 运行时的不确定性             | `O(1)` 转移     | `2ⁿ` 状态风险               |
| **LR 自动机**      | "识别 CFL 需要无限栈"的困难    | DFA 看栈顶 + 显式栈 | 冲突需人工消解                 |
| **SSA**         | 到达定义分析               | 稀疏分析 + **弦图** | 出 SSA / coalescing 的复杂性 |
| **MemorySSA**   | 密集的内存别名查询            | 内存优化也能稀疏化     | 构造与维护成本                 |
| **多面体模型**       | 十几种 ad-hoc 循环变换的独立实现 | 统一的仿射代数       | 只适用于仿射程序                |
| **E-graph**     | phase ordering（重写层）  | 保留所有等价程序      | 可能不饱和 / 爆炸              |
| **ANF/CPS**     | 表达式嵌套带来的特例           | 统一处理尾调用、闭包    | 代码膨胀                    |
| **规范化**         | 模式的组合爆炸              | 模式数从指数降到线性    | 需要设计规范形式                |

**两处最漂亮的结构定理**（值得当作"编译原理最美结论"记住）：

```
活前缀集合是正则语言        ⇒ LR 分析可行（CFL 的难度被隔离进显式栈）
严格 SSA 的干扰图是弦图      ⇒ 寄存器分配最优着色可行（难度被隔离进 coalescing）
```

**共同方法论**：**不要正面攻克难问题；寻找一个使问题落入易解子类的表示，把剩余难度隔离进一个单独的、可控的子问题。**

### 主题三：何时承诺 —— 这是编译器设计的核心自由度

几乎每个设计争议，本质上都是"**在什么时候做出不可逆的决定**"。

```
最早 ←────────────────────────────────────────────────→ 最晚

编译期静态决定        惰性/按需        推迟到运行期        永不承诺
     │                  │                  │                │
前端 │ LL(1)/LALR(1)    │ Bison 按需       │ ALL(*)          │ GLR/GLL
     │ LL(*) 前看 DFA   │ LALR 前看        │ (解析期分析)     │ + SPPF/GSS
     │                  │ RE2 lazy DFA     │                 │
     │                  │                  │                 │
后端 │ 固定 -O2 pipeline│ Braun 按需 SSA   │ JIT / PGO       │ Equality
     │ 贪心 peephole    │ LazyValueInfo    │ 投机 + deopt    │ Saturation
     │ AOT 编译         │ IFDS summary     │ 自适应重编译     │ + E-graph
     │                  │                  │                 │
病理 │ PEG 陷阱         │ 缓存管理复杂     │ warmup / 去优化  │ 不饱和/爆炸
     │ phase ordering   │ 首次访问慢       │ 风暴 / 不可复现  │ 提取需 ILP
     │ 局部最优         │                  │                 │ 编译时间不可控
```

**并且，"承诺得早"必须配一个可检测的失败信号。** 这是全文最实用的一条工程原则：

| 近似方案             | 失败信号                  | 退路            | 评价                   |
| ---------------- | --------------------- | ------------- | -------------------- |
| SLR 用全局 `FOLLOW` | shift/reduce 冲突报告     | 改用 LALR/LR(1) | ✔ 信号清晰               |
| 线性近似前看           | 虚报冲突                  | 对该决策做全前看      | ✔                    |
| ANTLR 4 的 SLL    | `requiresFullContext` | 完整 LL 重解析     | ✔                    |
| PEG 有序选择         | **无信号**（静默失败）         | 无             | ✘ 危险                 |
| CHA 去虚化          | 类加载时失效                | 撤销优化          | ✔                    |
| JIT 类型投机         | 守卫失败                  | deopt 回解释器    | ✔                    |
| **上下文不敏感指向分析**   | **无信号**               | 无             | ✘ 你无法知道"这次近似够不够"     |
| 贪心 peephole      | **无信号**               | 无             | ✘ phase ordering 的根源 |

> **好的近似必须可检测地失败。**
> SLR 的冲突报告、ANTLR 的 `requiresFullContext`、JIT 的守卫——它们都做对了。
> 而**上下文不敏感指向分析**和**贪心 peephole** 之所以更难用，恰恰因为它们**没有**这个信号。
> 
> 这条原则的适用范围远超编译器：缓存一致性、乐观并发控制（OCC）、事务内存、投机执行、CDN 缓存、分布式共识的快速路径——**全都是"乐观假设 + 可检测失败 + 昂贵退路"的三段结构。**

## 10. 小结、自检与阅读路径

### 10.1 三句话总结

1. **后端的主锤是"格上的单调不动点迭代"**，它与前端的子集构造是**同一个 worklist 算法**——只是把"NFA 状态子集"换成了"抽象域元素"，把"精确判定"换成了"保守近似"。前端的敌人是**状态爆炸**（多项式问题的效率），后端的敌人是 **Rice 定理 + NP-hard**（问题本身不可解），所以后端必然从"一把锤子"变成"一族锤子"。

2. **六把大锤各守一层**：SSA/支配是坐标系（让主锤稀疏化）；等价类合并/精化回答"是否等价"；DP 在树/链等受限结构上给出**真正最优**；图归约 + 启发式处理 NP-hard 的资源分配；多面体模型统一所有循环变换；代价模型 + 搜索是承认"我们不知道什么更快"之后的最后手段。**"合法性"由主锤保证，"收益性"由后四把处理**——这是两件本质不同的事，也是后端不可能只有一把锤子的根本原因。

3. **前后端共享同一批母题**（见 §8 的 22 行对照）。其中最深刻的三处对应是：
   
   - **`SSA 干扰图是弦图` ≡ `活前缀是正则语言`**（改变表示，落入易解类，把难度隔离）
   - **`E-graph + Equality Saturation` ≡ `SPPF + GLR`**（拒绝提前承诺，共享打包所有可能，最后再选）
   - **`JIT + 投机 + deopt` ≡ `ALL(*) + SLL/LL 两阶段`**（推迟决策到运行期，因为静态方案在理论上就不可能）

### 10.2 自检问题

能回答这些，说明前后端已经打通：

1. 把子集构造填进"格、图、transfer、汇合"四个格子，说明它为什么是数据流分析的特例。它求的是最小还是最大不动点？
2. **MFP vs MOP** 与 **精确 LL(k) vs 线性近似前看** 的共同点是什么？各自丢失了什么信息？举出常量传播的非分配反例。
3. **widening `∇`** 与 **LL(\*) 前看 DFA 中的循环自环** 在做同一件事——是哪件事？
4. 为什么**悲观 GVN 发现不了循环中 `i ≡ j`，而乐观 GVN 能**？这与"DFA 最小化必须从粗划分向下精化而不能从细划分向上合并"是同一件事吗？
5. `活前缀是正则语言` 和 `SSA 干扰图是弦图` 为什么是同一类结论？在这两个故事里，"剩余的难度"分别被隔离到了哪里？
6. **iburg 为什么故意不做确定化**？举出前端的两个同类判断。
7. 为什么 **DP 在树上最优、在 DAG 上 NP-hard**？"最优子结构"具体是被什么破坏的？
8. 为什么 **phase ordering 问题是 PEG 有序选择陷阱的后端版本**？E-graph 与 SPPF 各自解决了什么、留下了什么？
9. **SCCP** 严格强于"先跑可达性再跑常量传播"。为什么？这体现了什么原则？前端有对应物吗？
10. **两阶段解析（SLL→LL）** 和 **分层 JIT + deopt** 是同一个模式。这个模式的三个必要组件是什么？举出一个**缺少第二个组件**的反面例子。
11. 前端的敌人是状态爆炸，后端的敌人是什么？为什么后端可以"大胆近似"而前端不行？
12. 多面体模型"统一所有循环变换"，与 Parr 的 "Lexing = Parsing = Tree Parsing" 是同一类成就吗？两者的固有代价分别是什么？

### 10.3 建议学习顺序

```
第一阶段：把主锤打通（务必亲手写代码）
① 经典数据流四件套（Liveness / Reaching Defs / Available / Very Busy）
   └─ 关键：把你的 worklist 代码与子集构造代码并排放，逐行对照
② MFP vs MOP + 分配性
   └─ 关键：亲手构造常量传播的非分配反例
③ 抽象解释框架（Galois 连接、区间域、widening/narrowing）
   └─ 关键：理解 widening 与"限制 k"是同一个动作

第二阶段：坐标系与等价性
④ SSA：支配关系（Cooper-Harvey-Kennedy / Semi-NCA）→ 支配边界 → φ 插入
   └─ 关键：理解 SSA 是"改变表示"而非"新算法"
⑤ 稀疏分析：SCCP、稀疏值域传播
⑥ GVN 两条路线（悲观 Union-Find vs 乐观 AWZ）+ 同余闭包
   └─ 关键：把 AWZ 与 Hopcroft 最小化并排读，确认是同一个算法

第三阶段：变换与资源
⑦ 指令选择（Aho-Johnson 树 DP → BURG 树自动机 → iburg → DAG 的 NP-hard）
   └─ 关键：回到 NFA→DFA，看清"确定化 vs 不确定化"的工程权衡
⑧ 寄存器分配（Chaitin-Briggs → 线性扫描 → SSA/弦图 → LLVM greedy）
   └─ 关键：追踪"NP-hard → 换表示 → 多项式最优 → 但现实又打回启发式"这条完整弧线
⑨ PRE / Lazy Code Motion（四轮数据流 + 最小割视角）
   └─ 关键：这是 NP-hard 汪洋中的一座岛，看清什么结构让它可最优求解
⑩ 指令调度 + 相位耦合（表调度、模调度、寄存器压力感知）

第四阶段：现代前沿
⑪ 多面体模型（迭代域/访存函数/调度 → Feautrier → Pluto → CLooG/isl）
⑫ E-graph / Equality Saturation（egg → Cranelift aegraph）
   └─ 关键：与 GLR/SPPF 对照阅读
⑬ JIT / 投机 / PGO（HotSpot C2、V8 TurboFan、LuaJIT trace、Truffle）
   └─ 关键：与 ALL(*) 论文对照阅读，看"推迟决策"的完整论证
⑭ 搜索与学习（Halide/TVM autoscheduler、STOKE、Alive2、MLGO）

第五阶段：理论边界
⑮ Rice 定理；Chaitin 的 NP-hard 归约；k-CFA 的 EXPTIME 结论（Van Horn-Mairson）；
   DAG 覆盖 NP-hard；程序等价性不可判定
   └─ 关键：理解"哪些墙是撞不破的"，从而理解每把锤子为什么必须存在
```

## 收束

> **前端的锤子是 NFA → DFA：一个精确的、多项式的、消除不确定性的构造。**
> **后端的主锤是格上的单调不动点迭代：一个故意不精确的、保守的、逼近真理的构造。**
> 
> **而它们是同一把锤子**——子集构造就是幂集格上的最小不动点。差别只在于：
> 前端的问题**可判定**，所以追求"精确"，敌人是**效率**（`2ⁿ`），武器是确定化、最小化、压缩、惰性；
> 后端的问题**不可判定或 NP-hard**，所以只能追求"保守且够好"，敌人是**精度**和**代价模型不可知**，武器是抽象、启发式、换表示、以及最终——**去看真实的执行**。
> 
> 于是整个编译器只反复做三件事：
> 
> **① 迭代到不动点。**
> **② 换一个使问题变简单的表示。**
> **③ 决定什么时候承诺——并为承诺错了准备一条可检测的退路。**

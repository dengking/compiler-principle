# 表达式DAG构造中哈希表优化的值编号技术规范

## 1. 文档概述
本文基于编译原理经典教材《Compilers: Principles, Techniques, and Tools（龙书）》第6.1.2节的值编号法（Value-Number Method），针对原始暴力遍历方案构造表达式有向无环图（DAG）的性能瓶颈，系统阐述哈希表分桶优化的整体架构、执行流程与工程实现方法，重点补充哈希函数的设计原则、实现方案与参数选型规范。本技术适用于编译前端中间表示生成、局部公共子表达式消除（CSE），可拓展至全局值编号（GVN）等高级编译优化场景。

## 2. 技术背景：原始值编号法的性能瓶颈
### 2.1 原始算法逻辑（算法6.3）
基础值编号法以一维数组存储全部DAG节点，每个节点通过**签名三元组** $\langle op,\(l, r\) \rangle$ 唯一标识：
- $op$：节点运算符标签，如算术运算、数组构造、类型转换等；
- $l$：左子节点的值编号（即节点在全局数组中的下标）；
- $r$：右子节点的值编号，一元运算符场景下可置为0或空标识。

节点构造时执行全量遍历查重：
1. 遍历全局节点数组，逐一比对节点签名与待创建签名；
2. 匹配成功则复用已有节点，返回对应值编号；
3. 匹配失败则在数组尾部新增节点，分配并返回新值编号。

### 2.2 核心性能缺陷
原始方案的时间复杂度为 $\(O(N)\)$（$N$ 为已创建节点总数），在工程场景下存在显著瓶颈：
1. 随程序表达式规模增长，查重耗时呈线性上升，全程序范围下开销不可接受；
2. 绝大多数节点与当前待查询签名无匹配可能，全量遍历存在大量无效比对；
3. 高频节点创建场景下，遍历开销会成为编译前端的性能热点。

为解决该问题，工业界普遍引入**哈希表分桶索引**作为字典抽象数据结构，将平均查重复杂度优化至 $\(O(1)\)$。

## 3. 哈希表优化方案整体架构
### 3.1 分层存储结构
优化方案采用三层存储架构，在保留原始全局节点数组的基础上新增哈希索引层：
1. **全局节点数组**：存储节点的完整信息（运算符、子节点编号、语义属性等），值编号为数组下标，与原始方案完全兼容；
2. **哈希桶数组**：数组每个元素为桶链表的头指针，数组下标由哈希函数计算得到；
3. **桶内链表**：每个桶对应一条单向链表，存储所有哈希映射至该桶的节点值编号，用于解决哈希冲突。

### 3.2 核心优化思想
通过哈希函数将节点签名映射为桶数组下标，把全局范围的线性查重转化为**单桶内的短链表局部比对**：
- 均匀哈希下每个桶仅包含极少量节点，桶内遍历开销可忽略；
- 哈希函数的确定性保证同一签名始终映射至同一桶，不会遗漏匹配结果。

## 4. 哈希函数的工程化设计
哈希函数是整个优化方案的核心，其性能与分布特性直接决定优化效果。针对DAG节点签名的结构化特征，需从设计目标、输入特征、实现方案、参数选型多维度进行规范设计。

### 4.1 核心设计目标
1. **确定性**：相同的 $\langle op,\(l, r\) \rangle$ 输入必须输出完全一致的哈希索引，是查重正确性的基础保障；
2. **均匀性**：将不同签名尽可能均衡分散至所有哈希桶，避免哈希倾斜（单个桶承载远超平均数量的节点）；
3. **高效性**：计算逻辑轻量，无复杂运算，适配编译期节点高频创建的场景；
4. **低碰撞性**：具备良好的雪崩效应——输入的微小变化会导致哈希值大幅变化，降低不同签名映射至同一桶的概率。

### 4.2 输入签名特征分析
DAG节点签名为固定长度的结构化三元组 $\langle op,\(l, r\) \rangle$，其输入特征为：
- $op$：运算符枚举值，取值范围有限（通常为几十种），分布集中；
- $l, r$：子节点值编号，为单调递增的非负整数，取值范围随程序规模扩大；
- 三个分量均为整数类型，无需处理字符串、浮点等复杂输入。

### 4.3 主流实现方案
针对整数三元组输入，工程中常用三类哈希实现方案，可根据场景规模选型：

#### 方案一：多项式素数哈希（线性组合法）
通过大素数作为基数，将三个分量按位权组合为单个哈希值，最终对桶数取模得到索引：
$$
h(op,\(l, r\)) = \left( op \cdot P^2 + l \cdot P + r \right) \mod M
$$
其中：
- $P$ 为大素数基数（通常取 131、13331 等经典素数）；
- $M$ 为哈希桶数组的长度。

**代码示例（C风格）**：
```c
uint32_t polynomial_hash(int op, int l, int r, uint32_t bucket_num) {
    const uint32_t BASE = 131;
    uint32_t h = op;
    h = h * BASE + l;
    h = h * BASE + r;
    return h % bucket_num;
}
```
**适用场景**：中小规模局部基本块DAG构造，实现简单、分布均匀性良好。

#### 方案二：移位异或混合哈希
通过移位与异或操作混合三个分量的比特位，全程无乘法、除法运算，计算开销极低，同时具备良好的雪崩效应：
```c
uint32_t xor_shift_hash(int op, int l, int r, uint32_t bucket_num) {
    uint32_t h = (uint32_t)op;
    h ^= (uint32_t)l << 13;
    h ^= (uint32_t)r << 7;
    h ^= h >> 16;
    return h % bucket_num;
}
```
**适用场景**：编译前端高频节点创建、对哈希计算开销敏感的场景，是工业界编译器的常用轻量方案。

#### 方案三：标准化通用哈希（MurmurHash3 定长版）
采用经过工业界验证的通用哈希算法（如MurmurHash3、XXHash），针对12字节固定长度输入（3个32位整数）做适配，碰撞率极低，分布均匀性最优：
```c
// 简化版 MurmurHash3 32位，适配 3 个整数输入
uint32_t murmur3_hash(int op, int l, int r, uint32_t seed, uint32_t bucket_num) {
    uint32_t h = seed;
    const uint32_t c1 = 0xcc9e2d51;
    const uint32_t c2 = 0x1b873593;

    uint32_t k;
    // 处理 op 块
    k = op * c1; k = (k << 15) | (k >> 17); k *= c2;
    h ^= k; h = (h << 13) | (h >> 19); h = h * 5 + 0xe6546b64;
    // 处理 l 块
    k = l * c1;  k = (k << 15) | (k >> 17); k *= c2;
    h ^= k; h = (h << 13) | (h >> 19); h = h * 5 + 0xe6546b64;
    // 处理 r 块
    k = r * c1;  k = (k << 15) | (k >> 17); k *= c2;
    h ^= k; h = (h << 13) | (h >> 19); h = h * 5 + 0xe6546b64;

    h ^= 12; // 输入总长度 12 字节
    h ^= h >> 16; h *= 0x85ebca6b;
    h ^= h >> 13; h *= 0xc2b2ae35;
    h ^= h >> 16;
    return h % bucket_num;
}
```
**适用场景**：全局值编号（GVN）、全程序范围DAG构造等节点规模极大的场景，以轻微计算开销换取极低碰撞率。

### 4.4 哈希表容量与负载因子选型
1. **桶数组长度**：优先选取素数作为桶数，可减少模运算带来的分布偏差，降低规律性碰撞；
2. **负载因子（Load Factor）**：定义为「已存储节点总数 / 桶数组长度」，工程中通常控制在 0.6 ~ 0.8 之间；
3. **扩容策略**：当负载因子超过阈值时，执行扩容与重哈希（Rehash）：将桶数组扩容至原容量的2倍左右并选取邻近素数，遍历所有节点重新计算哈希值并插入新桶数组，保证长期运行下的查询效率。

### 4.5 哈希冲突处理机制
本方案采用**链地址法（分离链接法）**处理哈希冲突，与龙书描述的桶链表结构完全一致：
1. 每个哈希桶维护一条单向链表，存储所有映射至该桶的节点值编号；
2. 插入冲突时，将新节点值编号直接插入链表头部，插入复杂度 $\(O(1)\)$；
3. 查询时遍历链表，取出每个值编号对应的完整签名逐一比对，确保匹配结果准确。

**选型理由**：DAG节点创建后无删除操作，链表结构稳定无空洞；实现逻辑简单，无需处理探测序列；极端冲突场景下仅性能线性下降，不会出现插入失败或结果错误。

## 5. 优化后DAG节点构造完整流程
- **输入**：待创建节点的运算符 $op$、左子节点值编号 $l$、右子节点值编号 $r$
- **输出**：对应节点的值编号

1. **计算桶索引**：调用哈希函数计算 $h(op,\(l, r\))$，定位目标哈希桶；
2. **桶内查重**：遍历该桶的链表，对每个节点值编号读取完整签名，与输入签名比对：
   - 若匹配成功，直接返回该值编号，复用已有节点；
3. **新建节点**：若桶内无匹配节点，在全局节点数组末尾创建新节点，分配新的值编号；
4. **更新哈希表**：将新节点的值编号插入对应桶的链表头部；
5. **返回结果**：返回新分配的值编号。

## 6. 技术优势与工程价值
1. **复杂度量级提升**：将节点查重的平均时间复杂度从 $\(O(N)\)$ 优化至 $\(O(1)\)$，彻底解决大规模表达式下的遍历性能瓶颈；
2. **完全兼容上层逻辑**：对外接口与原始值编号法完全一致，上层语法制导定义（SDD）、节点构造函数无需修改即可无缝适配；
3. **可扩展性强**：架构可直接从局部基本块的LVN拓展至跨基本块的全局值编号（GVN），支撑常量传播、冗余表达式消除等高级优化；
4. **工程成熟度高**：哈希表+链地址法是工业界编译器的标准实现方案，稳定性与性能均经过大规模生产环境验证。

## 8. 总结
哈希表分桶优化是值编号法从理论走向工程落地的核心改进，通过设计合理的哈希函数与冲突处理机制，在保证公共子表达式准确识别的前提下，大幅提升DAG构造效率。哈希函数的选型需根据场景规模在计算开销与碰撞率之间权衡，中小规模场景优先轻量移位异或方案，大规模全局优化场景可采用标准化通用哈希算法。

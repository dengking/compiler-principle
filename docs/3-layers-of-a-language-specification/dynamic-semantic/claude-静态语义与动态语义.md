# 静态语义与动态语义:程序意义的两重划分

## 引言:三个问题

给定一段代码,可以问三个层次的问题:

```c
int x = ;              // ① 这是程序吗?
int x = "hello";       // ② 这是合法程序吗?
int x = y / z;         // ③ 这个合法程序做什么?
```

- ① 问**形状**:字符串是否符合语言的文法。这是 **syntax(语法)**。
- ② 问**良构性**:形状合法的程序是否满足语言的其他静态规则。这是 **static semantics(静态语义)**。
- ③ 问**含义**:良构的程序执行起来意味着什么,包括 `z == 0` 时会怎样。这是 **dynamic semantics(动态语义)**。

通常说的"语义"涵盖后两者。但把它们分开,是理解编译器行为、UB、优化合法性的前提。本文系统梳理这两层的分界、各自的内容、形式化方式,以及它们在真实编译器里的落点。

---

## 一、核心分界:守门人与承诺书

一句话概括:

> **静态语义是守门人,动态语义是承诺书。**

**静态语义**的使命是**拒绝**。它在编译期回答一个布尔问题:这个程序该不该被接受?一旦放行,它的工作就结束了。

**动态语义**的使命是**承诺**。它规定:对于每个被接受的程序,运行起来会发生什么(可观察行为的**集合**)。它不拒绝任何东西,只**描述**。

|       | 静态语义           | 动态语义               |
| ----- | -------------- | ------------------ |
| 问什么   | 这个程序**合法**吗    | 这个合法程序**做什么**      |
| 输出    | 接受 / 拒绝        | 可观察行为的**集合**       |
| 何时判定  | 编译期            | 规定运行期行为(但规范编译期即存在) |
| 失败表现  | 编译错误           | UB、panic、异常、崩溃     |
| 形式工具  | 类型规则、属性文法、推导规则 | 操作/指称/公理语义         |
| 判定成本  | 多项式(多数语言)      | 一般**不可判定**         |
| 编译器角色 | **执行者**(它来检查)  | **遵守者**(它被约束)      |

最后一行最关键,也最容易被忽略:**编译器执行静态语义,但只能遵守动态语义。** **类型检查器**是静态语义的实现;而**优化器**不是**动态语义**的实现,它是**动态语义**的受约束方(**动态语义**约束**优化器**)。

## 二、静态语义:编译期可判定的良构性

### 2.1 它包含什么

静态语义就是"语法之外、运行之前"的全部规则:

| 类别 | 内容 | 典型语言 |
|---|---|---|
| **名字解析** | 每个标识符引用绑定到哪个声明;作用域、遮蔽、可见性 | 全部 |
| **类型检查** | 操作数类型相容、函数调用签名匹配 | 全部静态类型语言 |
| **类型推导** | `auto` / `var` / Hindley–Milner | C++、Rust、ML |
| **重载决议** | 从候选集选最佳匹配 | C++、Java、Rust |
| **访问控制** | `private` / `pub` / 模块边界 | C++、Java、Rust |
| **常量求值** | `constexpr`、数组维度、`case` 标签 | C++、Rust |
| **definite assignment** | 变量使用前在所有路径上已赋值 | Java、C# |
| **可达性** | 死代码、缺失 `return` | Java、Rust |
| **借用检查** | 生命周期与别名规则 | Rust |
| **effect / 线性类型** | 资源使用次数、副作用追踪 | Rust(部分)、Koka、Linear Haskell |

### 2.2 一个重要的内部分裂:流不敏感 vs 流敏感

上表里有两类性质混在一起,实现机制完全不同:

**流不敏感(flow-insensitive)** 的检查只看声明和表达式结构,靠**符号表 + 类型规则**即可:

```c
int x = "hello";   // 看类型就知道不行,不需要知道控制流
```

**流敏感(flow-sensitive)** 的检查必须分析控制流图,靠**数据流分析 + 不动点迭代**:

```java
int x;
if (cond) x = 1;
System.out.println(x);   // 错误:x 可能未初始化
```

Java 的 definite assignment、Rust 的借用检查、C# 的 nullable 流分析都属于后者。它们在形式上是**前向数据流分析**:

$$\text{OUT}[B] = f_B(\text{IN}[B]), \qquad \text{IN}[B] = \bigcap_{P \in \text{pred}(B)} \text{OUT}[P]$$

注意这里用的是交(must 性质:"所有路径上都已赋值")。这和中端的常量传播、活跃变量分析是**同一套数学**——区别只在于它跑在前端的 AST/CFG 上,结论用于**拒绝程序**,而不是用于优化。

**这是一条值得记住的对应**:**静态语义**里最复杂的部分,其技术底座和**中端优化**完全相同。Rust 把借用检查放在 MIR(而非 AST)上做,正是因为需要一个像样的 CFG。

### 2.3 核心载体:符号表与类型表

静态语义的记忆是两张表:

```
符号表 (Symbol Table)    名字 → Symbol { kind, type, scope, linkage, ... }
类型表 (Type Table)      类型的规范表示,做 uniquing
```

类型表要做 **uniquing**(唯一化):`int*` 只构造一次,结构相同的函数类型共享同一对象。于是

$$\texttt{T1 == T2} \iff \text{两者是同一类型}$$

退化成**指针比较**。这个手法在编译器里到处出现——Clang 的 `IdentifierTable` 对标识符字符串做 interning,LLVM 的 `LLVMContext` 对 `i32` 和 `ConstantInt` 做 uniquing,动机完全一致:**把语义相等变成物理相等,把 $O(n)$ 比较变成 $O(1)$**。

### 2.4 静态语义会改写程序

一个常被忽略的事实:静态语义阶段**不只是检查,它主动修改 AST**。

```c
int add(int, int);
double r = add(5, 2);
return r;              // 函数返回 int
```

语义分析做了什么:

1. 查 `add` → 命中声明,签名匹配;
2. `add(5,2)` 类型为 `int`,赋给 `double` → **插入 `ImplicitCastExpr: int → double`**;
3. `return r`,`r` 是 `double`,返回类型是 `int` → **再插一次 `double → int`**。

所以出口的树比入口的树信息多得多,这就是所谓 **annotated AST / decorated AST**。类似地,重载决议把"一个名字"替换成"一个具体函数";`constexpr` 求值把表达式替换成字面量。

**静态语义的产物不是"是/否",而是一棵被充实过的树。**

### 2.5 分层在现实中会崩塌

理论上"先语法后语义",实践上做不到。经典反例:

```c
A * B;
```

这是声明(`B` 是 `A*`)还是表达式(`A` 乘 `B`)?取决于 `A` 是否 `typedef` 名——而这是**符号表里的静态语义信息**。于是 C 的 parser 必须在解析途中查符号表,把 `IDENTIFIER` 重分类为 `TYPEDEF_NAME`。这就是 **lexer hack**:**语法分析反向依赖语义分析**。

更极端的是 C++:模板实例化图灵完备,因此"这个 C++ 程序是否良构"**在一般情况下不可判定**。本该廉价的静态语义判定,这里直接撞上停机问题。

结论:**"什么算语法错误、什么算静态语义错误",相当程度上是实现决策,不是本质划分。** 真实语言在 Chomsky 层级上高于上下文无关,工程上的妥协是"用 CFG 近似 + 把剩下的塞进语义分析"。

### 2.6 错误恢复:中毒符号

实际编译器不能遇到第一个错误就停,否则一次编译只能报一个错。标准手法是插入**中毒(poisoned)符号**:

```c
int x = undeclared_thing;   // ① 报 "undeclared identifier"
x + 1;                      // ② 不应再报 "x 类型未知"
```

做法是:查找失败时插入 `type = ErrorType` 的占位符号,后续所有涉及 `ErrorType` 的检查**一律静默通过**;Clang 还会 `setInvalidDecl()` 并做 typo correction。

值得注意的是:**错误类型在类型系统里的角色,和 `poison` 在 LLVM IR 动态语义里的角色高度同构** —— 都是一个**吸收性的坏值**,会传播但不产生新噪音。两层语义面对同一个工程问题(如何在值已经无意义之后继续工作),给出了同形的解法。

## 三、动态语义:程序意义的完整承诺

### 3.1 它是什么

动态语义是从「程序」到「该程序**所有允许的**可观察行为」的映射:

$$\lbrack\!\lbrack \cdot \rbrack\!\rbrack : \text{Program} \longrightarrow \mathcal{P}(\text{Behavior})$$

注意是**集合**,不是单个行为。这是理解整个概念——尤其是 UB——的钥匙。

### 3.2 它必须规定的东西

| 维度 | 具体内容 | 例子 |
|---|---|---|
| **状态构成** | 内存、环境、调用栈、线程、外部世界 | 对象的生命周期与地址 |
| **求值顺序** | sequencing、副作用的先后 | `f(i++, i++)` 谁先 |
| **算术行为** | 溢出、除零、移位、浮点 | 有符号溢出是 UB,无符号回绕 |
| **内存模型** | 别名规则、悬垂指针、数据竞争、`memory_order` | strict aliasing |
| **控制转移** | 调用返回、异常展开与析构顺序、协程 | 抛异常时哪些析构函数跑 |
| **终止性** | 无限循环的合法性 | C++ 里无副作用的死循环是 UB |
| **可观察边界** | 哪些效应算"可观察" | I/O、`volatile`、退出状态 |

### 3.3 抽象机与 as-if 规则

**动态语义**通过一台 **抽象机(abstract machine)** 定义:一个与真实硬件无关的理想执行模型。C 标准明确使用这个概念,然后规定实现只需复现抽象机的**可观察行为**,而非每一步细节。这就是 **as-if 规则**:

> 实现可以任意变换程序,只要最终可观察行为与抽象机上的执行一致。

**这条规则是一切优化的法律依据。**

```c
int x = 0;
for (int i = 0; i < 1000000; i++) x += i;
printf("%d\n", x);
```

抽象机忠实地跑一百万次。但可观察行为只有一次 `printf`,因此编译器可以直接算出 $\frac{n(n-1)}{2}$ 一次输出。这不是"违反语义",而是语义明确授权的。

反向例子:

```c
volatile int *reg = (volatile int*)0x1000;
*reg = 1;
*reg = 2;
```

`volatile` 访问**是**可观察行为,两次写不能合并——哪怕第一次看起来多余。

**可观察性的定义,直接划定了优化器的权力边界。**

### 3.4 为什么是集合:四类不确定性

一个程序往往不止一种合法行为,来源有四类:

| 类型 | 含义 | 行为集合 | 例子 |
|---|---|---|---|
| **unspecified** | 有限几种,实现任选,无需文档化 | 有限集 | 函数实参求值顺序 |
| **implementation-defined** | 实现必须**文档化**自己的选择 | 有限集 + 文档义务 | `int` 位宽、右移是否算术 |
| **并发非确定性** | 内存模型允许的所有交错 | 受内存模型约束的集合 | 两线程读写同一变量 |
| **undefined (UB)** | **不作任何承诺** | **全集** | 有符号溢出、越界访问 |

于是 UB 获得了精确定义:

> **UB = 行为集合是全集 = 语义不作任何承诺。**

它不是"会崩溃",也不是"结果随机"。它是**约束的缺失**。一旦触发 UB,从 $\llbracket P \rrbracket$ 里拿不到任何信息。

这解释了 UB 为何能被"利用":

```c
int f(int x) {
    if (x + 1 < x) return 1;   // 有符号溢出是 UB
    return 0;
}
```

编译器推理:若条件成立则必然溢出,即 UB,即该执行**本就不在语义保证内**;故可假定条件永假,直接返回 0。

四类不确定性里,**只有 UB 是全局性的**: UB 一旦触发,整个程序的语义都失效(标准措辞:"no requirements on the behavior of the program")。
其他三类不确定性是局部、有界的;

### 3.5 形式化的三种风格

动态语义怎么写下来,有三条经典路线。以 `while (x > 0) x = x - 1;` 为例:

**(a) 操作语义** —— "一步步怎么跑"。数学对象是**状态转移关系**,用推导规则给出:

$$
\frac{\sigma(x) > 0}{\langle \texttt{while}\ b\ \texttt{do}\ c,\ \sigma\rangle \to \langle c;\ \texttt{while}\ b\ \texttt{do}\ c,\ \sigma\rangle}
$$

这条规则把循环**展开一层**,循环语义就是它不断自我应用。特点:最接近解释器,能自然表达非终止(无限转移链)、并发(交错)、异常。

落点:WebAssembly 官方规范、Rust MIR(Miri 直接实现它来检测 UB)、CompCert 的每层 IR、ISA 形式规范(RISC-V 的 Sail)。

**(b) 指称语义** —— "它等于哪个数学函数"。把语句映射成状态上的部分函数 $\llbracket c\rrbracket : \Sigma \rightharpoonup \Sigma$,要求**组合性**:

$$\llbracket c_1; c_2 \rrbracket = \llbracket c_2 \rrbracket \circ \llbracket c_1 \rrbracket$$

循环定义为**最小不动点**,需要域论(CPO、连续函数)这套机械,非终止用 $\bot$ 表示。

落点:**它在编译器里的真正归宿是抽象解释**。常量传播、值域分析、SCCP 的理论基础正是格论与不动点——$\text{lfp}$ 的抽象化。你每写一个数据流分析,其实都在做指称语义。

**(c) 公理语义** —— "它保证什么性质"。Hoare 三元组 $\{P\}\,c\,\{Q\}$,循环规则靠**不变式** $I$:

$$\frac{\{I \land b\}\ c\ \{I\}}{\{I\}\ \texttt{while}\ b\ \texttt{do}\ c\ \{I \land \neg b\}}$$

特点:**不完整地描述语义**——只说保证什么,不说具体算什么。但正因为部分,最适合验证。

落点:Dafny、Frama-C/ACSL、SPARK;分离逻辑(加 $P * Q$ 处理堆与别名)是 Iris、VST、Infer 的基础。SMT 求解器在此充当执行引擎。

**三者互补而非互斥。** 严谨的语言工作要证明它们一致:指称与操作的 adequacy、Hoare 逻辑相对操作语义的 soundness。

## 四、两层语义在编译器里的分布

### 4.1 静态语义:几乎全在前端

```
源码 → [lexer] → [parser] → [Sema] → annotated AST → IR
                              ↑
                        静态语义在这里
```

它的产物是**决定**(接受/拒绝)加**充实后的 AST**。到达 IR 之后,静态语义的使命基本结束——注意一个重要后果:

**IR 层的类型系统远弱于源语言。** LLVM IR 的 `i32` 不知道自己原本是 `int` 还是 `unsigned`——signedness 在 IR 里属于**操作**而非类型,故有 `sdiv`/`udiv` 之分。源语言的大量静态语义信息(作用域、访问控制、类名)在此丢失。

需要往下传的部分只能**另辟通道**:

- 名字 → **name mangling**(C++ 用 Itanium ABI)→ `.o` 符号表
- 类型与变量名 → **debug metadata**(`!DILocalVariable`、`!DIType`)→ DWARF

```llvm
%x.addr = alloca i32, align 4
  #dbg_declare(ptr %x.addr, !10, !DIExpression(), !11)
!10 = !DILocalVariable(name: "x", scope: !5, line: 3, type: !8)
```

**符号表的内容在这里被"再编码"了一次** —— 从编译器的工作数据结构,变成随 IR 流动的元数据。调试器能告诉你 `x = 42`,全靠这条链。

### 4.2 动态语义:贯穿全流水线,且**分层**

这是最容易误解的地方。动态语义不属于任何单一阶段,而是:

> **一条 IR 链,每一级语言都有自己独立的动态语义;编译的每一步都是相邻两份语义之间的精化(refinement)。**

```
C/C++ 源码   ← ISO 标准的抽象机语义
   │ frontend
LLVM IR      ← LangRef 定义的语义(poison/undef/UB/nsw/内存模型)
   │ middle-end(必须保 IR 语义)
LLVM IR      ← 同一份语义
   │ ISel
MIR          ← 机器层语义(物理寄存器、栈帧、调用序列)
   │ backend
机器码        ← ISA 手册 / Sail 规范定义的语义
```

每级箭头都要满足:

$$\llbracket P_{\text{下层}} \rrbracket \;\subseteq\; \llbracket P_{\text{上层}} \rrbracket$$

**注意是 $\subseteq$ 而非 $=$**。编译器允许**收窄**非确定性(把"任选一种求值顺序"固定成一种实现),但不允许**产生**原本不允许的行为。这就是 refinement,也是 CompCert 的组织方式:每层 IR 配一套小步语义,优化正确性表述为相邻两层间存在**模拟关系(simulation)**,再由传递性组合成端到端定理。

两层语义在流水线上的分布可以画成矩阵:

```
              frontend    middle-end    backend    runtime
syntax          ■            ·             ·          ·
static sem.     ■            ·             ·          ·
dynamic sem.    ■            ■             ■          ■     ← 贯穿
```

### 4.3 各阶段的动态语义义务

**前端**要把高层动态语义"烧进"IR 结构:

- C++ 的求值顺序与 sequenced-before 规则
- 构造/析构顺序、异常展开中的清理范围、临时对象生命周期
- 虚函数动态分派
- 隐式转换与整型提升

一旦降到 IR,`load`/`store` 的顺序就是 IR 语义说的顺序——源语言那套 sequencing 规则**已经不存在了**。

**中端**不"实现"语义,它被语义**限制**。所有 pass 的合法性判据都是 refinement。

**后端**独占一批义务,因为相关概念在 IR 层根本不存在:

| 义务 | 内容 | 搞错的后果 |
|---|---|---|
| 架构内存模型 | `atomic`/`fence` 降成具体屏障(x86-TSO vs ARM/RISC-V 弱序) | 并发偶发错误,极难复现 |
| 原子性粒度 | 保证 `atomic i32` 真用单条对齐访问 | 撕裂读写 |
| `volatile` | 禁止合并、重排、消除 | MMIO 驱动失效 |
| 浮点语义 | 舍入模式、denormal、FMA contraction、NaN payload | 数值与规范不符 |
| ABI | 参数位置、`sret`、callee-saved | 跨 TU/跨语言调用崩溃 |
| 异常展开 | `.eh_frame` / CFI / LSDA | 抛异常时栈无法展开 |
| GC stack map | 哪些槽/寄存器含托管指针 | 堆损坏 |

两个值得强调的点:

**`-ffast-math` 不是"优化更激进",而是换了一份动态语义。** 它声明程序不依赖 IEEE 754 结合律、不产生 NaN/Inf,于是编译器获得新的合法变换集。**语义先变,实现才跟着变。**

**内存模型是语义风险最高的一处。** "ARMv8 上 `acquire` 降成 `ldar` 还是 `ldr; dmb ishld`"是后端判断。做错不会被 verifier 抓到、不会稳定复现,只在特定微架构上偶发。

**runtime system** 是离"执行语义"最近的东西,但它不是后端。分工是:

```
backend 生成:  .eh_frame / LSDA / stack map / 调用 __cxa_throw
runtime 执行:  读这些表,真正做展开、扫栈、回收
```

两者是**契约的两端**,契约内容由动态语义规定。

## 五、两层语义如何互动

### 5.1 静态语义为动态语义**收窄**行为集合

这是类型系统的根本价值。一个良好的类型系统能保证:**类型正确的程序不会出现某一类动态语义错误**。这就是 **type soundness** 定理,经典表述:

$$\text{Progress} + \text{Preservation} \;\Rightarrow\; \text{"well-typed programs don't go wrong"}$$

- **Progress**:良类型的项要么是值,要么能继续走一步(不会卡死在无规则可用的状态);
- **Preservation**(subject reduction):走一步之后类型不变。

两者归纳组合,得出良类型程序永不进入"未定义状态"。

**这是静态语义与动态语义之间唯一真正严谨的桥。** 它的形式是:对操作语义做归纳,证明类型规则是其不变式。注意这需要**同时**有两套语义的形式定义——这也是为什么 WebAssembly 的规范同时给了小步语义和机器检查的类型安全证明。

### 5.2 不同语言在这条桥上的位置

| 语言 | 静态语义强度 | 动态语义 UB 量 | 策略 |
|---|---|---|---|
| **C** | 弱(类型可随意转换) | 极多(200+ 条) | 把负担全交给程序员,换优化空间 |
| **C++** | 中(RAII、模板、concepts) | 极多 | 同上,但用抽象降低出错率 |
| **Java** | 中强 | 极少(数组越界抛异常,溢出必回绕) | 动态检查兜底,牺牲部分性能 |
| **Rust** | **强**(所有权+借用+生命周期) | safe 代码为零,`unsafe` 内有 | **用静态语义消灭 UB** |
| **Haskell/ML** | 强(HM 类型推导) | 极少 | 纯函数式 + 强类型 |
| **WebAssembly** | 强(形式化类型系统) | **零** | 规范级保证 |

**Rust 是最清晰的案例**:它把 C 里属于动态语义 UB 的一大类错误(use-after-free、data race、iterator invalidation),通过所有权和借用检查**提升到静态语义层**,从"运行时未定义"变成"编译期拒绝"。代价是学习曲线和表达力限制(有些正确程序被拒绝,因为检查器是保守近似)。

这揭示了一个普遍权衡:

```
静态语义强  →  更多错误在编译期拒绝,但保守近似会拒绝部分正确程序
动态语义严  →  更多行为被承诺,程序员易推理,但优化空间小
```

C 选择"静态弱 + 动态松",换取最大优化自由;Rust 选择"静态强 + 动态严",换取安全;两者在同一光谱的两端。

### 5.3 一个有趣的对称:两层都需要"坏值"

前面提到过,但值得正式对照:

| | 静态语义 | 动态语义 |
|---|---|---|
| 坏值 | `ErrorType` / poisoned symbol | `poison` / `undef` |
| 产生时机 | 名字查找失败、类型检查失败 | `add nsw` 溢出、读未初始化内存 |
| 传播规则 | 吸收性:涉及它的检查静默通过 | 吸收性:大多数指令对 poison 操作数产生 poison |
| 目的 | 避免级联错误噪音,一次报多个真错误 | 允许优化器假定 UB 不发生,同时避免立即 UB |
| 如何"洗掉" | 不洗,到此为止 | `freeze` 指令:poison → 任意确定值 |

**两层语义面对同一个工程问题(值已无意义之后如何继续),给出了同形的解法。** 这不是巧合——两者都是"在格上传播信息"的系统,都需要一个顶/底元素来表示"无信息"。

### 5.4 优化合法性的完整判据

现在可以把这件事完整说清。一个 pass 合法,当且仅当:

$$\forall P \text{ 良构}: \quad \llbracket \text{pass}(P) \rrbracket \subseteq \llbracket P \rrbracket$$

三个要点:

1. **前提是"良构"** —— 静态语义已经筛过一轮。pass 不需要处理类型错误的 IR。
2. **判据是动态语义** —— 不是"IR 文本相似",不是"看起来等价"。
3. **方向是 $\subseteq$** —— 允许收窄,不允许扩张。

这就是 **Alive2** 在做的事:把一条 LLVM 优化前后的 IR 编码成 SMT 公式,证明 refinement 成立。回 UNSAT 即正确;回 SAT 则给出**具体反例输入**,直接定位 bug。

而 **EDA 的逻辑等价性检查(LEC)** 回答同一个问题形状——"RTL 与综合后网表功能一致吗"。组合电路无状态,退化成**布尔函数相等**,是这个问题最简形式。两边都归约到 SAT/SMT,因为两边都在问:**这个变换保不保语义?**

## 六、六个常见误解

**1. "静态/动态语义 = 静态/动态类型"**

完全无关的两套术语。C 是静态类型,有复杂的动态语义;Python 是动态类型,其动态语义同样是"程序运行起来意味着什么"。两个轴正交。

**2. "动态语义只在运行期起作用"**

恰恰相反,它**在编译期被大量消耗**。常量折叠、循环删除、UB 推理全发生在编译期——编译器读的就是动态语义。

**3. "动态语义 = 运行时行为"**

动态语义是**规范**(行为的集合),运行时行为是**一次具体执行**(集合里的一个元素)。一次执行没崩溃,不代表程序没 UB。

**4. "UB 意味着会崩溃"**

UB 最危险的表现恰恰是**不崩溃**:安静地产生错误结果,或在某个优化级别下突然改变行为。崩溃反而是运气好。

**5. "编译通过 = 程序正确"**

编译通过只覆盖到静态语义。前面四行例子里,`a[10] = 1` 语法合法、静态语义合法,但是动态语义层面的 UB。**静态语义能保证的性质有上限,这个上限由 Rice 定理决定**:任何非平凡的程序语义性质都不可判定。

**6. "动态语义属于后端"**

范畴错误。前端/中端/后端是**阶段划分**(谁在什么时候做什么),静态/动态语义是**规范划分**(程序是什么意思)。动态语义不是某阶段执行的工作,而是所有阶段必须遵守的契约。后端只是**独占了 IR→ISA 这一段精化的义务**。

## 七、编译器为什么必须在意

因为**动态语义就是优化的合法性判据**。每个 pass 的正确性条件都可以写成同一个式子:

$$\llbracket P_{\text{after}} \rrbracket \;\subseteq\; \llbracket P_{\text{before}} \rrbracket$$

即**精化(refinement)**:变换后的行为集合必须是变换前的子集。

### 为什么是 ⊆ 而不是 =

这个细节很关键。编译器被允许**收窄**非确定性,但不允许**产生**原本不允许的行为。

```c
f(g(), h());    // C/C++17 之前:g、h 的调用顺序未指定
```

源程序的行为集合里有两个元素(先 `g` 或先 `h`)。编译器选定一个顺序生成代码,行为集合变成单元素——这是**真子集**,合法。反过来,如果编译器生成的代码在某些输入下产生了源程序不允许的结果,那就是 miscompilation。

LLVM IR 里这件事体现得特别直接。`poison` 和 `undef` 构成一个精化偏序:

$$\texttt{poison} \;\sqsubseteq\; \texttt{undef} \;\sqsubseteq\; \text{任意具体值}$$

一个产生 `poison` 的指令可以被替换成任何东西(因为 poison 的行为集合是全集),但反过来不行。`freeze` 指令的作用正是**把这个偏序往下压一级**:把 poison/undef 固定成某个具体但不确定的值,从而阻止后续进一步利用它的自由度。Alive2 验证的就是这个 $\sqsubseteq$ 关系是否成立,而不是严格相等。

### 每个优化背后都有一条语义许可

这是最实用的视角:**优化不是"技巧",而是在兑现语义给的授权**。

| 优化 | 依赖哪条动态语义 | 语义不成立会怎样 |
|---|---|---|
| 常量折叠 | 算术行为确定、可在编译期复现 | 浮点舍入模式可变时就不能折叠 |
| 死代码消除 | 无副作用的计算不可观察 | 有 `volatile` 或 I/O 时失效 |
| **删除空循环** | C++ 的 forward progress 保证(无副作用无限循环是 UB) | 在 C 里 `while(1);` 合法,**不能删** |
| mem2reg / 寄存器提升 | 非 `volatile`、地址未逃逸 | 取过地址并传出去就不能提升 |
| 循环不变量外提 (LICM) | 该表达式无副作用、不抛异常、不触发 UB | 含除法时要先证明除数非零 |
| 向量化 / 循环交换 | 迭代间无依赖 ← **无别名** ← provenance / `noalias` | 别名分析保守时直接放弃 |
| 强度削弱、归纳变量重写 | `nsw` 保证无有符号溢出 | 没有 `nsw` 就只能按回绕语义处理 |
| 跨指令重排内存访问 | 非原子、无数据竞争 | 并发下必须按内存序约束 |
| 尾调用优化 | 栈帧不可观察 | 若语言暴露栈(如某些调试/反射场景)则不行 |

**第三行值得单独看**:同一段 `while(1);`,C 里必须保留(可能是嵌入式的死循环等中断),C++ 里可以删(标准允许编译器假定循环终止)。**同样的代码、同样的编译器后端,因为语言的动态语义不同,优化结论相反。** 这是"动态语义驱动实现"最干净的证据。

### UB 是优化的燃料

把前面"UB = 行为集合是全集"的定义套进 refinement 公式:若 $\llbracket P_{\text{before}} \rrbracket$ 在某条路径上是全集,那么**任何** $P_{\text{after}}$ 在那条路径上都满足 $\subseteq$。所以:

> **编译器遇到 UB,可以生成任意代码——这不是越权,而是精化条件被平凡满足。**

```c
int f(int *p) {
    int x = *p;        // 解引用 → 若 p 为空则 UB
    if (p == NULL)     // 所以此处 p 必非空
        return -1;
    return x;
}
```

编译器的推理链是:第 2 行若 `p == NULL` 则已 UB,该路径无任何保证;因此可以假定到达第 3 行时 `p != NULL`,把判断整个删掉。

这条推理**不是编译器在"找茬"**,而是它在做一个完全标准的逻辑步骤:从"这条路径无约束"推出"这条路径可以当作不存在"。所有"编译器恶意利用 UB"的抱怨,本质上都是在抱怨语言给的行为集合太大。

### 这里有一条根本的设计权衡

$$
\text{语义承诺多} \;\longleftrightarrow\; \text{优化空间小}
$$

| 语言 | 位置 | 后果 |
|---|---|---|
| C / C++ | 承诺极少(约 200 条 UB) | 优化空间最大,踩坑风险最高 |
| Rust (safe) | 承诺多,但靠**静态排除**而非运行时检查 | 两头兼顾,代价是类型系统复杂 |
| Java | 承诺多(越界抛异常、溢出回绕) | 推理容易,部分优化被堵死 |
| WebAssembly | 零 UB | 沙箱安全,但抽象层次低 |

Rust 的位置值得注意:它没有选"少承诺"也没有选"运行时检查",而是用借用检查**在编译期证明某些 UB 不可能发生**,从而既能承诺又不丢优化空间。这是过去二十年语言设计上最实质的一步。

### as-if 规则的边界

回到第三节的抽象机。as-if 给了编译器巨大自由,但它的边界恰恰由"什么算可观察"划定:

| 可观察(不能动) | 不可观察(随便动) |
|---|---|
| I/O、程序退出状态 | 执行了多少条指令 |
| `volatile` 访问(次数、顺序都不能变) | 用了多少栈、哪些寄存器 |
| 原子操作与同步 | 中间临时值 |
| 异常终止的事实 | 缓存命中率、分支预测 |

所以"优化改变了性能特征"从来不是正确性问题,"优化改变了 `volatile` 写的次数"才是。侧信道攻击之所以棘手,正是因为它观测的恰好是 as-if 规则声明"不可观察"的那一列——**语义层面没有被破坏,但现实世界里信息泄漏了**。这是抽象机模型与物理机器之间的真实裂缝。

## 八、几个常见误解

### 误解 1:"动态语义 = 运行时行为"

不是。**动态语义是规范(一个集合),运行时行为是一次具体执行(集合里的一个元素)。**

$$\text{一次执行} \in \llbracket P \rrbracket$$

直接后果:**一次执行没出错,完全不能说明程序没 UB。** 程序触发了 UB,意味着 $\llbracket P \rrbracket$ 变成全集,而"恰好得到你期望的结果"也在全集里。

### 误解 2:"动态语义只在运行期起作用"

恰恰相反,它**在编译期就被大量消耗**。常量折叠、循环删除、UB 推理、别名分析——这些全部发生在编译期,而编译器读的就是动态语义规范。

一个有用的说法是:**动态语义是编译期的输入,运行时行为是它的输出。**

### 误解 3:"动态语义 = 动态类型"

两套完全正交的术语。

| | 静态类型 | 动态类型 |
|---|---|---|
| **有复杂动态语义** | C、C++、Rust | Python、JavaScript |
| **动态语义较简单** | Java(相对) | Lua |

C 是彻底的静态类型语言,却有一份出了名复杂的动态语义。"静态/动态语义"说的是**规范的哪一半**,"静态/动态类型"说的是**类型检查在什么时候**。

### 误解 4:"UB 意味着会崩溃"

UB 最危险的表现恰恰是**不崩溃**。

```
崩溃        ← 运气好,立刻暴露
静默错误     ← 常态,生产环境里慢慢发酵
在 -O0 下正常、-O2 下出错  ← 典型,被误判为"编译器 bug"
换个编译器版本后出错  ← 升级 toolchain 时集中爆发
```

安全漏洞的来源主要是第二类——程序继续跑,但内存被写坏了。

### 误解 5:"UB 的影响是局部的"

这是最反直觉的一条。标准的措辞是 "**no requirements on the behavior of the program**" ——注意是 program,不是 statement。UB 的影响**不受时间和空间限制**,包括**向前传播到 UB 发生之前**:

```c
#include <stdio.h>
int main(void) {
    printf("before\n");
    int *p = NULL;
    return *p;              // UB
}
```

编译器完全可以推理:`main` 必然执行到 UB,所以整个 `main` 的行为无约束,于是连 `printf` 都可以删掉。这叫 **time-travel UB**。

更实际的例子:

```c
void f(int n) {
    int a[10];
    for (int i = 0; i <= n; i++)   // n >= 10 时越界
        a[i] = i;
    if (n < 10)                    // 编译器:既然循环没越界,必有 n < 10
        g();                       // → 条件恒真,删掉判断
}
```

**UB 的推理可以反向流动**,把"后面不能出问题"倒推成"前面的条件必然成立"。这就是为什么"我把危险代码放在出错之后就没事了"是错的。

### 误解 6:"unspecified、implementation-defined、UB 差不多"

三者在行为集合上是**量级不同**的东西:

| 类别 | 集合大小 | 实现的义务 | 例子 |
|---|---|---|---|
| **unspecified** | 有限的几种 | 任选其一,**无需文档化**,可以每次不同 | 实参求值顺序 |
| **implementation-defined** | 有限的几种 | 选一种并**必须文档化** | `int` 的位宽、右移是否算术 |
| **undefined** | **全集** | 无任何义务 | 有符号溢出、越界 |
| **locale-specific** | 由 locale 决定 | 文档化 | `isalpha` 的行为 |

前两类是**可移植性问题**(换平台结果可能不同,但每个平台上程序仍有意义);第三类是**正确性问题**(程序根本没有意义)。把它们混为一谈会导致严重的风险误判。

### 误解 7:"编译器利用 UB 是在故意为难人"

编译器里没有一个叫 "exploit UB" 的 pass。实际发生的是:

```
别名分析 / 值域分析 / 支配关系推导
        ↓  各自基于语义做出假设
某些路径被推导为"不可达"或"条件恒真"
        ↓
常规的死代码消除、条件简化照常工作
```

每一步都是局部的、机械的、完全标准的。"UB 被利用"是这些**独立正确的推理叠加**之后的涌现结果。没有人设计它,它就是逻辑闭合的后果。

### 误解 8:"开 -O0 就安全了"

`-O0` 只是减少了编译器利用 UB 的机会,**不会让 UB 变成有定义**。程序仍然是错的,只是暂时没显形。真正的做法是用 UBSan/ASan 把它找出来,而不是靠降低优化等级掩盖。

### 误解 9:"动态语义是确定的、权威的、不会有错"

ISO 标准也是人写的工程文档。前面提过两个活例子:

- **指针 provenance** 在 C 里直到近几年才有正式提案(TS 6010),此前几十年都是"大家心照不宣";
- **`relaxed` 原子的 OOTA 问题**至今无解,C++ 内存模型在这一角落是公认不健全的。

所以遇到特别刁钻的语义问题,正确的反应不是"标准一定说清楚了,是我没找到",而是"这可能真的还没定论"。

## 九、小结:动态语义是一份关于集合的契约

把一到八收束成一句:

> **动态语义 = 语言对「合法程序运行起来会发生什么」的全部承诺,其内容是一个可观察行为的集合。**

三个支点:

| 概念 | 作用 |
|---|---|
| **抽象机** | 定义"标准答案"——程序在理想机器上的行为 |
| **as-if 规则** | 定义"自由度"——实现只需复现可观察行为 |
| **行为集合** | 定义"承诺强度"——集合越小承诺越强,UB 是集合等于全集 |

而整个编译器的工作,就是在这个集合内部做选择:

$$
\text{源码} \;\sqsupseteq\; \text{AST} \;\sqsupseteq\; \text{LLVM IR} \;\sqsupseteq\; \text{MIR} \;\sqsupseteq\; \text{机器码}
$$

每一步都是精化,每一步都不许越出上一层允许的集合。这就是前面讨论过的"**动态语义不属于 backend,而是贯穿所有阶段的契约**"的精确含义。

同时,这个集合观也统一了后面要讲的几块难题:

- **provenance**(第十节)—— 指针的行为集合不只由地址决定,还由来源决定;
- **并发**(第十一节)—— 集合因交错而组合爆炸,SC-DRF 是把它压回直觉的那条定理;
- **检测工具**(第十二节)—— 动态工具采样集合里的点,静态工具过近似整个集合;
- **跨语言对比**(第十三节)—— 不同语言只是在"集合多大"这条轴上选了不同位置。

接下来就从最硬的那块开始:**provenance**。

# 续:动态语义里最难的几块

前面把框架搭完了。但真正让人栽跟头的,是框架里几个至今仍在演进的角落。下面挑三块最硬的讲——它们也正好是 LLVM 和 C/C++ 标准委员会现在还在吵的东西。

---

## 十、指针不只是地址:provenance

这是**当前最棘手的动态语义难题**,而且直接影响前面讨论的优化合法性。

### 问题现场

```c
int x = 1, y = 2;
int *p = &x + 1;          // 指向 x 的"尾后"
int *q = &y;
if ((uintptr_t)p == (uintptr_t)q) {
    *p = 42;              // 合法吗?
    printf("%d\n", y);    // 打印 42 还是 2?
}
```

假设编译器恰好把 `x`、`y` 相邻摆放,`p` 和 `q` 的**数值相同**。那 `*p = 42` 能改到 `y` 吗?

- 从"指针就是地址"的朴素模型看:能,因为地址一样。
- 从 C 标准看:**不能**。`p` 的"来源"是 `x`,它只被授权访问 `x` 这个对象;`&x + 1` 只允许用于比较,不允许解引用。

所以**指针的语义值 ≠ 它的数值**。完整的指针值是一个二元组:

$$\text{ptr} = (\text{provenance},\ \text{address})$$

**provenance(来源/出处)** 记录"这个指针被授权访问哪块内存"。它是编译期的语义概念,在运行时**不存在任何表示**——寄存器里只有 64 位地址。

### 为什么必须引入这个概念

因为没有它,下面这类优化全部非法:

```c
void f(int *restrict a, int *restrict b) {
    *a = 1;
    *b = 2;
    g(*a);   // 能不能复用寄存器里的 1?
}
```

如果任意两个指针都可能别名,编译器必须在每次写之后重新加载——**所有基于别名分析的优化都死掉**。LLVM 的 `TBAA`(type-based alias analysis)、`noalias`、`inbounds` 全都建立在 provenance 之上。

### LLVM 这边的具体表现

| LLVM 构造 | provenance 含义 |
|---|---|
| `getelementptr inbounds` | 结果必须仍在同一个分配对象内,否则 **poison** |
| `noalias`(对应 `restrict`) | 该指针的 provenance 与其他参数不交 |
| `ptrtoint` → `inttoptr` 往返 | **语义断裂点**——provenance 是否保留至今无定论 |
| `!tbaa` 元数据 | 把源语言的类型别名规则编码进 IR |

`ptrtoint`/`inttoptr` 往返是真正的开放问题:

```llvm
%i = ptrtoint ptr %p to i64
%q = inttoptr i64 %i to ptr
store i32 42, ptr %q        ; %q 继承了 %p 的 provenance 吗?
```

- 若说"继承",则整数运算也得携带 provenance,优化器对整数的所有变换都要重新审查;
- 若说"不继承",则大量真实代码(指针标记、哈希表、GC)变成 UB。

LLVM 目前的事实状态是**两头不靠**——优化器有些 pass 假定继承,有些假定不继承,于是出现过真实的 miscompilation。这就是为什么有 `-fno-strict-aliasing` 这种"关掉一部分动态语义"的开关。

### 标准侧的进展

C 标准委员会有 **TS 6010 / N2577 "Pointer provenance"** 提案,试图把 provenance 正式写进语义。Rust 侧更激进:**Strict Provenance** API(`ptr::addr()`、`ptr::with_addr()`、`expose_provenance()`)显式把"取地址数值"和"重建可用指针"分成两个操作,让 provenance 在类型层面可追踪。

**这是动态语义正在被"补写"的活例子**:语言用了五十年,核心概念才刚被形式化。

## 十一、并发:动态语义最容易不健全的地方

单线程语义已经难,并发更甚——因为行为集合会**组合爆炸**。

### 数据竞争的两种处理哲学

| 语言 | 数据竞争的语义 |
|---|---|
| **C / C++** | **UB**。整个程序失去所有保证 |
| **Java** | 良定义但"奇怪":可能看到撕裂值,但不破坏内存安全,不能伪造引用 |
| **Rust** | 安全代码里**静态排除**(借用检查 + `Send`/`Sync`) |
| **Go** | 未定义结果,但 runtime 不崩(除 map 竞争会主动 panic) |

C++ 选 UB 是为了性能:一旦承诺"竞争有定义",编译器就不能自由地把变量提到寄存器、不能重排非原子访问。Java 选"有界的奇怪"是为了安全性:它必须保证**沙箱不可被突破**,所以不能让竞争导致任意行为。

这是同一个权衡的两端——**语义承诺少 ↔ 优化空间大**,前面说过。

### SC-DRF:整套内存模型的核心定理

C++11 内存模型的根本承诺是 **SC-DRF(Sequential Consistency for Data-Race-Free programs)**:

> **若程序无数据竞争,则其行为与"所有操作存在一个全局顺序"一致。**

这条承诺的妙处是:**绝大多数程序员不需要理解弱内存模型**。只要用锁、或者全用 `seq_cst` 原子量,就能按"顺序一致"的直觉推理。弱序的复杂性只在你主动用 `relaxed`/`acquire`/`release` 时才暴露出来。

### `memory_order` 各级的语义内容

| 序 | 承诺 | 典型降级(ARMv8) |
|---|---|---|
| `relaxed` | 仅保证**该变量**自身的修改顺序(modification order)一致 | `ldr` / `str` |
| `acquire` | 本次读之后的操作不能提前到它之前 | `ldar` |
| `release` | 本次写之前的操作不能延后到它之后 | `stlr` |
| `acq_rel` | 两者兼有 | `ldar`/`stlr` |
| `seq_cst` | 全局单一顺序 | `ldar`/`stlr` + 必要屏障 |

注意这张表的两列:**左列是动态语义,右列是 backend 的实现义务**。前面那轮讨论的"backend 独占的语义义务"在这里体现得最清楚——语义说 `acquire`,backend 必须挑出在该微架构上刚好够强的指令。挑弱了是 miscompile,挑强了只是慢。

### 一个至今没解决的洞:OOTA

```c
// 线程 1                    // 线程 2
r1 = x.load(relaxed);        r2 = y.load(relaxed);
if (r1 == 42)                if (r2 == 42)
    y.store(42, relaxed);        x.store(42, relaxed);
```

`x`、`y` 初值为 0。直觉上 42 不可能出现——它需要自己证明自己。但 C++11 内存模型的形式定义**无法排除** `r1 == r2 == 42` 这个结果,因为它只约束读写之间的依赖关系,而"控制依赖"可以被编译器优化掉。

这叫 **out-of-thin-air (OOTA)** 问题。公认的结论是:**C/C++ 的 `relaxed` 语义目前是不健全的(unsound)** ——它要么太弱(允许 OOTA),要么太强(禁止真实的硬件优化)。学界有 Promising Semantics、Weakestmo 等候选方案,尚无定论。

这是个重要的提醒:**连 ISO 标准的动态语义也可能有洞。** 它不是从天上掉下来的真理,而是人写的、在修的工程文档。

## 十二、UB 的分类与检测:理论落到工具

既然 UB = 行为集合变全集,实践上就需要**把它抓出来**。

### UB 的六大类

| 类别 | 例子 | 为什么是 UB |
|---|---|---|
| **空间内存错误** | 越界读写、野指针、栈溢出 | 访问未分配给该对象的内存 |
| **时间内存错误** | use-after-free、double-free、悬垂引用 | 对象生命周期已结束 |
| **算术** | 有符号溢出、除零、移位 ≥ 位宽 | 抽象机未定义结果 |
| **类型 / 别名** | strict aliasing 违反、错误 `reinterpret_cast`、未初始化读 | 违反 provenance 或类型假设 |
| **并发** | 数据竞争、死锁(后者不是 UB)、原子性误用 | 无 happens-before 约束 |
| **契约** | 库函数前置条件违反(`memcpy` 重叠、`strlen` 非终止串) | 文档明确要求 |

### 检测工具与它们的能力边界

| 工具 | 抓什么 | 原理 | 根本局限 |
|---|---|---|---|
| **ASan** | 空间+时间内存错误 | 红区 + 影子内存 + 隔离释放 | **只覆盖实际走过的路径** |
| **UBSan** | 算术、对齐、类型混淆、空指针 | 编译期插桩检查 | 同上;部分检查有运行时开销 |
| **TSan** | 数据竞争 | happens-before 向量时钟 | 同上;需要竞争真的交错发生 |
| **MSan** | 未初始化读 | 位级影子传播 | 需全程序插桩(含 libc) |
| **Valgrind** | 内存错误 | 动态二进制翻译 | 慢 10–50×,不需重编译 |
| **Miri** | Rust UB(含 provenance、别名) | **直接解释 MIR 的操作语义** | 慢;不支持所有 FFI |
| **KLEE** | 全路径 | 符号执行 + SMT | **路径爆炸** |
| **Astrée / Frama-C** | 全输入保证无 UB | **抽象解释**(不动点) | **假警报**;需人工标注 |

这张表有一条贯穿的分界线:

$$
\underbrace{\text{ASan/TSan/Miri}}_{\text{动态:无假警报,但不完备}}
\quad\text{vs.}\quad
\underbrace{\text{Astrée/Frama-C}}_{\text{静态:完备,但有假警报}}
$$

**动态检测**只能说"我在这条路径上没发现问题";**静态分析**(抽象解释)能说"在所有输入下都没有 UB",代价是必须接受假警报,因为它在格上做的是**over-approximation**——这正好接回前面讲指称语义时提到的不动点。

值得单独点出 **Miri**:它不是插桩,而是**直接实现 Rust MIR 的小步操作语义并逐步解释执行**。所以它能抓到连 ASan 都看不见的东西——比如 Stacked Borrows 别名规则违反、provenance 误用。**这是"形式语义直接变成工具"的最佳案例**:有了可执行的操作语义,检测器几乎是免费的。对比之下,C/C++ 没有官方形式语义,所以只能靠一堆各管一块的 sanitizer 拼凑。

## 十三、跨语言对比:同一道题的不同答案

| 维度 | C / C++ | Rust (safe) | Java | Go | WebAssembly |
|---|---|---|---|---|---|
| 有符号溢出 | **UB** | panic (debug) / 回绕 (release) | 回绕 | 回绕 | 回绕 |
| 数组越界 | **UB** | **panic** | `ArrayIndexOutOfBoundsException` | panic | trap |
| use-after-free | **UB** | 静态排除 | GC 排除 | GC 排除 | 不适用(线性内存) |
| 数据竞争 | **UB** | 静态排除 | 良定义但弱 | 未定义结果,不崩 | 有明确模型 |
| 未初始化读 | **UB** | 静态排除 | 零初始化 | 零初始化 | 零初始化 |
| 规范形式 | 散文(ISO) | 散文 + Miri 可执行语义 | 散文(JLS,内存模型形式化) | 散文 | **完整小步操作语义** |
| UB 总量 | ~200 条 | `unsafe` 内才有 | 几乎为零 | 极少 | **零** |

两点值得注意:

**1. UB 清零不等于没有不确定性。** Java、Go 仍有大量**未指定行为**(哈希迭代顺序、调度顺序、`finalize` 时机)。它们把行为集合**收窄到有界**,但没有收成单点。回到那个集合视角:UB 是全集,未指定是有限集,确定行为是单元素集——**三者是程度差异,不是种类差异**。

**2. WebAssembly 是唯一做到"零 UB + 完整形式语义"的主流目标。** 代价是它的抽象层次很低(没有对象、没有指针类型,只有线性内存和数值),所以源语言的 UB 不会消失,只是**被挪到编译期**:C 的越界写在 wasm 里变成"在线性内存里写错地方",不会逃出沙箱,但也不会被抓住。**沙箱安全 ≠ 程序正确。**

## 十四、对日常工作的可操作结论

把前面这一大串收成几条能用的:

**1. "我测过没问题"不是 UB 的证据。** 动态语义规定的是**所有输入下的行为集合**;你的测试是集合里的几个点。UB 的危险性正在于它常常在某个优化级别、某个编译器版本、某个 CPU 上才显形。

**2. CI 里把 sanitizer 当编译器用。** `-fsanitize=address,undefined` 的开销通常在 2–3×,完全可以跑在 CI 上。TSan 更贵但对并发代码不可替代。这是投入产出比最高的单项工程实践。

**3. 看到 `-fno-strict-aliasing`、`-fwrapv`、`-ffast-math` 要警觉。** 这些 flag 的作用不是"调优化强度",而是**修改语言的动态语义**。前两个是**收紧**承诺(以性能换安全),后一个是**放松**承诺(以精度换性能)。知道自己在改语义,比记住 flag 名字重要。

**4. 调试"-O2 错 / -O0 对"时,先怀疑 UB,不要先怀疑编译器。** 统计上前者的概率高出两个数量级。用 UBSan 跑一遍比读汇编快得多。

**5. 写并发代码默认用 `seq_cst` 或锁。** SC-DRF 给了你顺序一致的推理环境。只有在 profile 证明确实是瓶颈、且你能说清 happens-before 链时,才下降到 `acquire`/`release`。`relaxed` 的语义连标准委员会都没完全理清(见 OOTA),不要赌自己理得清。

**6. 指针转整数要小心。** 只用于打印、哈希、对齐检查是安全的;转回去再解引用则踩在 provenance 的未决地带。Rust 的 `expose_provenance` / `with_exposed_provenance` 命名本身就是在提醒这件事。

## 十五、一张总图

把整轮讨论收束成一张结构图:

```
                语言规范(动态语义)
                        │
         ┌──────────────┼──────────────┐
         │              │              │
    行为集合的大小    抽象机 + as-if    形式化风格
         │              │              │
  UB=全集 / 未指定=有限集   优化的法律依据    操作/指称/公理
         │              │              │
         │              │              ├─ 操作 → 规范、解释器(Miri)、模拟证明(CompCert)
         │              │              ├─ 指称 → 抽象解释、数据流分析
         │              │              └─ 公理 → 契约验证 + SMT
         │              │
         │              └─ 各级 IR 各有一份语义,每步编译是 refinement
         │                     源码 ⊒ AST ⊒ LLVM IR ⊒ MIR ⊒ 机器码
         │
         └─ 检测:动态(sanitizer,无假警报不完备)
                   静态(抽象解释,完备有假警报)
                   符号(KLEE,全路径但爆炸)
```

**一句话:动态语义是一份关于"行为集合"的契约。** 集合的大小决定了程序员能推理什么、编译器能优化什么、工具能检测什么——而 UB 就是这份契约上明写着"此处不作任何承诺"的那些条款。前面聊过的一切(poison、`nsw`、Alive2、backend 内存模型、provenance、SC-DRF)都是在这同一份契约的不同角落上做工作。

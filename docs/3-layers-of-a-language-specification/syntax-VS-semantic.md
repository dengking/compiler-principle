# syntax VS semantic
front end关注点: syntax和semantic
syntax: context-free
semantic: context-sensitive

一句话:**Syntax 管"长什么样",Semantics 管"是什么意思"。** 但真正有价值的部分在于两者**在哪里分界、为什么分界、以及分界在哪里失效**——因为现实中的编译器几乎没法干净地把它们分成两层。

## 最朴素的区分

|      | Syntax(语法)            | Semantics(语义)                                                                                             |
| ---- | --------------------- | --------------------------------------------------------------------------------------------------------- |
| 关心   | 符号的**形状与排列**          | 符号的**含义与行为**                                                                                              |
| 形式工具 | BNF / EBNF、正则、上下文无关文法 | 类型系统、属性文法、操作语义、数据流分析                                                                                      |
| 判定成本 | 线性或接近线性               | 从多项式到**不可判定**                                                                                             |
| 典型实现 | lexer + parser        | Sema / 类型检查器 / verifier                                                                                   |
| 产物   | parse tree / AST      | 带类型与绑定的 AST(annotated AST)、[[front-end/architecture/symbol-table/index\|符号表]]、[[middle-end/IR/index\|IR]] |

四个层层递进的例子:

```c
int x = ;              // ① 语法错误:= 后缺表达式,CFG 直接拒绝
int x = "hello";       // ② 语法合法,类型错误(静态语义)
int x = y;             // ③ 语法合法,名字未声明(静态语义:名字解析)
int a[5]; a[10] = 1;   // ④ 语法合法、静态语义也合法 → 运行时 UB(动态语义)
```

这四行揭示了一个关键事实:**"编译通过"只覆盖到 ③。** ④ 落在静态语义的能力边界之外——它需要的是**动态语义**层面的保证,而 C 选择把它定义成 UB,也就是"不保证"。


## 三层而非两层:动态语义是独立的一层

把语义切成两半,结构才清楚:

```
Syntax            → 形状是否合法            (parser)
Static Semantics  → 编译期可判定的良构性     (Sema / 类型检查)
Dynamic Semantics → 程序运行时做什么        (语言规范定义,编译器据此优化)
```

**静态语义**包括:名字解析与作用域、类型检查与推导、可见性/访问控制、常量表达式求值、初始化顺序、借用检查(Rust)、`constexpr` 求值(C++)。它们都在编译期完成,结论是**接受或拒绝**。

**动态语义**定义的是"这段程序执行起来意味着什么"。**形式化方法**有三套经典路线:

| 方法                      | 做法                          | 典型用处                        |
| ----------------------- | --------------------------- | --------------------------- |
| **操作语义** (operational)  | 定义**状态转移规则**(小步 / 大步)       | 解释器、WebAssembly 规范、Rust MIR |
| **指称语义** (denotational) | 把程序映射成数学对象(函数)              | 理论研究、抽象解释的基础                |
| **公理语义** (axiomatic)    | Hoare 三元组 $\{P\}\,C\,\{Q\}$ | 程序验证、CompCert、契约式设计         |

**优化器真正吃的是动态语义。** 这点很重要:一个 pass 合不合法,判据不是"改完后语法还对吗",而是"改完后的**可观察行为**和改之前一致吗"。所以语义规范写得越精确,优化器能做的就越激进——这正是 LangRef 把大半篇幅花在 poison / undef / UB / `nsw` 上的原因。

## 三、分界在哪里崩塌:三个经典案例

这才是这个问题真正有意思的地方。理论上"先 parse 再查语义",实践中根本做不到。

### 1. C 的 lexer hack

```c
A * B;
```

这是**声明**(`B` 是指向 `A` 的指针)还是**表达式语句**(`A` 乘以 `B`)?答案取决于 `A` 是不是一个 `typedef` 名——而这是**符号表里的语义信息**。

所以 C 的 parser 必须在解析过程中查询符号表,把 `IDENTIFIER` 动态地重分类为 `TYPEDEF_NAME`。这就是著名的 **lexer hack**:**语法分析反向依赖语义分析**,分层被打穿。

### 2. C++ 的 most vexing parse

```cpp
Widget w(Thing());   // 这是变量定义?还是函数声明?
```

C++ 规定:**只要能解释成声明,就解释成声明**。于是这行声明了一个返回 `Widget`、接受"一个返回 `Thing` 的无参函数指针"的函数。消歧义规则本身就是语法与语义混合的产物。

更极端的是:C++ 模板实例化是**图灵完备**的,因此"这个 C++ 程序是否良构"在一般情况下**不可判定**。良构性(well-formedness)本该是编译器能回答的问题,这里它直接撞上了停机问题。

### 3. Chomsky 层级上的错位

真实编程语言属于**上下文相关**(context-sensitive)甚至更高,但没人用上下文相关文法写 parser——因为它没有高效算法。工程上的妥协是:

$$\text{用 CFG 近似} + \text{把剩下的约束塞进"语义分析"}$$

所以"什么算语法错误、什么算语义错误"在很大程度上是**实现决策**,不是本质划分。Rust 的借用检查本可以看作某种类型规则(语法性的),但它被实现成独立的 MIR 阶段分析(语义性的)。

## 四、交汇点:语法制导翻译

两者正式握手的地方是 **syntax-directed translation(语法制导翻译)**——把语义动作挂在文法产生式上:

```
expr → expr₁ '+' expr₂   { $$.type = unify($1.type, $2.type);
                           $$.code = emit(ADD, $1.place, $2.place); }
```

这就是**属性文法**:综合属性(自下而上)与继承属性(自上而下)在 AST 上流动,把语义信息沿着语法结构传播。yacc/bison 的 `{ ... }` 动作块、ANTLR 的 listener/visitor,都是这个思路的实现。

**它既不是纯语法也不是纯语义,而是"用语法结构组织语义计算"。** 现代编译器虽然很少在 parse 时直接生成代码(改为先建 AST 再多遍遍历),但这个"结构驱动语义"的模式贯穿始终——MLIR 的 pattern rewrite 本质上也是它的一个变体。

## 五、回到 LLVM:同一语义的三套语法

前面聊过"一套 IR,三种表现形式"。用 syntax/semantics 的框架看,那个结论可以说得更准:

> **内存表示、文本 `.ll`、bitcode `.bc` 是同一份语义的三种语法编码。**

| | Syntax | Semantics |
|---|---|---|
| 内存表示 | C++ 类层次、use list、uniqued 类型 | ← 同一份 |
| 文本 `.ll` | LangRef 定义的文本文法 | ← 同一份 |
| Bitcode `.bc` | 位流容器、abbreviation、VBR 编码 | ← 同一份 |

它们能**无损往返**,正是因为语义同构、只有语法不同。而 LangRef 这份文档恰好覆盖两件事:

- **Syntax 部分**:`define i32 @f(i32 %a) { ... }` 怎么写,标识符规则,类型怎么拼;
- **Semantics 部分**:`add nsw` 溢出产生 **poison** 而不是回绕,`sdiv` 除零是 **UB**,`freeze` 把 poison 变成任意确定值……

篇幅上**语义压倒性占多数**。原因很直白:语法错了,parser 会报错;语义没定义清楚,优化器会悄悄生成错误代码。

### SSA 不变量的两类

前面讨论 SSA 时列的那些约束,其实分属两边:

| 约束 | 性质 | 怎么查 |
|---|---|---|
| φ 必须在基本块头部且连续 | **语法性** | 扫一遍指令列表即可 |
| 终结指令必须且只能在块末尾 | **语法性** | 局部检查 |
| 类型必须精确匹配 | **语法性**(uniqued 后是指针比较) | 局部检查 |
| **use 必须被 def 支配** | **语义性** | 需要构造支配树 |
| φ 的每个前驱恰好一个条目 | **语义性** | 需要 CFG 结构 |

`Verifier` 两类都查,但代价差了一个数量级——这就是为什么支配关系检查只在 `-verify-each` 或 debug build 里全量跑。

## 六、为什么这个区分值得在意

### 1. 它决定你用什么工具

想检查的性质落在哪一层,直接决定技术选型:

| 性质 | 工具 |
|---|---|
| 形状合法性 | CFG + parser generator(LL/LR/PEG) |
| 类型、作用域 | 属性文法、类型系统、符号表 |
| 定值-引用、活跃性、支配 | 数据流分析、不动点迭代 |
| 变换是否保语义 | **SAT / SMT**(Alive2、LEC) |
| 任意程序性质 | 不可判定(Rice 定理) |

注意最后两行:**语法等价**是平凡的(比较两棵树),而**语义等价**需要 SMT 求解器——这正是前面讨论 Alive2 和 LEC 时的核心。Alive2 证明的从来不是"改写前后 IR 文本相同",而是"在所有输入下可观察行为相同"。

### 2. 它解释了 UB 的本质

UB 可以精确定义为:

> **语法合法、静态语义合法,但动态语义明确声明"不作保证"的程序。**

它不是 bug,是规范在语义层**主动留下的洞**,目的是换取优化空间。前面提过的 `add nsw` 溢出产生 poison、C 里有符号溢出是 UB,都是这个设计。这也是为什么"编译通过"从来不等于"程序正确"。

### 3. 它影响错误信息的质量

语法错误能精确定位(就在那个 token),而语义错误往往"案发现场"离"犯罪现场"很远:

```cpp
template<typename T> void f(T t) { t.foo(); }
f(42);   // 错误报在模板体内,但真正的问题在调用点
```

C++ 模板的错误信息臭名昭著,根源就是语义检查推迟到实例化期才发生。Concepts 的核心动机正是**把语义约束前移、变成接近语法层的可检查契约**。

## 七、一张收束表

| 维度 | Syntax | Static Semantics | Dynamic Semantics |
|---|---|---|---|
| 问什么 | 形状对吗 | 良构吗 | 跑起来干什么 |
| 谁负责 | lexer + parser | Sema / 类型检查器 | 语言规范 + 运行时 |
| 规范写法 | BNF / EBNF | 类型规则、推导规则 | 操作 / 指称 / 公理语义 |
| 失败表现 | syntax error | type error、name error | UB、panic、异常 |
| 成本 | $O(n)$ 左右 | 多项式(模板除外) | 一般不可判定 |
| 优化器是否依赖 | 否 | 部分(类型驱动) | **完全依赖** |

---

## 八、一句话总结

**Syntax 定义"什么样的字符串是合法程序",Semantics 定义"合法程序意味着什么"。** 编译器前端把前者交给 parser、把后者拆成静态与动态两段;但现实语言(C 的 typedef、C++ 的声明歧义)会让 parser 反向依赖语义,所以这条界线是工程约定而非本质鸿沟。真正的分水岭在**可判定性**:语法检查廉价且完备,语义检查从多项式一路滑向不可判定——于是才有了类型系统做近似、UB 做让步、SMT 求解器做兜底证明这一整套应对手段。

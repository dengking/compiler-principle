# 语言规范的三层
language-specification=语言规范

先消歧:"三层"在不同语境下指不同东西。

| 说法 | 三层是什么 | 常见场合 |
|---|---|---|
| **语言规范的三层** | syntax / static semantics / dynamic semantics | 语言设计、编译器前端 |
| **Chomsky 式的三层** | lexical / syntactic / semantic | 教科书讲前端流水线 |
| **实现的三层** | frontend / middle-end / backend | 编译器架构 |
| **抽象的三层** | 源语言 / IR / 目标机 | 编译流水线 |

本文讲**第一种**——它是**语言定义本身的三个部分**,由标准委员会决定,所有实现都必须遵守同一份,也是唯一一个"不随实现改变"的划分。另外三种是实现结构,换个编译器就可能重新切分;

## 三层各管什么

一个层层递进的例子:

```c
int x = ;              // ① 语法错误:= 后缺表达式,CFG 直接拒绝
int x = "hello";       // ② 语法合法,类型错误(静态语义)
int x = y;             // ③ 语法合法,名字未声明(静态语义:名字解析)
int a[5]; a[10] = 1;   // ④ 语法合法、静态语义也合法 → 运行时 UB(动态语义)
```

这四行揭示了一个关键事实:**"编译通过"只覆盖到 ③。** ④ 落在**静态语义**的能力边界之外——它需要的是**动态语义**层面的保证，把语义切成两半,结构才清楚:

$$
\underbrace{\text{Syntax}}_{\text{形状长什么样，形状是否合法(parser)}} \;\longrightarrow\;
\underbrace{\text{Static Semantics}}_{\text{编译期可判定的良构性(Sema/类型检查)}} \;\longrightarrow\;
\underbrace{\text{Dynamic Semantics}}_{\text{程序运行时做什么(语言规范定义,编译器据此优化)}}
$$


一段代码必须**依次通过**三道关:

```c
int x = ;              // ① 挡在 syntax
int x = "hello";       // ② 挡在 static semantics(类型)
int x = y;             // ③ 挡在 static semantics(名字解析)
int a[5]; a[10] = 1;   // ④ 三关全过 → dynamic semantics 说:UB
```

一句话:**Syntax 管"长什么样",Semantics 管"是什么意思"。
syntax: context-free
static semantic: context-sensitive

## 逐层展开

### 2.1 Syntax:符号的形状与排列

**管什么**:哪些字符串构成合法的程序文本。

**形式工具**:正则表达式(词法)+ 上下文无关文法 BNF/EBNF(句法)。

**判定成本**:$O(n)$ 到 $O(n^3)$,实践中基本是线性。

**产物**:parse tree,或直接是 AST。

**失败表现**:syntax error,**位置精确**——就在那个 token。

```
expr  →  expr '+' term  |  term
term  →  term '*' factor | factor
factor → NUMBER | '(' expr ')' | IDENT
```

注意这里一个常被忽略的点:**语法规则编码了结合性与优先级,但那已经带有语义意图了**。`a + b * c` 解析成 `a + (b * c)` 而不是 `(a + b) * c`,这是文法的形状决定的,但选择这个形状的理由来自**算术语义**。所以第一层也不是纯形式的。

### 2.2 Static Semantics:编译期可判定的良构性

**管什么**:形状合法的程序里,哪些是**有意义**的。

典型内容:

| 任务    | 例子                              |
| ----- | ------------------------------- |
| 名字解析  | 每个标识符绑定到哪个声明                    |
| 类型检查  | 操作数类型是否相容                       |
| 类型推导  | `auto` / `var` / Hindley–Milner |
| 可见性   | `private` / `pub` / 模块边界        |
| 常量求值  | `constexpr`、数组维度、`case` 标签      |
| 初始化检查 | Java 的 definite assignment      |
| 借用检查  | Rust 的生命周期与别名                   |

**形式工具**:类型系统(推导规则)、属性文法、符号表、数据流分析。

典型的类型规则长这样:

$$
\frac{\Gamma \vdash e_1 : \texttt{int} \qquad \Gamma \vdash e_2 : \texttt{int}}{\Gamma \vdash e_1 + e_2 : \texttt{int}}
$$

$\Gamma$ 就是**类型环境**,它在实现里的物理载体就是**符号表**。

**判定成本**:多项式居多,但有例外——**C++ 模板实例化是图灵完备的,所以"这个 C++ 程序是否良构"一般情况下不可判定**。良构性本该是编译器能回答的问题,这里它直接撞上停机问题。

**失败表现**:type error、name error。**位置可能很远**——C++ 模板的报错在实例化点和定义点之间来回跳,Concepts 的核心动机就是把语义约束前移、变成接近语法层的可检查契约。
#### 产物

带类型与绑定的 AST(annotated AST)、[[front-end/architecture/symbol-table/index|符号表]]、[[middle-end/IR/index|IR]]

### 2.3 Dynamic Semantics:程序运行起来意味着什么

**管什么**:给每个合法程序分配一组**可观察行为**。

$$\lbrack\!\lbrack \cdot \rbrack\!\rbrack : \text{Program} \longrightarrow \mathcal{P}(\text{Behavior})$$

是**集合**,不是单个行为。集合的大小就是"承诺强度":

| 集合 | 类别 |
|---|---|
| 单元素 | 行为完全确定 |
| 有限集,无需文档化 | unspecified(求值顺序) |
| 有限集,必须文档化 | implementation-defined(`int` 位宽) |
| **全集** | **undefined behavior** |

**形式工具**:三种风格——操作语义(状态转移)、指称语义(映射到数学函数)、公理语义(Hoare 三元组)。

**判定成本**:一般**不可判定**(Rice 定理:任何非平凡的语义性质都不可判定)。

**失败表现**:UB、panic、异常、崩溃——或者什么都不发生,错误静默传播。

## 三层的本质差异:可判定性

三者的真正分界不是时间(编译期/运行期),而是**可判定性**:前两层廉价且完备,第三层(动态语义)不可判定。

| 层 | 问题 | 可判定性 | 代价 |
|---|---|---|---|
| Syntax | 是否属于这个文法 | 可判定,**完备** | 线性 |
| Static Semantics | 是否良构 | 可判定(C++ 除外),**完备** | 多项式 |
| Dynamic Semantics | 程序做什么 | **不可判定** | — |

正是**动态语义不可判定**,催生了后面所有的应对手段:

```
动态语义不可判定
    ├─ 类型系统         → 用可判定的近似拦住一部分(代价:拒绝某些正确程序)
    ├─ UB               → 直接不承诺,把责任推给程序员(代价:踩坑)
    ├─ 运行时检查       → 推到运行期(代价:性能)
    ├─ 抽象解释         → 过近似(代价:假警报)
    ├─ 动态 sanitizer   → 采样路径(代价:不完备)
    └─ SMT / 定理证明   → 对具体性质做证明(代价:人力、超时)
```

**类型系统的本质就是"动态语义的可判定近似"。** 它必然要么拒绝一些实际正确的程序(不完备),要么漏掉一些错误(不可靠)。主流语言选前者:

```rust
// Rust 借用检查会拒绝这段,尽管它实际上是安全的
let mut v = vec![1, 2, 3];
let first = &v[0];
v.push(4);        // 拒绝:可变借用与不可变借用冲突
```

NLL(非词法生命周期)和 Polonius 这些工作,做的就是**让近似更精确**——在保持可判定的前提下,减少误拒。

## 分界在哪里崩塌

理论上三层顺序通过,实践中根本做不到干净分离。三个经典反例:

### 4.1 C 的 lexer hack:syntax 反向依赖 static semantics

```c
A * B;
```

这是**声明**(`B` 是 `A*`)还是**表达式语句**(`A` 乘 `B`)?取决于 `A` 是不是 typedef 名——而这是**符号表里的信息**。

于是 C 的 parser 必须在解析途中查符号表,把 `IDENTIFIER` 动态重分类为 `TYPEDEF_NAME`。**第一层调用了第二层的数据。**

Clang 的做法稍干净些:lexer 保持纯净,由 parser 调 `Sema::ClassifyName` 把 token 原地标注成 `annot_typename`,耦合上移到 parser↔Sema 之间。但分层仍然被打穿了。

### 4.2 C++ 的 most vexing parse

```cpp
Widget w(Thing());   // 变量定义?还是函数声明?
```

C++ 规定:**只要能解释成声明,就解释成声明**。于是这行声明了一个函数。消歧规则本身就是语法与语义混合的产物。

### 4.3 Chomsky 层级上的错位

真实语言是**上下文相关**甚至更强的,但没人用上下文相关文法写 parser——它没有高效算法。工程妥协是:

$$\text{用 CFG 近似} \;+\; \text{把剩下的约束塞进"语义分析"}$$

**所以"什么算语法错误、什么算语义错误"在相当程度上是实现决策,不是本质划分。** Rust 的借用检查本可以看作某种类型规则(语法性的),实际被实现成独立的 MIR 阶段分析(语义性的)。

## 三层与编译器阶段的关系

这是上一轮讨论过的问题,这里给出完整对照:

```
              frontend    middle-end    backend    runtime
syntax          ■            ·             ·          ·
static sem.     ■            ·             ·          ·
dynamic sem.    ■            ■             ■          ■     ← 贯穿
```

**前两层几乎只落在 frontend**,是**阶段性的工作**:做完就结束,结论是接受或拒绝。

**第三层横贯所有阶段**,不是工作而是**契约**:每一级 IR 都有自己的一份动态语义,编译的每一步都是相邻两份之间的精化。

$$\text{源码} \;\sqsupseteq\; \text{AST} \;\sqsupseteq\; \text{LLVM IR} \;\sqsupseteq\; \text{MIR} \;\sqsupseteq\; \text{机器码}$$

所以"动态语义属于 backend 吗"是个范畴错误——backend 只是**负责其中一段精化**(IR 语义 → ISA 语义),并因此独占一批义务:内存模型降级、浮点模式、ABI、异常表、`volatile`。

## 每层在工具链里的物化

| 层                 | 核心数据结构                 | 代表工具                          | 检查者          |
| ----------------- | ---------------------- | ----------------------------- | ------------ |
| Syntax            | token 流、parse tree、AST | yacc/bison、ANTLR、tree-sitter  | parser       |
| Static Semantics  | **符号表** + 类型表 + CFG    | Clang Sema、rustc HIR/类型检查     | type checker |
| Dynamic Semantics | IR + 语义规范              | LangRef、Alive2、Miri、sanitizer | verifier + 人 |

### 相等/等价 
有意思的是**三层的"相等"是三种不同的东西**:

| 层 | 什么叫相等 | 怎么判 |
|---|---|---|
| Syntax | 两棵 AST 结构相同 | 树遍历,平凡 |
| Static Semantics | 两个类型相同 | **uniquing 后变成指针比较** |
| Dynamic Semantics | 两个程序行为等价 | **SMT 求解器**(Alive2、LEC) |
**语义等价**需要 SAT/SMT 求解器——Alive2 和 LEC。Alive2 证明的从来不是"改写前后 IR 文本相同",而是"在所有输入下可观察行为相同"。

从"遍历树"到"指针比较"到"调 SAT 求解器",难度跨了三个数量级。这也是为什么编译器能廉价地验证 SSA 的语法不变量(φ 在块首、终结指令在块尾),却只能在专门工具里验证支配关系和语义等价。

## 跨语言:三层边界的不同划法

同一个"数组越界"问题,五种语言放在三层的不同位置:

| 语言 | 越界检查落在哪层 | 代价 |
|---|---|---|
| C / C++ | **动态语义(UB)** | 零开销,零保证 |
| Java / Go | **动态语义(有定义:抛异常/panic)** | 运行时检查开销 |
| Rust | 动态语义(panic),但**索引以外的别名错误在静态层排除** | 部分开销 + 类型系统复杂度 |
| 依赖类型语言(Idris、F*) | **静态语义**——必须在编译期证明 $i < n$ | 程序员要写证明 |
| ATS / Dafny | 静态语义 + SMT 自动证明 | 需要不变式标注 |

这张表揭示了语言设计的核心权衡:

$$
\text{往上搬(静态化)} \;\Rightarrow\; \text{保证更强,表达更累}
$$
$$
\text{往下放(动态化)} \;\Rightarrow\; \text{写得自由,保证更弱}
$$

## 三层上的"完备性"分别意味着什么

最后一个值得澄清的点,三层各有自己的完备性概念:

| 层 | 完备性指什么 |
|---|---|
| Syntax | 文法恰好生成意图中的语言,无歧义 |
| Static Semantics | **Soundness**:类型检查通过 ⇒ 不会发生某类错误<br>**Completeness**:不发生该类错误 ⇒ 能通过检查 |
| Dynamic Semantics | 规范本身无矛盾、覆盖所有情形 |

类型系统的著名口号 "**well-typed programs don't go wrong**" 说的就是 soundness。而它的表述方式恰好把三层串起来:

$$
\underbrace{\text{通过静态语义检查}}_{\text{第二层}} \;\Longrightarrow\; \underbrace{\text{动态语义中不出现 stuck state}}_{\text{第三层}}
$$

这个定理的标准证法是 **progress + preservation**:
- **Progress**:良类型的项要么是值,要么能继续走一步(不会卡住);
- **Preservation**:走一步之后类型不变。

两者都需要先有**操作语义**才能表述——所以**第二层的正确性定理,必须用第三层的语言来写**。这就是为什么严肃的语言设计必须三层一起做,不能只写语法和类型规则。

而第三层自己也可能不完备:前面提过 C++ `relaxed` 原子的 OOTA 问题,就是动态语义规范本身有洞的实例。

## 总表

|               | Syntax         | Static Semantics | Dynamic Semantics |
| ------------- | -------------- | ---------------- | ----------------- |
| **问题**        | 形状对吗           | 良构吗              | 跑起来干什么            |
| **形式工具**/规范写法 | 正则 + CFG       | 类型规则、属性文法、数据流    | 操作/指称/公理语义        |
| **核心结构**      | AST            | 符号表 + 类型表        | IR + 行为集合         |
| **可判定**       | 是,完备           | 是(C++ 除外),完备     | **否**(一般不可判定)     |
| **成本**        | $O(n)$         | 多项式(C++模板除外)     | —                 |
| **失败表现**      | syntax error   | type error       | UB / panic / 静默错误 |
| **实现落点**/谁负责  | lexer + parser | Sema/类型检查器       | 贯穿全流程(语言规范 + 运行时) |
| **验证手段**      | 树比较            | 指针比较             | **SMT 求解**        |
| **谁定义**       | 语言标准           | 语言标准             | 语言标准              |
| **演化趋势**      | 稳定             | **持续膨胀**         | **持续收缩(UB 减少)**   |
| 优化器是否依赖       | 否              | 部分(类型驱动)         | **完全依赖**          |

## 趋势

整个语言演化史可以概括为**责任在三层之间的迁移**，而语言设计的历史,就是**不断把责任从第三层往第二层搬**的历史——从 C 的两百条 UB,到 Rust 用借用检查静态排除内存错误,再到依赖类型把功能正确性也纳入编译期。每往上搬一层,保证更强,写起来也更累。

```
1970s  C:         几乎什么都往动态层扔(UB 约 200 条)
1990s  Java:      把内存错误搬到运行时检查(UB → 异常)
2010s  Rust:      把内存错误搬到静态层(运行时检查 → 编译错误)
2020s  Wasm:      动态层零 UB(但抽象层次低)
 ?     依赖类型:  把功能正确性也搬到静态层
```

**一个关键观察**:静态语义的内容在**大幅膨胀**。

```
C (1972)      类型 + 作用域
Java (1995)   + definite assignment + 异常检查 + 泛型
Rust (2015)   + 所有权 + 生命周期 + Send/Sync
依赖类型语言   + 任意命题的证明
```

趋势很清楚:**把原本属于动态语义的"坏行为"搬到静态语义层静态排除**。Rust 的借用检查就是把 use-after-free(原本是 UB)变成编译错误。这是过去三十年语言设计的主线。


## syntax和semantic的交汇点:语法制导翻译

两者正式握手的地方是 **syntax-directed translation(语法制导翻译)**——把语义动作挂在文法产生式上:

```
expr → expr₁ '+' expr₂   { $$.type = unify($1.type, $2.type);
                           $$.code = emit(ADD, $1.place, $2.place); }
```

这就是**属性文法**:综合属性(自下而上)与继承属性(自上而下)在 AST 上流动,把语义信息沿着语法结构传播。yacc/bison 的 `{ ... }` 动作块、ANTLR 的 listener/visitor,都是这个思路的实现。

**它既不是纯语法也不是纯语义,而是"用语法结构组织语义计算"。** 现代编译器虽然很少在 parse 时直接生成代码(改为先建 AST 再多遍遍历),但这个"结构驱动语义"的模式贯穿始终——MLIR 的 pattern rewrite 本质上也是它的一个变体。

## UB 的本质

UB 可以精确定义为:

> **语法合法、静态语义合法,但动态语义明确声明"不作保证"的程序。**

它不是 bug,是规范在语义层**主动留下的洞**,目的是换取优化空间。前面提过的 `add nsw` 溢出产生 poison、C 里有符号溢出是 UB,都是这个设计。这也是为什么"编译通过"从来不等于"程序正确"。

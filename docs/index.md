# 综述：传统编译器与深度学习编译器
系统介绍传统编译器与深度学习编译器，是一本编译器领域的百科全书。

> 编译器能做多少优化，取决于它对程序了解多少。
> 编译器必须做多少工作，取决于硬件替它做了多少。

---

## 本章导读

本书讨论两类编译器。一类是有六十余年历史的**传统编译器**，从 FORTRAN 到 GCC、LLVM，它们把通用编程语言翻译成机器码。另一类是近十余年兴起的**深度学习编译器**，从 Halide、TVM、XLA 到 MLIR、Triton、TorchInductor，它们把神经网络模型翻译成能在 GPU、TPU、NPU 等加速器上高效运行的代码。

两者常被当作两个独立的领域：前者属于程序设计语言与编译原理，后者属于机器学习系统。但深入观察会发现，它们共享同一套理论基础，遵循同一种架构范式，只是面对的程序、硬件和语义要求不同，于是在同一棵树上长出了不同的枝干。

本章的目的是在进入具体技术之前，给读者一张**完整的地图**。读完本章，读者应当能够回答以下问题：

1. 什么是编译器？两类编译器在抽象层面上做的是不是同一件事？
2. 两类编译器各自是如何演进而来的？是什么推动了深度学习编译器的诞生？
3. 两者的整体架构分别是什么样子？各个组成部分如何对应？
4. 两者共享哪些理论与技术？
5. 两者在哪些维度上不同？这些不同的根源是什么？
6. 深度学习编译器的版图如何划分？各个代表性系统处在什么位置？
7. 这个领域的前沿在哪里？本书的后续章节如何组织？

本章是全书的"鸟瞰图"。后续章节会逐一放大其中的细节，本章出现的许多概念只做简要定义，并注明在哪一部分详细展开。

## 1.1　编译器的统一模型

### 1.1.1　编译器的本质

从最抽象的层面看，编译器是一个函数：

$$
\mathcal{C}: P_{\text{src}} \rightarrow P_{\text{tgt}}
$$

它把用源表示描述的程序 $P_{\text{src}}$ 变换为用目标表示描述的程序 $P_{\text{tgt}}$，并满足两个要求：

- **语义保持（正确性）**：对所有合法输入，$P_{\text{tgt}}$ 的可观察行为与 $P_{\text{src}}$ 所规定的行为"一致"。
- **代价优化（性能）**：在所有语义上一致的目标程序中，选出在某种代价度量下尽可能好的一个，例如运行时间、能耗、内存占用或代码体积。

这个定义对两类编译器同样适用。两者的分歧，恰好落在定义中的三个关键词上：

| 关键词 | 传统编译器 | 深度学习编译器 |
|---|---|---|
| **程序**是什么 | 通用语言编写的任意程序 | 以张量算子为节点的计算图/张量程序 |
| **"一致"**指什么 | 严格遵守语言标准规定的语义 | 往往允许在数值容差内一致 |
| **"好"**指什么 | 主要指单机执行时间与代码体积 | 吞吐、延迟、显存占用、能耗，常涉及多设备 |

本章后半部分对两者差异的分析，基本都可以追溯到这张表。

### 1.1.2　编译器的三个要素

任何编译器都可以拆解为三个要素：

1. **表示（Representation）**：用什么数据结构描述程序，即中间表示（IR）。表示决定了编译器"看得见"什么。
2. **变换（Transformation）**：在表示上施加哪些保持语义的改写，即优化与降级（lowering）。变换决定了编译器"做得了"什么。
3. **决策（Decision）**：在众多合法变换中选择哪一个、以什么顺序施加，即启发式规则、代价模型与搜索策略。决策决定了编译器"做得好不好"。

这三个要素在后文中会反复出现，它们也是本书对比两类编译器的基本框架。可以先给出一个预告：

- 在**表示**上，传统编译器以低层、单一的 IR 为核心，深度学习编译器以高层、多层的 IR 为核心。
- 在**变换**上，两者共享大量经典变换，但深度学习编译器的主要收益来自融合、分块和数据布局等访存相关的变换。
- 在**决策**上，传统编译器主要依赖人工设计的启发式规则，深度学习编译器则大量使用搜索与学习。

### 1.1.3　编译器设计的四个目标

编译器设计永远是多目标的权衡：

- **正确性**：生成的代码必须符合语义契约。
- **性能**：生成的代码要尽可能快、省资源。
- **可移植性/可扩展性**：支持多种语言、多种硬件，并且容易添加新的语言或硬件。
- **编译开销**：编译本身要足够快，并且结果可预测、可调试。

传统编译器通常要求秒级编译，强调可预测性。深度学习编译器在部署场景下可以接受分钟甚至小时级的调优，以换取运行时性能，因为一个模型可能会被执行数十亿次。这种对编译开销容忍度的差异，深刻影响了两者的技术路线。

## 1.2　两条演进脉络

理解一个领域的最好方式之一，是了解它所解决的问题是如何一步步出现的。

### 1.2.1　传统编译器：从"能不能翻译"到"如何系统地优化"

**第一阶段：证明高级语言可行（1950 年代）。** 1957 年，John Backus 领导的团队发布 FORTRAN I 编译器。当时的普遍看法是，编译器生成的代码必然远慢于手写汇编。FORTRAN 团队把大量精力放在优化上，证明了高级语言可以生成足够高效的代码。从一开始，**优化就是编译器存在的理由**。

**第二阶段：理论体系建立（1960–1980 年代）。** 形式语言与自动机理论为词法和语法分析奠定了基础，LEX、YACC 等工具让前端构造变得机械化。Kildall 在 1973 年提出了数据流分析的统一框架，Allen、Cocke 等人系统研究了控制流分析和循环优化，Chaitin 在 1980 年代初提出了基于图着色的寄存器分配。Aho、Sethi、Ullman 的《编译原理》（"龙书"）将这一时期的成果系统化。

**第三阶段：中间表示与工程化（1980–2000 年代）。** IBM 的研究者提出静态单赋值形式（SSA），Cytron 等人在 1991 年给出了高效构造算法，SSA 很快成为优化编译器的标准 IR。GCC 于 1987 年发布，成为自由软件世界的基础设施。为了利用向量机和并行机，依赖分析与循环变换理论（Allen 与 Kennedy 等人的工作）以及多面体模型（Feautrier 等人的工作）相继发展。

**第四阶段：模块化与动态编译（2000 年代至今）。** 2000 年，Chris Lattner 在 UIUC 启动 LLVM 项目。LLVM 以清晰的 IR、模块化的 Pass 和可复用的库式架构，改变了编译器的开发方式：新语言只需实现前端，新硬件只需实现后端。同一时期，Java HotSpot（1999）、JavaScript V8（2008）等 JIT 编译器让"运行时编译"成为主流技术，推测优化、反优化等技术走向成熟。

这一路线的主线是：**在对程序了解有限的前提下，通过分析尽可能多地获取信息，并在可证明安全的范围内进行优化。**

### 1.2.2　深度学习编译器：从"算子库"到"编译栈"

**前史：高性能计算中的自动调优与领域专用语言。** 深度学习编译器的许多思想并非凭空出现。ATLAS（1998）通过在目标机器上实测不同参数来自动生成高效的 BLAS 库，FFTW（1998）用类似思路生成 FFT 代码，SPIRAL 等系统为信号处理生成程序。这些工作表明：**对于规整的数值计算，搜索可以胜过手工启发式规则。**

**第一阶段：计算图与手写算子库（2007–2016）。** Theano（约 2008 年起）已经把数学表达式构造成符号计算图，并对其进行优化和代码生成，可以看作深度学习编译器的雏形。随后，Caffe、TensorFlow（2015）、PyTorch（2016）等框架兴起。这一时期的主流做法是：框架负责构建计算图，每个算子调用厂商手写的高性能库，例如 NVIDIA 的 cuBLAS 和 cuDNN（2014）、Intel 的 MKL-DNN（后来的 oneDNN）。

这种模式很快暴露出问题：

- **组合爆炸**：框架数 × 算子数 × 硬件数，手写库无法覆盖所有组合，尤其是融合后的组合算子。
- **访存瓶颈**：算子逐个调用，中间结果反复读写显存。
- **新硬件难以接入**：每出现一款新的 AI 芯片，都要重写全套算子库。

**第二阶段：编译思想的引入（2012–2019）。** Halide（2012 年首次发表，2013 年的 PLDI 论文最为知名）提出把**算法（算什么）与调度（怎么算）分离**，最初用于图像处理，后来深刻影响了几乎所有张量编译器。2017 年，Google 公开 XLA，把 TensorFlow 计算图编译为融合后的代码，并成为 TPU 的主要编译路径。2018 年，TVM 发表于 OSDI，提出了从图到算子的端到端编译栈，并用机器学习代价模型指导自动调优。同一时期还出现了 Facebook 的 Glow、Tensor Comprehensions，Intel 的 nGraph 等系统。NVIDIA 的 TensorRT 则从推理优化器的角度切入，结合图优化、精度校准和算子库。

**第三阶段：基础设施化与普及（2019 年至今）。** 2019 年，Google 推出 MLIR，提出多层次、可扩展的 IR 基础设施，后来成为 LLVM 项目的一部分，并被 IREE、Triton、OpenXLA 以及许多芯片厂商的编译栈采用。同年，Triton 以"块级编程"的方式降低了编写高性能 GPU 核函数的门槛。2020 年，Ansor 把自动调度推向更大的搜索空间。2023 年，PyTorch 2.0 发布 `torch.compile`，其中 TorchDynamo 负责从 Python 字节码中捕获计算图，TorchInductor 负责生成以 Triton 为主的代码，深度学习编译从此进入了大量普通开发者的日常工作。

**第四阶段：大模型时代的系统级编译（进行中）。** 随着大语言模型的出现，编译器需要处理更长的序列、动态变化的形状、KV Cache、低比特量化、跨数千张加速卡的分布式切分（例如 GSPMD、Alpa 等工作）。编译器的优化对象正在从单个算子、单张计算图，扩展到整个训练和推理系统。

这一路线的主线是：**利用领域知识获得关于程序的完整信息，再用搜索和自动化来处理硬件多样性带来的巨大优化空间。**

## 1.3　两类编译器的体系结构总览

### 1.3.1　传统编译器的典型结构

```
              ┌────────────────────────── 前端 ──────────────────────────┐
源程序 ──► 词法分析 ──► 语法分析 ──► 语义分析 ──► AST ──► IR 生成
              └─────────────────────────────────────────────────────────┘
                                         │
              ┌────────────────────────── 中端 ──────────────────────────┐
              │  SSA 构造 → 标量优化 → 过程间优化 → 循环优化 → 向量化 …   │
              └─────────────────────────────────────────────────────────┘
                                         │
              ┌────────────────────────── 后端 ──────────────────────────┐
              │  指令选择 → 指令调度 → 寄存器分配 → 窥孔优化 → 代码发射   │
              └─────────────────────────────────────────────────────────┘
                                         │
                         汇编/目标文件 ──► 链接器 ──► 可执行文件
                                                   （+ 运行时库）
```

它的特点包括：

- **前端很重**：要处理复杂的语法、类型系统、模板/泛型、作用域、重载等语言特性。
- **中端是优化的核心**：IR 通常是基于 SSA 和控制流图的低层表示，基本单位是标量指令。
- **后端面对稳定的指令集**：x86、ARM、RISC-V 等指令集多年保持稳定，硬件本身有乱序执行、分支预测、缓存一致性等机制，可以弥补编译器的不足。

### 1.3.2　深度学习编译器的典型结构

```
  模型定义（PyTorch / JAX / TensorFlow / ONNX ……）
                  │
  ┌───────────── 图捕获 / 导入 ─────────────┐
  │ 追踪（tracing）、字节码分析、导出格式解析 │
  └─────────────────────────────────────────┘
                  │
  ┌───────────── 图层（Graph IR）───────────┐
  │ 规范化 → 常量折叠 → 代数化简 → 布局变换   │
  │ → 算子融合 → 量化/混合精度 → 自动微分     │
  │ → 分布式切分 → 内存规划                   │
  └─────────────────────────────────────────┘
                  │
  ┌───────────── 算子层（Tensor/Loop IR）────┐
  │ 计算定义 + 调度：分块、重排、向量化、并行 │
  │ 线程绑定、片上存储提升、软件流水、张量化  │
  │ ◄──── 自动调优 / 代价模型 / 搜索 ────►    │
  └─────────────────────────────────────────┘
                  │
  ┌───────────── 代码生成 ───────────────────┐
  │ LLVM IR / CUDA / PTX / SPIR-V / 厂商指令  │
  │ 或调用厂商库（cuBLAS、cuDNN、CUTLASS …）  │
  └─────────────────────────────────────────┘
                  │
  ┌───────────── 运行时 ─────────────────────┐
  │ 内存池、流与同步、多设备通信、编译缓存    │
  └─────────────────────────────────────────┘
```

它的特点包括：

- **前端很轻，也很特殊**：通常没有传统意义上的词法和语法分析，而是从框架中**捕获**计算图。如何可靠地从动态的 Python 程序中提取计算图，本身就是一个难题。
- **IR 分为多层**：图层表达"算什么"，算子层表达"怎么算"。
- **调优与代码生成交织**：后端常常需要在目标硬件上进行搜索。
- **运行时承担更多职责**：显存管理、异步执行、跨设备通信等工作都在运行时完成。

### 1.3.3　结构对照

| 传统编译器 | 深度学习编译器 | 说明 |
|---|---|---|
| 词法/语法/语义分析 | 图捕获、模型导入 | 获取程序的方式完全不同 |
| AST | 计算图（数据流图） | 都是高层结构化表示 |
| 中端 IR（如 LLVM IR） | 图 IR + 张量/循环 IR | 后者有两层甚至更多层 |
| 过程间优化、内联 | 图级优化、算子融合 | 后者在算子粒度上操作 |
| 循环优化、向量化 | 算子调度（分块、向量化、并行） | 理论基础相同，深度学习编译器更激进 |
| 指令选择 | 张量化（映射到张量指令）、库调用选择 | 后者匹配的是"大指令" |
| 寄存器分配 | 张量内存规划、片上存储分配 | 管理对象的规模不同 |
| 指令调度 | 软件流水、异步拷贝、流调度 | 都用于隐藏延迟 |
| 链接与运行时库 | 运行时、算子库、通信库 | 后者的运行时更重 |
| 常常不存在 | 自动调优 | 深度学习编译器的标志性组件 |

一个需要强调的事实是：**深度学习编译器的最底层，通常就是传统编译器。** TVM 生成 CPU 代码要经过 LLVM，Triton 通过 LLVM 的 NVPTX 后端生成 PTX，CUDA C++ 代码则由 NVCC 编译。因此两者更接近"上下游"的关系，而不是"替代"的关系。

## 1.4　共同的理论基础

在讨论差异之前，必须先说明两者有多少共同之处。这些共同的基础构成了本书的"公共基础"部分。

### 1.4.1　语义保持变换

两类编译器的每一次优化，本质上都是一个保持语义的程序变换。判断变换是否合法、证明变换是否正确，依赖的是相同的形式化工具：操作语义、等价关系、不变式。区别只在于"语义"的定义不同（见 1.6.5 节）。

### 1.4.2　中间表示的设计原则

无论哪一类编译器，好的 IR 都要满足以下原则：

- **显式化**：把隐含的信息变成显式的，例如 SSA 把定义—使用关系变成显式的。
- **规范化**：同一含义尽量只有一种表达方式，便于模式匹配。
- **可分析**：方便进行依赖分析、别名分析、形状推导等。
- **可组合**：Pass 之间可以自由组合。

深度学习编译器的图 IR 普遍采用 SSA 形式，TVM 的 Relax、XLA 的 HLO、MLIR 的各个方言都是如此。函数式表示、区域（region）与块参数等概念也在两边通用。

### 1.4.3　数据流分析与依赖分析

传统编译器中的活跃变量分析、到达定值分析、常量传播，在计算图上都有对应形式，例如张量生命周期分析、形状传播、常量子图识别。

循环优化所依赖的**数据依赖理论**，例如依赖向量、距离向量、方向向量，以及判断循环变换合法性的方法，是传统编译器和张量编译器共同的基础。

### 1.4.4　循环变换与多面体模型

循环分块（tiling）、交换（interchange）、融合（fusion）、分裂（fission）、展开（unrolling）、倾斜（skewing）等变换，最初是为了让 FORTRAN 数值程序在向量机和缓存体系上高效运行而研究的。张量编译器的调度原语，本质上就是这些变换的参数化封装。

多面体模型把循环嵌套视为整数集合与仿射映射，从而把循环变换转化为数学上的线性规划或整数规划问题。它在传统编译器中有 Polly（LLVM）、Graphite（GCC）、PLuTo 等实现，在深度学习编译器中有 Tensor Comprehensions、AKG，以及 MLIR 中的 Affine 方言。

### 1.4.5　代价模型与 Pass 管理

两类编译器都需要估计"某个变换是否值得做"，都需要组织数十到数百个 Pass，都面临 **Pass 顺序问题**：Pass 之间相互影响，不同的执行顺序会得到不同的结果，而找到最优顺序本身是一个难解问题。

### 1.4.6　渐进式降级

"从高层抽象逐步降低到低层抽象，在每一层做适合该层的优化"，这一思想在传统编译器中已有体现，例如 GCC 从 GENERIC 到 GIMPLE 再到 RTL，LLVM 从 LLVM IR 到 SelectionDAG 再到 MachineInstr。深度学习编译器把这一思想发挥到了极致，MLIR 更是把它变成了基础设施层面的通用机制。

### 1.4.7　小结：同一门学科

| 共同基础 | 在传统编译器中的体现 | 在深度学习编译器中的体现 |
|---|---|---|
| 语义保持 | 遵守语言标准 | 遵守算子语义与数值契约 |
| SSA | LLVM IR、GIMPLE | HLO、Relax、MLIR 方言 |
| 数据流分析 | 活跃变量、常量传播 | 张量生命周期、形状推导 |
| 依赖分析 | 循环并行化、向量化 | 调度合法性检查 |
| 循环变换 | 循环优化 Pass | 调度原语 |
| 多面体模型 | Polly、Graphite | Tensor Comprehensions、AKG、Affine |
| 代价模型 | 内联、展开的启发式规则 | 调度的性能预测 |
| 渐进式降级 | GIMPLE → RTL | 图 → 张量 → 硬件 |

可以说，**深度学习编译器不是一门新学科，而是编译学科在一个新领域中的重新展开。** 掌握传统编译的读者理解深度学习编译会快得多；反过来，深度学习编译器中被重新发现的问题，也会加深对传统编译的理解。

## 1.5　差异的根源：三个变化

两类编译器在细节上有数十处差异，但这些差异主要来自三个根本变化。理解了这三个变化，就能推导出大多数具体差异。

### 变化一：程序变了，从"任意程序"到"张量程序"

传统编译器面对的是**图灵完备的通用程序**，有任意的控制流、递归、指针、动态内存分配、副作用和外部调用。编译器对程序的意图几乎一无所知，很多重要性质（例如两个指针是否指向同一块内存）在一般情况下是**不可判定**的。

深度学习编译器面对的主要是**张量程序**：

- 以数据流为主，控制流少且结构化；
- 基本操作是语义明确的算子，例如矩阵乘、卷积、归约、逐元素运算；
- 张量之间通常没有别名，访问模式规整，多为仿射访问；
- 形状往往在编译时已知，或者至少可以符号化表示。

**推论**：深度学习编译器知道得更多，因此能够更激进地优化。

### 变化二：硬件变了，从"聪明的 CPU"到"简单而强大的加速器"

CPU 投入大量晶体管来做乱序执行、分支预测、硬件缓存管理，目的就是让各种程序都能跑得不错，即使编译器做得不够好。

AI 加速器反其道而行：把晶体管尽可能用于计算单元（张量核心、脉动阵列、向量单元）和片上存储，把调度、数据搬运、存储分配等复杂工作**交给软件**。GPU 的共享内存需要显式管理，TPU 等加速器大量依赖编译器的静态调度。

**推论**：深度学习编译器承担的责任更重，必须显式管理存储层次、数据搬运和计算编排；同时，硬件的多样性和快速迭代，使得手写启发式规则难以跟上，搜索与自动化变得必要。

### 变化三：语义契约变了，从"精确等价"到"容差等价"

传统编译器的语义契约由语言标准规定。例如 IEEE 754 浮点运算不满足结合律，在默认设置下，编译器不得重排浮点加法。

神经网络对数值扰动有很强的容忍度：改变归约顺序、降低精度到 FP16/BF16/FP8，甚至量化到 INT8/INT4，往往只会让模型精度产生可接受的轻微变化。很多时候，**最终的评价标准是模型的任务精度，而不是逐比特的一致**。

**推论**：深度学习编译器可以进行许多传统编译器不允许的变换，但正确性的定义和验证也因此变得更加复杂。

这三个变化可以概括为一张因果图：

```
程序变了（张量程序）  ──► 编译器知道更多 ──► 可以做高层、激进的优化
                                              （融合、布局、代数改写）
硬件变了（加速器）    ──► 编译器负责更多 ──► 必须显式管理存储与调度
                                              必须依赖搜索与自动化
语义变了（容差等价）  ──► 编译器允许更多 ──► 低精度、量化、重排
                                              正确性验证更加复杂
```

## 1.6　分维度对比

下面从十二个维度系统比较两类编译器。每个维度都会说明差异是什么、为什么会这样，以及在本书的哪一部分深入讨论。

### 1.6.1　输入：源语言与程序获取

传统编译器的输入是**文本形式的源代码**，前端通过词法分析、语法分析、语义分析得到完整的程序结构。程序是静态、完整、自包含的。

深度学习编译器的输入是**框架中的模型**。模型通常用 Python 编写，而 Python 是动态语言，模型代码中混杂着张量运算、Python 控制流、日志打印、第三方库调用。因此，"获取程序"本身就成了一个问题，常见的方式有：

- **追踪（tracing）**：实际运行一次程序，记录执行过的张量运算。简单可靠，但会丢失数据相关的控制流。JAX 的 `jit`、早期的 `torch.jit.trace` 采用这种方式。
- **源码或 AST 分析**：解析 Python 源码。能保留控制流，但很难覆盖 Python 的全部语义，例如 `torch.jit.script`。
- **字节码分析**：在 Python 字节码层面捕获计算图，遇到无法处理的部分就"断开计算图"并回退到 Python 执行，例如 TorchDynamo。
- **导出格式**：从 ONNX、StableHLO、TorchScript 等交换格式导入。

**本质差异**：传统编译器拥有程序的全部内容；深度学习编译器常常只拥有程序的一部分，必须处理"可编译部分"和"不可编译部分"之间的边界。

### 1.6.2　中间表示：单层低级 IR 与多层领域 IR

**传统编译器**的核心优化 IR 一般是低层的：基于 SSA、以基本块组成控制流图、以标量指令为基本单元、类型系统接近机器（整数、浮点、指针、向量）。它的优点是通用、稳定，缺点是**高层语义在降级时丢失**。当矩阵乘被展开为三重循环和指针运算时，编译器再想"认出"这是矩阵乘，就需要复杂的模式识别（idiom recognition），而且往往失败。

**深度学习编译器**普遍采用多层 IR：

| 层次 | 表达内容 | 典型代表 | 适合的优化 |
|---|---|---|---|
| 图层 | 算子及其数据依赖 | XLA HLO、StableHLO、TVM Relax、PyTorch FX、ONNX | 融合、代数化简、布局、量化、切分 |
| 张量/循环层 | 循环嵌套、张量访问、调度 | TVM TensorIR、MLIR Linalg/Affine/SCF、Halide IR | 分块、重排、向量化、并行 |
| 硬件抽象层 | 线程层级、片上存储、特殊指令 | MLIR GPU/NVGPU 方言、Triton GPU IR | 线程映射、张量化、流水 |
| 机器层 | 指令 | LLVM IR、PTX、厂商 ISA | 寄存器分配、指令调度 |

**本质差异**：传统编译器"先降级后优化"，深度学习编译器"边降级边优化"，在信息最充分的层次上完成每一种优化。MLIR 的方言机制把这种设计提升为通用的基础设施，也正在反过来影响传统编译器（例如 Flang、ClangIR 等项目开始引入更高层的 IR）。

### 1.6.3　分析：从"艰难地证明"到"直接读取"

传统编译器的大量精力花在**分析**上，以证明某个优化是安全的：

- **别名分析**：两个指针是否可能指向同一块内存？这是阻碍优化的最大障碍之一。
- **过程间分析**：被调用的函数有没有副作用？
- **依赖分析**：循环迭代之间是否存在依赖？在下标不是仿射表达式时，往往只能保守处理。

深度学习编译器的许多信息可以**直接从语义中读取**：算子的语义说明了它读什么、写什么、有没有副作用；张量之间通常没有别名（原地操作需要特殊处理）；访问模式大多是仿射的。深度学习编译器特有的分析任务包括：

- **形状推导**：静态形状、符号形状、动态形状的传播与约束求解；
- **布局分析**：数据在内存中的排列方式（NCHW、NHWC、分块布局等）；
- **数值范围分析**：为量化确定数值的范围和缩放因子；
- **切分传播**：在分布式场景下推导张量如何在设备间切分。

### 1.6.4　优化：从"减少指令"到"减少数据搬运"

**传统编译器的优化重心**：

- 减少执行的指令数：常量传播、公共子表达式消除、死代码消除、强度削减、内联；
- 减少流水线停顿：指令调度、分支优化；
- 减少内存访问：寄存器分配、标量替换；
- 利用数据级并行：自动向量化。

**深度学习编译器的优化重心**：

- **减少显存访问**：算子融合是首要手段；
- **提高数据复用**：在寄存器、共享内存、缓存等各级存储上进行分块；
- **匹配硬件计算单元**：张量化，即把计算映射到张量核心、矩阵引擎等专用指令；
- **选择合适的数据布局**，并在图层面减少布局转换；
- **降低精度**：混合精度、量化；
- **减少内存占用**：内存复用、重计算、卸载；
- **代数改写**：利用数学等价性改写计算图，例如合并多个并行的矩阵乘、改变归约与逐元素运算的顺序。

为什么优化重心会转向访存？**Roofline 模型**给出了解释。一个计算任务的性能上限由两个因素决定：

$$
\text{可达性能} = \min\left(\text{峰值算力},\ \text{内存带宽} \times \text{算术强度}\right)
$$

其中算术强度是每搬运一个字节所做的运算次数。现代加速器的算力增长远快于带宽增长，导致大量算子（逐元素运算、归一化、Softmax 等）都受限于带宽。对这些算子来说，"少搬运一次数据"比"少执行一条指令"重要得多。FlashAttention 的成功，正是通过分块和融合，避免了把注意力矩阵写入显存。

**注意**：传统编译器中也有循环融合、分块等优化，深度学习编译器中也有常量折叠、死代码消除。差异不在于"有没有"，而在于"哪些优化是收益的主要来源"。

### 1.6.5　正确性：语义契约与验证方式

| | 传统编译器 | 深度学习编译器 |
|---|---|---|
| 语义来源 | 语言标准（C/C++ 标准、IEEE 754 等） | 算子定义 + 框架行为 + 隐含的数值容差 |
| 浮点重排 | 默认禁止（`-ffast-math` 等选项可放宽） | 通常允许 |
| 精度变化 | 不允许 | 混合精度、量化是常规手段 |
| 未定义行为 | 是优化的重要依据（也是众多问题的根源） | 较少依赖 |
| 正确性判定 | 输出逐位一致 | 在容差内一致，最终以模型精度为准 |
| 验证工具 | 形式化验证（CompCert）、变换验证（Alive）、随机测试（Csmith） | 数值对比测试、精度回归、差分测试，形式化验证尚在早期 |

"容差等价"带来了新的难题：容差应该多大？误差在深层网络中会如何积累？某次精度下降究竟是编译器的错误，还是可接受的数值波动？这些问题在传统编译器中基本不存在。

此外，深度学习编译器还需要处理**可复现性**问题：非确定性的并行归约会导致同样的输入在不同运行中得到略有差异的结果，这在调试和科研中都可能造成困扰。

### 1.6.6　决策：启发式规则、搜索与学习

这是两类编译器在方法论上最显著的区别之一。

**传统编译器**主要依赖专家设计的启发式规则和解析式代价模型。例如：函数小于某个阈值就内联；循环展开若干次；按某种优先级进行寄存器溢出。这种方式编译速度快、结果可预测，但难以适应硬件的细微差异。

**深度学习编译器**面对的调度空间极其庞大。以 GPU 上的一个矩阵乘为例，分块大小、循环顺序、线程映射、是否使用共享内存、流水级数、向量化宽度等参数的组合可达数百万种，而最优选择高度依赖具体的硬件型号和张量形状。因此，深度学习编译器发展出了一系列新方法：

1. **算法与调度分离**（Halide）：让调度成为可以独立描述和搜索的对象；
2. **基于模板的调优**（AutoTVM）：专家写调度模板，机器搜索参数；
3. **自动生成搜索空间**（Ansor、MetaSchedule）：由编译器自动构造调度空间；
4. **学习型代价模型**：用梯度提升树或神经网络预测性能，减少实测次数；
5. **等价改写搜索**（TASO、PET 以及基于 e-graph 的方法）：在图层面搜索等价的改写组合；
6. **启发式规则与模板库**（如 TorchInductor 的融合规则加上 Triton 配置的少量调优，或 CUTLASS 的模板）：在编译时间与性能之间取得平衡。

需要说明的是，搜索并非深度学习编译器的首创。ATLAS、FFTW、迭代编译、超级优化（superoptimization）等工作早已有之，近年 LLVM 的 MLGO 项目也把机器学习用于内联和寄存器分配决策。但只有在深度学习编译器中，搜索才成为**主流的、工业级的**决策方式。

### 1.6.7　代码生成与后端

**传统编译器的后端**有三个经典问题：

- **指令选择**：把 IR 映射为目标指令，常用树覆盖或 DAG 覆盖；
- **寄存器分配**：图着色、线性扫描等算法；
- **指令调度**：列表调度、软件流水。

**深度学习编译器的后端**面对的问题有所不同：

- **张量化**：把计算的一部分映射到"大指令"上，例如 GPU 的 Tensor Core 指令（MMA）、各类 NPU 的矩阵乘指令。这相当于粒度大得多的指令选择，而且要求数据布局严格匹配。
- **线程层级映射**：把计算分配到线程块（block）、线程束（warp）、线程三个层级，或分配到 NPU 的多个核心上。
- **显式数据搬运**：生成全局内存到共享内存、共享内存到寄存器的拷贝指令，常常使用异步拷贝和双缓冲。
- **同步插入**：在适当位置插入屏障，保证并发访问的正确性。
- **库调用与代码生成的选择**：对某个算子，是调用 cuBLAS，还是使用模板库，还是自动生成代码？

许多深度学习编译器最终会把生成结果交给传统编译器的后端（LLVM、NVCC 等）完成寄存器分配和指令调度。

### 1.6.8　内存管理

| | 传统编译器 | 深度学习编译器 |
|---|---|---|
| 主要对象 | 寄存器、栈帧 | 张量（KB 到 GB 级别）、片上存储 |
| 核心问题 | 寄存器分配与溢出 | 张量内存复用、峰值内存控制、片上存储分配 |
| 动态内存 | 由程序员或垃圾回收负责 | 由编译器和运行时规划，通常配合内存池 |
| 典型技术 | 逃逸分析、栈上分配 | 生命周期分析、原地计算、重计算、卸载、内存池 |

在大模型训练中，显存常常比算力更稀缺。编译器需要在"保存中间激活值"和"反向传播时重新计算"之间做权衡，这是一种以计算换内存的优化。在大模型推理中，KV Cache 的管理（例如分页式管理）则成为系统级的核心问题。

### 1.6.9　并行

**传统编译器**中，并行主要需要**挖掘**：自动向量化依赖别名分析和依赖分析，自动并行化长期效果有限，许多情况下需要程序员通过 OpenMP 指令、SIMD 内建函数等方式显式表达。

**深度学习编译器**中，并行**天然存在**：批次、通道、空间维度、矩阵的行和列都可以并行。问题变成了**如何把海量并行映射到硬件的多级层次上**：

1. 指令级：SIMD、张量核心；
2. 线程级：线程、线程束、线程块；
3. 设备级：单设备上的多个核心或多个计算单元；
4. 集群级：数据并行、张量并行、流水线并行、专家并行。

在集群级，编译器需要自动或半自动地决定如何切分张量和计算，并插入集合通信操作（AllReduce、AllGather 等）。XLA 的 GSPMD、Alpa 等工作就是这方面的代表。这已经超出了传统编译器的职责范围，进入了分布式系统的领域。

### 1.6.10　编译时机与动态性

**传统编译器**以 AOT（提前编译）为主，JIT 主要出现在 Java、JavaScript、Python（PyPy）等语言的运行时中。传统 JIT 关心的"动态性"主要是**类型和控制流**的动态性，核心技术是基于剖析的推测优化与反优化。

**深度学习编译器**中 JIT 与 AOT 并存：

- **JIT**：训练和研究场景，例如 `torch.compile`、JAX 的 `jit`，在首次执行时编译并缓存；
- **AOT**：部署场景，例如 TensorRT、TVM、IREE、移动端推理引擎，提前为目标设备编译好。

深度学习编译器关心的"动态性"主要是**形状**的动态性。张量形状对优化影响极大：形状不同，最优分块方案可能完全不同。常见的处理方式有：

- 为每种形状单独编译，并用守卫（guard）检查形状变化；
- 形状分桶（bucketing）和填充（padding）；
- 符号形状：在 IR 中用符号表示未知维度，生成对一类形状都有效的代码。

有趣的是，"守卫加重新编译"的机制，与传统 JIT 的"推测优化加反优化"在思想上是一脉相承的。

### 1.6.11　运行时与系统集成

传统编译器生成的程序依赖相对轻量的运行时：C 运行时库、动态链接器，以及语言特定的运行时（例如垃圾回收器）。

深度学习编译器生成的代码通常需要较重的运行时支持：设备内存管理、异步执行流与事件、核函数启动、集合通信、编译缓存，以及与框架的交互（自动微分、优化器、数据加载）。在 GPU 上，**核函数启动开销**也是不可忽视的因素，CUDA Graph 等技术可以把一系列核函数调用打包，减少 CPU 端的开销。

此外，深度学习编译器与**手写算子库**的关系非常复杂。对于矩阵乘、卷积等核心算子，厂商库往往经过极致调优，编译器常常直接调用它们；对于融合算子和长尾算子，编译器自动生成代码的优势更明显。因此，实际系统大多采用"库与编译器混合"的策略。

### 1.6.12　工程生态与评价方式

| | 传统编译器 | 深度学习编译器 |
|---|---|---|
| 成熟度 | 数十年积累，高度稳定 | 快速演进，接口和架构变化频繁 |
| 标准 | 语言标准、ABI 标准 | 交换格式（ONNX、StableHLO）仍在发展 |
| 评测基准 | SPEC CPU 等 | MLPerf、模型级基准、算子级基准 |
| 评价指标 | 运行时间、代码体积、编译时间 | 吞吐、延迟、显存、能耗、精度、编译/调优时间 |
| 调试工具 | 调试器、性能分析器、sanitizer 非常成熟 | 数值调试、图可视化、性能剖析，仍在完善中 |
| 主要用户 | 所有软件开发者 | 模型开发者、框架开发者、芯片厂商 |

对芯片厂商而言，深度学习编译器还有一层特殊意义：**软件栈往往决定了一款 AI 芯片能否被实际使用。** 这使得深度学习编译器成为产业竞争的焦点之一。

| 维度 | 传统编译器 | 深度学习编译器 | 根源 |

| 决策 | 启发式规则 | 搜索 + 学习 + 规则 | 硬件 |

## 1.7　深度学习编译器的版图

"深度学习编译器"是一个宽泛的称呼，涵盖了定位差异很大的多种系统。为了让读者对这个领域有清晰的认识，本节从几个角度对它们进行分类。

### 1.7.1　按抽象层次分类

- **图编译器**：主要在计算图层面做优化，算子实现多依赖库或下层编译器。例如 TensorRT 的图优化部分、ONNX Runtime 的图优化器、早期的 TASO。
- **算子编译器/张量编译器**：专注于为单个（或融合后的）算子生成高效代码。例如 Halide、Tensor Comprehensions、Triton、TVM 的 TensorIR 部分、AKG。
- **全栈编译器**：覆盖从图到代码的完整流程。例如 TVM、XLA、IREE、TorchInductor（与 TorchDynamo 一起）。
- **编译器基础设施**：提供构建编译器的通用框架，而不是某个具体的编译器。例如 MLIR，以及传统编译器中的 LLVM。

### 1.7.2　按应用场景分类

- **训练编译**：需要支持自动微分、优化器、分布式并行，重视编译时间与灵活性。例如 XLA（JAX、TensorFlow）、`torch.compile`。
- **推理编译**：重视延迟、吞吐与资源占用，可以接受较长的离线编译和调优。例如 TensorRT、TVM、IREE、各类移动端和边缘端推理引擎。
- **大模型服务**：在推理编译的基础上，还要处理连续批处理、KV Cache、投机解码等系统问题。通常是编译器与专用推理系统的结合。

### 1.7.3　按决策方法分类

- **规则驱动**：以模式匹配和启发式规则为主，例如 XLA 的大部分融合策略、TorchInductor 的融合规则。
- **库驱动**：以调用或组装手写库为主，例如 TensorRT 的核心算子选择、基于 CUTLASS 模板的代码生成。
- **搜索驱动**：以自动调优为主，例如 AutoTVM、Ansor、MetaSchedule。
- **多面体驱动**：以多面体模型为核心，例如 Tensor Comprehensions、AKG。
- **人机协作**：人提供高层结构，编译器负责细节，例如 Triton、Halide 的手写调度，以及近年出现的各种块级/分块级编程语言。

### 1.7.4　代表性系统概览

| 系统                          | 主要发起方                | 定位                 | 关键特征                           |
| --------------------------- | -------------------- | ------------------ | ------------------------------ |
| Halide                      | MIT 等                | 图像处理/张量 DSL        | 算法与调度分离                        |
| XLA / OpenXLA               | Google 及社区           | 全栈编译器              | HLO/StableHLO，TPU 主要编译路径，GSPMD |

## 1.8　统一的视角

在列举了大量差异之后，有必要重新站在更高的位置，用统一的框架看待两类编译器。

### 1.8.1　抽象阶梯

可以把两类编译器放在同一个"抽象阶梯"上：

```
  抽象层次高
     ▲
     │  模型/数学描述         ←── 深度学习编译器的起点
     │  计算图（算子级）
     │  张量程序（循环 + 张量）
     │  通用语言源码          ←── 传统编译器的起点
     │  低层 IR（SSA、标量）   ←── 两者的汇合处（如 LLVM IR）
     │  机器指令
     ▼
  抽象层次低
```

从这个角度看，深度学习编译器是把编译的起点**向上延伸**到了更高的抽象层次。起点越高，编译器掌握的语义信息越多，可以施加的优化就越多；但同时，适用的程序范围也越窄。

### 1.8.2　通用性与性能的谱系

编译技术存在一个基本的权衡：**通用性越强，可利用的领域知识越少；领域越专，可以施加的优化越激进。**

```
  通用 ◄──────────────────────────────────────────► 专用
  C/C++ 编译器 → 带 OpenMP 的编译器 → 多面体编译器 → Halide/Triton → XLA/TVM → 针对特定模型的手写核函数
  适用面最广                                                                 性能上限最高
```

深度学习编译器的兴起，可以看作这一谱系在 AI 领域的一次大规模实践。而 MLIR 的意义在于：它试图提供一种基础设施，让同一个编译框架可以在这条谱系的不同位置上灵活取舍。

### 1.8.3　一个总结性的公式

如果用一句话总结本书的核心观点：

> **编译器的能力 = 对程序的了解程度 × 对硬件的建模程度 × 在合法空间中的搜索能力。**

- 传统编译器的主要挑战在第一项：它对程序了解有限，需要大量分析。
- 深度学习编译器在第一项上具有天然优势，主要挑战转移到了第二项和第三项：硬件多样且复杂，优化空间巨大。

## 1.9　交汇与前沿

两类编译器正在相互借鉴、逐步融合。以下是本书将会重点讨论的几个前沿方向。

**1. 基础设施的统一。** MLIR 让传统编译器与深度学习编译器可以共享同一套基础设施。传统语言前端开始引入更高层的 IR（例如 Fortran 的 Flang、实验中的 ClangIR），深度学习编译器则复用 LLVM 的后端。两者之间的边界在基础设施层面正在消失。

**2. 编程模型的演进。** 在"完全手写"与"完全自动"之间，出现了一批中间层次的编程模型，例如 Triton 的块级编程、CUTLASS 与 CuTe 的分层抽象，以及多种新的分块级领域专用语言。它们的共同思想是：**人决定高层的分块与数据流，编译器负责低层的线程、同步与指令细节。**

**3. 机器学习用于编译。** 学习型代价模型、强化学习驱动的 Pass 选择与顺序决策、以及近年来利用大语言模型生成或优化代码的尝试，正在把"用 AI 优化编译器"变为现实。这一方向不仅影响深度学习编译器，也开始影响传统编译器。

**4. 等价改写与超级优化。** 基于 e-graph 的等式饱和（equality saturation）技术，可以在不丢失信息的情况下同时探索多种等价改写，正在被用于图优化、张量程序优化甚至硬件设计。

**5. 动态性与大模型。** 动态形状、稀疏计算、混合专家模型（MoE）、超长序列、KV Cache 管理、投机解码等问题，正在迫使深度学习编译器处理更多的"不规则性"。从某种意义上说，深度学习编译器正在面对传统编译器早已面对的问题：程序不再那么规整了。

**6. 分布式与系统级编译。** 自动并行、计算与通信重叠、异构集群上的调度，使编译器的边界扩展到整个数据中心。编译器正在从"程序优化器"演变为"系统优化器"。

**7. 正确性与可信性。** 随着编译器变得越来越激进，如何验证低精度变换、如何保证数值稳定性、如何对复杂的融合与改写进行形式化验证，将成为越来越重要的研究问题。

**8. 软硬件协同设计。** 新型 AI 芯片的设计越来越需要与编译器同步进行：硬件提供什么样的指令和存储结构，取决于编译器能否有效利用它们。编译器正在成为芯片设计流程的一部分。

## 1.11　本章小结

1. 两类编译器都是**语义保持的程序变换器**，都由**表示、变换、决策**三个要素构成，都在正确性、性能、可移植性和编译开销之间权衡。
2. 传统编译器从 FORTRAN 一路发展到 LLVM，主线是**在信息有限的条件下安全地优化**；深度学习编译器从算子库发展到完整的编译栈，主线是**利用领域知识，借助搜索应对硬件多样性**。
3. 两者共享 SSA、数据流分析、依赖分析、循环变换、多面体模型、代价模型、渐进式降级等**共同的理论基础**，深度学习编译器的底层通常就是传统编译器。
4. 两者的差异主要来自**三个变化**：程序从任意程序变为张量程序，硬件从通用 CPU 变为把复杂度交给软件的加速器，语义契约从精确等价变为容差等价。
5. 由此产生了输入、IR、分析、优化、正确性、决策、后端、内存、并行、动态性、运行时、生态等十余个维度上的具体差异。
6. 深度学习编译器的版图可以按**抽象层次、应用场景、决策方法**来划分。
7. 两类编译器正在**基础设施、编程模型、方法论**上相互融合，前沿问题集中在动态性、分布式、机器学习辅助编译、正确性与软硬件协同设计。

## 思考题

1. 为什么说"编译器能做多少优化，取决于它对程序了解多少"？请分别从传统编译器和深度学习编译器中各举一个例子。
2. 浮点加法不满足结合律。深度学习编译器在改变归约顺序时，如何判断这种变化是"可接受"的？这种判断能否形式化？
3. 自动调优在深度学习编译器中被广泛使用，在传统编译器中却不是主流。请从编译开销、程序特征和硬件特征三个角度分析原因。
4. 如果未来的 AI 加速器重新变得"聪明"（例如具备硬件管理的缓存和动态调度），深度学习编译器的哪些部分会变得不那么重要？哪些部分仍然必不可少？
5. 大模型中的动态形状、稀疏计算和混合专家结构，使张量程序变得不那么规整。这会让深度学习编译器在多大程度上重新面对传统编译器的难题？

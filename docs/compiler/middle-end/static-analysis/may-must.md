# May Analysis 与 Must Analysis（静态分析）
在程序静态分析（Static Program Analysis）中，May Analysis（可能分析） 和 Must Analysis（必然分析） 是最核心的两个概念。为了建立直觉，你可以把它们想象成 “宁可错杀，不可放过” 与 “宁缺毋滥，绝对保真” 的两种思维模式。

下面通过生活场景、核心对比以及编译器里的实际例子来帮你彻底建立直觉。

## 一、生活直觉：防盗报警器 vs 核验确认
假设你要为一栋大楼设计安保系统，判断大楼里 “有没有小偷”：

### May Analysis（可能分析）—— 宁可错杀，不可放过
逻辑：只要传感器检测到任何风吹草动（哪怕是风吹树叶或流浪猫），系统就报警：“大楼里可能有小偷！”

结果：只要真有小偷，系统绝对不会漏报（Over-approximation，过近似）。代价是偶尔会有误报（False Positive）。

目的：找 Bug、保安全。比如检查空指针异常，只要代码走某条分支“可能”导致空指针，就先警告程序员，绝不放过任何潜在隐患。

### Must Analysis（必然分析）—— 宁缺毋滥，绝对保真
逻辑：只有高清摄像头拍到了正脸、指纹比对完全一致，系统才确认：“大楼里一定有小偷！”

结果：只要系统说有，那就百分百是真的（Under-approximation，欠近似）。代价是如果小偷戴了口罩，系统就不敢下结论，可能会漏报（False Negative）。

目的：做代码优化。编译器要把代码改得更快，前提是绝对不能改出 Bug。只有“百分百确定”某段代码永远不会执行时，编译器才敢把它删掉。

## 二、代码直觉：两条岔路口
看下面这段包含 `if-else` 分支的代码，我们在汇合位置（第 7 行）观察变量的状态：
```c
1: int x, y;
2: if (条件) {
3:     x = 1;  y = 10;
4: } else {
5:     x = 2;  y = 10;
6: }
7: // <--- 我们站在这里往下看！
````

站在第 7 行时，静态分析器不知道程序运行时会走 if 还是 else，它只能同时考虑两条路：

### May Analysis（求并集 $\cup$）：只要有一条路成立，就算数

问题：变量 x 的值可能是多少？ 直觉：左边路 x 是 1，右边路 x 是 2。汇合后，x 可能是 1，也可能是 2。所以结果是 ${1, 2}$。 特点：路径越多，集合越大（把所有可能性都装进来）。

### Must Analysis（求交集 $\cap$）：必须所有路都成立，才算数

问题：哪些变量的值是必然确定的？ 直觉：x 在两边不一样，无法确定；但 y 在左边是 10，在右边也是 10。不管程序怎么跑，到了第 7 行 y 一定是 10！所以只有 $y = 10$ 留了下来。 特点：路径越多，集合越小（只有共同点才能活下来）。

## 三、核心差异速查表

|维度|May Analysis (可能分析)|Must Analysis (必然分析)|
|---|---|---|
|核心口诀|存在一条路径满足即可 ($\exists$)|所有路径都必须满足 ($\forall$)|
|汇合操作|并集 $\cup$：海纳百川|交集 $\cap$：求同存异|
|近似方向|过近似 (Over-approximation)：包含所有真实情况 + 一些假情况|欠近似 (Under-approximation)：真实情况的子集，绝对保真|
|主要用途|漏洞检测 / Bug 查找（如：污点分析、空指针检查、到达定值）|编译器优化（如：常量传播、死代码消除、可用表达式）|
|经典例子|活跃变量分析 (Live Variables)：只要后面可能用到这个变量，我就不能覆盖它的内存。|可用表达式 (Available Expressions)：只有所有路径都算过 a+b 且没改过值，我才敢直接复用结果。|

## 一句话总结

做安全检查时用 May（胆子要小，有一点可能出事就要报警）；做性能优化时用 Must（胆子要谨慎，没有百分之百的把握绝不乱改代码）。 

## may&must&lattice

补充说明：在数据流分析的语境中，"may" 与 "must" 是两种经典的格（lattice）方向 ——may 分析取**上近似**（可能发生即记为发生，对应并集），must 分析取**下近似**（必然发生才记为发生，对应交集）。活跃性分析之所以是 "may"，是因为只要某条路径上变量未来会被用到，就不能在当前点将其寄存器回收。

# 语法制导翻译在现代编译器中的位置

## ——从 Bison 到 Clang、LLVM 与指令选择

---

## 引子：一个看似简单的问题

“LLVM 这样的现代编译器，还用语法制导翻译吗？”

这个问题有两个都站得住的答案：

- **不用。** 打开 Clang、GCC、rustc、Go 编译器的源码，找不到 Bison 文件，也没有 `$$ = $1 + $3`。LLVM 的优化器处理的是控制流图和 SSA 值，那里没有“语法”。
- **到处都在用。** Clang 的 `Parser` 每识别完一个结构就调用 `Sema` 做检查；`CodeGen` 按 AST 节点类型递归地生成 LLVM IR；LLVM 后端用 TableGen 模式把 IR 翻译成机器指令。这些都是“按结构递归地计算”。

两个答案并不矛盾，因为“语法制导翻译”这个词同时指两样东西：一种**具体的实现技术**，和一种**思想**。现代编译器淘汰了前者，同时让后者渗透进了每一层，渗透得太彻底，人们已经不再给它起名字。

本文沿着编译流水线从头走到尾，看 SDT 在每一站的处境：哪里被淘汰，哪里改头换面地存活，哪里根本不适用，又在哪里以意想不到的形式重新出现。

---

## 一、三分钟回顾：SDT 到底是什么

### 1.1 属性与两种信息流

语法制导翻译的思路是：给文法符号挂上**属性**，用**语义规则**规定属性之间如何计算。类型、值、临时变量名、生成的代码片段、符号表指针，都可以是**属性**。

属性按信息流向分两种：

- **综合属性**：父节点的值由子节点算出，信息**向上**流。
  例：`E → E₁ + T`，`E.val = E₁.val + T.val`。
- **继承属性**：子节点的值由父节点或左边的兄弟给出，信息**向下、向右**流。
  例：`D → T L`，`L.type = T.type`，把类型“发给”后面的变量列表。

### 1.2 SDD 与 SDT

龙书区分了两个层次：

- **语法制导定义（SDD）**：只说明属性之间的依赖关系，不规定计算顺序。它是**规范**。
- **语法制导翻译方案（SDT）**：把**语义动作**嵌入产生式的特定位置，从而固定了计算顺序。它是**算法**。

这个区分在后文很重要：现代编译器抛弃的主要是“把动作嵌进文法”这种 SDT 写法，而 **SDD** 所描述的**属性依赖关系**，任何编译器都绕不开。

### 1.3 S 属性与 L 属性

- **S 属性定义**：只用综合属性。归约时就能算，天然适合 LR 分析器，Yacc/Bison 的 `$$` 就是它。
- **L 属性定义**：允许继承属性，但只许依赖父节点和**左**兄弟，不许依赖右兄弟。

L 属性有一个关键性质，也是整个理论的支点：

> **深度优先、从左到右地遍历语法树：进入节点时，继承属性所需的信息都已就绪；离开节点时，综合属性所需的信息都已就绪。因此，这种遍历顺序恰好能完成所有 L 属性定义的求值。**

推论很硬：如果某个属性依赖右兄弟，或者依赖“看完整个程序之后才知道”的信息，**一遍从左到右的遍历在原理上就算不出来**。这和实现水平无关，问题出在依赖关系上，没有可行的求值顺序。

现代编译器普遍采用**多遍**架构，根源就在这条推论上。

### 1.4 带注释的语法树

把**属性值**挂在**语法树**的每个节点上，就得到**带注释的语法树**。翻译就是按依赖关系给这棵树填值。

从这个视角看，“一遍翻译”和“多遍翻译”的区别只在于：树是隐式的（遍历过后就消失），还是显式的（可以反复访问）。

## 二、先把概念拆开：两个“SDT”

| | 严格意义的 SDT | 宽泛意义的 SDT |
|---|---|---|
| 形态 | 文法 + 内嵌动作 / 属性文法 | 按程序的结构递归地计算 |
| 驱动者 | 解析器生成器的归约顺序 | 程序员手写的递归函数 / visitor |
| 典型代码 | `expr: expr '+' term { $$ = ... }` | `Value *VisitBinAdd(BinaryOperator *E)` |
| 在生产编译器中 | **基本退场**（仍存活于部分语言实现与 DSL） | **无处不在** |

本文的结论可以先放在这里：

> **严格形态已经边缘化；宽泛形态成了编译器前端的默认写法。中间端不在 SDT 的适用范围内；指令选择则是 SDT 形式化血脉最清晰的后代。**

## 三、第一站：严格形态为何退场

1970 到 1990 年代，教科书式的做法是把动作写进文法：

```yacc
expr : expr '+' term   { $$ = mk_add($1, $3); }
     | term            { $$ = $1; }
     ;
```

这是最纯粹的 SDT：动作的位置就是求值的时刻，求值顺序由 LR 分析器的归约顺序决定。它声明式、紧凑，和理论一一对应。

主流生产编译器后来几乎都放弃了这种写法。GCC 的 C++ 前端在 3.4 版本换成手写递归下降，C 前端在 4.1 版本跟进；Clang、Go、rustc、Swift、TypeScript、V8 从一开始就是手写的。原因有三个，都是工程上的硬需求。

### 3.1 诊断质量

解析器生成器的错误恢复是通用的：插入或删除 token，然后继续。可用户需要的是“这里漏了一个 `)`，是否要插入？”这类带修复建议的诊断。

手写递归下降可以在任意位置插入针对性的恢复逻辑：记住最近的有效位置，根据上下文猜测意图，定制每一条错误信息。Clang 能给出高质量的 fix-it 提示，一个重要原因就是它的 `Parser` 每一处 `ExpectAndConsume` 都是人写的。

### 3.2 上下文相关的语法

看这两行 C 代码：

```c
T * p;      // 声明一个指针 p？还是 T 乘以 p？
(T) * p;    // 把 *p 强制转换为 T？还是 T 乘以 p？
```

答案取决于 `T` 是不是一个 typedef 名字，而这个信息在符号表里。**决定走哪条产生式，需要先知道语义。**

“先上下文无关地解析，再按结构做**语义分析**”这个分层假设，在这里直接失效。C 编译器的传统解法是 lexer hack：**解析器**把符号表信息反馈给**词法分析器**，让它把标识符标记成“类型名”或“普通名字”。C++ 和 Rust 也有各自的同类问题，比如 C++ 的“最令人烦恼的解析”，以及 Rust 泛型参数中 `<` 的歧义。

纯文法表达不了这种**反馈环**，手写解析器可以随时查表。

### 3.3 IDE 与增量解析

编辑器需要容错、局部重解析、对写了一半的代码给出高亮和补全。这催生了 tree-sitter 这样的增量解析器，以及 Roslyn、rust-analyzer 那样专门的“无损语法树”架构。在这些场景里，语法树本身就是产品，把语义动作塞进文法反而碍事。

### 3.4 严格形态并没有灭绝

它退出的是“大型、工业级、对诊断要求极高”的编译器前端，在其他地方仍然活跃：

- **CPython**（3.9 起）使用 PEG 解析器生成器 pegen，文法规则里直接写构造 AST 的动作；
- **GHC** 的解析器由 LR 生成器 Happy 生成，文法里嵌有 Haskell 动作；
- **PostgreSQL** 的 SQL 解析器是 Bison 文件 `gram.y`；
- **OCaml** 使用 Menhir；
- 大量 DSL、配置语言、查询语言，以及用 ANTLR 搭建的工具。

这些项目的共同点是：语法相对规整，或者语义分析本来就会单独做一遍，所以文法动作只负责建树。**而“文法动作只用来建 AST”，正是严格 SDT 在今天最常见的存活形态。**

## 四、第二站：SDT 被吸收进手写解析器

严格形态退场之后，翻译的结构其实没变。变化在于，驱动它的从产生式换成了手写函数。

### 4.1 Clang：Parser + Sema

Clang 前端是理解这一点最好的样本。`Parser` 负责识别语法结构，每识别完一个结构，就调用 `Sema` 的某个 `ActOn*` 回调：

```cpp
// Parser 解析完一个二元表达式后：
ExprResult Sema::ActOnBinOp(Scope *S, SourceLocation TokLoc,
                            tok::TokenKind Kind,
                            Expr *LHSExpr, Expr *RHSExpr);
```

把它和属性文法逐项对应：

| 属性文法 | Clang 中的载体                                                                 |
| ---- | -------------------------------------------------------------------------- |
| 综合属性 | `ActOn*` 的返回值 `ExprResult` / `StmtResult` / `DeclResult`，其中携带类型 `QualType` |
| 继承属性 | `Sema` 维护的上下文：当前 `Scope` 栈、当前 `DeclContext`、模板参数、是否处于 `constexpr` 求值等      |
| 语义规则 | `ActOn*` 内部的名字查找、类型检查、隐式转换插入、常量折叠                                          |
| 求值时刻 | 语法结构识别完成的那一刻                                                               |

**这正是 L 属性求值，而且是加强版**：上下文相关的消歧也被并进来了。遇到标识符时，`Parser` 会询问 `Sema` 它是否命名一个类型，然后把 token 注释成类型名再继续解析，相当于 lexer hack 的现代、结构化版本。

属性的载体从 Bison 的 `$$` 换成了 C++ 函数的返回值，从文法文件里的动作换成了 `Sema` 类的成员函数，计算的结构仍是属性文法那一套。

### 4.2 非 L 依赖如何处理：延迟解析

C++ 有一条典型的“非 L”规则：类内定义的成员函数体，可以引用**写在它后面**的成员。

```cpp
struct S {
    int f() { return x; }   // x 在后面才声明
    int x;
};
```

从左到右一遍处理时，解析到 `f` 的函数体，`x` 还不存在。按照第一节的推论，这不可能一遍完成。

Clang 的做法是：遇到类内成员函数体时，先把它的 token **缓存起来不解析**，等整个类定义结束后再回头解析这些函数体，默认参数等也是同样处理。这相当于在局部“多做了一遍”，把非 L 依赖拆成了两段各自满足 L 属性的计算。

理论在这里给出的不是实现方案，而是一个**提前的判断**：只要看出依赖关系里有“右兄弟”，就知道必须延迟或分遍，不必等到写出 bug 才发现。

## 五、第三站：AST → IR，结构递归的完全体

如果说解析阶段的 SDT 还受语法结构的牵制，那么从 AST 生成 IR 的 lowering 阶段，就是宽泛 SDT 最纯粹的形态：输入是一棵结构明确的树，输出由每个节点类型的翻译规则组合而成。

各家编译器的写法几乎一模一样。

**Clang CodeGen**

```cpp
class ScalarExprEmitter
    : public StmtVisitor<ScalarExprEmitter, llvm::Value *> {
  // 每个节点类型一个 Visit 函数，返回生成的 LLVM 值
  llvm::Value *VisitBinaryOperator(const BinaryOperator *E);
  llvm::Value *VisitCallExpr(const CallExpr *E);
  ...
};
```

返回值 `llvm::Value*` 是**综合属性**：子表达式生成的值，被父节点拿去组合。`CodeGenFunction` 里维护的当前插入点、`break`/`continue` 的跳转目标栈、清理作用域栈，则是**继承属性**：父节点（比如一个 `while` 语句）设置好，子节点（比如循环体里的 `break`）读取。

**GCC gimplify**

```c
enum gimplify_status
gimplify_expr (tree *expr_p, gimple_seq *pre_p, gimple_seq *post_p,
               bool (*gimple_test_f) (tree), fallback_t fallback);
```

一个巨大的 `switch` 按 `TREE_CODE` 分派，把嵌套的 GENERIC 树拍平成三地址形式的 GIMPLE。`pre_p` 是“副作用语句要追加到哪里”，这是由调用者传下来的上下文，即继承属性。

**Go 编译器**

```go
// cmd/compile/internal/walk（简化）
func walkExpr1(n ir.Node, init *ir.Nodes) ir.Node {
    switch n.Op() {
    case ir.OADD, ir.OSUB, ir.OMUL:
        n := n.(*ir.BinaryExpr)
        n.X = walkExpr(n.X, init)
        n.Y = walkExpr(n.Y, init)
        return n
    ...
    }
}
```

逐节点重写，返回新节点（综合属性）；`init` 收集需要提到前面执行的语句（继承属性，形式和 GCC 的 `pre_p` 如出一辙）。

**rustc**：AST → HIR（`rustc_ast_lowering`）→ THIR → MIR（`rustc_mir_build`），每一步都是结构递归的树到树翻译。

**V8**：`BytecodeGenerator` 继承 `AstVisitor<BytecodeGenerator>`，`VisitBinaryOperation`、`VisitCall` 逐节点发射字节码。

**Babel**（JavaScript 工具链）

```js
traverse(ast, {
  BinaryExpression: {
    enter(path) { /* 下行：可读 path.scope 等上下文 */ },
    exit(path)  { /* 上行：子节点已处理完毕 */ }
  }
});
```

这个 `enter`/`exit` 的形状，和 ANTLR 的 Listener 完全相同。进入时处理继承属性，离开时处理综合属性，正是第一节那个支点命题的直接实现。

### 5.1 一张对照表

把这些写法和属性文法、以及 ANTLR 4 的机制并排放：

| 属性文法概念    | ANTLR 4                            | 现代编译器的惯用写法                                          |
| --------- | ---------------------------------- | --------------------------------------------------- |
| 综合属性      | Visitor 返回值；Listener 的 `exit` + 值栈 | 递归函数返回值（`Value*`、`ExprResult`）                      |
| 继承属性      | Visitor 构造参数；Listener 的 `enter`    | 上下文对象 / 参数（`Sema`、`CodeGenFunction`、`init`、`pre_p`） |
| 带注释的语法树   | 侧表 `Map<ctx, Attr>`                | AST 节点字段、侧表、类型缓存                                    |
| 固定的 L 序求值 | Listener + `ParseTreeWalker`       | `enter`/`exit` 式遍历器（Babel、各种 linter）                |
| 自定义求值顺序   | Visitor 手动调用 `visit`               | 手写递归函数，想先算哪个子节点就先算哪个                                |
| 多遍        | 多个 Listener/Visitor                | AST → HIR → MIR，或 Sema → CodeGen                    |

所以更准确的说法是：

> **SDT 从“文法的附属物”变成了“树上的通用编程范式”。** 形式化版本（属性文法、S/L 属性）退到教学、DSL 和工具链；实践版本（结构递归 + 上下文参数 + 返回值）成了所有编译器前端的默认写法。人们不再说“写一个 SDT”，只说“写个 visitor”或“写个 lower 函数”。

## 六、边界的工程处理：多遍、引用与侧表

第一节说过，非 L 依赖一遍算不出来。现代编译器有三种系统性的应对手段。

### 6.1 多遍

最直接的办法是把一次翻译拆成几遍，让每一遍都只做 L 属性能完成的事。一个典型的前端：

1. 解析，构造 AST；
2. 收集声明，建立符号表骨架；
3. 名字解析、类型检查；
4. 生成 IR。

Java 中类成员可以互相引用、可以先使用后声明，就是靠“先收集所有成员签名，再检查方法体”这样的两遍完成的。

### 6.2 用引用拆掉依赖环

很多看似有环的依赖，可以通过“属性值存引用而非值”拆开。

以互相引用的两个结构体为例：

```c
struct A;                         // 前向声明
struct B { struct A *a; };
struct A { struct B *b; };
```

处理 `B` 时，`A` 的完整定义还不存在。但 `B` 的成员只需要一个**指向 `A` 的符号表条目的引用**，条目内容可以之后再填。依赖图从“A 与 B 互相依赖”变成了“各自引用一个稍后才完整的条目”，就能一遍处理。

类型推断中的类型变量也是同一个思路：先用一个未知量占位，之后通过合一（unification）求出它。

> **很多“非 L 属性”不是天生的，是因为属性被当作值传递才变成非 L。改成引用，常常就退回 L 了。**

### 6.3 侧表

属性不一定要存在 AST 节点的字段里，也可以存在一张以节点为键的表里，即 `Map<Node, Attr>`。这在语义上和“给节点加字段”等价，好处是把**属性的存在**和**计算它的那一遍**解耦：第一遍填一部分，第二遍读出来再填另一部分，互不干扰。这就是“带注释的语法树”最直接的工程实现。

### 6.4 判据表

面对一个新的翻译任务，先问：**属性依赖图长什么样？**

| 依赖形状 | 最少遍数 | 现代写法 | 例子 |
|---|---|---|---|
| 纯综合（只向上） | 1 | 递归函数返回值 | 常量折叠、表达式求值 |
| L 属性（向下、向左） | 1 | 递归 + 上下文参数；`enter`/`exit` | 作用域解析、`break` 目标 |
| 依赖右兄弟但无环 | 1 | 自定义子节点访问顺序 | 先求右侧类型再处理左侧 |
| 有环，但可换成引用 | 1 | 符号表引用 + 延迟填充 | 前向声明、类型变量 |
| 局部非 L | 局部 2 遍 | 缓存后延迟处理 | C++ 类内成员函数体 |
| 需要全局信息 | ≥2 | 多遍 + 侧表 / 中间 IR | Java 成员互引、全程序分析 |

这张表的价值在于，它在写第一行代码之前就能告诉你：这件事一遍能不能做完。

## 七、分水岭：中间端没有语法

到这里必须划一条清楚的界线，否则结论就会说过头。

**到了 IR 层，语法结构已经不存在了。**

LLVM IR 是一张控制流图加一组 SSA 值。“父节点”“子节点”“左兄弟”这些概念失去了意义，取而代之的是支配树、逆后序、循环嵌套树、use-def 链。

- 常量传播、GVN、LICM、死代码消除的理论基础，是**格上的单调框架与不动点迭代**。遍历顺序由算法决定（逆后序、支配树序、worklist 出队序），与源代码的句法结构毫无关系。
- GVN 和 hash-consing 会把 `a+b` 和 `b+a` 合并成同一个值，把原本分散在不同语句里的相同计算合并。**刻意摧毁源程序的语法结构，正是优化的目的之一。**
- Sea of Nodes（HotSpot C2、早期的 V8 TurboFan）更进一步：连控制流顺序都不作为固定结构，节点只通过数据依赖和控制依赖相连。

所以，对“LLVM 用不用 SDT”最诚实的回答是：**LLVM 中间端处理的对象没有语法，SDT 在这里无从谈起。**

LLVM 中唯一处理“语法”的地方是 `.ll` 文本的解析器 `LLParser`。它是手写的，边解析边直接构造 IR 对象，不建立独立的语法树，一遍完成，相当于一个极简的严格 SDT。

MLIR 的情况稍微微妙一些。它的 `RewritePattern`、方言转换（Dialect Conversion）和贪婪重写驱动，确实借用了“匹配局部模式、替换成新结构”的直觉。但它匹配的是操作（operation）及其数据依赖，而不是文法产生式；驱动方式是工作列表上反复重写直到不动点，而不是一遍遍历。它属于**项重写系统**，不属于属性文法。

## 八、意外的重逢：指令选择就是树文法

穿过没有语法的中间端，到了后端的指令选择，SDT 以一种意想不到的形式重新出现。而且这里保存的是它**最形式化**的那一支血脉。

### 8.1 曾经，指令选择就是一次语法分析

1978 年，Glanville 和 Graham 提出了一个大胆的想法：把 IR 表达式树按前缀顺序线性化成一个“句子”，把机器指令描述成文法的产生式，然后**用 LR 分析器去解析它**。每次归约就发射一条机器指令。

这字面意义上就是语法制导翻译：文法是机器描述，归约动作是代码生成，翻译由分析驱动。

### 8.2 BURG：带代价的树文法

后来的研究把“字符串上的 LR 分析”推广为“树上的匹配”。到 1990 年代初，Fraser、Hanson、Proebsting 等人的 BURG 和 iburg 把指令选择写成一种**带代价的树文法**：

```
reg  : ADD(reg, reg)          = 1   (add)
reg  : ADD(reg, CONST)        = 1   (addi)
addr : ADD(reg, CONST)        = 0
reg  : LOAD(addr)             = 1   (ld)
```

这里的 `reg`、`addr` 就是**非终结符**，表示“一个值可以以什么形式存在”：在寄存器里，还是作为一个可被吸收的地址表达式。每条规则是一条产生式，附带一条指令和一个代价。

指令选择于是变成**树文法上的语法分析**：给定一棵 IR 树，找出代价最小的推导。由于树的后序遍历就是一个拓扑顺序，可以自底向上做动态规划，每个节点为每个非终结符记录最小代价。Aho 和 Johnson 在 1976 年就证明了这类问题在树上可以在线性时间内最优求解。

这里的对应关系非常整齐：

| 属性文法 | 树文法指令选择 |
|---|---|
| 非终结符 | 值的存在形式（`reg`、`addr`、`imm`） |
| 产生式 | 指令模式 |
| 综合属性 | 每个非终结符的最小代价 + 对应选择 |
| 自底向上求值 | 后序遍历上的动态规划 |
| 语义动作 | 发射机器指令 |

### 8.3 LLVM：保留形式，放弃最优

LLVM 的 SelectionDAG 指令选择继承了这套形式。目标描述文件里的模式就是树模式：

```tablegen
def ADD64rr : ... [(set GR64:$dst, (add GR64:$src1, GR64:$src2))]>;
def ADD64ri32 : ... [(set GR64:$dst, (add GR64:$src1, i64immSExt32:$src2))]>;
```

x86 的寻址模式则用 `ComplexPattern` 描述：

```tablegen
def addr : ComplexPattern<iPTR, 5, "selectAddr", [], [SDNPWantParent]>;
```

`addr` 扮演的正是 BURG 里非终结符 `addr` 的角色：一棵子树如果能被分解成 `base + index*scale + disp`，就可以作为一个整体被 load 或 store 指令吸收。

但 LLVM 在三处偏离了经典理论：

1. **树变成了 DAG。** 公共子表达式被共享，一个节点可能有多个使用者。Aho、Johnson、Ullman 在 1977 年证明，带公共子表达式的最优代码生成是 NP 完全的。
2. **放弃了动态规划。** LLVM 的匹配器是贪婪的：在每个节点上按模式复杂度排序，选第一个能匹配的，不做全局代价最小化。代码质量主要依靠匹配之前的类型合法化、运算合法化和 DAG combine 预先把图“整形”好。
3. **作用范围是单个基本块。** SelectionDAG 按基本块构建，跨块的模式看不到。这是 GlobalISel 出现的动因之一：它直接在函数级的 SSA 形式 Machine IR 上工作，并在选择指令之前先确定寄存器银行（通用寄存器、浮点寄存器、向量寄存器）。GlobalISel 和 SelectionDAG 共享同一套 TableGen 模式。

其他编译器也是同一家族的变体：

- **Go**：`_gen/*.rules` 里的文本重写规则，如 `(ADDQconst [c] x) => (LEAQ [c] x)`，生成为按操作码分派的重写代码，反复应用直到不动点，没有代价模型；
- **Cranelift**：用专门的 DSL ISLE 编写 lowering 规则，编译成 Rust 的决策树；
- **HotSpot C2**：`.ad` 机器描述文件经 ADLC 生成匹配器，带有代价，最接近 BURG 传统。

### 8.4 为什么说这是血脉而非巧合

前端的 SDT 是“在源语言的语法树上，按产生式计算属性”；指令选择是“在 IR 的表达式树（或 DAG）上，按机器描述的模式计算代价和代码”。两者的骨架相同：**用文法（或模式集）描述结构，用结构驱动翻译**。

区别在于求值顺序的决定方式：前端由 L 序决定，指令选择由代价模型或模式优先级决定。从第一节的角度看，这只是“求值顺序由谁决定”这一个参数的不同取值。

## 九、全景：每一层的身份

| 层 | 处理对象 | 主导理论 | 与 SDT 的关系 |
|---|---|---|---|
| 词法分析 | 字符流 | 有限自动机 | 正则文法 + 动作，严格形态仍常见 |
| 语法 + 语义分析 | token 流 → AST | **L 属性求值**，上下文相关消歧 | **严格形态退场，实质被手写解析器吸收并加强** |
| AST → IR | 带类型的树 | **结构递归 / 树到树翻译** | **宽泛形态的完全体** |
| 中间端优化 | CFG + SSA | 格上单调框架、不动点、图算法、项重写 | **不适用：没有语法** |
| 指令选择 | DAG / SSA MIR | 树模式匹配、带代价的树文法 | **形式化血脉的后代**，求值顺序由代价或优先级决定 |
| 调度、寄存器分配 | 机器指令序列 | 列表调度、图着色、组合优化 | 不适用 |

## 十、给编译器作者的建议

把以上内容转成可操作的判断：

**1. 解析器优先手写。** 理由主要不是性能，而是诊断、错误恢复和上下文相关的语法。手写递归下降和 SDT 的映射是天然的：每个 `parseXxx()` 的返回值是综合属性，传下去的上下文是继承属性。如果语言语法规整、只需要建 AST，用 PEG 或 LR 生成器也完全合理，CPython 和 GHC 就是例子。

**2. 先画依赖图，再决定遍数。** 第六节的判据表能在写代码前告诉你一遍够不够。看到“依赖右边”“依赖全局”，就提前规划延迟处理或分遍。

**3. 遇到依赖环，先想引用，再想加遍。** 符号表引用、类型变量、占位条目，能拆掉大部分看似有环的依赖。

**4. 属性优先放侧表或独立结构，不要把所有东西都塞进 AST 字段。** 遍数增多之后，这能避免 AST 节点不断膨胀。

**5. 到了 IR 层，换一套思维方式。** 不要再寻找“父节点”，开始考虑支配关系、数据流不动点和工作列表。用语法树的直觉去读优化器会走偏：优化的目的之一，就是打破源程序的结构。

**6. 写指令选择时，记得它是一种“文法”。** 模式集描述的是“IR 结构可以被什么样的指令覆盖”。模式的优先级、非终结符式的抽象（如 `addr`）、覆盖不到时的回退路径，都可以用文法的眼光来检查。

## 结语

语法制导翻译在现代编译器中的处境，可以用一句话概括：

**作为一种技术，它退场了；作为一种思想，它无处不在；作为一种形式化方法，它在指令选择中找到了第二个家。**

严格形态（文法里嵌动作、`$$` 与 `$1`、归约顺序驱动求值）退出了主流生产编译器的前端，原因是诊断质量、上下文相关语法和增量解析这三项需求。它的实质，即“按结构递归地计算属性：综合属性靠返回值上行，继承属性靠上下文下行”，成了前端每一层的默认写法，普遍到人们已经不再给它起名字。

它的边界也很清楚：中间端处理的是图和格，没有语法可依；后端的调度与寄存器分配是组合优化问题。在这两者之间，指令选择又把“用文法描述结构、用结构驱动翻译”这件事重新捡了起来，只是树变成了 DAG，L 序变成了代价顺序。

所以教科书仍然要讲 SDD 与 SDT。这套理论的价值不在于能直接照抄成代码，而在于它提供了一套**可行性判据**：某个翻译在什么遍历顺序下算得出来，什么时候必须延迟、分遍或换一种中间表示。这套判据在 LLVM 时代依然成立，只是应用对象从“文法”变成了你自己定义的 AST、IR 和机器描述。

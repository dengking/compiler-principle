# 编译器领域的其他万能锤

> **开场**
> 
> 前两轮我们确认了两把锤子：前端的 **NFA → DFA**、后端的 **格上单调不动点迭代**，并发现它们其实是同一把（子集构造 = 幂集格上的最小不动点）。
> 
> 但编译器远不止"前端识别 + 后端优化"。类型系统、IR 设计、控制流降级、增量编译、正确性保证、语言运行时——每个领域都有自己的万能锤。下面这十把是我认为**真正达到"万能锤"标准**的：
> 
> |       | 锤子                        | 一句话                                  | 统一了什么                                       |
> | ----- | ------------------------- | ------------------------------------ | ------------------------------------------- |
> | **A** | **合一与约束求解**               | 把"推导"变成"解方程"                         | 类型推导、重载决议、泛型实例化、trait 求解、模式匹配、别名分析          |
> | **B** | **控制流即数据（CPS / 状态机化）**    | 任何控制结构都能变成"显式状态 + 分派循环"              | CPS、闭包转换、去函数化、async/await、生成器、协程、异常、SSA     |
> | **C** | **偏求值与分阶段（Futamura）**     | 编译 = 对解释器做偏求值                        | 常量折叠、内联、单态化、模板实例化、宏、循环展开、JIT、Truffle        |
> | **D** | **归纳结构上的折叠**              | 程序是归纳定义的，所以一切关于程序的计算都是折叠             | 属性文法、语法制导翻译、类型检查、代码生成、recursion schemes     |
> | **E** | **唯一化与记忆化（hash-consing）** | 用共享把"结构相等"降为"指针相等"，顺带把指数压成 DAG       | 符号表、类型内部化、GVN、BDD、e-graph、packrat、增量编译      |
> | **F** | **SCC 分解 + 拓扑序**          | 把"需要迭代"的部分局部化到强连通分量内部                | 依赖顺序、递归绑定组、自然循环、过程间分析顺序、Datalog 分层          |
> | **G** | **判定树与分派**                | 一切多路选择都归约为构造判定树，权衡是表大小 vs 判定深度       | 模式匹配编译、switch 降级、虚表、PIC、指令选择匹配器             |
> | **H** | **模拟关系**                  | 一切"变换正确"的证明都是构造一个模拟关系                | CompCert、翻译验证、Alive2、差分测试、以及 `L(D)=L(N)` 本身 |
> | **I** | **需求驱动 / 查询式架构**          | 把编译器从 push 的 pass 流水线翻成 pull 的查询 DAG | rustc queries、Salsa、Roslyn、增量解析、按需分析、构建系统   |
> | **J** | **归约与逐层降级（nanopass）**     | 不解决问题，把它翻译成一个已解决的问题                  | 异常→CPS、OO→闭包、泛型→字典、协程→状态机、MLIR 渐进降级         |
> 
> 最后 §11 会说明：**这十把 + 前两轮的八把，最终只有五种机制。**

## 0. 什么算"万能锤"：三条判据

在继续之前先立标准，否则"万能锤"会退化成"技术清单"。

> **判据一：跨领域复现。** 至少在编译器的三个互不相邻的子领域独立出现（例如：类型系统 / 优化 / 运行时）。
> 
> **判据二：有统一的数学骨架。** 不是"手法相似"，而是能写出一段**参数化的代码或一条定理**，各处只是不同实例化。
> 
> **判据三：解释力。** 用它能*事后解释*为什么某些看似无关的技术是同一个东西，并**预测**新技术的形态。

按这三条：

| 不算万能锤      | 为什么                  |
| ---------- | -------------------- |
| "位向量优化"    | 只是编码技巧，无统一骨架（判据二不过）  |
| "内联"       | 单个变换，不跨领域（判据一不过）     |
| "用哈希表加速"   | 无解释力（判据三不过）          |
| "启发式 + 调参" | 是**放弃**使用锤子后的兜底，不是锤子 |

下面十把都能过三条。每把我都会给出：**骨架 → 钉子表 → 深层洞察 → 与已讨论锤子的连线**。

## A. 合一与约束求解

### A.1 骨架

**合一（unification）**：给定两个含变量的项 `t₁`、`t₂`，求最一般的代换 `σ` 使 `σ(t₁) = σ(t₂)`。

```python
def unify(a, b, subst, uf):
    a, b = uf.find(resolve(a, subst)), uf.find(resolve(b, subst))
    if a is b: return
    if is_var(a): 
        occurs_check(a, b)            # ← 防止 α = α → α 这种循环
        uf.union(a, b); return
    if is_var(b): return unify(b, a, subst, uf)
    if a.ctor != b.ctor or a.arity != b.arity:
        raise TypeError(f"cannot unify {a} with {b}")
    uf.union(a, b)                    # ★ 先合并再递归：打断循环 + 记忆化
    for x, y in zip(a.args, b.args):  # 同余规则：结构相同则逐个合一
        unify(x, y, subst, uf)
```

**注意 `uf.union` 出现在递归之前**——这正是 §E 的 hash-consing 和 ANTLR 4 的"先写入占位再递归填操作数"（Braun SSA 构造）用的同一个技巧：**先承诺假设，再验证，从而处理环**。

**约束求解**是它的推广：不再只解等式 `t₁ = t₂`，还解 `t₁ ⊆ t₂`（包含）、`t₁ <: t₂`（子类型）、`C(t₁,…,tₙ)`（谓词）。

### A.2 钉子表

| 应用                                   | 约束形式                     | 求解器                                 |
| ------------------------------------ | ------------------------ | ----------------------------------- |
| **Hindley–Milner 类型推导**              | `τ₁ = τ₂`                | 合一 + Union-Find；泛化/实例化              |
| **重载决议 / C++ 模板推导**                  | `τ = f(?)`，带偏序           | 合一 + 偏特化排序                          |
| **Rust trait 求解 / Haskell 类型类**      | `C τ₁ … τₙ`              | **归约（Prolog SLD）** + 一致性检查          |
| **局部类型推断**（Java/C#/Scala/TypeScript） | `τ₁ <: τ₂`（子类型约束）        | 双向定型 + 约束图 + 变型求解                   |
| **GADT / 局部等式**（OutsideIn(X)）        | 分层：先解简单约束，难的推迟           | 约束生成与求解**分离**                       |
| **区域推断**（MLKit、早期 Rust）              | 区域包含 `ρ₁ ⊆ ρ₂`           | 包含约束的传递闭包                           |
| **借用检查**（NLL）                        | 生命周期约束 `'a: 'b`          | CFG 上的约束图 + 可达性                     |
| **模式匹配**                             | **单向合一**（只有一侧有变量）        | 匹配（matching），线性时间                   |
| **项重写 / 指令选择**                       | LHS 匹配                   | 判别网络（discrimination net）、e-matching |
| **e-graph 的 e-matching**             | 模式 → e-class             | 关系式查询 / 编译成 join 计划                 |
| **Steensgaard 指向分析**                 | **等式** `pts(p) = pts(q)` | **合一**，`O(n α(n))`                  |
| **Andersen 指向分析**                    | **包含** `pts(p) ⊇ pts(q)` | 约束图上的传递闭包，`O(n³)`                   |
| **SMT 求解器的 EUF 理论**                  | 等式 + 同余                  | 同余闭包（§E）                            |
| **多面体调度**                            | 仿射不等式                    | Farkas + ILP（后端大锤⑤）                 |

### A.3 深层洞察

> **洞察一：合一是"最快但最粗"的等价推导，包含约束是"更慢但更细"的版本。这又是一次近似阶梯。**
> 
> |       | 合一（等式）                        | 包含（子集）               |
> | ----- | ----------------------------- | -------------------- |
> | 指向分析  | **Steensgaard** `O(n α(n))`   | **Andersen** `O(n³)` |
> | 类型系统  | HM（无子类型）                      | 带子类型的推断（`<:`）        |
> | 精度损失  | `p = q` 强行把两侧**合并**，方向信息丢失    | 保留方向                 |
> | 前端对应物 | **SLR 用全局 `FOLLOW`**（合并所有上下文） | **LR(1)** 精确上下文      |
> 
> 这与前两轮的 `SLR → LALR → LR(1)`、`线性近似前看 → 全前看`、`SLL → LL`、`MFP → MOP`、`上下文不敏感 → k-CFA` 是**同一条阶梯的第六次出现**。
> 
> **合一 = 把"有向的包含关系"塌缩成"无向的等价关系"。** 这正是我们反复见到的"把笛卡尔积压扁成投影"在**关系方向**这个维度上的版本。

> **洞察二：约束生成与约束求解分离，是现代类型系统的架构革命。**
> 
> 传统 HM 是"边遍历 AST 边合一"——错误信息糟糕、无法处理 GADT/局部等式、难以扩展。
> OutsideIn(X)、Rust 的 trait solver、Scala 3 的定型都改成两阶段：
> 
> ```
> ① 遍历 AST，只生成约束（不求解），记录来源位置
> ② 把约束集合整体交给求解器，按难度分层求解
> ```
> 
> **好处**：错误信息可归因、约束可推迟（deferred）、可插拔不同求解器、可与其他分析共享求解器。
> 
> **这与后端 SCCP"把常量与可达性合并为积格联合求解 > 顺序组合"是同一个原则**：把耦合的决策交给一个统一求解器，而不是顺序地各自贪心。

> **洞察三：`occurs check` 就是"检测不动点计算中的非良基环"。** 关掉它，你得到的就是**递归类型**（equirecursive types）——而处理递归类型的类型相等判定，又需要**互模拟**（§H）或**Union-Find + 先假设后验证**。同一批工具再次出现。

### A.4 连线

```
合一的数据结构 = Union-Find = 后端大锤②的悲观合并方向
合一的同余规则 = §E 的同余闭包
合一处理环的技巧（先 union 再递归）= Braun 惰性 SSA 构造 = e-graph rebuilding
Steensgaard vs Andersen = 又一次"近似阶梯"母题
约束生成/求解分离 = SCCP 的"联合求解 > 顺序组合"
模式匹配（单向合一）→ 编译成判定树 = §G
```

## B. 控制流即数据：CPS 与状态机化

### B.1 骨架

> **任何控制结构，都可以被转换为"显式的状态数据 + 一个分派循环"。**

这句话的三种形态：

| 形态                            | 把什么变成数据                                                |
| ----------------------------- | ------------------------------------------------------ |
| **CPS 转换**                    | 把"接下来做什么"变成一个函数值（续延）                                   |
| **去函数化**（defunctionalization） | 把"函数值"变成一个标签 + 数据（tag + payload），调用变成 `switch`         |
| **状态机化**                      | 把"当前执行到哪"变成一个整数状态变量，控制流变成 `loop { match state { … } }` |

三者是同一条流水线的三段：

```
高阶控制流  ──CPS──>  续延作为一等函数  ──去函数化──>  标签 + 数据 + 分派循环
                                                       ↑
                                                  这就是一台状态机
```

### B.2 钉子表

| 应用                                              | 用了哪一段            | 备注                                                             |
| ----------------------------------------------- | ---------------- | -------------------------------------------------------------- |
| **CPS 转换**（Scheme/ML 编译器）                       | CPS              | 尾调用、`call/cc` 免费获得                                             |
| **ANF / 一元中间语言**                                | CPS 的"命名化"部分     | 所有操作数变为原子                                                      |
| **SSA ≡ CPS**（Appel 1998、Kelsey 1995）           | ——               | φ 函数 ≡ 续延的参数；支配树 ≡ 词法作用域嵌套                                     |
| **闭包转换**                                        | 去函数化的前半          | 把自由变量打包成环境记录                                                   |
| **去函数化**（Reynolds 1972）                         | 去函数化             | 高阶 → 一阶；也是 Futamura 的常见搭档                                      |
| **异常**                                          | CPS（双续延：正常 + 异常） | 或降为零成本方案：**表驱动的 unwinding**（`.gcc_except_table` = 又一张判定表，见 §G） |
| **生成器 / 迭代器**（Python `yield`、C# `yield return`） | 状态机化             | `yield` 点 = 状态                                                 |
| **async/await**（C#、Rust、Kotlin、JS）              | 状态机化             | `await` 点 = 状态                                                 |
| **C++20 协程**                                    | 状态机化             | `coroutine_handle` + `resume`                                  |
| **Kotlin 挂起函数**                                 | CPS + 状态机化       | 编译成 `Continuation` 参数 + 状态字段                                   |
| **Trampolining**                                | 去函数化 + 分派循环      | 在无尾调用优化的平台上实现深递归                                               |
| **解释器的 threaded code / 计算 goto**                | 分派循环             | 把 `switch` 换成间接跳转，改善分支预测                                       |
| **Effect handlers**（OCaml 5、Eff）                | 分段 CPS           | 一等续延的受限形式                                                      |

### B.3 深层洞察：async/await 降级就是手写的 NFA → DFA

这是本轮最强的一条连线。

```rust
async fn f(x: u32) -> u32 {
    let a = g(x).await;          // 挂起点 1
    let b = h(a).await;          // 挂起点 2
    a + b
}
```

编译器生成的东西（简化）：

```rust
enum FState {
    Start { x: u32 },                     // 状态 0
    AwaitG { fut: GFut },                 // 状态 1：等 g，需保存 —— 
    AwaitH { a: u32, fut: HFut },         // 状态 2：等 h，需保存 a ★
    Done,
}

impl Future for F {
    fn poll(&mut self, cx: &mut Context) -> Poll<u32> {
        loop {                                     // ← 分派循环
            match &mut self.state {                // ← 状态转移表
                Start { x } => {
                    let fut = g(*x);
                    self.state = AwaitG { fut };   // δ(0, ·) = 1
                }
                AwaitG { fut } => match fut.poll(cx) {
                    Poll::Pending  => return Poll::Pending,   // 让出：状态被保存
                    Poll::Ready(a) => {
                        let fut = h(a);
                        self.state = AwaitH { a, fut };       // δ(1, ready) = 2
                    }
                },
                AwaitH { a, fut } => match fut.poll(cx) {
                    Poll::Pending  => return Poll::Pending,
                    Poll::Ready(b) => { let r = *a + b;
                                        self.state = Done;
                                        return Poll::Ready(r); }  // 接受态
                },
                Done => panic!("polled after completion"),
            }
        }
    }
}
```

**逐项对照**：

| NFA → DFA / DFA 词法器                               | async/await 降级                         |
| ------------------------------------------------- | -------------------------------------- |
| DFA 状态                                            | `enum FState` 的一个变体                    |
| 转移表 `δ[state][char]`                              | `match state { … }` 分派                 |
| 主循环 `while (c = next()) { state = δ[state][c]; }` | `loop { match &mut self.state { … } }` |
| 输入符号                                              | `poll` 的一次调用（外部事件）                     |
| 接受态                                               | `Poll::Ready`                          |
| **DFA 状态携带的附加信息**（token 标签、优先级）                   | **状态变体携带的活跃变量**（`a` 必须存进 `AwaitH`）     |
| 状态可保存在一个整数中（增量词法分析可跨行续扫）                          | 状态机可保存在堆上（协程可跨线程恢复）                    |

> **关键之处**："状态变体里要存哪些变量？"这个问题的答案是——**在该挂起点处活跃的变量集合**。也就是说：
> 
> ```
> async/await 降级 = 状态机化（锤 B）
>                  + 每个挂起点的活跃变量分析（后端主锤）
>                  + 状态布局/联合体优化（可看作按状态求最大同时活跃集，类似 MAXLIVE）
> ```
> 
> **三把锤子在一个特性上组合。** 这也解释了为什么 Rust 的 `Future` 大小 = 各挂起点活跃集的"并集式布局"，以及为什么"在 `.await` 跨越处持有大对象"会让 Future 变胖——这就是**寄存器分配里的溢出问题在协程状态布局上的重演**。

> **洞察二：去函数化 = 把高阶控制流"确定化"。**
> 
> ```
> 高阶函数值 = "接下来可能做的事"，是一个不确定的集合
> 去函数化   = 枚举程序中所有可能的续延形态，编号，用 switch 分派
>            = 把"不确定的间接跳转"变成"有限的、可枚举的多路分支"
> ```
> 
> **这与子集构造在做同一件事**：都是把"运行时的不确定选择"换成"编译期枚举 + 表驱动分派"。而它的代价也一样——**控制流爆炸**（去函数化后的 `switch` 可能巨大，且失去模块性，因为需要**全程序**才能枚举所有续延，正如子集构造需要完整 NFA 才能确定化）。
> 
> 反面选择也一样存在：**保留间接调用（不去函数化）= 直接模拟 NFA**；用 **PIC/内联缓存**在运行期按需特化 = **lazy DFA**。

### B.4 连线

```
CPS ≡ SSA            → 后端大锤①（同一表示的两种语法）
状态机化 ≡ NFA→DFA   → 前端主锤
去函数化 ≡ 确定化     → 前端主锤；其反面（PIC）≡ lazy DFA
挂起点活跃变量        → 后端主锤（数据流分析）
状态布局             → 后端大锤④（寄存器分配的同构问题）
异常表 / unwind 表   → §G（判定表）
```

## C. 偏求值与分阶段：Futamura 投影

### C.1 骨架

**偏求值器**（partial evaluator）`mix`：

```
mix(p, s) = p_s        使得   ∀d.  p_s(d) = p(s, d)
                              ↑ 把已知的输入 s 烧进程序里
```

**Futamura 三投影**（1971）：

```
第一投影：  mix(interp, prog)  =  target        —— 编译！
           对解释器做偏求值 = 编译该程序

第二投影：  mix(mix, interp)   =  compiler      —— 编译器生成器！
           对 mix 自己做偏求值 = 从解释器自动得到编译器

第三投影：  mix(mix, mix)      =  cogen         —— 编译器生成器的生成器
```

> **这是编译原理最深刻的一条定理**：它说明**编译器不是一个独立的东西，而是"解释器 + 偏求值"的自动产物**。GraalVM/Truffle 就是这条定理的工业实现。

### C.2 钉子表：这些"不同的优化"全是同一个操作

| 优化                                 | 被烧进程序的"已知输入"                                            |
| ---------------------------------- | ------------------------------------------------------- |
| **常量折叠**                           | 操作数的值                                                   |
| **常量传播**                           | 变量在此处的值                                                 |
| **内联**                             | 调用点的实参（尤其是常量实参、函数实参）                                    |
| **循环展开**                           | 循环计数器的具体值                                               |
| **循环剥离 / peeling**                 | 前几次迭代的索引                                                |
| **单态化**（Rust/C++ 模板）               | **类型参数**                                                |
| **字典传递的特化**                        | 类型类实例                                                   |
| **宏展开 / `constexpr` / `comptime`** | 编译期已知的一切（Zig 的 `comptime` 是显式偏求值）                       |
| **模板实例化**                          | 模板实参                                                    |
| **去虚化 + 内联**                       | 接收者的具体类型                                                |
| **JIT 值特化**                        | 运行时观测到的实参值                                              |
| **Trace JIT**                      | 整条已观测的执行路径（把分支结果烧进去 + 守卫）                               |
| **Truffle / Graal**                | **AST 解释器 + 用户程序 ⇒ 编译码**（字面的第一投影）                       |
| **Halide/TVM 的 schedule 应用**       | 调度参数（tile 大小、展开因子）                                      |
| **`printf` 格式串特化**                 | 格式字符串                                                   |
| **正则表达式编译**                        | **正则式本身**（`match(regex, text)` 对 `regex` 偏求值 = 生成 DFA！） |
| **数据库查询编译**                        | SQL 语句                                                  |
| **simdjson / 结构索引**                | 输入的结构特征                                                 |

> **注意倒数第三行**：`正则匹配 = 一个解释器 interp(regex, text)`；对 `regex` 做偏求值就得到一个专用的匹配程序——**这正是 NFA→DFA + 代码生成**。
> 
> 也就是说：**前端的万能锤是偏求值这把锤子的一个实例。** 词法器生成器 = 对"正则解释器"做第二投影；parser 生成器 = 对"通用 CFG 解析器（Earley/GLL）"做第二投影。这解释了为什么"生成器"（flex/bison/ANTLR）这个形态在编译器领域如此普遍。

### C.3 深层洞察

> **洞察一：绑定时间分析（binding-time analysis, BTA）就是一个数据流分析。**
> 
> 偏求值的第一步是判断每个表达式是 **static**（编译期可算）还是 **dynamic**（必须留到运行时）。这是一个两点格 `static ⊑ dynamic` 上的正向单调不动点计算——**后端主锤的直接实例**。
> 
> ```
> BTA 的格：{static, dynamic}，static ⊑ dynamic
> 传递函数：  一个操作是 static ⟺ 所有操作数都是 static
> 汇合：      join = 取 dynamic（有一个 dynamic 则整体 dynamic）
> ```
> 
> 这与常量传播的格 `⊤ ⊒ const ⊒ ⊥` 结构相同——事实上 **BTA 是常量传播的"是否已知"投影**（丢掉具体值，只保留"知不知道"）。**又一次投影近似。**

> **洞察二：偏求值的核心难题是终止性，其解法与 widening 完全同构。**
> 
> ```
> 偏求值的爆炸： 展开一个递归函数时，若参数总是 static，可能无限展开
> 数据流的爆炸： 区间格高度无限，Kleene 迭代不收敛
> ```
> 
> 两者的解法也一样：
> 
> | 偏求值                                                   | 数据流分析                             | 共同动作        |
> | ----------------------------------------------------- | --------------------------------- | ----------- |
> | **泛化**（generalization）：把某个 static 参数**主动降级为 dynamic** | **widening `∇`**：把区间**主动扩到 `±∞`** | 主动丢弃精度以保证终止 |
> | 展开预算 / 内联深度阈值                                         | `k`-limiting / `k`-CFA 截断         | 有界化         |
> | Truffle 的 `@ExplodeLoop` vs 编译边界 `@TruffleBoundary`   | 手动指定 widening 点                   | 人工标注在哪里停    |
> 
> 而 §6 讲过的 **LL(\*) 用 DFA 自环抽象 `b*`** 也是同一个动作。这是"有界化/加速收敛"母题的第四次出现。

> **洞察三：JIT = 以运行时值为 static 输入的在线偏求值 + 守卫。**
> 
> ```
> 静态偏求值： static 输入必须编译期已知 ⇒ 能特化的很少
> JIT：       把"运行期观测到的值/类型"当作 static ⇒ 能特化的极多
>             代价：观测可能失效 ⇒ 必须加守卫 + 去优化
> ```
> 
> **而 ANTLR 4 的 ALL(\*) 就是这件事在解析器上的实现**：把"眼前这串 token 和这个具体栈"当作 static 输入，在线特化出一个 DFA 并缓存。
> 
> 所以第三轮说的"JIT ≡ ALL(\*)"可以升级为更准确的说法：
> **两者都是"以运行时信息为 static 输入的在线偏求值 + 记忆化 + 可检测失败的退路"。**

### C.4 连线

```
BTA                  → 后端主锤（数据流分析）
泛化/展开预算         → widening / k-limiting（有界化母题）
第二投影             → 解释了"生成器"（flex/bison/ANTLR/BURG）这个形态
对 regex 偏求值       → 前端主锤（NFA→DFA + 代码生成）
JIT = 在线偏求值      → 后端大锤⑥ + ALL(*)
记忆化（避免重复特化）  → §E
分阶段编程（显式 static/dynamic）→ 把 §J 的"降级"变成用户可控
```

## D. 归纳结构上的折叠 —— 并证明它与后端主锤是同一把

### D.1 骨架

程序（AST、类型、IR）是**归纳定义**的。因此一切关于程序的计算，都是在其归纳结构上的**折叠（fold / catamorphism）**：

```
fold : (代数 F A → A) → μF → A
```

具体化为**属性文法**：

```
综合属性（synthesized）：  自下而上   —— 子节点 → 父节点
继承属性（inherited）：    自上而下   —— 父/兄 → 子节点
```

| 属性种类                    | 遍历方式        | 与解析的关系              |
| ----------------------- | ----------- | ------------------- |
| **S-属性**（只有综合属性）        | 一遍自底向上      | 可在 **LR 规约动作**中直接求值 |
| **L-属性**（继承属性只依赖左兄弟和父）  | 一遍从左到右深度优先  | 可在 **LL 递归下降**中直接求值 |
| **一般属性文法**              | 需要多遍或按依赖排序  | 需要拓扑序（§F）           |
| **循环属性文法**（circular AG） | **需要不动点迭代** | ← 关键！见 §D.3         |

### D.2 钉子表

| 应用                                         | 综合属性                  | 继承属性                                |
| ------------------------------------------ | --------------------- | ----------------------------------- |
| **类型检查**                                   | 表达式的类型                | 期望类型（双向定型的 checking 模式！）            |
| **常量折叠**                                   | 子表达式的常量值              | ——                                  |
| **代码生成**                                   | 生成的指令序列、结果寄存器         | 目标寄存器、跳转标签                          |
| **Sethi–Ullman 编号**                        | 所需寄存器数                | ——                                  |
| **短路布尔翻译**                                 | ——                    | `trueLabel` / `falseLabel`（经典 L-属性） |
| **作用域/符号表**                                | 声明的符号                 | 当前环境                                |
| **`nullable/firstpos/lastpos`**（龙书 §3.9.5） | 全是综合属性                | ——                                  |
| **`FIRST` 集合**                             | 综合                    | ——                                  |
| **`FOLLOW` 集合**                            | ——                    | 继承（且**有环 ⇒ 需迭代**）                   |
| **树模式匹配 / BURS 标号**                        | `cost[nt]`            | 选中的规则（第二遍自顶向下）                      |
| **MLIR / LLVM 的 pattern rewrite**          | ——                    | 折叠 + 重写的组合                          |
| **Recursion schemes**（Haskell）             | cata                  | ana / para / histo…                 |
| **JastAdd / Silver / Kiama**               | 参考属性文法（RAG），属性可指向别的节点 | 支持循环属性                              |

### D.3 深层洞察：树上的折叠 = 图上的不动点

> **这是本轮最重要的一条洞察，它解释了为什么后端主锤必然出现。**

```
结构是树（无环）    ⇒  依赖关系是偏序  ⇒  一遍拓扑序遍历即可求值   = 折叠
结构是 DAG          ⇒  依赖仍是偏序    ⇒  拓扑序 + 记忆化          = 折叠 + hash-consing (§E)
结构有环（CFG/递归） ⇒  依赖有环        ⇒  拓扑序不存在
                                       ⇒  **必须迭代到不动点**    = 后端主锤
```

**证据链**：

| 计算                            | 结构                | 方法              |
| ----------------------------- | ----------------- | --------------- |
| `FIRST` 集                     | 文法依赖图（可能有环，因为左递归） | 迭代到不动点          |
| `FOLLOW` 集                    | 有环                | 迭代到不动点          |
| `ε-closure`                   | NFA 的 ε 图（有环）     | 迭代到不动点（工作栈）     |
| `nullable/firstpos/followpos` | 正则式**语法树**（无环）    | **一遍折叠** ✔      |
| 类型检查（非递归类型）                   | AST（树）            | **一遍折叠** ✔      |
| 类型检查（递归类型/递归函数组）              | 依赖图（有环）           | **SCC 内迭代**（§F） |
| 数据流分析                         | CFG（有环）           | 迭代到不动点          |
| 支配关系                          | CFG（有环）           | 迭代到不动点          |
| Sethi–Ullman                  | 表达式树              | **一遍折叠** ✔      |
| BURS 标号                       | 表达式树              | **一遍折叠** ✔      |
| e-graph 提取                    | e-graph（**有环！**）  | 迭代到不动点，或专门算法    |

> **结论**：**折叠与不动点迭代不是两把锤子，而是同一把锤子在"无环 / 有环"两种结构上的两种形态。**
> 
> ```
> fold  =  在良基（well-founded）结构上的不动点计算，恰好一遍收敛
> lfp   =  在非良基结构上的折叠，需要多遍收敛
> ```
> 
> 这也给出一条实用的**设计诊断法**：
> **当你的分析"需要迭代"时，问一句——依赖图里的环从哪来？** 若能通过换表示消除环（例如：SSA 把变量的环变成 φ 的显式边、SCC 分解把环局部化），迭代就退化为一遍折叠。

> **洞察二：双向定型（bidirectional typing）就是"综合属性 + 继承属性"的重新发现。**
> 
> ```
> Γ ⊢ e ⇒ τ     (synthesis/推断模式)   ← 综合属性
> Γ ⊢ e ⇐ τ     (checking/检查模式)    ← 继承属性
> ```
> 
> 双向定型之所以能处理 HM 处理不了的东西（高阶多态、GADT、字面量重载），正是因为它**引入了继承属性**——让期望类型自上而下流动。而"哪些语法构造该用哪个模式"的设计原则，本质上是在设计一个 **L-属性文法**（保证一遍从左到右可求值）。
> 
> 反过来，**HM 之所以只需综合属性**，是因为它把所有"自上而下的信息"都推迟成了合一变量（§A）——**用约束求解替代继承属性**。这是两条不同的设计路线：
> 
> ```
> HM：       全综合属性 + 合一变量 + 全局求解      → 推断能力强，错误信息差
> 双向定型： 综合 + 继承属性，局部即时检查          → 推断能力受限，错误信息好，易扩展
> ```

### D.4 连线

```
折叠 ↔ 不动点          → 后端主锤（同一把锤子的两种结构）
L-属性 ↔ LL、S-属性 ↔ LR → 前端（属性求值与解析策略的匹配）
双向定型 ↔ 继承/综合属性  → §A（约束求解是另一条路线）
循环属性文法            → 后端主锤 + §F（SCC）
折叠 + 记忆化            → §E（DAG 上的折叠）
```

## E. 唯一化与记忆化：hash-consing

### E.1 骨架

```python
class HashCons:
    def __init__(self): self.table = {}          # 结构 → 唯一实例
    def mk(self, op, *args):                     # args 已是唯一实例（指针）
        key = (op, tuple(id(a) for a in args))   # ★ 用指针而非结构做 key
        if key not in self.table:
            self.table[key] = Node(op, args)
        return self.table[key]                   # 同构的结构 ⇒ 同一个对象
```

**不变式**：`结构相等 ⟺ 指针相等`。

**三个自动获得的好处**：

1. **相等判定 `O(n) → O(1)`**
2. **表示从树变成 DAG**：共享子结构 ⇒ 指数大的项可能只占多项式空间
3. **记忆化的天然键**：以指针为键的缓存表

### E.2 钉子表

| 应用                                          | 被唯一化的对象               | 收益                                  |
| ------------------------------------------- | --------------------- | ----------------------------------- |
| **字符串驻留 / 符号表**                             | 标识符                   | 名字比较 `O(1)`                         |
| **类型内部化**（LLVM `Type`、rustc `Ty<'tcx>`、GHC） | 类型                    | **类型相等 `O(1)`**（对泛型密集代码至关重要）        |
| **常量池 / `ConstantExpr`**                    | 常量                    | 去重 + `O(1)` 比较                      |
| **CSE / GVN**                               | 值                     | 本质就是"对值做 hash-consing"              |
| **BDD / ZDD**                               | 判定图节点                 | 布尔函数的规范形式；`O(1)` 判等价                |
| **E-graph**                                 | e-node（模 e-class 唯一化） | 见 §3.4；`rebuild` 就是维护 hash-cons 不变式 |
| **DFA 状态去重**（子集构造中的 `if T not in index`）    | NFA 状态子集              | **就是 hash-consing！**                |
| **LR 项目集去重**                                | 项目集                   | 同上                                  |
| **GSS / SPPF**                              | 栈节点 / 解析森林节点          | 把指数多的栈/树压成 DAG                      |
| **Packrat 备忘表**                             | `(规则, 位置)`            | 线性时间 PEG                            |
| **DP 表**                                    | 子问题                   | §4 的所有 DP                           |
| **增量编译**（Salsa/rustc）                       | 查询结果                  | 见 §I                                |
| **AST 去重 / 代码克隆检测**                         | 子树                    | 后缀自动机也是最小 DFA                       |
| **`llvm::ICF`**（相同代码折叠）                     | 函数体                   | 二进制体积                               |

### E.3 深层洞察

> **洞察一：子集构造里的"状态去重"就是 hash-consing。**
> 
> 回看第一轮的代码：
> 
> ```python
> T = frozenset(eps_closure(move(S, a)))
> if T not in index:                    # ← hash-cons 查表
>     index[T] = len(dfa_states)        # ← 分配唯一 id
>     dfa_states.append(T)
> delta[(index[S], a)] = index[T]       # ← 之后只用 id（= 指针）
> ```
> 
> **"DFA 状态 = NFA 状态子集"这句话之所以能成立，全靠 hash-consing 保证"同一个子集只有一个状态"。** 否则 DFA 会无限增长（每次重新计算同一个子集都新建一个状态）。
> 
> 同理：
> 
> - LR 项目集规范族的 `if GOTO(I,X) ∉ C` = hash-consing
> - ANTLR 4 的 `dfa.addState(D)`（已存在则复用）= hash-consing
> - e-graph 的 `hashcons` 表 = hash-consing
> - GSS 的节点共享 = hash-consing
> 
> **所以：一切"状态集合作为状态"的构造，都必须配一个 hash-cons 表。** 这是判据三（解释力）的好例子：它解释了这些算法为什么长得像。

> **洞察二：hash-consing + 不动点 = 保证终止。**
> 
> ```
> 不动点迭代要终止，需要"格高度有限"
> hash-consing 保证"结构相同的对象只有一个"
> ⇒ 状态空间从"无限多的结构"降为"有限多的唯一实例"
> ⇒ 只要唯一实例数有界，迭代必终止
> ```
> 
> 这在 e-graph（`rebuild` 维护同余不变式 ⇒ e-class 数量单调有界）、Datalog（元组去重 ⇒ 有限论域下必终止）、合一（Union-Find 的类数单调递减）中反复使用。

> **洞察三：代价是"全局表 + 弱局部性 + 难以并行"。**
> 
> hash-consing 不是免费的：
> 
> | 代价     | 后果                    | 应对                                            |
> | ------ | --------------------- | --------------------------------------------- |
> | 全局哈希表  | 并行编译时成为争用点            | 分片、per-thread arena + 合并、rustc 的 `Sharded<T>` |
> | 缓存不友好  | 指针追逐（pointer chasing） | Arena 分配 + 索引化（`u32` 而非指针）                    |
> | 无法原地修改 | 必须持久化（persistent）     | 与函数式 IR 天然契合，与可变 IR 冲突                        |
> | 表本身占内存 | 长生命周期编译器（IDE）会累积      | GC / 分代驱逐 / `clearDFA()` 式清理                  |
> 
> **这解释了为什么 LLVM 只对 `Type`/`Constant`（不可变、小、比较频繁）做唯一化，而对 `Instruction` 不做。** 判断标准：**"相等判定的频率"×"结构比较的代价" 是否超过"维护全局表的代价"。**

### E.4 连线

```
hash-consing → 前端主锤的必要组件（状态去重）
             → 后端大锤②（GVN = 对值 hash-cons；e-graph = 模等价的 hash-cons）
             → §D（DAG 上的折叠 = 折叠 + 记忆化）
             → §I（增量编译 = 记忆化 + 失效）
             → 与不动点组合 ⇒ 终止性保证
```

## F. SCC 分解 + 拓扑序：不动点的通用加速器

### F.1 骨架

**Tarjan SCC**（1972），`O(V+E)`，一遍 DFS 求出所有强连通分量，且**输出顺序即逆拓扑序**。

**通用用法**：

```python
def solve_by_scc(graph, transfer, join):
    sccs = tarjan_scc(graph)                  # 逆拓扑序输出
    result = {}
    for comp in reversed(sccs):               # 按拓扑序处理
        if len(comp) == 1 and not self_loop(comp[0]):
            result[comp[0]] = transfer(comp[0], result)   # ★ 一遍即可，无需迭代
        else:
            iterate_to_fixpoint(comp, transfer, join, result)  # ★ 仅在环内迭代
    return result
```

> **核心价值**：**把"需要迭代"的部分从整个图缩小到单个 SCC 内部。** SCC 之间只需一遍拓扑序。对典型程序（大多数依赖是无环的），这能把迭代次数从 `O(图直径)` 降到 `O(最大 SCC 直径)`。

### F.2 钉子表

| 应用                                | 图是什么           | SCC 意味着什么                                                                |
| --------------------------------- | -------------- | ------------------------------------------------------------------------ |
| **模块/编译单元顺序**                     | import 图       | 循环依赖（需报错或特殊处理）                                                           |
| **链接顺序 / 静态库**                    | 符号依赖图          | 循环依赖（`--start-group`）                                                    |
| **构建系统**（make/ninja/bazel）        | 文件依赖图          | 循环依赖 = 错误                                                                |
| **递归绑定组**（ML/Haskell 的 `let rec`） | 变量引用图          | **必须一起做类型推导**，且**组内不泛化**，组间才泛化                                           |
| **递归类型 / 类层次**                    | 类型引用图          | 递归类型；循环继承 = 错误                                                           |
| **静态初始化顺序**                       | 初始化依赖图         | C++ 的静态初始化顺序问题                                                           |
| **自然循环识别**                        | CFG            | **循环 = SCC**（不可归约流图只能靠 SCC 识别，无法靠支配边界）                                   |
| **循环嵌套森林**                        | CFG            | 递归 SCC 分解（Havlak / Ramalingam）                                           |
| **过程间分析顺序**                       | 调用图            | **自底向上分析非递归部分（一遍 summary），只在递归 SCC 内迭代**                                 |
| **Datalog 求值**                    | 谓词依赖图          | **分层（stratification）**；否定必须跨层                                            |
| **数据流分析的迭代序**                     | CFG            | RPO 序 + SCC ⇒ 迭代次数最优                                                     |
| **Andersen 指向分析加速**               | 约束图（**动态变化！**） | **在线 SCC 检测**（Pearce–Kelly）+ **环折叠**（cycle collapsing）是让 Andersen 可扩展的关键 |
| **类型类实例一致性**                      | 实例依赖           | 循环 = 无法归约                                                                |
| **rustc 的 trait 求解**              | obligation 图   | 循环 = coinductive 处理或报错                                                   |

### F.3 深层洞察

> **洞察一：SCC 分解是"迭代次数"这个母题的通用答案。**
> 
> 前两轮我们讨论"状态爆炸"和"NP-hard"，但**迭代次数**是第三个独立的效率维度：
> 
> | 措施                           | 效果                     |
> | ---------------------------- | ---------------------- |
> | 朴素 worklist                  | 迭代次数取决于访问顺序，可能很糟       |
> | **RPO 序**（逆后序）               | 正向分析：迭代次数 ≈ 循环嵌套深度 + 2 |
> | **SCC 分解 + 组内迭代**            | 迭代局部化；SCC 之间零迭代        |
> | **优先级 worklist**（按 RPO 编号排序） | 实践中最快；LLVM/GCC 都用      |
> 
> **一个实用结论**：如果你的数据流分析很慢，**先检查迭代顺序**，通常比优化 transfer 函数收益大得多。

> **洞察二：Andersen 指向分析的"环折叠"是 SCC 与合一的合流。**
> 
> ```
> Andersen 用包含约束 pts(p) ⊇ pts(q)，比 Steensgaard 精确但慢
> 但：若约束图中 p 和 q 在同一个 SCC 里（互相包含）
>     ⇒ pts(p) = pts(q)  必然相等！
>     ⇒ 可以把它们"折叠"成一个节点（= 合一！）
>     ⇒ 不损失任何精度，但大幅缩图
> ```
> 
> **这是"精确方法借用近似方法的技巧、且不损失精度"的漂亮例子**：`包含约束 + SCC 折叠` 在环上退化为 `合一`，但只在**可证明等价**的地方退化。
> 
> 前端有对应物吗？有：**Pager 的弱兼容合并**（Menhir 用）——只在**可证明不产生新冲突**时才合并 LR(1) 状态，从而得到"接近 LALR 的状态数 + LR(1) 的能力"。**两者是同一个策略：只在无损处合并。**

> **洞察三：递归绑定组解释了一个语言设计的历史谜题。**
> 
> ML 的 `let rec f … and g …` 为什么必须显式写 `and`？Haskell 为什么不用？
> 
> ```
> ML：  要求程序员显式给出绑定组 ⇒ 编译器不必求 SCC
> Haskell/Rust/OCaml 的模块级： 编译器自动求 SCC ⇒ 程序员可任意顺序书写
> ```
> 
> 而**组内不泛化、组间才泛化**是 HM 的关键规则——它直接对应 `按 SCC 拓扑序处理，组内迭代到不动点后再泛化`。**语言的语法规则是算法结构的外化。**

### F.4 连线

```
SCC → 后端主锤的加速器（迭代局部化）
    → §D（有环 ⇒ 需迭代；SCC 把环隔离，其余退化为折叠）
    → §A（环折叠 = 在可证明等价处退化为合一）
    → Pager 弱兼容合并（只在无损处合并，同一策略）
    → 自然循环 / 循环嵌套森林（后端大锤⑤的前提）
```

## G. 判定树与分派：NFA→DFA 的孪生兄弟

### G.1 骨架

**问题**：给定一个"值"和一组"候选"，尽快确定命中哪个候选。

**通用解法**：构造一棵**判定树**（或它的表格化形式），每个内部节点测试一个"位置"，边按测试结果分叉。

**通用权衡**（这是本节的核心）：

```
        判定树 / 完全展开的表          回溯自动机 / 部分表
        ─────────────────────          ──────────────────
时间     每个位置最多测一次 O(depth)     可能重复测试，最坏 O(候选数 × depth)
空间     可能指数爆炸                    线性于候选总大小
对应     DFA                            NFA 模拟
实例     Maranget 判定树 / flex -Cf      Le Fessant–Maranget 回溯自动机 / flex 默认压缩表
```

### G.2 深层洞察：模式匹配编译 ≡ 子集构造

这是本轮第二强的连线。ML/Haskell/Rust 的模式匹配编译（Maranget 2008）算法如下：

```
输入：子句矩阵 P（行 = 一个子句的模式向量），以及各列对应的"位置"（occurrence）

① 若 P 无行            ⇒ 匹配失败（编译期报"非穷尽"警告）
② 若第一行全是通配符    ⇒ 成功，选该子句                        ← 第一匹配语义
③ 否则：选一列 i（启发式）
     对列 i 中出现的每个构造子 c：
         构造特化矩阵 S(c, P)：保留列 i 匹配 c 的行，
                              把 c 的子模式展开为新列
         递归
     构造默认矩阵 D(P)：保留列 i 是通配符的行，删掉列 i
         递归（处理未列出的构造子）
```

**逐项对照子集构造**：

| 子集构造 / 词法器                    | 模式匹配编译                          |
| ----------------------------- | ------------------------------- |
| DFA 状态 = **仍然可行的 NFA 状态集合**   | 判定树节点 = **仍然可行的子句集合**（矩阵的行集）    |
| `move(S, a)`：所有候选沿符号 `a` 推进一步 | **`S(c, P)`：所有候选沿构造子 `c` 特化一步** |
| `ε-closure`：展开可省略的中间步骤        | 子模式展开为新列                        |
| "其他字符"的转移                     | **`D(P)` 默认矩阵**                 |
| 接受态（子集含某规则的接受态）               | 第一行全通配（该子句命中）                   |
| **规则优先：取子集内序号最小者**            | **第一匹配语义：取矩阵中最上面的行** ✔ 完全一致     |
| DFA 状态去重（hash-consing）        | 判定树节点共享（DAG 化）⇒ 代码体积可控          |
| **完全展开的表 vs 压缩表 + failure 链** | **判定树 vs 回溯自动机**                |
| 状态爆炸 `2ⁿ`                     | **判定树体积爆炸**（同一列被多次测试）           |
| ——                            | **列选择顺序影响树大小，最优选择 NP-hard**     |

> **两个新增的知识点**：
> 
> 1. **"最优列选择 NP-hard"** 与 **BDD 的变量顺序选择 NP-hard** 是同一个问题。Maranget 给出了一组启发式（`needed prefix`、`small default`、`arity`…），这与 BDD 的 sifting 启发式在精神上一致。
> 2. **穷尽性检查（exhaustiveness）与冗余检查（redundancy）是同一个算法的副产品**：`P` 无行且还有构造子未覆盖 ⇒ 非穷尽；某行永远不会被选到 ⇒ 冗余（unreachable pattern）。
>    **这与词法器的"某条规则永远匹配不到"（flex 的 `rule cannot be matched` 警告）是同一个诊断**——都是"该候选在所有判定路径上都被更早的候选遮蔽"。

### G.3 钉子表

| 应用                      | 测试什么   | 表格化形式                             | 权衡                                   |
| ----------------------- | ------ | --------------------------------- | ------------------------------------ |
| **模式匹配编译**              | 构造子标签  | 判定树 / 回溯自动机                       | 代码体积 vs 重复测试                         |
| **`switch` 降级**         | 整数值    | 跳转表 / 二分树 / 位测试 / 完美哈希            | LLVM 按密度自动选择（见下）                     |
| **词法分析**                | 字符     | DFA 表                             | flex `-Cf` vs 压缩表                    |
| **指令选择匹配**              | 树形状    | BURG 表 / `MatcherTable` 字节码       | §4.1                                 |
| **虚方法分派**               | 对象的类   | vtable（单继承 `O(1)`）                | 多继承/接口需 itable 或搜索                   |
| **接口分派**                | 类 × 接口 | itable / 二维稀疏表 / 哈希               | Go 的 itab 缓存、JVM 的 `invokeinterface` |
| **PIC（多态内联缓存）**         | 类      | **运行期增长的小判定树**                    | **lazy DFA 的对应物！**                   |
| **类型测试 / `instanceof`** | 类层次    | 区间编码（Cohen/Schubert 编号）、位集        | 层次编码使 `O(1)` 判定                      |
| **异常表 unwinding**       | PC 范围  | `.gcc_except_table` / `.eh_frame` | 零成本 EH：正常路径无开销，异常路径查表                |
| **safepoint / GC 栈图**   | PC     | 每个 safepoint 的活跃指针位图              | 表大小 vs 精度                            |
| **调试信息行号映射**            | PC     | DWARF 行号程序（**一个字节码解释器！**）         | 极致压缩                                 |
| **CPU 分支预测器**           | 历史     | ——                                | 硬件版的同一权衡                             |

**`switch` 降级的具体决策**（LLVM `SwitchLoweringUtils`）——这是"表 vs 树"权衡的教科书实例：

```
case 值集合的密度 = 案例数 / (max - min + 1)

密度高（≥ ~40%）且案例数 ≥ 4    ⇒ 跳转表（jump table）：O(1)，但有间接跳转（预测差）
案例值可放进一个机器字            ⇒ 位测试（bit test）：O(1)，无间接跳转 ★
案例数少 / 稀疏                   ⇒ 二分搜索树：O(log n)，分支可预测
案例集含大段连续区间              ⇒ 区间比较（range check）
若某个 case 极热（有 profile）    ⇒ 提到最前面做单次比较（PGO！）
```

> **注意最后一条**：这是 §C 的偏求值/JIT 母题在 `switch` 上的微型版本——**用运行时频率信息把最可能的候选提前**。而 PIC 是它的完全动态版本。

### G.4 连线

```
模式匹配编译 ≡ 子集构造        → 前端主锤（第一匹配 ≡ 规则优先）
穷尽性/冗余检查 ≡ flex 的规则遮蔽警告
判定树 vs 回溯自动机 ≡ DFA vs NFA 模拟 ≡ 表 vs failure 链

PIC ≡ lazy DFA                 → §C（在线特化）
异常表 / GC 栈图 / DWARF       → 都是"用表换取正常路径零开销"
switch 的 PGO 重排              → 后端大锤⑥
判定树节点共享                  → §E（hash-consing）
```

## H. 模拟关系：正确性的万能锤

前面所有锤子都在回答"怎么做"。这一把回答"**做对了吗**"——而它同样是万能的。

### H.1 骨架

要证明变换 `C : Src → Tgt` 正确，构造一个**模拟关系**（simulation relation）`≈ ⊆ State_Src × State_Tgt`，并证明一个**图表交换**性质：

```
前向模拟（forward simulation）：

   s₁  ──────→  s₂          (源程序走一步)
   ≈            ≈
   t₁  ─ ─ ─→  t₂          (目标程序走 0、1 或多步)

即：  s₁ ≈ t₁  ∧  s₁ → s₂   ⟹   ∃ t₂. t₁ →* t₂ ∧ s₂ ≈ t₂
```

**变体与用途**：

| 变体                      | 条件                      | 用于                      |
| ----------------------- | ----------------------- | ----------------------- |
| **Lockstep**            | 源一步 ↔ 目标一步              | 简单的一对一变换                |
| **Plus / Star**         | 源一步 ↔ 目标一步以上/零步以上       | 内联、指令选择（一条 IR → 多条机器指令） |
| **带度量的 Star**           | 零步时需一个递减的度量（防止"目标永远不动"） | 死代码消除、常量折叠              |
| **Backward simulation** | 反向                      | 目标可能比源更确定时              |
| **Bisimulation**        | 双向                      | 证明两个程序完全等价              |
| **Refinement**          | 目标行为 ⊆ 源行为              | 允许目标"更确定"（如把 UB 具体化）    |

**关键定理**：若源语言是确定性的且目标不引入新行为，**前向模拟 ⟹ 语义保持**。（若源有不确定性，需要后向模拟或额外条件——这是 CompCert 论文里反复讨论的技术点。）

### H.2 深层洞察：`L(D) = L(N)` 的证明本身就是一个模拟关系

回到最开始的子集构造正确性证明：

```
定理： L(D) = L(N)
证明的核心引理：
    δ_D*(s₀, w) = ε-closure( δ_N*(q₀, w) )
    即：DFA 读完 w 后所处的那个"子集状态"，恰好等于 NFA 读完 w 后可能所处的状态集合
```

**这就是一个模拟关系**：

```
关系 ≈ ：  S ≈ Q    ⟺    S = Q    (DFA 状态 S 恰好是 NFA 可达状态集 Q)

图表：  Q  ──a──→  Q' = ε-clos(move(Q,a))     (NFA 一步)
        ≈                ≈
        S  ──a──→  S' = δ_D(S, a)             (DFA 一步)
        且 S' = Q'  ✔ lockstep 前向模拟
```

> **所以：整个编译原理里，"证明正确"这件事从头到尾只用一把锤子。**
> 从子集构造的 `L(D)=L(N)`，到 LR 分析器的正确性（栈内容 ≈ 右句型前缀），到 CompCert 的 20 个 pass，到 Alive2 的 peephole 验证——**全是构造模拟关系**。

### H.3 钉子表

| 应用                       | 关系 `≈` 是什么                           | 工具/项目                                |
| ------------------------ | ------------------------------------ | ------------------------------------ |
| **子集构造正确性**              | DFA 状态 = NFA 可达集                     | 教科书                                  |
| **LR 分析器正确性**            | 栈内容 ≈ 右句型的可行前缀                       | Knuth 1965                           |
| **CompCert 的每个 pass**    | 各 pass 各自定义（内存注入、寄存器映射…）             | **CompCert**（Coq，端到端验证的 C 编译器）       |
| **CakeML**               | 类似                                   | CakeML（HOL4，验证的 ML 编译器）              |
| **翻译验证**（Necula 2000）    | 自动推断（不需要预先给出）                        | 事后验证，无需改编译器                          |
| **Alive / Alive2**       | 位精确的 SMT 编码（含 UB、poison、undef）       | 验证 LLVM peephole；发现数百真实 bug          |
| **Superoptimizer 的等价检查** | SMT                                  | STOKE、Souper                         |
| **重写规则的正确性**             | 项重写的合流性 + 语义保持                       | egg 的规则验证、Ruler                      |
| **数据流分析的可靠性**            | **Galois 连接 + `α∘F_c ⊑ F_a∘α`**      | 抽象解释的可靠性定理                           |
| **类型系统的可靠性**             | **进展 + 保持**（progress + preservation） | 类型系统的标准证明范式                          |
| **差分/模糊测试**              | 观测行为一致（实用近似）                         | **Csmith**、EMI、YARPGen、`llvm-reduce` |
| **递归类型相等判定**             | **互模拟**（coinduction）                 | equirecursive 类型系统                   |

### H.4 洞察二：抽象解释的可靠性定理 = 模拟关系的格版本

```
模拟关系：   s ≈ t  ∧  s → s'  ⟹  ∃t'. t →* t' ∧ s' ≈ t'
抽象解释：   α(c) ⊑ a  ∧  c' = F_c(c)  ⟹  α(c') ⊑ F_a(a)
             即：α ∘ F_c  ⊑  F_a ∘ α
```

**结构完全相同**：`≈` 变成了 `α(·) ⊑ ·`，"存在一条目标路径"变成了"抽象值更大（更保守）"。

> **这解释了为什么"局部可靠 ⟹ 全局可靠"在两个场景都成立**：
> 
> - 抽象解释：只要每条指令的 transfer 是可靠的，`lfp(F_a)` 自动是可靠近似
> - 编译器验证：只要每个 pass 有模拟关系，模拟关系可**组合**（`≈₁ ∘ ≈₂` 仍是模拟关系），整个流水线自动正确
> 
> **模拟关系的可组合性，正是 CompCert 能规模化的根本原因**——也正是"nanopass 架构"（§J）在正确性上的理论依据：小 pass 更容易证明，而证明可以拼起来。

### H.5 洞察三：`undef`/`poison`/UB 是"细化关系"而非"等价关系"

LLVM 的 `undef`/`poison` 让"等价"变成了单向的：

```
优化可以把不确定的行为变得更确定（refinement），但不能反过来。

  x + 0  →  x                 ✔ 合法
  x      →  x + 0             ✔ 也合法（这里恰好双向）

  freeze(undef)  →  0         ✔ 合法（细化）
  0  →  freeze(undef)         ✘ 非法（引入不确定性）
```

**这就是 Alive2 必须用"细化（refinement）"而非"等价（equivalence）"作为验证条件的原因**，也是历史上大量 LLVM bug 的来源（把细化关系当作等价关系，于是在某个方向上用错）。

> **教学价值**：这说明"正确性"这把锤子的**关系方向**必须精确——和 §A 的"合一（无向）vs 包含（有向）"是同一类问题。**把有向关系误当无向，是编译器 bug 的一大类根源。**

### H.6 连线

```
模拟关系 → 前端主锤的正确性证明（L(D)=L(N)）
        → 抽象解释的可靠性定理（同一结构的格版本）
        → 类型系统的 progress+preservation
        → §J（模拟关系可组合 ⇒ nanopass 可验证）
        → §A（有向 vs 无向关系的区分）
差分测试 → 模拟关系的工程近似版（不证明，只测）
```

## I. 需求驱动与查询式架构

### I.1 骨架：把编译器从 push 翻成 pull

```
传统（push / pass pipeline）：
    parse → typecheck → optimize₁ → … → optimizeₙ → codegen
    每个阶段处理"整个程序"，顺序固定，全量重算

查询式（pull / query DAG）：
    codegen("f") ──需要──> mir("f") ──需要──> typeck("f") ──需要──> hir("f")
                                   └─需要──> type_of("g")  ──需要──> …
    只计算被需要的东西；记忆化每个查询；输入变化时按依赖失效
```

**三个必要组件**：

```
① 查询函数     query(key) → value          必须是纯函数
② 记忆化表     key → (value, 依赖集合, 版本号)
③ 失效机制     输入变化 ⇒ 沿依赖图标记为 dirty
```

**关键优化（红绿算法 / early cutoff）**：

```
标记 dirty 后，重新求值时若结果与旧值相同 ⇒ 不再向下游传播 dirty
⇒ "改一个注释"不会导致整个 crate 重新代码生成
```

### I.3 深层洞察

> **洞察一：查询式架构的最大难点是"纯性"与"循环"。**
> 
> | 难点          | 表现                                                        | 应对                                                              |
> | ----------- | --------------------------------------------------------- | --------------------------------------------------------------- |
> | **纯性**      | 查询必须是 `key → value` 的纯函数；任何隐藏可变状态（全局符号表、可变 IR）都会破坏记忆化     | 强制 immutable IR + `interner`（§E）；rustc 用 `TyCtxt<'tcx>` 的 arena |
> | **循环查询**    | `type_of(a)` 需要 `type_of(b)`，`type_of(b)` 需要 `type_of(a)` | ① 检测并报错（大多数）② **在 SCC 内迭代到不动点**（§F！）③ coinduction               |
> | **key 的粒度** | 太粗 ⇒ 失效范围大；太细 ⇒ 表开销大                                      | 经验调优；rustc 花了多年调整 query 边界                                      |
> | **诊断信息的归属** | 一个查询产生的警告该归给谁？重跑时会不会重复报？                                  | 把诊断作为查询结果的一部分                                                   |
> 
> **注意"循环查询在 SCC 内迭代"**——这正是 §F 的 SCC 锤子在架构层面的重现。递归类型/递归函数组的类型推导，在查询式编译器里表现为**循环查询**，其解法与 ML 的递归绑定组处理完全相同。

> **洞察二：查询式架构是"何时承诺"母题在架构层面的答案。**
> 
> 回顾第三轮的那张时间轴：
> 
> ```
> 编译期静态决定 → 惰性/按需 → 推迟到运行期 → 永不承诺
> ```
> 
> **查询式架构就是把"惰性/按需"从单个算法提升为整个编译器的架构。** 它的好处与代价与单点惰性完全对应：
> 
> |       | 单点惰性（lazy DFA / 惰性 SSA） | 架构级惰性（查询式）                 |
> | ----- | ----------------------- | -------------------------- |
> | 好处    | 只为用到的部分付费               | 只为用到的部分付费；**IDE 场景下收益巨大**  |
> | 缓存管理  | `clearDFA()`            | LRU 驱逐、磁盘持久化、增量数据库         |
> | 首次访问慢 | 冷启动做完整模拟                | 冷编译不比传统快（甚至更慢）             |
> | 前提条件  | 状态可去重（hash-consing）     | 查询纯 + IR 不可变（hash-consing） |
> 
> 两者都**依赖 §E 作为前提**。这不是巧合：**记忆化的前提是有可靠的 key，而可靠的 key 需要唯一化。**

> **洞察三：IDE 需求正在反向重塑编译器设计。**
> 
> 传统编译器的优化目标是"批量编译整个程序的吞吐"。IDE 的目标是"**改一个字符后，100ms 内给出该文件的诊断**"——这是一个完全不同的目标函数，导致：
> 
> | 传统设计             | IDE 驱动的设计                                                |
> | ---------------- | -------------------------------------------------------- |
> | 全量 pass pipeline | 查询 DAG + 增量                                              |
> | 遇错即停 / panic     | **错误恢复 + 部分结果**（错误节点、`ErrorType`）                        |
> | 可变 IR（省内存）       | 不可变 + 持久化数据结构                                            |
> | AST 丢弃细节（空白、注释）  | **无损语法树**（lossless CST：Roslyn、rust-analyzer、tree-sitter） |
> | 单线程              | 可取消（cancellation）+ 并行查询                                  |
> 
> **"无损语法树"值得单独一提**：它要求解析器保留所有 trivia（空白、注释、甚至错误 token），以支持格式化、重构、代码操作。这与"编译用的 AST 只保留语义相关信息"是完全冲突的目标——现代方案是**两层**（CST → AST），又是一次"换表示"。

### I.4 连线

```
查询式架构 → §E（记忆化必须有可靠 key ⇒ 需要 hash-consing）
          → §F（循环查询 = SCC，组内迭代）
          → 第三轮的"何时承诺"母题（架构级的惰性）
          → ALL(*) / lazy DFA / 惰性 SSA（同一机制的不同粒度）
          → 构建系统（同一机制的更粗粒度）
```

## J. 归约与逐层降级：最元的一把锤子

### J.1 骨架

> **不要解决问题。把它翻译成一个你已经解决的问题。**

这是编译器领域**使用频率最高**的技术，也最容易被忽视——因为它太理所当然了。

```
高级语言特性  ──降级──>  中级构造  ──降级──>  低级构造  ──降级──>  机器指令
     ↑                                                              ↑
表达力强、便于人书写                                    表达力弱、便于机器执行
信息多                                                            信息少
```

### J.2 钉子表：语言特性的归约谱系

| 高级特性                        | 归约到                            | 丢失了什么                            |
| --------------------------- | ------------------------------ | -------------------------------- |
| **`for`/`while`/`foreach`** | 条件跳转 + 标签（CFG）                 | 循环结构（需 `llvm.loop` 元数据或重新识别自然循环） |
| **`switch`**                | 判定树 / 跳转表（§G）                  | 案例集的整体结构                         |
| **模式匹配**                    | 判定树（§G）                        | 穷尽性信息                            |
| **异常**                      | CPS 双续延 / 表驱动 unwinding（§B、§G） | 异常边（需 `invoke`/`landingpad` 保留）  |
| **async/await、生成器**         | 状态机（§B）                        | "这是一个协程"（调试器难以还原调用栈）             |
| **闭包 / lambda**             | 结构体 + 函数指针（闭包转换，§B）            | 词法作用域关系                          |
| **高阶函数**                    | 去函数化 + `switch`（§B） 或 保留间接调用   | ——                               |
| **对象 / 方法**                 | 记录 + 函数 + vtable（§G）           | 类层次（需保留以做 CHA）                   |
| **泛型 / 类型类**                | **单态化**（§C 偏求值）**或** 字典传递      | 单态化：代码膨胀；字典：运行时开销                |
| **Trait 对象 / 接口**           | vtable / itable（§G）            | 具体类型（需 PIC 或投机恢复）                |
| **多重继承**                    | 多个 vptr + this 调整（thunk）       | ——                               |
| **`defer` / RAII / 析构**     | 显式清理代码 + 异常路径                  | 作用域结构                            |
| **`unsafe` / UB**           | 语义上的"细化关系"（§H）                 | 是 bug 的一大源头                      |
| **GC**                      | 写屏障 + safepoint + 栈图（§G）       | ——                               |
| **原子 / 内存序**                | 屏障指令 + 优化限制                    | 优化必须尊重的 fence                    |
| **`inline asm`**            | 优化屏障（黑盒）                       | 编译器基本放弃优化                        |
| **向量化 / SIMD 内建**           | 目标指令                           | 可移植性                             |
| **多面体循环变换**                 | 带守卫的循环嵌套（CLooG）                | 仿射结构（无法再变换）                      |

**以及"归约到已解决的组合问题"（第三轮的大锤③④⑤）**：

```
寄存器分配 ──归约──> 图着色       （已有大量启发式）
指令调度   ──归约──> 资源约束调度   （已有表调度）
指令选择   ──归约──> 树覆盖 DP / PBQP / ILP
PRE        ──归约──> 数据流 + 最小割
循环变换   ──归约──> 仿射 ILP
等价性     ──归约──> SMT
指向分析   ──归约──> Datalog / CFL-可达性
```

### J.3 深层洞察

> **洞察一：归约的代价永远是"信息丢失"，而现代编译器的主要演进方向就是"推迟丢失"。**
> 
> ```
> 1970s–2000s： 尽早降到一个通用低层 IR（如 LLVM IR），所有优化在那里做
>               优点：一个后端服务所有语言
>               缺点：语言特有的高层信息被过早丢弃
> 
> 2010s–now：   保留高层 IR，在高层做语言特有优化，再逐层降级
>               Rust:   HIR → THIR → MIR → LLVM IR
>                       （借用检查、Drop 精化必须在 MIR 做——LLVM IR 上信息已丢失）
>               Swift:  AST → SIL → LLVM IR
>                       （ARC 优化、独占性检查在 SIL 做）
>               MLIR:   任意多个 dialect，渐进降级（progressive lowering）
>                       （linalg → affine → scf → vector → llvm）
>               Java:   保留字节码 + 运行期类型 profile
> ```
> 
> **MLIR 是这条洞察的制度化**：它不预设一个"正确的抽象层次"，而提供**基础设施让你自由定义任意多层**，并把"在哪一层做什么优化"变成一个显式设计决策。
> 
> 这与前端的对应物：
> 
> ```
> 前端：AST 丢弃 trivia ⇒ 无法格式化/重构
>       ⇒ 现代方案：无损 CST → AST（两层）
> 后端：早降 ⇒ 丢失高层信息
>       ⇒ 现代方案：多层 dialect 渐进降级
> ```
> 
> **同一条演进：从"一个正确的表示"到"多层表示 + 显式的降级点"。**

> **洞察二：nanopass 架构 —— 归约的极致，其可行性依赖于 §H 的可组合性。**
> 
> ```
> Nanopass（Sarkar–Waddell–Dybvig 2004）：
>   把编译器分解为几十个"每个只做一件微小事情"的 pass
>   每个 pass 有自己的、精确定义的输入输出语言（用 DSL 声明）
>   ⇒ 每个 pass 极易理解、测试、验证
>   ⇒ 但 pass 数量多，且 phase ordering 问题依然存在
> ```
> 
> **为什么这可行？** 因为 §H 的模拟关系**可组合**：`≈₁ ∘ ≈₂` 仍是模拟关系。所以"每个小 pass 正确 ⟹ 整体正确"自动成立。CompCert 正是这个架构（20 个 pass，每个单独证明）。
> 
> **代价**：pass 之间的接口开销、编译时间、以及**归约顺序的选择**（这就是 phase ordering 问题的另一副面孔）。

> **洞察三：归约的方向性 —— 什么是"已解决的问题"取决于时代。**
> 
> ```
> 1960s： "已解决" = 可用汇编手写      ⇒ 归约到汇编模板
> 1980s： "已解决" = 图着色、DP        ⇒ 归约到组合优化
> 2000s： "已解决" = ILP、SAT/SMT      ⇒ 归约到求解器
> 2010s： "已解决" = 大规模搜索、Datalog ⇒ 归约到搜索/声明式规则
> 2020s： "已解决" = 神经网络能拟合的  ⇒ 归约到学习型代价模型（MLGO、Ithemal）
> ```
> 
> **每一代编译器的"归约目标"就是那一代最强的通用求解技术。** 这是判据三（预测力）的直接应用：**下一代编译器会把更多问题归约到 LLM/学习系统上**——这已经在发生（学习型内联策略、学习型调度、LLM 辅助的优化规则发现）。

### J.4 连线

```
归约 → 所有其他锤子的"元锤子"（决定用哪把锤子 = 决定归约到什么）
     → §H（模拟关系可组合 ⇒ nanopass 可验证）
     → 第三轮的 phase ordering（归约顺序的选择）
     → §C（单态化 = 归约到偏求值）
     → §B（异常/协程 = 归约到状态机）
     → §G（模式匹配/switch = 归约到判定树）
     → MLIR = 把"归约的层数"变成用户可配置
```

## K. 小锤集

以下四把没有完全达到"万能"标准（各差一条判据），但足够重要且有强连线。

### K.1 位并行：NFA 模拟的第三条路

第一轮我们说过：面对 NFA 有两条路——**确定化**（DFA，快但爆炸）或**直接模拟**（`O(nm)`）。其实有**第三条**：

> **把整个 NFA 状态集合装进一个机器字，用位运算一次并行推进 `w` 个状态。**

```c
// Shift-Or 算法：在 O(n·⌈m/w⌉) 时间内做精确字符串匹配
// D 的第 j 位 = 0  表示 "模式的前 j+1 个字符匹配到当前位置"
//              （即 NFA 状态 j 是活跃的）
uint64_t D = ~0ULL;                       // 初始：所有状态都不活跃
for (int i = 0; i < n; i++) {
    D = (D << 1) | B[text[i]];            // ★ 一条指令推进全部 64 个 NFA 状态
    if (!(D & (1ULL << (m-1)))) report(i - m + 1);
}
```

| 算法                                           | 用途                                   |
| -------------------------------------------- | ------------------------------------ |
| **Shift-Or / Shift-And**（Baeza-Yates–Gonnet） | 精确匹配                                 |
| **BNDM / BOM**                               | 带跳跃的匹配                               |
| **位并行编辑距离**（Myers 1999）                      | 近似匹配、`diff`                          |
| **Glushkov 位并行正则匹配**                         | 小正则式的极速匹配                            |
| **Hyperscan**                                | Intel 的多正则引擎：大量 SIMD + 位并行 + 分解为小自动机 |
| **simdjson / SIMD 结构索引**                     | 用 SIMD 一次处理 64 字节，做引号/括号/空白的结构化索引    |
| **数据流分析的位向量**                                | 一个字并行处理 64 个变量的 meet                 |
| **BDD 表示指向集**                                | 指向集的紧凑表示（bddbddb）                    |

> **洞察**：这给出"NFA 三选一"的完整图景：
> 
> ```
> ① 确定化 → DFA         ：时间 O(n)，空间可能 2^m         【前端主锤】
> ② 直接模拟状态集合      ：时间 O(nm)，空间 O(m)          【GLR/iburg 的选择】
> ③ 位并行模拟状态集合    ：时间 O(n⌈m/w⌉)，空间 O(m)     【Shift-Or】
> ④ 惰性确定化            ：时间摊销 O(n)，空间有界        【lazy DFA / ALL(*)】
> ```
> 
> **①②③④ 是同一个权衡空间的四个角落**，而 ③ 的存在说明：**"状态集合"这个抽象如果编码得足够紧凑，"不确定化"的代价可以小到可忽略**。

### K.2 区域与所有权：把内存管理变成类型/数据流问题

| 技术                           | 归约到                               |
| ---------------------------- | --------------------------------- |
| **区域推断**（Tofte–Talpin、MLKit） | 包含约束求解（§A）                        |
| **逃逸分析**                     | 数据流分析（后端主锤）                       |
| **Rust 的借用检查（NLL）**          | **CFG 上的数据流 + 约束图可达性**（§A + 后端主锤） |
| **Rust Polonius**            | **Datalog**（§A + 后端主锤 + §J）       |
| **线性/仿射类型**                  | 类型系统（§A）                          |
| **ARC 优化**（Swift）            | 数据流分析 + 引用计数配对消除                  |
| **Cyclone 的区域**              | 区域多态 + 约束                         |

> **洞察**：**"内存安全"这个看起来完全不同的问题，被归约成了本文已有的锤子**——约束求解 + 数据流分析 + Datalog。
> 而 NLL（non-lexical lifetimes）的历史特别有教学价值：
> 
> ```
> 旧借用检查：生命周期 = 词法作用域       ⇒ 折叠（§D，AST 上一遍）  ⇒ 太保守
> NLL：      生命周期 = CFG 上的活跃范围  ⇒ 不动点（后端主锤）      ⇒ 精确得多
> ```
> 
> **这是"从树上折叠升级到图上不动点"（§D.3）的一次真实语言演进。**

### K.3 类型即抽象解释

Cousot（1997）证明：**类型系统是抽象解释的一个实例**。

```
具体域：程序的执行轨迹集合
抽象域：类型（一个类型 = 一组值的集合，即 γ(τ)）
类型规则 = 抽象 transfer 函数
类型可靠性（soundness）= 抽象解释的可靠性定理
```

**由此得到的统一图景**：

|          | 类型检查                                 | 抽象解释                  |
| -------- | ------------------------------------ | --------------------- |
| 抽象域      | 类型                                   | 区间/多面体/指向集…           |
| 可靠性      | progress + preservation              | `α∘F_c ⊑ F_a∘α`       |
| 精度不足     | 需要类型标注、类型断言                          | 需要 widening 提示、断言     |
| 提升精度的手段  | 依赖类型、精化类型、多态、流敏感类型                   | 关系域、路径敏感、上下文敏感        |
| 保证终止的手段  | 类型语法有限、秩限制                           | widening、`k`-limiting |
| **两者合流** | **精化类型（Liquid Types）= 类型 + 抽象解释求解器** |                       |

> **洞察**：这解释了一个常见困惑——"类型系统和静态分析有什么区别？"
> **答案：没有本质区别，只有工程侧重不同。**
> 
> ```
> 类型系统：  抽象域由语言语法固定，需要程序员标注，可组合（模块化），错误信息好
> 静态分析：  抽象域由分析器选择，全自动，通常不模块化，错误信息差（"可能有问题"）
> ```
> 
> 现代趋势是两者融合：**精化类型**（Liquid Haskell、Flux）、**Gradual typing**、**Rust 的借用检查器**（一个内置于类型系统的数据流分析）、**effect systems**。

### K.4 归纳-协归纳的对偶

| 归纳（induction）           | 协归纳（coinduction）             |
| ----------------------- | ---------------------------- |
| 最小不动点 `lfp`             | 最大不动点 `gfp`                  |
| 有限数据（列表、树、AST）          | 无限数据（流、递归类型、无限执行）            |
| 折叠（cata）、递归             | 展开（ana）、余递归                  |
| 悲观 Union-Find（§A、后端大锤②） | **乐观划分精化**（Hopcroft、AWZ GVN） |
| 子集构造（可达子集的最小集合）         | **DFA 最小化**（最粗的一致划分）         |
| 终止性证明（递减度量）             | **安全性/不变式证明**（互模拟）           |
| 类型推导的正常情形               | **递归类型的相等判定**                |
| Datalog 的最小模型           | Büchi 自动机的接受条件（ω-正则）         |

> **洞察**：第三轮提到的"最小 vs 最大不动点是对偶的两个方向"，其完整名字就是**归纳与协归纳的对偶**。
> **一个实用判别法**：
> 
> - 要证明"某个坏事**不会**发生"（安全性）⇒ 找不变式 ⇒ **最大不动点 / 协归纳**
> - 要证明"某个好事**会**发生"（活性/终止）⇒ 找递减度量 ⇒ **最小不动点 / 归纳**
> 
> 这也解释了 §6.3 的 Büchi 自动机为什么不能用子集构造确定化：**它的接受条件是 ω-条件（协归纳的），而子集构造只保留了可达性（归纳的）信息**。

## 11. 全局归并：十八把锤子只有五种机制

现在把三轮的所有锤子放在一起。前端 1 把、后端 7 把、本轮 10 把 + 4 把小锤——**归并后只剩五种机制**。

### 机制 I：归纳结构上的计算（折叠 ⟷ 不动点）

```
结构无环 ⇒ 一遍折叠                结构有环 ⇒ 迭代到不动点
─────────────────────              ────────────────────────
S/L-属性文法（§D）                  数据流分析（后端主锤）
Sethi–Ullman、BURS 标号             子集构造 / LR 项目集（前端主锤）
类型检查（非递归）                   FIRST/FOLLOW、ε-closure
nullable/firstpos/followpos          支配关系、支配边界
                                    指向分析、Datalog
                                    同余闭包、e-graph rebuild
                                    重写到不动点
        ↑                                    ↑
        └────── SCC 分解（§F）把环隔离 ──────┘
                环外折叠，环内迭代
```

**统一签名**：

```python
while worklist:
    x = worklist.pop()
    new = transfer(join(inputs(x)))
    if new != current[x]:
        current[x] = new
        worklist.extend(dependents(x))
```

**两个方向**（归纳 vs 协归纳，§K.4）：`lfp` 从 `⊥` 向上合并（Union-Find）；`gfp` 从 `⊤` 向下精化（Partition Refinement）。

### 机制 II：等价性管理

                    ┌── 判定"是否等价" ──┐
                    │                    │
        合一（§A）              划分精化（Hopcroft / AWZ）
        Union-Find              同余闭包（§A、§E）
        包含约束                E-graph（后端大锤②）

                    GVN / CSE / ICF
                              │
                    ┌── 证明"确实等价" ──┐
                    │                    │
              模拟关系（§H）        SMT / Alive2

```

### 机制 III：表示变换（换表示以消灭分析）

| 变换                        | 消灭了什么               | 代价                 |
| ------------------------- | ------------------- | ------------------ |
| NFA → **DFA**             | 运行时不确定性             | `2ⁿ` 风险            |
| 项目 NFA → **LR 自动机**       | "CFL 需无限栈"的困难       | 需显式栈 + 冲突消解        |
| → **SSA**                 | 到达定义分析              | 出 SSA / coalescing |
| → **CPS / 状态机**（§B）       | 隐式控制流               | 状态爆炸、调试困难          |
| → **去函数化**（§B）            | 高阶间接调用              | 需全程序、switch 巨大     |
| → **判定树**（§G）             | 多路选择的重复测试           | 代码体积爆炸             |
| → **多面体**                 | 十几种 ad-hoc 循环变换     | 只适用仿射程序            |
| → **E-graph**             | phase ordering（重写层） | 可能不饱和              |
| → **弦图**（SSA 干扰图）         | 图着色的 NP-hard        | 难度移到 coalescing    |
| → **无损 CST + AST**（§I）    | "格式化 vs 编译"的冲突      | 两层维护成本             |
| → **多层 dialect**（MLIR，§J） | 过早的信息丢失             | 层数管理复杂             |

**两条最美的结构定理**：

```
活前缀集合是正则语言       ⇒ LR 可行（CFL 难度隔离进显式栈）
严格 SSA 的干扰图是弦图     ⇒ 最优着色可行（难度隔离进 coalescing）
```

## 12. 锤子的反面：什么时候该放下它

万能锤的危险是"手里有锤子，看什么都像钉子"。每把锤子都有明确的失效域，诚实列出如下。

| 锤子                   | 什么时候是错的工具                | 症状                                                | 该换成什么                            |
| -------------------- | ------------------------ | ------------------------------------------------- | -------------------------------- |
| **不动点/抽象解释**         | 用来回答**收益性**问题（"这个优化更快吗"） | 分析结果全是 `⊤`；或分析很精确但不知道拿它干什么                        | 代价模型 + 搜索 + PGO（大锤⑥）             |
| **不动点**              | 整个依赖图是一个巨大 SCC           | 迭代次数 = 图直径，慢到不可用                                  | 换表示打破环（SSA、SCC 折叠）；或改用需求驱动只算被问到的 |
| **合一（§A）**           | 需要子类型/方向性时               | 强行把 `p <: q` 当 `p = q`，精度崩塌（Steensgaard 的困境）      | 包含约束 / 双向定型                      |
| **子集构造 / 确定化**       | 一次性使用、状态空间高维、或理论上不可确定化   | 表爆炸；或构造成本摊销不回来                                    | NFA 模拟、位并行（§K.1）、惰性确定化、GLR       |
| **偏求值（§C）**          | 缺乏终止控制                   | 编译时间/代码体积爆炸（模板元编程的经典病）                            | 泛化、展开预算、显式分阶段                    |
| **状态机化（§B）**         | 状态数随程序结构指数增长；或需要可调试性     | Future 巨大；调用栈无法还原                                 | 保留一等续延、分段栈、绿色线程                  |
| **hash-consing（§E）** | 对象需频繁修改、生命周期短、或需要并行      | 全局表争用、缓存不友好                                       | Arena + 可变 IR + 局部 CSE           |
| **判定树（§G）**          | 候选极多且分布均匀                | 代码体积爆炸                                            | 表驱动 / 回溯自动机 / 哈希 / 运行期 PIC       |
| **E-graph**          | 规则集含交换/结合律且无预算控制         | 不饱和、内存爆炸、提取需 ILP                                  | 有界重写（aegraph）、精选规则集              |
| **多面体模型**            | 非仿射程序（间接寻址、数据相关控制流）      | 模型直接不适用                                           | 传统循环优化 + 运行时检查                   |
| **查询式架构（§I）**        | 只做批量 AOT 编译，无 IDE 需求     | 冷编译更慢、架构复杂度不划算                                    | 传统 pass pipeline                 |
| **形式验证（§H）**         | 语言语义本身尚未稳定/未形式化          | 证明的工作量远超编译器本身                                     | 差分/模糊测试（Csmith）+ 翻译验证            |
| **归约（§J）**           | 归约丢失了解决问题所必需的信息          | 在低层 IR 上"再把高层结构猜回来"（如从 CFG 重新识别循环、从指令序列识别 memcpy） | 保留高层 IR，在正确的层做（MLIR/MIR/SIL）     |
| **搜索/ML（大锤⑥）**       | 需要可解释性、可复现性、或编译时间受限      | 不可复现、无法调试、CI 时间爆炸                                 | 解析式代价模型 + 人工启发式                  |

> **一条通用诊断法**：
> **当你发现自己在"用一个分析把之前某个变换丢掉的信息猜回来"时，说明归约做早了。**
> 
> 经典实例：
> 
> - 从 CFG 重新识别自然循环（因为 `for` 结构被过早降级）→ 解法：`llvm.loop` 元数据、MIR 保留循环
> - 从指令序列识别 `memcpy` 模式（因为循环被过早展开）→ 解法：idiom recognition，或不要过早展开
> - 从 LLVM IR 反推借用关系（不可能）→ 解法：借用检查在 MIR 做
> - 从 AST 反推原始格式（不可能）→ 解法：无损 CST
> 
> **这是"何时承诺"母题的第三种表现**：不只是"何时做决定"，还有"**何时丢弃信息**"。

## 收束

> **三轮下来，编译原理里被反复使用的东西其实只有这些：**
> 
> **① 在归纳结构上算东西。** 结构无环就折叠一遍；有环就迭代到不动点；用 SCC 把环隔离，让大部分退化为折叠。子集构造、LR 项目集、数据流分析、`FIRST`/`FOLLOW`、支配关系、类型推导、e-graph rebuild——全是这一件事，只是格和图不同。
> 
> **② 管理等价性。** 判定等价（合一、划分精化、同余闭包）、表示等价（hash-consing、规范化、E-graph）、证明等价（模拟关系、SMT、差分测试）。前两者决定编译器算得快不快，后者决定它对不对。
> 
> **③ 换表示。** DFA、LR 自动机、SSA、CPS、状态机、判定树、多面体、弦图、E-graph、多层 dialect——每一次都是"用一次不可逆的信息重组，换掉一整类分析"。最美的两条结构定理（活前缀是正则语言、SSA 干扰图是弦图）都属于此。
> 
> **④ 特化并摊销。** 偏求值是它的完整理论（编译本身就是对解释器的偏求值），常量折叠、内联、单态化、宏、JIT、PIC、lazy DFA、查询式架构、构建系统缓存，全是它在不同粒度上的实例。它的永恒难题是终止性（泛化 = widening = 限制 k），以及猜错时的退路。
> 
> **⑤ 归约到已解决的问题，并分层。** 每一代编译器的"归约目标"就是那一代最强的通用求解技术。归约的代价永远是信息丢失，而现代编译器的主要演进方向就是**推迟丢失**。
> 
> **而三条元原则贯穿全部：**
> 
> **迭代到不动点。**
> **换一个使问题变简单的表示。**
> **决定何时承诺、何时丢弃信息——并为承诺错了准备一条可检测的退路。**
> 
> 最后一条是最难也最重要的。它解释了为什么 `SLR → LALR → LR(1)`、`SLL → LL`、`CHA → PIC`、`Tier-1 → Tier-N JIT`、`合一 → 包含约束`、`折叠 → 不动点`、`AOT → JIT + deopt` 这些看起来毫不相干的阶梯，其实是同一条阶梯；也解释了为什么 **PEG 的有序选择**、**贪心 peephole**、**上下文不敏感指向分析** 这三样东西共同的缺陷不是"不够精确"，而是——**它们失败的时候，你不知道。**

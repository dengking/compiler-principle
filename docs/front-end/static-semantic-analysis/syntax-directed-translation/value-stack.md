# 值栈（Value Stack）：属性如何沿着栈流动

---

## 引子：`$$` 到底存在哪里

写过 Yacc 或 Bison 的人都熟悉这样的规则：

```yacc
expr : expr '+' term   { $$ = $1 + $3; }
     ;
```

`$1` 是左操作数的值，`$3` 是右操作数的值，`$$` 是整个表达式的值。规则本身很直观，但有一个问题很少被追问：**这些值在运行时存放在哪里？**

分析器在识别出 `expr '+' term` 之前，已经处理了成百上千个 token。左操作数 `expr` 的值是在很久以前算出来的，它必须被保存到某个地方，等到 `+` 和 `term` 都处理完，归约（reduce）发生时再取出来。

答案是一个与分析栈（parse stack）并行增长、并行收缩的栈：**值栈**（value stack）。它也被称为语义栈（semantic stack）、属性栈（attribute stack），在 Bison 生成的代码里叫作语义值栈（semantic value stack）。

值栈是语法制导翻译（Syntax-Directed Translation, SDT）中最古老、最高效的属性存储方式。它出现在 LR 分析器里、递归下降分析器的调用栈里、ANTLR 的 Listener 里，也以另一种面貌出现在 JVM、CPython 和 WebAssembly 的操作数栈（operand stack）里，甚至出现在 JIT 编译器的寄存器分配中。

前一篇讲了侧表（side table）：把属性放在树之外的映射里。本文讲另一种做法：**把属性放在遍历过程本身的栈里**。它不需要树，也不需要键，只依赖一件事：遍历顺序。

---

## 一、定义

> **值栈**是一个后进先出（Last In, First Out, LIFO）的存储结构，用于在自底向上（bottom-up）的计算过程中保存已经求出、但尚未被父节点消费的属性值。

它的工作方式可以用一句话概括：

> **子结构完成时压入（push）自己的值；父结构完成时弹出（pop）所有子结构的值，计算出自己的值，再压入。**

这正是综合属性（synthesized attribute）的求值方式：信息自下而上流动，每个节点的值只依赖它的子节点。

值栈之所以能工作，依赖于一个结构性事实：**在后序遍历（post-order traversal）中，一个节点的所有子节点恰好是最近完成的那几个、彼此相邻的计算结果。** 因此它们恰好位于栈顶，按从左到右的顺序排列。不需要任何查找，栈顶的那几个元素就是要找的东西。

这也是值栈与侧表的本质区别：

| | 侧表 | 值栈 |
|---|---|---|
| 如何找到子节点的属性 | 按键（节点标识）查找 | 按位置：就在栈顶 |
| 是否需要树 | 需要（节点作为键） | **不需要** |
| 属性的生存期 | 直到表被丢弃 | 直到被父节点弹出 |
| 依赖什么才能正确 | 键的唯一性 | **遍历顺序** |

## 二、理论来源：LR 归约与 S 属性定义

### 2.1 S 属性定义与自底向上分析

龙书（Compilers: Principles, Techniques, and Tools）把只使用综合属性的语法制导定义（Syntax-Directed Definition, SDD）称为 **S 属性定义**（S-attributed definition）。它有一个重要性质：可以在 LR 分析的过程中直接求值，不需要建立语法树。

原因在于 LR 分析器的归约动作。LR 分析器维护一个状态栈（state stack），每次归约产生式 $A \to X_1 X_2 \cdots X_n$ 时：

1. 栈顶恰好是 $X_1, X_2, \ldots, X_n$ 对应的 $n$ 个状态，这段内容称为句柄（handle）；
2. 弹出这 $n$ 个状态；
3. 根据新栈顶状态和 $A$ 查 goto 表，压入一个新状态。

如果在每个状态旁边并排存放对应文法符号的属性值，那么：

- 归约时，$X_1, \ldots, X_n$ 的属性恰好在值栈顶部的 $n$ 个位置；
- 计算 $A$ 的综合属性只需要读取这 $n$ 个位置；
- 弹出 $n$ 个值，压入 $A$ 的值，值栈与状态栈继续保持同步。

**语法制导翻译方案（SDT）中只把动作放在产生式最右端的情形**，龙书称为后缀翻译方案（postfix translation scheme）。后缀 SDT 正是能直接用值栈实现的那一类。

### 2.2 一次完整的手工模拟

以经典的表达式文法为例：

```
E → E + T    { E.val = E₁.val + T.val }
E → T        { E.val = T.val }
T → T * F    { T.val = T₁.val × F.val }
T → F        { T.val = F.val }
F → num      { F.val = num.lexval }
```

分析输入 `3 * 4 + 5`，符号栈（这里用文法符号代替状态以便阅读）和值栈的变化如下：

| 步骤 | 动作 | 符号栈 | 值栈 |
|---|---|---|---|
| 1 | 移入 `3` | `num` | `3` |
| 2 | 归约 F → num | `F` | `3` |
| 3 | 归约 T → F | `T` | `3` |
| 4 | 移入 `*` | `T *` | `3 _` |
| 5 | 移入 `4` | `T * num` | `3 _ 4` |
| 6 | 归约 F → num | `T * F` | `3 _ 4` |
| 7 | 归约 T → T * F | `T` | `12` |
| 8 | 归约 E → T | `E` | `12` |
| 9 | 移入 `+` | `E +` | `12 _` |
| 10 | 移入 `5` | `E + num` | `12 _ 5` |
| 11 | 归约 F → num、T → F | `E + T` | `12 _ 5` |
| 12 | 归约 E → E + T | `E` | `17` |

几个观察：

- **终结符也占一个槽位**。`*` 和 `+` 的槽位里存放的是词法分析器给出的值（这里无意义，记作 `_`）。这保证了值栈与符号栈严格等高。
- **单产生式归约（unit reduction）不改变值**。`F → num`、`T → F` 只是把同一个值“重新标记”为另一个符号的属性。
- **第 7 步**是整个过程的缩影：弹出 `3 _ 4` 三个值，计算 `3 × 4`，压入 `12`。
- 整个过程**从未建立语法树**。树只存在于归约的历史中，计算结束后什么也没留下。

### 2.3 不变式

值栈的正确性可以归结为一条不变式（invariant）：

> **在任意时刻，值栈的第 $i$ 个槽位保存符号栈第 $i$ 个符号的属性值。**

由此可以推出：归约 $A \to X_1 \cdots X_n$ 时，$X_k$ 的值位于“栈顶往下数第 $n-k$ 个”位置。这就是 Bison 生成代码中下标计算的来源（见 3.1 节）。

### 2.4 栈效应

Forth 语言社区有一种描述栈操作的记法，称为**栈效应**（stack effect）：

```
( 输入 -- 输出 )
```

例如乘法是 `( a b -- a*b )`：消费两个值，产生一个值。

用这个视角看值栈，可以得到一个非常有用的推论：

> **任何一棵完整子树的净栈效应都是 `( -- v )`：它恰好在栈上留下一个值。**

证明很简单（对子树高度归纳）：叶子压入一个值；内部节点的 $n$ 个子树各自净压入一个值，节点本身弹出 $n$ 个、压入一个，净效应还是一个。

这条推论是调试值栈代码时最重要的检查标准。只要某处的压入与弹出数目不平衡，后面所有计算都会错位。第九节会看到，大多数值栈 bug 都是这条性质被破坏的结果。

## 三、Yacc 与 Bison 中的值栈

Yacc（1975）和它的后继 Bison 是值栈最经典的工程实现。理解它们的细节，能看清值栈的全部能力与边界。

### 3.1 `$$` 与 `$n` 的翻译

Bison 生成的分析器中，值栈是一个数组，`yyvsp` 指向栈顶。归约一条长度为 `yylen` 的产生式时，`$n` 被翻译为：

```c
yyvsp[(n) - (yylen)]
```

以 `expr : expr '+' term` 为例，`yylen = 3`：

| 记号 | 翻译 | 含义 |
|---|---|---|
| `$1` | `yyvsp[-2]` | 栈顶往下第 2 个 |
| `$2` | `yyvsp[-1]` | 栈顶往下第 1 个 |
| `$3` | `yyvsp[0]` | 栈顶 |
| `$$` | `yyval` | 临时变量，动作执行完后压栈 |

归约的骨架（简化）如下：

```c
yylen = yyr2[yyn];                 /* 产生式右部长度 */
yyval = yyvsp[1 - yylen];          /* 默认动作：$$ = $1 */
switch (yyn) {
    case 5:  /* expr : expr '+' term */
        yyval = yyvsp[-2] + yyvsp[0];
        break;
    /* ... */
}
yyvsp -= yylen;                    /* 弹出右部的所有值 */
*++yyvsp = yyval;                  /* 压入左部的值 */
```

注意在用户动作执行之前，Bison 先执行了 `yyval = yyvsp[1 - yylen]`，也就是 `$$ = $1`。这就是 Yacc 著名的**默认动作**（default action）：没有写动作的规则，自动把第一个符号的值传给左部。这正好覆盖了 `E → T`、`T → F` 这类单产生式归约。

### 3.2 值的类型：`YYSTYPE` 与 `%union`

值栈的每个槽位必须能存放任何文法符号的属性，因此槽位的类型是所有属性类型的并集。Bison 用 `YYSTYPE` 表示这个类型，通常通过 `%union` 声明：

```yacc
%union {
    long         ival;
    char        *sval;
    struct Node *node;
}

%token <ival> NUM
%token <sval> ID
%type  <node> expr term factor
```

`%token <ival>` 和 `%type <node>` 告诉 Bison 每个符号使用联合体（union）的哪个成员。之后在动作中写 `$1`，Bison 会根据符号类型自动生成 `yyvsp[-2].node`。

这是一种**静态的槽位类型检查**（static slot typing）：每个槽位的类型由该位置的文法符号决定，而文法符号在编译期就已知。如果某条规则没有声明类型却使用了 `$$`，Bison 会在生成分析器时报错。

C++ 接口中，Bison 还提供 `%define api.value.type variant`，用带类型标签的变体（variant）代替裸联合体，使 `std::string`、`std::unique_ptr` 等非平凡类型也能安全地放入值栈。

### 3.3 位置栈

Bison 在值栈之外还维护一个并行的**位置栈**（location stack），`yylsp` 指向它的栈顶。每个槽位记录对应符号的源码范围，在动作中用 `@n` 和 `@$` 访问：

```yacc
expr : expr '+' term
       { $$ = mk_add($1, $3);
         if (overflow($$))
             error(@2, "整数溢出");   /* 在 '+' 的位置报错 */
       }
     ;
```

`@$` 的默认值是从 `@1` 的起点到 `@n` 的终点。位置栈与值栈完全同构，它说明了一个一般原则：**任何综合属性都可以拥有自己的并行栈**，只要它和分析栈保持同步。

### 3.4 中间动作

Bison 允许把动作写在产生式中间，称为中间动作（mid-rule action）：

```yacc
block : '{'  { push_scope(); }  stmts  '}'  { pop_scope(); }
      ;
```

Bison 的处理方式是：为中间动作**引入一个匿名的空非终结符**（在报告中显示为 `$@1`），把规则改写成：

```yacc
$@1   : %empty { push_scope(); } ;
block : '{' $@1 stmts '}' { pop_scope(); } ;
```

后果有两个：

1. **中间动作占用一个值栈槽位**，并参与 `$n` 的编号。上例中 `stmts` 是 `$3` 而不是 `$2`。
2. 中间动作也可以有值，在动作内部写作 `$<type>$`，后续动作中用它所占的编号引用。

第二点还有一个副作用：引入的空产生式可能造成新的移入-归约冲突（shift-reduce conflict），因为分析器必须在看到更多输入之前就决定是否执行这个动作。

### 3.5 `$0` 与负下标：在值栈上模拟继承属性

值栈天生只支持综合属性。但 Yacc 有一个非常巧妙、也非常危险的特性：**`$0`、`$-1` 可以访问句柄下方的槽位**。

考虑 C 风格的声明：

```c
int a, b, c;
```

变量列表需要知道前面声明的类型，这是典型的继承属性（inherited attribute）。用 `$0` 可以这样写：

```yacc
decl   : type idlist ';' ;

type   : INT    { $$ = TY_INT; }
       | FLOAT  { $$ = TY_FLOAT; }
       ;

idlist : ID               { declare($1, $<ty>0); }
       | idlist ',' ID    { declare($3, $<ty>0); }
       ;
```

为什么 `$0` 恰好是类型？看归约 `idlist : ID` 时的值栈：

```
... | type 的值 | ID 的值 |
       ↑ $0        ↑ $1
```

句柄只有 `ID` 一个符号，紧挨在它下面的，正是之前已归约完成的 `type`。对 `idlist : idlist ',' ID` 也一样：句柄是 `idlist ',' ID`，它下方依然是 `type`。

这是在自底向上分析中求值继承属性的经典技巧。它成立的前提非常苛刻：

> **在 `idlist` 出现的所有上下文中，它左边紧邻的符号都必须是 `type`。**

如果文法中另有一处 `param : idlist ':' type`，`$0` 读到的就是别的东西，而 Bison 无法检查这一点，因为 `$0` 的类型必须用 `$<ty>0` 显式指定。Bison 手册对此有明确警告。

当不同上下文中句柄下方的内容不一致时，标准做法是插入**标记非终结符**（marker nonterminal），一个只用于复制值的空产生式：

```yacc
decl : type M idlist ';' ;
M    : %empty   { $$ = $0; }    /* 把 type 的值复制到固定位置 */
     ;
```

龙书把这种技术称为“在自底向上分析中实现 L 属性定义”：通过在合适的位置插入标记，保证每个继承属性在需要时总能在栈中的可预测位置找到。这是值栈能力的上限，再往上就必须建树。

### 3.6 错误恢复与 `%destructor`

值栈带来一个侵入式字段和侧表都不会遇到的问题：**值可能被丢弃**。

Bison 的错误恢复（error recovery）机制在遇到语法错误时，会不断弹出状态栈，直到找到一个能移入 `error` 记号的状态。随着状态被弹出，对应的值也被弹出，而这些值永远不会被任何动作消费。

如果值是 `malloc` 出来的 AST 节点或字符串，它们就泄漏了。Bison 为此提供了 `%destructor`：

```yacc
%destructor { free($$); }        <sval>
%destructor { free_node($$); }   <node>
```

当一个值在错误恢复中被丢弃，或者分析器因 `YYABORT` 终止时，Bison 会调用对应类型的析构代码。

这暴露了值栈的一个根本特性：**值的所有权（ownership）属于栈，而不属于树。** 正常路径上，动作把子值的所有权转移给父值；异常路径上，栈必须自己负责清理。C++ variant 接口借助析构函数自动完成了这件事。

### 3.7 栈深度与递归方向

值栈的深度由什么决定？考虑两种写法的列表：

```yacc
list : list ',' item   ;   /* 左递归（left recursion） */
list : item ',' list   ;   /* 右递归（right recursion） */
```

- **左递归**：每读完一个 `item` 就可以归约，栈深度保持常数。
- **右递归**：必须读完整个列表才能开始归约，`n` 个元素的列表需要 $O(n)$ 的栈深度。

Bison 手册明确建议优先使用左递归。默认情况下，C 分析器的栈初始深度是 `YYINITDEPTH = 200`，最多扩展到 `YYMAXDEPTH = 10000`，超出就报“memory exhausted”。一个有一万个元素的右递归数组初始化器，就足以让分析器失败。

这一点和自顶向下分析正好相反：LL 分析器无法处理左递归，而 LR 分析器偏爱左递归。原因正是值栈：LR 分析器在归约时清理栈，左递归让归约尽早发生。

### 3.8 GLR 分析中的值栈

Bison 的 GLR 模式允许文法有歧义：遇到冲突时，分析器同时尝试多条路径，相当于同时维护多个分析栈。

这对值栈提出了难题：如果每条路径都立即执行语义动作，那么最终被抛弃的路径上也会产生副作用。Bison 的解决方式是：**分析器分裂期间推迟执行语义动作**（deferred semantic actions），只记录要执行哪些归约；等到歧义消解、只剩一条路径时，再按顺序执行。如果两条路径最终都成功，可以用 `%merge` 指定一个函数合并两个语义值。

这说明了值栈的另一个隐含假设：**它假设计算是确定性的、单线索的。** 一旦需要回溯或分裂，值栈就必须配合额外机制。

## 四、自顶向下分析中的值栈

### 4.1 递归下降：调用栈就是值栈

在手写的递归下降分析器（recursive descent parser）里，看不到显式的值栈：

```c
long parse_expr(void) {
    long v = parse_term();             /* 综合属性：由返回值带上来 */
    while (tok == '+') {
        next();
        v += parse_term();
    }
    return v;
}

long parse_term(void) {
    long v = parse_factor();
    while (tok == '*') {
        next();
        v *= parse_factor();
    }
    return v;
}
```

值栈并没有消失，它变成了**调用栈**（call stack）：

- 每个 `parse_xxx` 的栈帧（stack frame）就是一个“值栈槽位”的集合，局部变量 `v` 保存着部分计算结果；
- 函数返回值就是“压入值栈”；
- 调用者拿到返回值就是“弹出值栈”。

而且递归下降天然支持继承属性：函数参数就是向下传递的属性。

```c
void parse_idlist(Type ty) {           /* 继承属性：参数 */
    declare(expect(ID), ty);
    while (tok == ',') { next(); declare(expect(ID), ty); }
}
```

LR 分析器需要用 `$0` 和标记非终结符才能勉强做到的事，在递归下降里只是一个函数参数。这是现代编译器偏爱手写递归下降的又一个原因：**调用栈是一个同时支持上行和下行属性、并且由编程语言保证类型正确的值栈。**

代价也来自调用栈：嵌套很深的表达式（比如自动生成的几千层括号）会导致栈溢出（stack overflow）。生产级编译器通常会对递归深度设置上限，或者在检测到深度过大时切换到更大的栈。

### 4.2 表驱动 LL 分析：语义栈

在表驱动的 LL(1) 分析器中，没有递归函数，分析栈中存放的是**待匹配的文法符号**，而不是已识别的符号。这与 LR 正好相反，值栈因此不能简单地与分析栈并行。

龙书描述的方法是在分析栈中混入两类特殊记录：

- **动作记录**（action record）：轮到它出栈时，执行一段语义动作；
- **综合记录**（synthesize record）：为某个非终结符预留的位置，用于收集它的子结构算出的值。

非终结符展开时，它的继承属性放在自己的记录中；它的综合属性要等右部全部处理完才能得到，所以先在下方放一个综合记录占位，等右部出栈完毕后再把结果填进去。

这套机制比 LR 的值栈复杂得多，也是表驱动 LL 分析器在实践中很少直接用于翻译的原因之一。

## 五、树遍历中的显式值栈

当分析器已经构建出完整的语法树，遍历器又不支持返回值时，值栈以显式数据结构的形式重新出现。ANTLR 4 的 Listener 就是典型。

### 5.1 Listener 中的值栈

ANTLR 的 `ParseTreeWalker` 按深度优先、从左到右的顺序遍历树，在每个节点触发 `enter` 和 `exit`，但这两个回调都没有返回值。要计算综合属性，最直接的办法是自己维护一个栈：

```java
public class ThreeAddrListener extends ExprBaseListener {
    private final Deque<String> vals = new ArrayDeque<>();   // 值栈
    private final List<String> code = new ArrayList<>();
    private int tmp = 0;

    @Override public void exitInt(ExprParser.IntContext ctx) {
        vals.push(ctx.INT().getText());                // ( -- v )
    }

    @Override public void exitAddSub(ExprParser.AddSubContext ctx) {
        String r = vals.pop();                         // 先出栈的是右操作数
        String l = vals.pop();
        String t = "t" + (++tmp);
        code.add(t + " = " + l + " " + ctx.op.getText() + " " + r);
        vals.push(t);                                  // ( l r -- t )
    }

    @Override public void exitParens(ExprParser.ParensContext ctx) {
        // ( v -- v )：括号不改变栈，什么也不做
    }
}
```

`exitAddSub` 被调用时，两个子表达式都已经 `exit` 过，按左、右顺序各自压入了一个值，所以栈顶是右操作数，其下是左操作数。这就是 `r = pop(); l = pop();` 这个顺序的来历，也是这类代码最常见的 bug 来源。

这段代码和 Bison 的值栈在本质上完全一样：`exit` 回调就是归约，`exit` 的调用顺序就是后序遍历。区别只是 Bison 的值栈与分析栈同步，而这里的值栈与遍历器的隐式递归同步。

### 5.2 变长子节点：栈高标记

二元运算的子节点数目是固定的，弹出两次即可。函数调用的参数个数却不固定：

```
f(a, b + c, g(d))
```

`exitCall` 被调用时，应该弹出几个值？一种做法是从树上数参数个数；更通用的做法是**栈高标记**（stack height mark）：

```java
private final Deque<Integer> marks = new ArrayDeque<>();

@Override public void enterCall(ExprParser.CallContext ctx) {
    marks.push(vals.size());                 // 记住进入时的栈高
}

@Override public void exitCall(ExprParser.CallContext ctx) {
    int base = marks.pop();
    List<String> args = new ArrayList<>();
    while (vals.size() > base) args.add(0, vals.pop());   // 弹回进入时的高度
    String t = "t" + (++tmp);
    code.add(t + " = call " + ctx.ID().getText() + "(" + String.join(", ", args) + ")");
    vals.push(t);
}
```

这和 Bison 中“在句柄下方找到上下文”的思路如出一辙，只是更安全：标记显式记录了边界，而不是依赖文法结构的隐含假设。

同时它还说明了一件事：`marks` 是一个**在 `enter` 时压入、在 `exit` 时弹出**的栈，它记录的是“从上往下传的信息”。这引出了下一个区分。

### 5.3 值栈与上下文栈

在树遍历中经常同时出现两种栈，它们形状一样，方向相反：

| | 值栈（value stack） | 上下文栈（context stack） |
|---|---|---|
| 对应的属性 | 综合属性（synthesized） | 继承属性（inherited） |
| 何时压入 | 子节点 `exit` 时 | 父节点 `enter` 时 |
| 何时弹出 | 父节点 `exit` 时 | 同一节点 `exit` 时 |
| 谁读取 | 父节点 | 所有后代节点 |
| 典型例子 | 表达式的值、临时变量名 | 作用域栈（scope stack）、循环跳转目标栈（break/continue target stack） |

一个用于生成三地址码的 Listener 往往两种都有：

```java
private final Deque<String> breakTargets = new ArrayDeque<>();   // 上下文栈

@Override public void enterWhile(ExprParser.WhileContext ctx) {
    breakTargets.push(newLabel());       // 父节点为后代设置 break 目标
}
@Override public void exitBreak(ExprParser.BreakContext ctx) {
    code.add("goto " + breakTargets.peek());   // 后代读取，不弹出
}
@Override public void exitWhile(ExprParser.WhileContext ctx) {
    code.add(breakTargets.pop() + ":");
}
```

注意上下文栈的读取用的是 `peek` 而不是 `pop`：继承属性可以被任意多个后代读取，而综合属性只被父节点消费一次。这个“读一次 vs 读多次”的区别，是判断某个栈是哪一类的简单方法。

Clang 的 `CodeGenFunction` 中的 `BreakContinueStack`、各种作用域栈，就是工业级的上下文栈。

### 5.4 值栈与侧表的取舍

前一篇介绍的 ANTLR `ParseTreeProperty` 是侧表方案。两者对比：

| | 值栈 | 侧表 |
|---|---|---|
| 访问子属性 | 隐式，依赖栈序 | 显式，按节点查找 |
| 出错方式 | 压弹不平衡导致整体错位 | 漏填导致查到空值 |
| 性能 | 极快，无哈希 | 有哈希开销 |
| 内存 | 只保存“活跃”的值 | 保存所有节点的值，直到表被丢弃 |
| 跨节点访问 | 不能，值被弹出后就消失 | 可以，随时回查 |
| 多遍共享 | 不能 | 可以 |

经验法则是：**值只被父节点消费一次、且计算结束后不再需要时，用值栈；值需要被回查、被多遍共享时，用侧表。**

## 六、值栈与栈式求值

值栈的思想不只服务于语法分析。“后序遍历 + 栈”是求值表达式最基本的模式，它在编译器的另一端以**操作数栈**（operand stack）的形式出现。

### 6.1 后缀表达式

表达式 `3 * 4 + 5` 的后缀形式（postfix notation，也称逆波兰表示法 Reverse Polish Notation, RPN）是：

```
3 4 * 5 +
```

求值方法正是值栈：遇到数字就压栈，遇到运算符就弹出两个、计算、压回。比较一下第 2.2 节 LR 分析的值栈变化：`3`、`3 4`、`12`、`12 5`、`17`，两者完全一致。

这不是巧合。**LR 分析器执行归约的顺序，就是语法树的后序遍历顺序**，因而也就是后缀表达式的顺序。龙书第 2 章那个把中缀表达式翻译成后缀表达式的小翻译器，展示的正是这个对应关系。

### 6.2 调度场算法

Dijkstra 在 1961 年提出的调度场算法（shunting-yard algorithm）用两个栈解析中缀表达式：

- **操作数栈**（operand stack）：就是值栈，存放已经算出的值或已经构造的子树；
- **运算符栈**（operator stack）：存放尚未处理的运算符，按优先级（precedence）和结合性（associativity）决定何时弹出。

每当一个运算符从运算符栈弹出，就从操作数栈弹出两个操作数，组合后压回去。这实际上是一个专门针对运算符优先级文法、手工实现的 LR 分析器，操作数栈与 Bison 的值栈承担着同样的职责。许多手写解析器中的优先级爬升（precedence climbing）或 Pratt 解析，则是把这两个栈换成了调用栈。

### 6.3 栈式虚拟机

把“后序遍历 + 值栈”从编译期搬到运行期，就得到了栈式虚拟机（stack-based virtual machine）。

**JVM**：`a + b * c` 编译成字节码：

```
iload_1      // ( -- a )
iload_2      // ( a -- a b )
iload_3      // ( a b -- a b c )
imul         // ( a b c -- a b*c )
iadd         // ( a x -- a+x )
```

每个方法的栈帧中都有一个操作数栈，`Code` 属性中的 `max_stack` 字段记录它的最大深度。

**CPython**：字节码同样基于求值栈（evaluation stack），代码对象的 `co_stacksize` 记录所需的最大深度。

**WebAssembly**：指令也是栈式的，`i32.add` 的语义是弹出两个 `i32`、压入一个 `i32`。

从 AST 生成这些字节码，几乎就是一次后序遍历：叶子发射“压栈”指令，内部节点发射“运算”指令。值栈从编译器的数据结构，变成了目标程序的数据结构。

这也解释了为什么栈式字节码这么流行：**生成它的编译器极其简单**，不需要寄存器分配，代码也非常紧凑。代价是解释执行时指令数较多，而把它编译成高效的机器码需要额外的工作（见 7.3 节）。

## 七、编译期的抽象值栈

最有意思的是：当编译器或验证器**处理**栈式字节码时，它们需要在编译期模拟运行期的值栈。栈中存放的不再是具体的值，而是关于值的**抽象信息**（abstract information）。这是抽象解释（abstract interpretation）在值栈上的直接应用。

### 7.1 WebAssembly 验证：类型栈

WebAssembly 规范的附录中给出了一个验证算法（validation algorithm），它维护两个栈：

- **值栈**（value stack，规范中记作 `vals`）：每个槽位存放一个**值类型**（value type），如 `i32`、`f64`，而不是具体的值；
- **控制栈**（control stack，记作 `ctrls`）：每个元素代表一个尚未结束的 `block`、`loop` 或 `if`，记录它的参数类型、结果类型，以及进入时值栈的高度。

验证 `i32.add` 就是对类型栈执行它的栈效应：

```
pop_val(i32)
pop_val(i32)
push_val(i32)
```

如果弹出的类型不是 `i32`，或者栈高低于当前控制帧记录的高度，验证失败。控制帧记录的栈高，与 5.2 节的“栈高标记”是同一个思想：它保证一个块内的代码不能消费块外的值。

规范中还有一个精巧的细节：在 `unreachable`、`br` 等无条件跳转之后，值栈进入**栈多态**（stack-polymorphic）状态，弹出操作可以返回“未知类型”，因为这段代码永远不会执行，不需要真正检查。

### 7.2 JVM 字节码验证

JVM 的字节码验证器（bytecode verifier）对每条指令推导出执行前操作数栈中每个槽位的类型。由于存在跳转，同一条指令可能从多个前驱到达，验证器需要在合流点合并（merge）各条路径上的栈类型，这本质上是一次数据流分析（data-flow analysis），也就是格上的不动点迭代。

为了加快验证，Java 6 引入、Java 7 起强制要求的 `StackMapTable` 属性，由编译器在每个跳转目标处直接写下操作数栈和局部变量的类型。验证器只需检查这些声明是否一致，不再需要迭代求解。

### 7.3 基线 JIT：虚拟栈

把栈式字节码编译成寄存器机器码时，最直接的方法是把操作数栈原样搬到内存里：每次压栈就写内存，每次弹栈就读内存。这样生成的代码非常慢。

基线 JIT 编译器（baseline JIT compiler），比如 V8 中编译 WebAssembly 的 Liftoff，采用的是另一种做法：在编译期维护一个**虚拟值栈**（virtual value stack），每个槽位不存放值本身，而是记录“这个值现在在哪里”：

| 槽位状态 | 含义 |
|---|---|
| 常量（constant） | 值是编译期已知的常量，还没有生成任何指令 |
| 寄存器（register） | 值在某个物理寄存器中 |
| 栈槽（stack slot） | 值已经溢出（spill）到内存 |

编译 `i32.const 5; i32.add` 时：

1. `i32.const 5` 只在虚拟栈上压入一个“常量 5”，**不生成任何指令**；
2. `i32.add` 弹出两个槽位，发现右边是常量，于是直接生成 `add reg, 5`，把常量编码成立即数。

这是一种**延迟物化**（deferred materialization）：值只在真正需要时才被放进寄存器。它把前一篇关于指令选择的文章中讨论的“立即数折叠”，用一个值栈就实现了，而且只需对字节码做一遍线性扫描。

这个例子说明，值栈不仅能存放属性的值，还能存放**关于值的元信息**。槽位内容从“具体的数”到“类型”再到“位置”，值栈的结构始终不变。

## 八、全景：值栈的几种身份

| 场景 | 栈中存放的 | 与谁同步 | 典型实现 |
|---|---|---|---|
| LR 语法分析 | 文法符号的语义值 | 分析栈（状态栈） | Yacc/Bison `yyvsp` |
| LR 语法分析 | 源码位置 | 分析栈 | Bison `yylsp` |
| 递归下降 | 局部变量与返回值 | 调用栈 | 手写解析器 |
| 表驱动 LL | 综合记录、动作记录 | 分析栈 | 龙书第 5 章 |
| 树遍历 | 子节点的综合属性 | 遍历器的隐式递归 | ANTLR Listener |
| 中缀表达式解析 | 操作数或子树 | 运算符栈 | 调度场算法 |
| 字节码执行 | 运行期的值 | 指令流 | JVM、CPython、Wasm |
| 字节码验证 | 值的类型 | 指令流 + 控制栈 | Wasm 验证器、JVM 验证器 |
| 基线 JIT | 值的位置 | 指令流 | V8 Liftoff 等 |

把这张表从上往下看，可以发现一条线索：**值栈总是伴随一个后序的、线性的计算过程出现**。只要计算顺序保证“子结构总在父结构之前完成，且相邻地完成”，值栈就能工作。

## 九、常见陷阱

| 陷阱 | 症状 | 原因 | 对策 |
|---|---|---|---|
| 左右操作数颠倒 | `a - b` 算成 `b - a` | 忘了先出栈的是右操作数 | 固定写法 `r = pop(); l = pop();` |
| 压弹不平衡 | 之后所有结果都错位 | 某个节点违反了 `( -- v )` 栈效应，例如括号节点多压了一次 | 每个节点检查净栈效应；遍历结束时断言栈中恰好一个值 |
| 中间动作导致编号错位 | `$2` 拿到的不是预期的值 | 中间动作占用了一个槽位 | 中间动作计入编号；或改用命名引用 `$name` |
| `$0` 读到错误的值 | 偶发的类型错误 | 某个上下文中句柄下方不是预期的符号 | 插入标记非终结符；或改为建树 |
| 错误恢复时内存泄漏 | 语法错误输入导致泄漏 | 被丢弃的值没有释放 | Bison `%destructor`；或使用带析构的 variant |
| 栈溢出 | 长列表或深嵌套时失败 | 右递归文法；或递归下降深度过大 | 改为左递归；限制嵌套深度 |
| 变长子节点弹出个数错误 | 函数参数丢失或多出 | 用固定次数弹出变长结构 | 使用栈高标记 |
| 混淆值栈与上下文栈 | 继承属性被意外消费 | 对上下文栈用了 `pop` 而不是 `peek` | 两种栈分开声明、分开命名 |
| 跨节点回查失败 | 想用的值已经不在栈上 | 值栈只保留活跃的值 | 这类属性改用侧表 |
| 错误恢复产生畸形树后错位 | 部分节点缺失时栈不平衡 | 缺失的子节点没有压入值 | 对缺失子节点压入占位值（错误值） |

最后一条值得多说一句：在 ANTLR 这类会做错误恢复的工具中，树可能缺少某个子节点。缺少的子节点不会触发 `exit`，也就不会压栈，父节点弹出时就会拿走不属于自己的值。稳妥的做法是在父节点中检查子节点是否存在，缺失时压入一个专门的“错误值”，保持栈效应平衡。这和编译器类型检查中常用的错误类型（error type）是同一个思路。

## 十、选型判据

| 问题 | 倾向值栈 | 倾向其他方案 |
|---|---|---|
| 属性是否只有综合属性（S 属性）？ | 是 | 否：需要继承属性时，考虑递归下降参数或上下文栈 |
| 是否只需一遍、边分析边计算？ | 是 | 否：多遍时用侧表或 AST |
| 每个值是否只被父节点使用一次？ | 是 | 否：需要回查时用侧表 |
| 是否追求极致性能和低内存？ | 是 | 否 |
| 遍历器是否没有返回值（Listener、LR 动作）？ | 是 | 否：有返回值时直接用返回值更清晰 |
| 子节点数目是否固定？ | 是 | 否：需要栈高标记 |

几条实践建议：

1. **能用返回值就用返回值。** 递归下降和 Visitor 的返回值是由语言保证类型和平衡的值栈，比手写的 `Deque` 安全得多。显式值栈适合遍历器不给你返回值的场合。
2. **把栈效应写进注释。** 每个回调旁边写上 `( l r -- t )`，代码审查时一眼就能看出是否平衡。
3. **在遍历结束时检查不变式。** 断言值栈中恰好剩下一个值、上下文栈为空。这条断言能捕获绝大多数值栈 bug。
4. **继承属性不要硬塞进值栈。** `$0` 是一个精巧的技巧，但它把文法的上下文假设隐藏在了代码里。需要继承属性时，优先使用递归下降的参数、上下文栈或者建树。
5. **栈中的内容可以是任何东西。** 值、AST 节点、临时变量名、类型、寄存器位置，只要它们遵循后序的生产与消费顺序，值栈都适用。

## 结语

值栈的核心思想只有一句话：**在后序的计算过程中，子结构的结果总是恰好位于栈顶。**

这一结构性事实让值栈成为最高效的属性存储方式：没有键，没有查找，没有树，只有压入和弹出。它支撑了 Yacc 和 Bison 的 `$$` 与 `$n`，隐藏在递归下降分析器的调用栈里，以显式 `Deque` 的形式出现在 ANTLR 的 Listener 中。

它的边界同样清楚：值栈天然只支持综合属性，继承属性需要借助 `$0`、标记非终结符或另一个上下文栈；值一旦被弹出就不再可见，需要回查或多遍共享时只能交给侧表；它还依赖确定的、单线索的计算顺序，错误恢复和 GLR 分裂都需要额外机制来维持它的平衡。

而在编译器的另一端，同样的结构以操作数栈的形式出现在 JVM、CPython 和 WebAssembly 中；验证器把栈里的值换成类型，基线 JIT 把栈里的值换成位置。从语法分析到代码生成，值栈的内容一再变化，但“后序生产、栈顶消费”这个结构始终没有变。

理解了值栈，也就理解了语法制导翻译最初、最朴素的实现方式：**在没有树的时代，属性就存在遍历的轨迹里。**

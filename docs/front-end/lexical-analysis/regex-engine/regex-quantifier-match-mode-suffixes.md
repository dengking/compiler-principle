# 量词的匹配模式后缀详解

在文法中,量词的定义是:

```
quant ::= ('*' | '+' | '?' | '{' m (',' n?)? '}') ('?' | '+')?
           └──────────── 重复次数 ────────────┘   └─ 模式后缀 ─┘
```

**重复次数**规定"可以匹配多少次",**模式后缀**规定"在允许的范围内,先尝试多少次,以及失败后是否回头"。

---

## 一、三种模式总览

| 写法 | 模式 | 尝试顺序 | 失败后能否回退 |
|---|---|---|---|
| `X*` `X+` `X?` `X{m,n}` | **贪婪** Greedy | 从多到少 | 能 |
| `X*?` `X+?` `X??` `X{m,n}?` | **惰性** Lazy | 从少到多 | 能 |
| `X*+` `X++` `X?+` `X{m,n}+` | **占有** Possessive | 只取最多 | **不能** |

三种模式的**允许次数范围完全相同**,区别只在于尝试的顺序和是否回溯。要理解它们,需要先了解回溯。

---

## 二、基础:回溯是什么

大多数正则引擎(Perl、PCRE、Java、Python、JavaScript 等)采用**回溯式 NFA**。当量词有多种可能的匹配次数时,引擎会:

1. 先选择一种次数,继续匹配后面的模式;
2. 如果后面失败了,就**退回**到这个选择点,换一种次数再试;
3. 所有次数都试过仍然失败,才宣告从当前起点开始匹配失败。

三种模式的本质区别就在于这个"选择点"如何安排:

- 贪婪:选择点按 **多 → 少** 排列
- 惰性:选择点按 **少 → 多** 排列
- 占有:**不留选择点**,只有"最多"这一种

---

## 三、逐步追踪对比

我们用同一个字符串,分别测试三种模式:

```
字符串:<b>bold</b>
位置:  0123456789…
```

### 1. 贪婪:`<.+>`

| 步骤 | 动作 | 状态 |
|---|---|---|
| 1 | `<` 匹配位置 0 | ✓ |
| 2 | `.+` 尽可能多吃,吃到串尾:`b>bold</b>` | ✓ |
| 3 | `>` 尝试匹配串尾,无字符 | ✗ |
| 4 | **回溯**:`.+` 吐出 1 个字符 `>` | |
| 5 | `>` 匹配吐出的 `>` | ✓ |

**结果:`<b>bold</b>`**(整个字符串)

### 2. 惰性:`<.+?>`

| 步骤 | 动作 | 状态 |
|---|---|---|
| 1 | `<` 匹配位置 0 | ✓ |
| 2 | `.+?` 尽可能少吃,只吃最少的 1 个:`b` | ✓ |
| 3 | `>` 匹配位置 2 的 `>` | ✓ |

**结果:`<b>`**

如果第 3 步失败,惰性量词会**多吃一个**再试,这也是一种回溯,只是方向相反。

### 3. 占有:`<.++>`

| 步骤 | 动作 | 状态 |
|---|---|---|
| 1 | `<` 匹配位置 0 | ✓ |
| 2 | `.++` 吃到串尾:`b>bold</b>` | ✓ |
| 3 | `>` 尝试匹配串尾 | ✗ |
| 4 | `.++` **拒绝吐出任何字符**,从位置 0 开始的匹配失败 | ✗ |
| 5 | 引擎将起点移到下一个 `<`(位置 7),同样失败 | ✗ |

**结果:匹配失败**

### 对比总结

```
<b>bold</b>
└─────────┘   贪婪   <.+>
└─┘           惰性   <.+?>
(无)          占有   <.++>
```

## 四、惰性模式详解

### 1. 典型用途:匹配"到最近的结束符为止"

```
".*?"      匹配最近的一对引号
<!--.*?--> 匹配一段 HTML 注释
```

### 2. 单独使用时的表现

惰性量词后面没有其他约束时,它会取**下限**:

| 模式 | 对 `"aaa"` 的匹配结果 |
|---|---|
| `a+?` | `a`(取 1 次) |
| `a*?` | 空串(取 0 次) |
| `a??` | 空串(取 0 次) |
| `a{2,4}?` | `aa`(取 2 次) |

### 3. 常见误解:惰性 ≠ 全局最短

正则引擎遵循**"最左优先"**原则:先确定最靠左的成功起点,再在这个起点上应用贪婪或惰性规则。

```
模式:a+?b
字符串:aaab
```

很多人以为结果是 `ab`,实际结果是 **`aaab`**。因为从位置 0 开始就能匹配成功,引擎不会去找更靠右、更短的匹配。惰性只决定"从这个起点出发吃多少",不改变起点。

### 4. 更好的替代方案:否定字符类

匹配引号字符串时,下面两种写法结果通常相同:

```
".*?"      惰性:每吃一个字符都要试一次后面的 "
"[^"]*"    否定类:直接排除引号,不需要试探
```

第二种更快、语义更明确,也不会因为后续匹配失败而越过引号继续扩展,一般更推荐。

---

## 五、占有模式详解

### 1. 为什么需要"不回退"

看起来占有模式只会让匹配更容易失败,它的价值在于:**当回退注定没用时,直接放弃可以省下大量无意义的尝试**。

```
"[^"]*+"
```

`[^"]*` 永远不会吃进引号,因此把吃进的字符吐出来,也不可能让后面的 `"` 匹配成功。用占有模式,失败时就能立即结束,省掉所有回溯。

### 2. 防止灾难性回溯

经典的反面例子:

```
模式:(a+)+b
字符串:aaaaaaaaaaaaaaaaaaaaaaaaa!   (25 个 a,没有 b)
```

`n` 个 `a` 可以被内外两层 `+` 以约 2ⁿ 种方式切分,例如 `aaa` 可以切成 `(aaa)`、`(aa)(a)`、`(a)(aa)`、`(a)(a)(a)`。由于最终找不到 `b`,引擎会逐一尝试所有切分方式,耗时呈**指数级增长**。这就是 **ReDoS(正则表达式拒绝服务攻击)**的原理。

改为占有模式:

```
(a++)+b
```

内层 `a++` 一次吃掉所有 `a` 且不吐出,切分方式只剩一种,失败会被迅速发现。

### 3. 与原子组等价

占有量词其实是原子组的简写:

```
X*+   ≡   (?>X*)
X++   ≡   (?>X+)
X?+   ≡   (?>X?)
```

这正对应文法中 `atom` 里的 `'(?>' alt ')'`。两者的区别在于,原子组可以包住更复杂的子表达式,而占有量词只作用于单个量词。

### 4. 注意:占有模式可能改变匹配结果

占有模式不仅影响性能,还会影响语义:

```
\d++0    对 "1230"  → 失败(\d++ 吃掉了 0,不肯吐出)
\d+0     对 "1230"  → 成功,匹配 "1230"
```

只有在**确定回退不可能带来成功**时,才能安全地把贪婪改为占有。

## 六、`{m}` 加后缀的情况

固定次数的量词只有一种可能的次数,所以后缀没有实际作用:

```
a{3}  ≡  a{3}?  ≡  a{3}+
```

文法允许这样写,但没有意义。

---

## 七、与文法相关的解析问题

文法中同时存在两条规则:

```
repeat ::= atom quant*
quant  ::= (...) ('?' | '+')?
```

于是 `a++` 存在两种解析方式:

| 解析方式 | 含义 |
|---|---|
| `a` + 量词 `+`(带后缀 `+`) | 占有的 `a+` |
| `a` + 量词 `+` + 量词 `+` | 叠加两个贪婪量词 |

同理,`a+?` 也可以理解为"`a+` 后面再跟一个 `?` 量词"。

解决方法是**最长匹配**:解析量词时,如果紧跟 `?` 或 `+`,就把它当作当前量词的后缀,而不是新的量词。实际引擎都采用这种约定。

对应到解析器代码:

```python
def parse_quant(node):
    lo, hi = parse_count()          # 解析 * + ? {m,n}
    mode = 'greedy'
    if peek() == '?':               # 后缀立即消费,不留给下一个量词
        advance(); mode = 'lazy'
    elif peek() == '+':
        advance(); mode = 'possessive'
    return Repeat(node, lo, hi, mode)
```

## 八、各引擎支持情况

| 引擎/语言 | 贪婪 | 惰性 | 占有 | 原子组 `(?>…)` |
|---|---|---|---|---|
| Perl 5.10+ | ✓ | ✓ | ✓ | ✓ |
| PCRE / PHP | ✓ | ✓ | ✓ | ✓ |
| Java | ✓ | ✓ | ✓ | ✓ |
| Ruby | ✓ | ✓ | ✓ | ✓ |
| Python 3.11+ | ✓ | ✓ | ✓ | ✓ |
| Python ≤ 3.10 | ✓ | ✓ | ✗ | ✗ |
| .NET | ✓ | ✓ | ✗ | ✓ |
| JavaScript | ✓ | ✓ | ✗ | ✗ |
| Go (RE2) | ✓ | ✓ | ✗ | ✗ |

补充说明:

- **.NET** 不支持占有量词,但可以用原子组代替。
- **Go / RE2** 不采用回溯算法,匹配时间始终是线性的,天然不存在灾难性回溯,因此也不需要占有模式。
- **POSIX 正则**(如 `grep`)采用"最左最长"语义,原则上不支持惰性量词。

---

## 九、总结

| | 贪婪 | 惰性 | 占有 |
|---|---|---|---|
| 写法 | `X*` | `X*?` | `X*+` |
| 首次尝试 | 最多次 | 最少次 | 最多次 |
| 失败后 | 逐个吐出 | 逐个多吃 | 直接失败 |
| 主要用途 | 默认行为 | 匹配到最近的边界 | 提升性能、防止 ReDoS |
| 风险 | 可能吃过头 | 可能较慢,"最短"只是局部的 | 可能错误地导致匹配失败 |

一句话概括:**贪婪先多后少,惰性先少后多,占有只要最多且绝不让步。**

# 指令选择

## ——现代编译器如何把 IR 变成机器指令

---

## 一、这个阶段到底在做什么

指令选择（instruction selection）的任务可以一句话说清：**给定一段中间表示，找出一个语义等价、代价尽量低的机器指令序列。**

形式化地说，它是一次覆盖（covering）：把 IR 的运算图切成一堆小块（tile），每一块对应一条机器指令，块之间的边界由寄存器或内存传递。

关键在这个“切”字。同一个 `(a + b) * 4`，可以切成：

```
切法 A（三块）:  t = a + b        ; add
                t2 = t * 4       ; imul
                或 t2 = t << 2   ; shl
切法 B（两块）:  t = a + b        ; add
                t2 = t * 4       ; lea (t, t, 4)? 不行，lea 只做加
切法 C（一块）:  lea rax, [a + b] ; 再 shl —— 还是两块
```

但如果写成 `(a + b*4)`，x86 的 `lea rax, [rdi + rsi*4]` 就一条指令搞定。**选择什么形状的 tile，决定了代码质量。**

这里已经能看出难点了：**tile 不是独立的**。选一个大 tile 省了一条指令，但它占用的**寄存器**更多、**活区间**更长，可能让寄存器分配器多溢出一次。所以“局部最优”和“全局最优”之间有一道结构性裂缝，这条裂缝贯穿整个后端。

### 位置

在一个典型的 LLVM 式流水线里：

```
源码 → AST → IR → [合法化] → [DAG/图] → 【指令选择】→ MachineInstr → 调度 → 寄存器分配 → 编码
                                          ↑
                                    这一节的主角
```

但要注意一个事实：**指令选择不是一个 pass，而是散布在多个阶段的同一件事。**

- IR 层就已经开始选了：LLVM 的 target-specific IR combine 会把 `(x << 3) - x` 改写成 `x * 7`，专门为了后面能一条 `lea` 搞定。
- DAG/MIR 层是主战场。
- Machine 层还在选：peephole、load/store 配对（ARM64 的 `ldp`）、宏融合（`cmp` + `jcc`）。

所以更准确的描述是：**指令选择是一条从 IR 延伸到机器码的“逐步落地”链条**，每往下一层，抽象就少一点，直到完全绑定到具体指令。

## 二、难点从哪来

如果目标机器是“三地址、正交、每条指令对应一个运算”的纯 RISC，指令选择几乎就是 1:1 的 lowering，没什么可选的。所有真正的复杂度来自这些地方：

**① 异构与不规则。** x86 的 `lea` 能做加法、能做乘 2/4/8、能算地址、能同时算两个加法（`lea rax, [rdi + rsi + 8]`），但它不设置标志位、不写内存、且强迫目标是寄存器。CISC 的每条指令都是一堆特例的集合。

**② 寻址模式。** `[base + index*scale + disp]` 这种模式意味着一个 load 指令可以吸收一棵子树的加法与乘法。吸收是好事（少指令），但它是跨语义边界的：它把“算术”和“访存”焊在一起，而这两者在 IR 上本该是可分离、可重排、可优化的。

**③ 立即数。** 一个常量是“免费的立即数”还是“得先 `mov` 到寄存器”？取决于值和指令编码。ARM64 的逻辑指令只能编码特定位模式的立即数，其他值必须先物化。而“是否物化”这个决定又和寄存器压力耦合。

**④ 多结果指令。** `divmod`（商和余数一次算出）、`smull`（高低 64 位）、`ldp`（一次加载两个）。这些打破了“一条指令一个结果”的假设，也让调度器必须把它们当成不可分的整体。

**⑤ 标志位与隐式操作数。** x86 的 `add` 顺手改了 EFLAGS，`jne` 用它。这两条指令必须相邻（中间不能有改标志的指令），但它们之间没有数据依赖。x86 的 `mul`/`div` 强制用 `RAX:RDX`，`shl` 强制用 `CL`。这些“看不见的依赖”必须在选择阶段就建模，否则寄存器分配器无从下手。

**⑥ 类型合法化。** 目标机不支持的类型必须先被拆掉：32 位机器上的 `i64` 乘法、没有 FP16 的机器上的 `f16`、任意长度的向量。这发生在**选择之前**，是选择的前置工序，但它经常比选择本身更难写。

**⑦ 向量。** 向量指令的模式匹配（尤其是 shuffle/permute）是整个后端代码量最大、最丑陋的部分。x86 的 `vpshufb`、`vpermd`、`vpunpck*` 组合起来能表达的置换集合极其复杂，通常靠手写的 C++ 逻辑加一堆启发式。

## 三、经典理论：从字符串到树到图

### 3.1 三代方法

指令选择的形式化研究走了三代：

| 代际 | 匹配对象 | 代表 | 复杂度 |
|---|---|---|---|
| Peephole / 字符串重写 | 线性指令序列 | Glanville & Graham (1978)、Davidson & Fraser | 随模式长度线性 |
| **树模式匹配** | 表达式树 | Cattell (1978)、Aho & Johnson (1976)、BURG/iburg | **线性**(简单代价函数) |
| 图覆盖 | DAG(公共子表达式共享) | 工业界的贪婪匹配;理论上 NP-hard | — |

Peephole 的思路最朴素：把指令序列当成字符串，用模式 `(mov r, x) (add r, y)` → `(add r, x)` 这样的规则反复重写。它的优点是能捕捉跨语句的优化，缺点是**没有全局观**，且依赖前一步生成的指令质量。

树模式匹配才是理论的高峰。核心想法如下。

### 3.2 树覆盖 + 动态规划

给定一棵表达式树，和一组模式（每个模式是一棵小树模板加上一条指令和一个代价），求最小代价覆盖。

关键技巧是**把模式反转过来看**：不去枚举“怎么切”，而是对每个节点，枚举“以这个节点为根的 tile 有哪些”，然后递归到“剩下未被覆盖的子树”。

```
cost(v) = min over 所有以 v 为根的 tile T:
            cost(T) + Σ cost(r)   对 T 的每个"叶子位置" r（即 T 覆盖不到的子树根）
```

由于一棵树的后序遍历是拓扑序，这个 DP 可以自底向上一次算完。每个节点上只需存一个数（最小代价）和一个选择（选了哪个 tile）。

**为什么这几乎是线性的？** 因为每个节点上候选 tile 的数量只取决于模式集的大小（常数），而且子问题的总数是节点数。Aho 与 Johnson 在 1976 年给出了简单代价函数下的 O(n) 算法；Fraser、Hanson、Proebsting 的 BURG（1991）和 iburg 把常数压到很小，生成的表非常紧凑。

这解释了 BURG 为什么在 1990 年代的编译器里风靡：**生成式、可重定向、理论最优、速度快**。

一个小例子。假设机器有：

```
ADD rd, rs        代价 1
ADD rd, rs, imm   代价 1
MUL rd, rs, imm   代价 1
SHL rd, rs, imm   代价 1
MOV  rd, rs       代价 1
```

表达式 `((a, +, b), *, 4)`，其中 `4` 是常量：

- 叶子 `a`、`b`：已在寄存器，代价 0
- `a+b`：tile `ADD rd, rs` 覆盖它，代价 1
- `×4`：可以用 `MUL rd, rs, 4`（代价 1），或 `SHL rd, rs, 2`（代价 1）。等价。
- 总代价 2。

但如果机器有 `LEA rd, [rs1 + rs2*4]`，那么整个 `(a+b)*4` 可以……不行，因为 `lea` 只能做一次带缩放的加法，`(a+b)*4 = a*4 + b*4`，需要两个 `lea` 或者一个 `lea` 加一次加法。**注意这里出现了一个理论没有直接覆盖的情况：改写。**

经典树覆盖只匹配**已有的树结构**，而最优代码有时需要先改写树（分配律、结合律）。这就是为什么真实编译器一定需要“选择前的 combine”，BURG 类方法不能单独用。

### 3.3 为什么 DAG 就难了

一旦允许共享子表达式（DAG 而非树），问题立刻变难。Aho、Johnson、Ullman 1977 年证明：**带公共子表达式的表达式的最优代码生成是 NP-完全的**。

直观理解：在树上，每个子表达式只有唯一的父节点，覆盖是“局部”的。但在 DAG 上，共享节点必须被**求值一次**，其值要保留到所有使用者用完为止，这就引入了寄存器分配问题；而“什么时候溢出”、“哪些值复用到什么程度”是全局组合优化。

Bruno 与 Sethi 1976 年也证明：即使对树，只要机器有多个寄存器，最优代码生成也是 NP-难的；一寄存器机器才有多项式算法。

这两个结论合起来说明一件事：

> **“最优指令选择”在现实中不可能做到。所有工业编译器做的都是“局部最优 + 启发式”。**

这里给出 BURG 的“可移植”承诺：它可以在给定模式集下**精确地**求解树覆盖。但 DAG 上的真实代码不是纯树，所以 BURG 类系统必须配合“先做 DAG 到树的拆解”或“贪心地处理共享节点”。

## 四、LLVM 的 SelectionDAG

LLVM 是这个问题上最有教育价值的样本，因为它的设计取舍非常显式。

### 4.1 构造：三种边

IR 进 DAG 的第一件事是构造 `SelectionDAG`。节点是 `SDNode`，边有三类：

| 边 | 含义 | 例子 |
|---|---|---|
| **数据边** | 值依赖 | `add` 的输出被 `mul` 使用 |
| **链边（chain）** | 副作用顺序 | `store` 必须在另一个 `store` 之后；`load` 顺序；`volatile` 严格保序 |
| **胶边（glue）** | 不可分割 | 一条指令编码需要相邻，如 ARM64 的 `ldp` 两个 load 必须成对；x86 的 `cmp`+`jcc` 共享标志 |

数据边是自然的。链边的存在说明一件事：**IR 是无序的，但机器码是有序的**。为了让 DAG 能表达顺序，链就像一条“虚拟线程”，把整个函数串起来。

这也是 SelectionDAG 的一个著名痛点：**DAG 横跨整个函数**（基本块之间靠 chain 连接），所以巨大函数的 DAG 会吃掉大量内存，某些 combine 会呈现超线性行为。这是后来 GlobalISel 出现的主要动因之一。

而胶边是一个工程妥协的产物，值得单独说：`cmp` 和 `jcc` 在语义上完全可以是两条独立指令加一个 EFLAGS 虚拟寄存器，但那样就要求寄存器分配器给 EFLAGS 分配物理寄存器，还要保证不冲突。用 glue 把它们焊死，就避免了这套建模。**代价是灵活性丧失**：被 glue 绑住的节点不能重新排序，调度器无能为力。

### 4.2 合法化：选择之前的三道工序

这是在讲选择前必须交代的，因为它占了 LLVM 里 `TargetLowering` 的大半代码量。

一个从 IR 下来的 DAG，大部分节点对目标机是“不存在”的：`i128` 乘法、任意长度向量的加法、没有硬件支持的 `f16`、`ctpop`（某些目标）、`vselect`。合法化分三步（实际执行顺序见下面的代码）：

```cpp
// SelectionDAGISel::CodeGenAndEmitDAG 的主干（简化）
CurDAG->Combine(BeforeLegalizeTypes);
CurDAG->LegalizeTypes();            // ① 类型合法化
CurDAG->Combine(AfterLegalizeTypes);
CurDAG->LegalizeVectors();          // ② 向量合法化
CurDAG->Legalize();                 // ③ 运算合法化
CurDAG->Combine(AfterLegalizeDAG);
DoInstructionSelection();           // ④ 匹配
```

**① 类型合法化。** 对每个非法类型，做一个动作：

- Promote：`i8` 提升成 `i32`（做运算，必要时截断）
- Expand：`i128` 拆成两个 `i64`
- SoftenFloat：没有硬件浮点，用软件模拟（`f32` → `i32` 运算）
- WidenVector / SplitVector：向量加宽/拆分到合法宽度

**③ 运算合法化。** 对每个非法运算，按目标 hook 决定：

- Legal：直接选
- Promote / Expand：拆成合法运算的序列（例如 64 位乘在 32 位机上展开成 4 个 32 位乘 + 加）
- Custom：调用目标的 `ReplaceNodeResults` 自定义 C++ 代码（x86 的 `i128` 乘法、向量 shuffle 都走这条路）
- LibCall：调用运行时函数（`__udivti3`）

**② 向量合法化** 单独存在，是因为向量类型的拆分方式与运算的组合很特殊，且 shuffle 的合法化常常需要目标自定义。

合法化之后，**每条指令都保证能选到**，或者保证有 fallback。这是“选择”能保持贪婪、简单的前提。

### 4.3 DAG combine：真正的代码质量来源

合法化前后各跑若干轮 `DAGCombine`。它的工作是在图上做局部重写，直到不动点：

- 常量折叠、strength reduction（乘变移位）、`x - x` 归零
- 目标特定的重写：x86 的 `(x<<3)-x` → `x*7`（为了 `lea`）
- 把 `select` 提升成带条件的运算
- 把 load 往使用者那里推（fold），这是后面要重点说的

**工程上的现实是：代码质量的大头来自 combine，而不是来自选择本身。** 选择只是“把合法节点翻译成指令”，真正的优化发生在合法化和 combine 里。

### 4.4 TableGen：模式如何变成匹配器

指令选择的模式写在目标描述文件里（`X86InstrInfo.td` 等）：

```tablegen
def ADD64rr : X86Inst<0x01, (outs GR64:$dst), (ins GR64:$src1, GR64:$src2),
                      "add{q}\t{$src2, $dst|$dst, $src2}",
                      [(set GR64:$dst, (add GR64:$src1, GR64:$src2))]>;

def ADD64ri32 : X86Inst<0x81, (outs GR64:$dst), (ins GR64:$src1, i32imm:$src2),
                        "add{q}\t{$src2, $dst|$dst, $src2}",
                        [(set GR64:$dst, (add GR64:$src1, i32imm:$src2))]>;
```

方括号里的 `[(set GR64:$dst, (add ...))]` 就是**模式**：一棵小树模板，叶子是类型约束或立即数约束。

`llvm-tblgen -gen-dag-isel` 把这些模式编译成**一个字节码式的匹配表**，由 `SelectionDAGISel::SelectCode` 解释执行。这个匹配表大致长这样（概念上）：

```
CheckOpcode add
  MoveChild 0
    CheckValueType i64
    MoveParent
    CheckOpcode add  →  尝试 ADD64rr  的路径
      ...
  CheckInteger  →  尝试 ADD64ri32 的路径
  ...
CompleteMatch ADD64rr
```

几个关键机制：

**模式排序与优先级。** 表生成器会按“复杂度”给模式排序（更具体的模式优先）。例如 `ADD64ri32`（立即数版本）必须排在 `ADD64rr`（寄存器版本）前，否则后者会把立即数也吃掉，导致生成 `mov` + `add`。这个排序规则是 `PatternSortingPredicate`，是日常调试中最常碰到的地方。

**可交换操作数的两个方向。** `add` 可交换，所以 matcher 会对 `(add imm, reg)` 和 `(add reg, imm)` 都试。这静态地翻倍了搜索空间，但换来正确性。

**谓词（predicate）。** `i32imm` 不只是类型检查，还要检查值是否在编码范围内（`isInt<32>`、`isUInt<12>`）。这些通过 `PatLeaf`、`ImmLeaf` 表达，最终变成 matcher 里的 `CheckInteger` / `CheckPatternPredicate` 指令。

**ComplexPattern：寻址派生的关键。** 有些模式不是一个固定的小树，而是“能被某个 C++ 函数分解成一组操作数”的任意子树。x86 的寻址模式就是典型：

```tablegen
def addr : ComplexPattern<i64, 5, "SelectAddr", [add, or, mul, X86WrapperRIP]>;
```

它的意思是：调用 `X86DAGToDAGISel::SelectAddr`，看这棵子树能不能被分解成 `base + index*scale + disp`。如果能，就产出 5 个值（base、index、scale、disp、segment），每个都能在指令里被引用。**这是把“最优代码生成是 NP-hard”这件事用工程手段局部化解的核心技巧：不做全局搜索，而是给出一组可判定的吸收函数。**

### 4.5 一个必须说清的取舍：LLVM 不做最优覆盖

这是理解 LLVM 指令选择最关键的一点，也是它和 BURG 类系统的根本区别：

> **LLVM 的指令选择是贪婪的、自顶向下的，在每个节点上取“最具体的匹配模式”，不做跨节点的代价最小化。**

没有 DP，没有全局代价表。理由是：

1. 合法化之后树形状高度可预测，贪婪常常就够。
2. 全局代价需要寄存器压力估计，而它要到调度之后才准。
3. 模式语言太表达性（谓词、ComplexPattern、多结果、glue、链），DP 无法在其上定义可计算的状态空间。

代价是什么？代价是**次优代码是常态**。例如某个大模式被选中后，导致寄存器压力上升，最后溢出，比选两个小模式更差。LLVM 用一堆“benefit”启发式在 combine 阶段弥补（比如 `getArithmeticInstrCost`、`isLegalAddressingMode`），但本质上是在局部做判断。

这一点值得反复强调：**理论上的“最优覆盖”在工业编译器里被放弃了，换来的是可维护性和可扩展性。**

## 五、GlobalISel：为什么重做一遍

到 2014 年左右，SelectionDAG 的一堆问题已经很明显：

- **慢**。DAG 横跨整个函数，大函数（自动生成的代码、内联后的巨函数）会吃掉巨量内存；有些 combine 是超线性的。
- **信息丢失**。DAG 里没有 SSA 性质，没有 IR 层的类型信息（已经退化到 `i64`/`f64`），也没法在选指令之前做寄存器银行选择。
- **调度太晚**。`SelectionDAG` 内部有一个局部的 list scheduler（为了把 DAG 排成 `MachineInstr` 序列），但真正好的调度需要全局视野，而且它必须处理已选的机器指令。
- **扩展性差**。加一个 pass（比如在选指令前做 pattern 匹配以外的分析）几乎不可能。

GlobalISel 的重构思路是：**不再造 DAG，就在 SSA 形式的 Machine IR 上逐条处理。**

四个阶段：

| 阶段 | 输入 → 输出 | 做什么 |
|---|---|---|
| **IRTranslator** | LLVM IR → gMIR | 机械地翻译成通用操作（`G_ADD`、`G_LOAD`） |
| **Legalizer** | gMIR → gMIR | 把不支持的通用操作/类型拆成支持的（`G_SMULH` 在不支持的目标上展开） |
| **RegBankSelect** | gMIR → gMIR | 给每个虚拟寄存器分配**寄存器银行**（GPR / FPR / 向量），不分配具体寄存器 |
| **InstructionSelect** | gMIR → MIR | 把 `G_*` 换成目标指令 |

关键差异：

- **寄存器银行在选指令之前定**。这解决了一个真实痛点：SelectionDAG 里，选完指令才知道值要进哪个寄存器类，而寄存器类又影响指令选择（例如 x86 的 `movd`/`movq` 跨域移动），形成循环。GlobalISel 把它提前拆开：先定银行，再选指令。
- **无 DAG，无 chain**。顺序由 MachineFunction 的指令序列自然表达，副作用靠 MIR 的 `mayLoad`/`mayStore` 等属性处理。
- **模式来源相同**。TableGen 里的 `Pat` 能被 `-gen-global-isel` 复用，生成一套模仿 SelectionDAG matcher 的匹配器。所以移植目标时，大部分 `.td` 模式两边共享。
- **更快**。IRTranslator 是线性的，Legalizer 是工作列表式的，RegBankSelect 是两轮扫描（fast 或 greedy）。对优化级别较低或编译速度敏感的场景，收益明显。

代价是**覆盖面**。SelectionDAG 积累了十几年的特例（向量 shuffle、复杂寻址、`i128` 运算、各种目标 Hook），GlobalISel 到 2020 年代中期仍是 AArch64 基本可用、x86 部分可用、其他目标靠 fallback 的状态。因此现实中是“两者共存 + 逐函数 fallback”。

这段历史给出一个可推广的教训：

> **指令选择的理论核心（覆盖问题）早就定型了，真正在演进的是“承载它的数据结构”。** DAG → SSA MIR 的迁移，换来的是编译速度、可扩展性和更早的寄存器类决策，而不是更好的指令选择质量。

## 六、别的编译器怎么做

不同编译器的选择差异，恰好说明了“没有唯一正解”。

### GCC：展开 + 单条匹配

GCC 的路线完全不同于 LLVM 的“整图覆盖”。

- **RTL**（Register Transfer Language）：一个线性指令列表（现在实际是 `rtx` 的链）。不是 SSA（`-fssa` 只是局部使用），不是 DAG。
- **`define_expand`**：把一棵 RTL 生成成多棵（相当于 IR → 多条 RTL）。这是“展开”阶段，指令选择的一部分在这里完成。
- **`define_insn`**：单条 RTL 到单条机器指令的匹配，用 `match_operand` 的谓词与约束做检查。**这是逐条 `recog()` 匹配，没有跨节点的搜索。**
- **`combine.c`**：把相邻的几条 RTL 指令合成一条（例如 `cmp` + `branch`、地址计算 + load）。这是 GCC 真正做“跨节点优化”的地方。
- **`define_peephole2`**：更晚的序列级重写。
- **LRA**（Local Register Allocator，GCC 4.8+ 取代 reload）：寄存器约束不满足时的修复。

所以 GCC 的模型是：**展开 → 寄存器分配前的 combine → 逐条匹配 → peephole**。它没有 BURG，也没有全局覆盖搜索。它的优势是 RTL 表达力极强、目标描述非常成熟；劣势是 pass 之间耦合严重、调试困难（这是 GCC 后端“难以移植”名声的来源）。

### Go：文本规则 + 不动点重写

Go 1.7 之后的 SSA 后端用的是最朴素也最好维护的办法：**重写规则**。

`cmd/compile/internal/ssa/_gen/AMD64.rules` 里写：

```
(ADD(Q|L)const [off] x) -> (LEA(Q|L) [off] x)
(MOVQstore [off] {sym} ptr (MOVQconst [c]) mem) && is32Bit(c) -> (MOVQstoreconst [valAndOff(c,off)] {sym} ptr mem)
(CMPQconst [c] x) && isUint32(c) -> (CMPLconst [int32(c)] x)
```

`_gen` 工具把这些规则编译成一棵按操作码索引的特里（trie），生成为 Go 代码。跑的时候是**自顶向下的递归重写，直到不动点**。

这个方案的特点：

- 优点：极简、可读、改一条规则只改一行、模式匹配逻辑自动生成。
- 缺点：**没有代价模型，没有最优性**。规则写错或顺序不当就会生成次优代码，靠人工调整规则集来逼近。规则的优先级由写下的顺序决定。
- 但它的工程质量很高：规则集是分层的（generic → arch），每个操作码对应一组规则，生成的代码可预测、可 profile。

这是一个重要的数据点，说明一件事：

> **对很多目标而言，“有代价模型的最优覆盖”带来的收益，抵不上“规则简单、易改、可读”带来的维护收益。**

### Cranelift：ISLE DSL

Cranelift 早期用一组手写的 `lower` 函数（每个 CLIF 操作一个）。后来换成 **ISLE**（Instruction Selection Lowering Expressions），一个专门为此设计的领域语言，编译成 Rust 代码。

它的形态仍然是项重写：规则是一组 `(rule (lower (iadd x y)) (add x y))` 形式的模式，用外部提取器（extractor）把复杂操作分解。价值在于：

- **指令定义单一来源**：同一条指令的编码、自动生成的反汇编器、ISLE 模式都从同一份定义派生，避免不一致。
- 生成的是决策树，性能接近手写。

### HotSpot C2：ADLC 生成匹配器

Java 的 C2 用的是 `.ad`（architecture description）文件 + **ADLC**。ADLC 从 `.ad` 里读出指令与模式，生成一个**状态机式的匹配器**。这更接近 BURG 的传统：机器描述 → 匹配器代码。

C2 的结构还有一个值得注意的地方：它有 `instruct`、`operand`、`match` 三种规则，`match` 做的是模式合并（类似 peephole 的规则级联），这也是一种“重写”。

### 一句话总结各家

| 编译器 | 模型 | 代价模型 | 最优性 |
|---|---|---|---|
| LLVM DAG | 贪婪模式匹配 + 合法化 + combine | 无（局部启发式） | 局部 |
| LLVM GlobalISel | 同上，SSA MIR 承载 | 无 | 局部 |
| GCC | 展开 + 逐条 recog + combine | 有（`define_insn` 的 cost） | 逐条 |
| Go | 文本规则 + 不动点重写 | 无 | 无 |
| Cranelift | ISLE 项重写 | 部分 | 局部 |
| C2 ADLC | 生成的 DFA 匹配器 + 规则 | 有 | 局部 |
| BURG/iburg | 树覆盖 DP | **有** | **树内最优** |

值得注意的是：**只有 BURG 类系统真正实现了“给定模式集下的最优”**，而它们在实践中已被放弃或降级为教学工具。原因不是理论错，而是模式集的表达力需求（谓词、复杂寻址、多结果、副作用）超过了 DP 的状态空间，以及真实代码是 DAG 而非树。

## 七、三个永恒的难点

前面讲的是“怎么实现”，这一节讲“为什么它永远做不完美”。

### 7.1 选址、调度、寄存器分配的三体问题

这是后端设计的根本困难，值得说透。

三者的目标互相冲突：

- **指令选择** 想让一条指令干更多事（大 tile、内存操作数折叠、寻址模式吸收），这样指令数少。
- **寄存器分配** 想让同时活跃的值少，这样不溢出。大 tile 通常意味着更长的活区间、更多的临时值。
- **调度** 想填满流水线延迟，这要求重新排序，而排序的前提是独立的指令。折叠大的指令会减少调度空间。

而它们的顺序是**固定的**：选址 → 调度 → 分配。因为分配依赖指令对寄存器的要求，而要求由选址决定。**这个顺序本身就排除了全局最优**。

一个具体的例子，x86 上 `x = a[i] + b`：

```
选项 A（折叠）:  add rax, [rdi + rsi*8]     ; 一条，地址被吸收
选项 B（不折叠）: lea rcx, [rdi + rsi*8]
                 mov rdx, [rcx]
                 add rdx, rbx               ; 三条
```

A 显然更好，指令少、寄存器少。但如果 `b` 在这条之后马上要被大量使用，`rax` 占用会延续，可能挤压别的值。更极端的，如果 `a[i]` 是这条循环里的不变量，B 的 load 可以被提升到循环外，A 不能（因为折叠进了循环体的算术指令）。

所以折叠的决策不能由选择阶段单独做出。现代编译器靠**多层判断**：

- IR 层：`foldMemoryOperand` 的收益计算、循环不变量提升先做掉。
- ISel 层：只对“明显好”的模式折叠（例如叶子节点、单次使用）。
- Machine 层：`MachineCombiner` 之类的 pass 在分配前做重新组合。

这个问题的学术名字叫 **phase ordering problem**，没有一般解。

### 7.2 折叠的边界

“折叠”（fold）是指把上游运算吸收进下游指令。它的收益和代价都很微妙：

**收益**：少一条指令、少一个虚拟寄存器、省一次发射。

**代价**：
1. **活区间变长**：折叠后，原本可以早死的中间值现在活到使用点。
2. **优化机会消失**：折叠掉的运算在机器层不可见，后面的 peephole/combine 抓不到。
3. **可能抑制其他折叠**：一条指令只能吸收一次。
4. **调试信息变差**：折叠的指令对应多个源位置，行号映射退化（这是 LLVM 里一个真实且长期的问题）。

因此现代编译器对 fold 有明确的策略：

- **单次使用优先**。一个值如果只被用一次，折叠几乎总是有收益（不会延长活区间，因为本来就要用到它）。
- **叶子节点优先**。地址的 `base`/`index` 如果本来就是变量，吸收不增加成本。
- **只在 IR 层做“会改变语义结构”的折叠**，机器层只做“编码层面”的折叠。

### 7.3 立即数的物化与重物化

一个常量有两种身份：**编码在指令里**（免费，但受位数/位模式限制），或**放在寄存器里**（贵，但通用）。

麻烦在于：

- ARM64 的逻辑指令 `and`/`orr` 只能编码“循环位模式”的立即数。`0xFF00FF00` 可以，`0x12345678` 不行。
- x86 的 64 位立即数大多只能编码 32 位符号扩展。
- RISC-V 的 `addi` 只有 12 位立即数，大常量必须走 `lui` + `addi` 或常量池。

于是选择阶段必须处理“这个常量能不能免费用”。LLVM 的 `ImmLeaf`/`PatLeaf` 谓词就是干这个的：匹配失败就退回“先物化到寄存器”。

但这又和寄存器分配交互：如果常量被物化到寄存器，分配器需要考虑**重物化**（rematerialization）——与其溢出这个值到栈上再读回来，不如溢出时什么都不做，在需要时重新算一遍（`mov imm` 比重载便宜）。

这个决策需要“值是否可廉价重算”的信息，而这个信息由选择阶段产生（`MachineInstr::isRematerializable` 等）。**所以指令选择还在为一千行之后的寄存器分配提供输入**，这就是耦合的深度。

## 八、工程实践：给 LLVM 加一条指令

把理论落到操作上，一个典型的流程（以 AArch64 为例）：

**1. 在 `.td` 里定义指令。**

```tablegen
def ADDXrr : BaseRegOffsetPair<...> {
  let Inst{31-21} = 0b10001011000;
  ...
}
```

**2. 写模式。**

```tablegen
def : Pat<(add GPR64:$lhs, GPR64:$rhs), (ADDXrr GPR64:$lhs, GPR64:$rhs)>;

// 带立即数范围检查
def : Pat<(add GPR64:$lhs, (i64 imm0_4095:$rhs)), (ADDXri GPR64:$lhs, imm0_4095:$rhs)>;
```

**3. 处理合法化**（如果这个指令引入新能力，可能需要改 `TargetLowering` 让某个 op 变成 legal）。

**4. 处理 regalloc 约束**（两地址形式、固定寄存器）。

**5. 写测试**：`llc -mtriple=aarch64 -verify-machineinstrs` + FileCheck。

日常最常改的三个地方：

- **模式优先级**：新模式的排序不对，会被更通用的模式抢走。调 `AddedComplexity` 或改模式形状。
- **combine**：模式匹配不上，通常是因为 DAG 的形状和你预期不同（常数被提到别的节点、`i32` 被 promote 成 `i64`）。用 `llc -view-dag-combine1-dags` 或 `-debug-only=isel` 看实际形状。
- **ComplexPattern**：寻址类的新模式需要写 C++ 的分解函数。

调试工具：`-debug-only=isel`（看匹配过程）、`-view-dags`（Graphviz 输出）、`-print-after-all`（MIR 层）、`LLVM_DEBUG`。GlobalISel 对应 `-debug-only=legalizer,regbankselect,instruction-select`。

一个现实提醒：**指令选择相关的 bug 绝大多数不是“选错指令”，而是“选了语义不等价的指令”**。一条 `Pat` 就是一条语义断言，写错了就是错误编译。而这一层几乎没有形式化验证工具（Alive2 覆盖的是 IR 层，不到 ISel）。所以 `.td` 的 review 质量和测试覆盖非常关键。

## 九、判据表

把全文压成一张图，用来判断“某个指令选择任务该怎么做”。

| 你的情况 | 建议 |
|---|---|
| 目标机规整、三地址、无复杂寻址（教学 ISA、嵌入式小核） | 手写逐节点 lowering，或文本规则重写（Go 式）。不要引入 DP。 |
| 目标机有复杂寻址/CISC，追求代码质量 | 模式匹配 + ComplexPattern + 强 combine。LLVM 式贪婪匹配是正解。 |
| 目标机结构简单但模式集规整，且你**真的需要最优** | 树覆盖 + DP（BURG 式）。注意：只对树有效。 |
| 编译速度优先（JIT、`-O0`） | 线性扫描 + 简单匹配，不做合法化的激进展开（LLVM 的 FastISel 就是这条路）。 |
| 大量向量代码 | 准备好写 C++ 特例。向量 shuffle 的合法化/选择是手写代码的重灾区。 |
| 需要形式化保证 | 目前没有成熟方案。退而求其次：把模式写得可测，用差分的指令级测试。 |

以及三条贯穿全文的判断：

**一、代码质量的主要来源是 combine 和合法化，而不是匹配本身。** 匹配只是把已经规范化的节点翻译成指令。把精力投在“选择前把 DAG 变成想要的形状”上，回报远高于优化匹配器。

**二、最优性在实践中被放弃了。** 树覆盖 DP 有最优性但表达力不足；工业匹配器表达力强但没有代价模型。这个交换在可预见的将来不会改变，因为根本障碍（NP-hard + 寄存器约束 + phase ordering）是结构性的。

**三、指令选择正在从“一个算法”变成“一条流水线”。** IR combine → 合法化 → 匹配 → 机器层 peephole/pairing/融合，每一层都在做同一件事的不同粒度。理解这一点，比理解任何一个具体算法都重要。

## 结语

指令选择的理论核心在 1970 年代就成型了：Cattell 的树模式匹配、Aho-Johnson 的线性 DP、Aho-Johnson-Ullman 的 NP-完全性证明。这些结论今天仍然精确地界定了什么是可能的。

但工业实践走的是另一条路：**放弃树覆盖的 DP，改用贪婪匹配 + 强合法化 + 大量 combine**。理由是真实的输入是 DAG、真实的需求是表达力（谓词、多结果、复杂寻址、副作用）、真实的约束是编译速度。BURG 类系统的退场不是因为错了，是因为它们解决的问题比实际需要的窄。

而承载这一切的数据结构，从 DAG 正在迁移到 SSA 形式的 Machine IR（GlobalISel）。这次迁移的收益是编译速度和可扩展性，不是更好的指令选择。

所以最终的回答是：**指令选择是一个“局部最优 + 全局妥协”的工程问题。** 它的算法是已知的，它的困难在于算法之间、pass 之间的耦合——而这些耦合来自硬件本身的约束（寄存器数量、编码位宽、延迟），不是来自编译器写得不够聪明。

理解了这一点，就能判断一个新目标、新指令该怎么接进去，而不是靠试错。
